 Comment 2: Subscription Booking Error (shubham79a)

 Type: Bug Report
 Status: ✅ LEGITIMATE (ALREADY FIXED)
 Evidence:
 Commit d4bf4f2: "fix(checkout): resolve missing appointment and
 appointment type creation in mock payment flow"

 Root Cause Analysis:
 - Mock payments were creating Payment records with SUCCEEDED status immediately
 - When handlePaymentSuccess() was called, it had idempotency check (line 88-91 in handlers.ts)
 - If payment was already SUCCEEDED, the handler returned early without creating appointment
 - Result: Payment exists but no appointment created

 Fix Applied:
 - Mock payments now start with PENDING status
 - handlePaymentSuccess() creates appointment then updates to SUCCEEDED
 - This was fixed in commit d4bf4f2

 Current Status: RESOLVED ✅

 Comment 3: Consultation Payment Success But No Appointment (shubham79a)

 Type: Bug Report
 Status: ⚠️ LEGITIMATE ISSUE - PARTIALLY FIXED

 Reported Issue:
 "On booking consultation we are able to payment successfully. But In database we are able to view the payment entry
 but no entry in appointment or consultation which refers this payment. No update in dashboard on consultee."

 Root Cause Analysis:
 Location: lib/payments/webhooks/handlers.ts lines 154-216

 When real payment succeeds (Stripe/Razorpay), webhook calls:
 await handlePaymentSuccess(
   paymentIntent.id,
   paymentIntent.metadata || {}  // ← CRITICAL: metadata from gateway
 );

 Inside handlePaymentSuccess():
 const {
   appointmentType,  // Required
   planId,          // Required
   slotStartTimeInUTC,  // Required for consultation
   slotEndTimeInUTC,    // Required for consultation
   // ...
 } = metadata;

 The Problem:
 1. If payment gateway doesn't preserve metadata OR
 2. If metadata is malformed/incomplete, then
 3. Appointment creation fails silently (throws error but transaction rolls back)
 4. Payment record exists with status=SUCCEEDED but appointmentId=null

 Evidence from Code:
 - Stripe webhook (stripe/route.ts:44-47) passes succeededEvent.data.object.metadata || {}
 - If metadata is empty object, destructuring gets undefined values
 - createConsultation() would create invalid dates: new Date(undefined) = Invalid Date
 - This would throw but error isn't surfaced to user

 Is This Fixed?
 Commit 45466eb mentions "address PR review feedback for multi-currency and webhook handling" but doesn't explicitly
 fix metadata validation.

 Current Status: PARTIALLY FIXED - Webhook handling improved but missing defensive validation ⚠️

 Comment 4: Payment Bypass Issue (shubham79a)

 Type: Design Flaw / Security Issue
 Status: ✅ LEGITIMATE - BY DESIGN BUT PROBLEMATIC

 Reported Issue:
 "When slots are booked, after selecting the slot when we are clicking on 'Request for Approval' without payment we
 are able to submit our request. And from the consultant dashboard when we approved and allocate slots to consultee it
  forms an Appointment without the payment on dashboard."

 Root Cause Analysis:
 Location: /app/api/slots/request-for-approval/route.ts

 The Alternative Flow:
 // POST /api/slots/request-for-approval
 const consultation = await prisma.consultation.create({
   data: {
     requestStatus: RequestStatus.PENDING,  // NO PAYMENT
     appointment: {
       create: {
         appointmentType: "CONSULTATION",
         slotsOfAppointment: {
           create: {
             isTentative: true,  // Tentative without payment
             user: { connect: [consulteeId, consultantId] }
           }
         }
       }
     }
   }
 });

 What Happens:
 1. User clicks "Request for Approval" on consultant profile
 2. Consultation + Appointment + Slot created WITHOUT payment
 3. Consultant sees request in "Requests" tab
 4. Consultant can approve without checking payment
 5. When approved, createAppointmentForConsultation() is called
 6. Appointment becomes confirmed WITHOUT linked payment record

 Evidence from Code:
 /app/api/events/consultations/[consultationId]/route.ts lines 358-417
 async function createAppointmentForConsultation(consultation: any) {
   // Creates appointment with now + 1 hour slot
   // NO payment validation
   // Sets isTentative: false (confirmed)
 }

 Is This Intentional?
 YES - this is by design for a "request-then-pay" workflow, but it has problems:

 1. Business Logic Flaw: Consultant can approve slots without payment
 2. Revenue Loss: Users can get confirmed appointments without paying
 3. No Payment Link: No way to collect payment after approval
 4. Inconsistent State: Appointment exists but Payment record doesn't

 Current Status: LEGITIMATE DESIGN FLAW - Working as coded but needs payment enforcement ⚠️
