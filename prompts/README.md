# prompts/ — the agent-driven test and tour corpus

This folder holds the prompt files that drive agent-run verification of the platform: end-to-end test cases an agent executes against a locally running app (Supabase MCP for SQL, Chrome DevTools MCP for the UI), plus guided-tour and UI-build prompts. It contains 141 prompt files across seven directories and one root template (this index excluded). The booking suite, `booking-qa/`, replaced the older numbered `booking-algorithm-tests/` corpus on 2026-11-10.

The corpus is complementary to the human-facing verification docs: [`docs/team/mock-credentials.md`](../docs/team/mock-credentials.md) gives a person the seeded logins and click-through flows to verify the enterprise subsystem by hand, while `enterprise-tests/` gives an agent the same territory as executable case files with DB-level assertions and a fix-and-retest gate. Both are built on the same deterministic seed cohort (`prisma/seedFiles/`), and the credential roster in the verification guide is the authoritative one — `enterprise-tests/_shared/shared-setup.md` §2 points at it.

## Conventions the corpus follows

Four rules keep the case files safe to run repeatedly:

- **Read the shared setup first.** Every `enterprise-tests/` case assumes [`_shared/shared-setup.md`](./enterprise-tests/_shared/shared-setup.md) (rules, glossary, schema reference, mock-data strategy) and [`_shared/case-template.md`](./enterprise-tests/_shared/case-template.md) (skeleton and the fix-and-retest gate). Every `booking-qa/` case assumes its own [`_shared/`](./booking-qa/_shared/00-read-first.md) folder in the same way.
- **Deterministic, suffixed test data.** Booking cases prefix every fixture title and note with `qa-<caseId>`; enterprise cases spawn throwaway orgs under a `test-2026-{date}-{slug}` prefix. Both clean up at the end of the run so reruns never collide.
- **The DB is the arbiter.** Every meaningful action is verified with SQL against the double-entry ledger and the domain tables, not against what the UI shows.
- **Weekly availability is seeded with its local columns.** Every reader refuses a weekly row whose `timezone` or `local*` columns are NULL, so a SQL-seeded row sets `timezone`, `localStartDay`, `localStartMinutes`, `localEndDay` and `localEndMinutes` as well as the UTC columns (`Asia/Kolkata`, offset 330, unless a booking case names another zone).
- **Relative dates are pinned to a weekday, never counted from today.** Booking cases use weekday-specific availability (the base fixtures in `booking-qa/_shared/personas-and-fixtures.md`), so a case that writes `D+3` has to say which weekday `D` is; counting days from whatever day the run happens to start on lands the target on a weekend, where the setup fails long before the assertion the case was written for.
