# 1-membership-auth — SSO + domain claims

> **Required reading:** [`_shared/shared-setup.md`](../_shared/shared-setup.md),
> [`_shared/mcp-recipes.md`](../_shared/mcp-recipes.md),
> [`_shared/case-template.md`](../_shared/case-template.md).
> Apply the **fix-and-retest gate** when any case fails.

SSO is OIDC-only; SAML and SCIM are not supported. The full design is in
[`docs/authentication/sso.md`](../../../docs/authentication/sso.md).

**Surface(s) under test:**
- `app/api/organizations/[orgId]/sso/providers/route.ts` (provider create + list)
- `app/api/organizations/[orgId]/sso/providers/[providerId]/route.ts` (get + delete; no PATCH)
- `app/api/organizations/[orgId]/sso/route.ts` (org SSO settings: `enforceSSO`, `defaultRoleForAutoJoin`)
- `app/api/organizations/[orgId]/domain-claims/route.ts` (DNS TXT verify)
- `app/api/admin/organizations/[orgId]/sso-providers/[providerId]/approval/route.ts` (platform staff approval)
- `lib/sso/derive-urls.ts` — `deriveCallbackUrl`
- `lib/sso/provider-schemas.ts` — Zod bodies, `generateProviderId`
- `lib/sso/enforce-session.ts` — `shouldRejectSession` (called from the `session.create.before` hook)
- `app/dashboard/organization/[orgId]/settings/SsoPanel.tsx` — settings UI (`/settings/sso`)

**Case roster:**
1. **SSO.1** — Create OIDC provider (happy)
2. **SSO.2** — List providers: redirect URI present, secret never returned
3. **SSO.3** — Create domain claim, verify status pending
4. **SSO.4** — Enforce SSO: gates, staff approval, then password sign-in → 403 `SSO_REQUIRED`
5. **SSO.5** — UI: settings/sso panel
6. **SSO.6** — SAML refused
7. **SSO.7** — Unverified or unowned domain → 422
8. **SSO.8** — JIT default role locked to LEARNER
9. **SSO.9** — Domain-check rate limit
10. **SSO.10** — Role change → session refresh (sessionGeneration)

## Common preconditions

Use Wipro (or spawn a fresh sponsor org). OWNER session required.
`AUTH_CONFIG_ENCRYPTION_KEY` must be set (64 hex chars) or provider
creation returns 500 `SSO_ENCRYPTION_KEY_MISSING`. The server fetches the
issuer's OIDC discovery document at registration, so `oidcConfig` must
point at a reachable IdP (a dev Okta/Auth0/Google tenant).

Cleanup at end:
```sql
DELETE FROM "ssoProvider" WHERE "organizationId" = '<wipro-id>'
  AND domain LIKE '%test-sso%';
DELETE FROM "org_domain_claims" WHERE "organizationId" = '<wipro-id>'
  AND domain LIKE '%test-sso%';
```

## SSO.1: Create OIDC provider

Precondition: a **verified** domain claim for `test-sso.example` on Wipro
(SSO.3, then set `verifiedAt` once the TXT record resolves).

```js
() => fetch("/api/organizations/<wipro-id>/sso/providers", {
  method: "POST", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({
    domain: "test-sso.example",
    issuer: "https://<dev-idp>",
    providerType: "oidc",
    oidcConfig: {
      issuer: "https://<dev-idp>",
      clientId: "<client-id>",
      clientSecret: "<client-secret>",
      discoveryEndpoint: "https://<dev-idp>/.well-known/openid-configuration"
    }
  })
}).then(async r => ({ status: r.status, body: await r.json() }))
```

### Assertions
- `status === 201`
- `body.provider.providerId` matches `/^oidc-[0-9a-f]{16}$/` (server-generated; a client-sent `providerId` is ignored).
- `body.provider.domainVerified === false` (awaiting platform approval).
- `body.provider.callbackUrl === "<NEXT_PUBLIC_APP_URL>/api/auth/sso/callback/<providerId>"`.
- DB: `ssoProvider.oidcConfig` starts with `sso:v1:` (encrypted envelope), `samlConfig IS NULL`, `userId IS NULL`.
- Audit: `SSO_ENABLED` row whose description ends "awaiting platform approval".

```js
  method: "POST", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({ domain: "test-sso.example" })

```

### Assertions
- `status === 201`
- `body.data.verificationToken` is a string (DNS TXT record value).
- `body.data.verifiedAt === null`.
- DB row in `org_domain_claims` with `verifiedAt IS NULL`.

Verification requires the user to add the TXT record; do not auto-verify
in tests unless you can mock DNS. Document the pending state.

## SSO.4: Enforce SSO + non-SSO sign-in

1. With no verified domain: `PATCH /api/organizations/<wipro-id>/sso`
   `{ enforceSSO: true }` → `403`, `code === "DOMAIN_VERIFICATION_REQUIRED"`.
2. With a verified domain but the SSO.1 provider still unapproved: same
   PATCH → `409` ("Cannot enforce SSO until at least one SSO provider has
   been approved").
3. As platform ADMIN, approve the provider:
   ```js
   () => fetch("/api/admin/organizations/<wipro-id>/sso-providers/<providerId>/approval", {
     method: "POST", credentials: "include",
     headers: {"Content-Type": "application/json"},
     body: JSON.stringify({ approve: true })
   })
   ```
   DB: `ssoProvider.domainVerified = true`; an `OpsActionLog` row exists.
4. Repeat the PATCH as Wipro OWNER → `200`, `enforceSSO === true`.
5. Attempt email-password sign-in for an existing `someone@test-sso.example`
   user who has no `Account` with the provider's `providerId`.

### Assertions
- Sign-in returns `403` with `code === "SSO_REQUIRED"`; no `sessions` row
  is created (the veto runs in `session.create.before`).
- The sign-in page shows the "use SSO" message from the error catalog.
- Deleting the only approved provider while enforced is refused.

- No `ssoProvider` row created.

## SSO.7: Domain ownership — unverified-domain provider registration → 422

Pre-condition: claim a domain but do NOT verify it.

```js
() => fetch("/api/organizations/<wipro-id>/domain-claims", {
  method: "POST", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({ domain: "test-sso-unverified.example" }),
})
```

Then POST the SSO.1 body with `domain: "test-sso-unverified.example"`.

### Assertions
- `status === 422`
- `body.code === "DOMAIN_NOT_VERIFIED"`
- No `ssoProvider` row created.

Repeat with a domain not even claimed:
- `status === 422`
- `body.code === "DOMAIN_NOT_OWNED"`

**Audit Phase B.3.** The pre-fix behaviour was "defended by accident" —
the runtime auth hook would silently never honour the unverified
provider, but registration appeared to succeed; the org admin saw a
provider that mysteriously didn't fire.

## SSO.8: JIT default role — PATCH `defaultRoleForAutoJoin: "OWNER"` → 400

```js
() => fetch("/api/organizations/<wipro-id>/sso", {
  method: "PATCH", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({ defaultRoleForAutoJoin: "OWNER" }),
}).then(async r => ({ status: r.status, body: await r.json() }))
```

### Assertions
- `status === 400`
- `body.detail.fieldErrors.defaultRoleForAutoJoin` mentions LEARNER
- DB: `OrganizationSSOSettings.defaultRoleForAutoJoin` unchanged

Repeat with `MAINTAINER`, `MANAGER`, `EXPERT`, `SUPPORT` — all 400.
Only `defaultRoleForAutoJoin: "LEARNER"` (or omitting the field) is
accepted.

**Audit Phase A.1.** Pre-fix, setting `OWNER` made the first SSO user
co-owner instantly. Schema is now `z.literal("LEARNER")`.

## SSO.9: Domain-check rate limit — flood the unauth endpoint

Without authentication, fire 150 GETs at the domain-check endpoint:

```js
() => Promise.all(
  Array.from({ length: 150 }, () =>
    fetch("/api/auth/sso/domain-check?email=probe@example.com", {
      credentials: "omit",
    }).then(r => r.status)
  )
)
```

### Assertions
- The first ~120 responses are `200`.
- The remainder are `429` — the edge policy `enterprise.sso-domain-check`
  (`lib/rate-limit/policies.ts`, 120/h per IP).

Re-run from the SAME IP within the same hour and confirm 429 persists.

**Regression guard for audit Phase B.8.** If all 150 succeed,
domain-enumeration of registered orgs is unrestricted — a public
attack surface.

## SSO.10: Role change → session refresh on next request (sessionGeneration)

Spawn a fresh test user, add as LEARNER to a test org. Capture the
user's session cookie (login via Chrome MCP).

```sql
-- Baseline: assert current role + sessionGeneration value
SELECT u.id, u."sessionGeneration", m.role
FROM users u
JOIN "Membership" m ON m."userId" = u.id
WHERE u.email = 'test-sessiongen@familiarise.test';
-- Capture <gen-before>
```

Now PATCH the role to MANAGER via the members endpoint (as Wipro OWNER):

```js
() => fetch("/api/organizations/<wipro-id>/members/<member-id>", {
  method: "PATCH", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({ role: "MANAGER" }),
})
```

### Assertions
- `status === 200`
- DB:
  ```sql
  SELECT u."sessionGeneration", m.role FROM users u JOIN "Membership" m ON m."userId" = u.id
  WHERE u.email = 'test-sessiongen@familiarise.test';
  -- Expected: sessionGeneration = <gen-before> + 1, role = 'MANAGER'
  ```
- As the patched user, hit `GET /api/auth/get-session` (or any
  customSession-emitting endpoint) and assert the response's
  `user.sessionGeneration` equals the new DB value AND
  `organizationMemberships[]` shows the new MANAGER role — **without
  forcing a logout**.

Repeat for member removal (DELETE): `sessionGeneration` increments by
1, and the next session lookup omits the now-REMOVED org from the
memberships array.

**Audit Phase B.5.** Pre-fix, the user kept their LEARNER session for
up to 24h after promotion — operating with stale permissions.
