# Booking & Host Time

Applies to `lib/booking/`; the root `AGENTS.md` points `lib/appointments/` and `utils/scheduling-engine/` here too. The root `AGENTS.md` still applies.

1. **`occurrence_no_confirmed_overlap` has limits**: it guards only one host's live, non-tentative, non-cancelled occurrences. It does **not** cover tentative holds, co-host seats, a consultant booking as a client, or webinar/class attendee seats; those stay app-enforced (slot locks, the Serializable seat count) until the busy-time ledger lands. It also ignores CANCELLED and RESCHEDULED rows, while the app's occupancy checks still treat a RESCHEDULED row as holding its time.
2. **The database arbitrates host time; Redis is the fast refusal.** Every writer that makes an expert's time busy takes one all-or-nothing `tryLockSlotBatch` (`utils/appointmentlock.ts`) over the host, ACCEPTED co-hosts and an expert buyer's own profile before its write transaction. Then call `lockHostTimeInTx` (`lib/booking/allocation/host-time-locks.ts`), or the door's wrapper (`lockHostBatchInTx`, `lockAllocationTimesInTx`, `lockTrialPickInTx`), with the same entries as the **first statement** of that transaction, and only then run the conflict re-check. A 1:1 writer passes the learner's time too; a webinar or class seat does not. A held atom answers the door's existing slot-taken 409: never wait or retry on it. Make no Redis call inside a host-time write transaction; renew grants ahead of each attempt. Order inside the transaction: host-time try-locks, then waiting advisory locks, then row locks, then compare-and-set writes.
