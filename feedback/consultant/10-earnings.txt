ISSUES
─────────────────────────────────────────────

[1] 🔴 P0 — Plan Price column is 100× inflated — confirmed originalAmount * 100 bug
All five Plan Price values are implausibly large:
  $64,369 for a Subscription, $97,827 for a Subscription, £4,966 for a Webinar, 8,054 € for a Consultation, 81,502 € for a Subscription.
Dividing each by 100 yields plausible figures ($643.69, $978.27, £49.66, €80.54, €815.02). This confirms the earnings page uses `originalAmount * 100` when rendering Plan Price (likely a paise-to-rupee or cent-to-dollar conversion is being applied in the wrong direction — the raw integer stored in the DB is already in the smallest currency unit, and the frontend is multiplying instead of dividing). A consultant reviewing this page would see a $97,827 subscription plan price and question the entire data's validity.

> **Proposed fix:** Verify the currency unit used in `ConsultantEarning.grossAmount` / `originalAmount`. If stored as integer paise/cents, divide by 100 before rendering. If stored as a float in major currency units, remove any × 100 multiplication in the display layer. Add a unit test that asserts: a ₹500 plan price renders as "₹500.00", not "₹50,000.00".

[2] 🔴 P0 — Mixed currencies across rows make total earnings meaningless — ₹, $, €, £ all present
The stat cards show INR (₹407.17 total, ₹200.00 ready, ₹43.17 paid) but the individual table rows show:
  - Row 1: $USD, Row 2: €EUR (European format), Row 3: £GBP, Row 4: €EUR, Row 5: $USD.
No two rows share the same currency. The "Total Earnings" of ₹407.17 appears to sum values from different currencies without conversion. ₹43.17 in the "Already Paid Out" card suspiciously matches Row 4's 43.17 € — suggesting the system is treating currency symbols as interchangeable and summing raw numbers.

> **Proposed fix:** (a) Determine the canonical currency for each consultant (based on their payment gateway's base currency). (b) If multiple currencies are possible, convert all values to the consultant's default currency using stored exchange rates before aggregating. (c) Display a single consistent currency symbol per row and in stat cards. The mixed currency display is the single most trust-eroding issue on this page.

[3] 🟠 P1 — Stat card "Pending (In Hold)" conflates two distinct statuses
The stat card is labeled "Pending (In Hold)" and shows ₹96.00 — which corresponds only to the PENDING row ($96). The HELD/On Hold earnings (₹68.00) are separately noted in the alert banner. Having "(In Hold)" in the card label when the card only represents PENDING implies both statuses are included, which they are not. "Released after hold period" as the subtitle further confuses things — PENDING amounts are released on service completion, not after a hold period.

> **Proposed fix:** Rename to "Pending" with subtitle "Awaiting service completion." Add a separate stat card for "On Hold" (earnings under dispute/review) currently only shown via the alert banner.

[4] 🟠 P1 — Role column inconsistency — "Owner 80%" vs bare "Owner"
Rows 1 and 3 show "Owner 80%" while rows 4 and 5 show only "Owner" (no percentage). All four should show the revenue share percentage. The missing % makes rows 4 and 5 appear to be on a different (possibly higher) commission rate. The Collaboration row correctly shows "Collab 25%."

> **Proposed fix:** Consistently display percentage on every row: "Owner 80%", "Collab 25%", "Owner 80%". Never show "Owner" without the revenue share percentage.

[5] 🟠 P1 — Payout column shows raw ALL_CAPS enum "PROCESSING"
The Paid row's Payout column shows "PROCESSING" in uppercase — a raw DB enum value. All other rows show "–". "PROCESSING" should be humanized and ideally show contextual information (e.g. "Processing — est. 2–5 business days" or a spinner icon).

> **Proposed fix:** Humanize to "Processing" (Title Case). Add a tooltip or sub-text: "Payout is being processed by your payment provider."

[6] 🟠 P1 — "Ready for Payout: ₹200.00" is below the ₹500 minimum threshold — no contextual alert
The "Ready for Payout" stat card shows ₹200.00. The footer note says "Minimum payout threshold is ₹500.00." A consultant seeing ₹200 ready might try to request a payout and only then discover it's blocked. The ₹500 threshold context is only visible at the very bottom of the page. There is no inline indication on the "Ready for Payout" card that the threshold has not been reached.

> **Proposed fix:** Add a progress indicator on the "Ready for Payout" card: "₹200 / ₹500 minimum" with a progress bar or badge "₹300 more needed." Or add an inline subtitle: "Below minimum payout threshold (₹500)."

[7] 🟠 P1 — "Platform Fee" column doesn't communicate the commission percentage
The Platform Fee column shows a raw amount (e.g. $24.00) but no indication of what percentage this represents. A consultant unfamiliar with the platform's 20% commission has no way to verify whether the fee is correct. The column header alone says "Platform Fee" with no % hint.

> **Proposed fix:** Either rename the column to "Platform Fee (20%)" or add a tooltip on the column header: "Familiarise charges a 20% platform fee on all transactions." This is especially important given the confusing 80/20 split (which appears as 25% of consultant earnings when expressed as a ratio).

[8] 🟡 P2 — European number format (81.502,00 €) mixed with Anglo format ($64,369.00)
Row 2 displays "81.502,00 €" and "68,00 €" using the European convention (period as thousands separator, comma as decimal separator). Rows 1, 3, 4, 5 use Anglo convention (comma as thousands separator, period as decimal). This inconsistency likely reflects the underlying locale settings per payment gateway record and produces a jarring, inconsistent table.

> **Proposed fix:** Normalize all currency display to a single locale format (e.g. always use `Intl.NumberFormat('en-IN')` or the consultant's profile locale). Do not allow individual database records to control the display format.

[9] 🟡 P2 — "Refunded" row has inconsistent visual treatment — only Platform Fee is greyed, others normal
The Refunded row (Row 5) shows the Plan Price and Your Earnings in normal dark text, but the Platform Fee column ($131.09) is greyed/dimmed. For a refunded transaction, the visual treatment should be consistent — either all columns dimmed/struck-through, or none. The partial greying is confusing: it implies the platform still collected its fee even on a refunded transaction.

> **Proposed fix:** Apply a uniform visual style to all cells in a Refunded row (light grey text or strikethrough on all monetary values). Add a tooltip on the Refunded status badge explaining: "The client was refunded. Platform fee may or may not have been reversed — contact support."

[10] 🟡 P2 — No payout request mechanism visible — "Ready for Payout" is read-only
The page shows ₹200.00 ready for payout but provides no "Request Payout" button. A consultant who wants to trigger a payout has no path from this page. The payout information footer only shows the minimum threshold, not how to initiate a payout.

> **Proposed fix:** Add a "Request Payout" button in the "Ready for Payout" stat card (or in the page header). Show it as disabled when below threshold. When above threshold, clicking it should show a payout confirmation dialog with the expected timeline.
