ISSUES
─────────────────────────────────────────────

[1] 🟠 P1 — Empty table has no empty state message — blank area is confusing
When there are no pending requests, the table renders column headers followed by nothing. There is no "No pending requests" message, no illustration, and no CTA. A consultant seeing this page for the first time has no idea if the table failed to load, if no one has submitted a request, or if the feature is broken.

> **Proposed fix:** Add an empty state with icon + message: "No pending slot requests. When consultees request subscriptions or classes, they'll appear here for you to assign timeslots." Include a link to "Event Planner" for context.

[2] 🟠 P1 — Page heading "Slot Allocation" doesn't match nav label "Requests"
The sidebar nav link reads "Requests" but the page's primary heading reads "Slot Allocation." These must be consistent. "Requests" is the user-facing concept; "Slot Allocation" is the technical implementation. A consultant searching mentally for the page they just navigated to will call it "Requests" not "Slot Allocation."

> **Proposed fix:** Rename the page heading to "Requests" (and optionally add the subtitle "Allocate timeslots for pending subscription and class bookings").

[3] 🟠 P1 — Consultation request approval workflow is absent from this page
The subtitle explicitly limits scope to "subscription and class requests." Consultations also have a `requestStatus` field (PENDING → APPROVED_PENDING_PAYMENT → CONFIRMED) and require the consultant to approve and assign a timeslot. If consultation requests are handled elsewhere (e.g. in the Appointments page or via email), that flow is not visible anywhere in the dashboard. A consultant receiving a consultation request has no clear dashboard path to approve it.

> **Proposed fix:** Expand this page (or add a separate section) to also show PENDING consultation requests with Approve/Decline actions and a timeslot picker. The current table's "Type" column suggests multi-type support was intended.

[4] 🟠 P1 — "Requests" nav badge shows "1" but the requests table is empty
The Requests sidebar link displays a "1" unread count badge, yet the Slot Allocation table contains zero rows. The badge count is stale or computed from a different data source (possibly ALL-time requests, not just pending ones). This creates a false expectation — the consultant clicks "Requests" expecting to see something and finds an empty table.

> **Proposed fix:** The badge should reflect only PENDING requests. If there are 0 PENDING rows, the badge must be 0 (or not shown). Recalculate from a query scoped to `requestStatus = 'PENDING'` for the authenticated consultant.

[5] 🟡 P2 — Primary page heading "Slot Allocation" is H3 instead of H1/H2
The heading `<h3>Slot Allocation</h3>` is the only visible heading on the page. Being H3, it's semantically positioned as a sub-sub-heading when it is actually the page title. Screen readers traversing heading hierarchy will not find an H1 or H2 and may report the page as having poor structure.

> **Proposed fix:** Change the heading level to H1 (or H2 if nested inside a DashboardHeader H1 container). Ensure every page in the consultant dashboard uses a consistent heading level for its primary title.

[6] 🟡 P2 — No status filter tabs (Pending / Approved / Declined / All)
Even if requests were present, there is no way to filter by status. A consultant who approved some requests and wants to review declined ones has no way to access them. The table lacks any tab bar, dropdown filter, or search.

> **Proposed fix:** Add status filter tabs above the table: All | Pending | Approved (Awaiting Payment) | Declined | Expired. Default to the "Pending" tab to minimize noise.

[7] 🟡 P2 — "Requested Times" column label is unclear
The column header "Requested Times" could mean: (a) the timestamp when the request was made (duplicate of "Requested At"), or (b) the times the consultee suggested for the session. The functional intent (consultee's preferred time slots) requires a clearer label.

> **Proposed fix:** Rename to "Consultee's Preferred Times" or "Requested Timeslots" to distinguish it from the "Requested At" (submission timestamp) column.

The subtitle "Allocate slots for subscription and class requests" excludes consultations, yet consultation rows appear in the table. The subtitle actively misleads consultants into thinking consultation requests are handled elsewhere.

[9] 🟠 P1 — Status column shows raw ALL_CAPS enum ("PENDING") — same issue as Trials page
All status cells show "PENDING" in uppercase, inconsistent with human-readable conventions.
> **Proposed fix:** Humanize to "Pending", "Approved", "Declined" etc.

[10] 🟠 P1 — "Decline" button only appears on CONSULTATION rows, absent from SUBSCRIPTION rows
Both CONSULTATION rows have a red "Decline" button alongside "Allocate Slots." The two SUBSCRIPTION rows have only "Allocate Slots." Consultants cannot decline subscription requests — there is no corresponding action. This is likely intentional (subscriptions auto-cancel if unallocated?) but there is no explanation, and it creates an inconsistent action surface.
> **Proposed fix:** Add a "Decline" action for subscriptions too (with a confirmation explaining it will cancel the request). If declining subscriptions is not supported, add a tooltip on the missing button slot explaining why.

[11] 🟠 P1 — "Required Slots" shows inflated values for 1:1 consultations (4 for a single session)
Basic Consultation shows Required Slots = 2, Extended Consultation = 4. A consultation is a single 1:1 session. "4 required slots" implies the system is calculating slots as duration divided by slot-size (e.g. 4h session ÷ 1h slots = 4). But the consultant's job is to pick ONE timeslot for the whole consultation, not 4 separate slots. This is confusing for non-technical consultants.
> **Proposed fix:** For CONSULTATION type, display "1 slot" regardless of duration. The duration is already visible in the plan details. "Required Slots" as a concept only meaningfully applies to subscription/class multi-session scheduling.

[12] 🟡 P2 — "Not available" for Requested Times is misleading — sounds like a data error
Consultation rows show "Not available" in the Requested Times column. This looks like a data loading failure. The correct meaning is "the consultee didn't specify a preferred time." The label should reflect intent, not suggest a bug.
> **Proposed fix:** Change to "No preference specified" or "—" (em dash).

[13] 🟡 P2 — Timestamps include seconds (14/03/2026, 15:57:37) — excess precision
The Requested At column shows full timestamps including seconds. Consultants don't need second-level precision; they need to know "today at 4pm" not "14/03/2026, 15:57:37". The excessive detail also makes the column wider than necessary.
> **Proposed fix:** Display as "Mar 14, 2026 at 3:57 PM" using a human-readable, locale-appropriate format without seconds.
