Every confident claim made by reasoning about code structure, without measuring,
was wrong at least once. Every measured claim held. Five failed predictions:
  1. "Suspense will cut FCP"              -> shell flushed 458ms, FCP unchanged
  2. "Real header text will fire FCP"     -> unchanged

  4. "The page's auth awaits cause the 3.3s"   -> 1 cached read + 1 indexed query
  5. "ISR won't reintroduce the #932 build DB connect" -> BACKWARDS. See §4.

WHAT ACTUALLY WORKS HERE:
  * STREAM THE HTML and grep for markup that should be there. Distinguish MARKUP
    (">Event Planner<") from RSC FLIGHT PAYLOAD (bare "Event Planner"). Payload
    only = NOT server-rendered.
  * A/B TWO PREVIEWS, same account/page, one variable changed.
  * WARM THE FUNCTION FIRST. A cold Netlify boot measured 23,059ms TTFB.
  * CI's build ROUTE TABLE answers prerender questions: ○ = prerendered at build,
    ƒ = dynamic. This settled §4 definitively.

GREEN CI IS NOT VERIFICATION. tsc + eslint + 2518 tests were green on: a build

D.5  PG_POOL_MAX=1 MEANS PARALLELISING PRISMA READS CANNOT WIN.  [V — measured]
  PG_POOL_MAX is 1 on production, deploy-preview AND branch-deploy, and
  lib/prisma.ts passes it to pg.Pool as `max`. Each function instance holds ONE
  client, so concurrent Prisma queries SERIALISE.
  Evidence: 20 order-balanced interleaved rounds against get-session with a real
  session — dev 1,142ms median, the Promise.all'd preview 1,176ms. Anonymous
  get-session identical on both (557 vs 558ms), ruling out a deployment offset.
  >> Check PG_POOL_MAX before ever proposing "these queries are independent,
     parallelise them". The idea is dead until the pool is widened. Issue #1117. <<
  Widening it is a CAPACITY question about Supabase pooler limits across concurrent
  function instances, not a config tweak.
  This REFRAMES the wave-depth finding in [#16]: 30 statements for 3 appointments
  with summed DB time (3,108ms) over wall time (1,127ms) is about statement count
  under a SERIALISING pool, not only cross-region round trips — which makes
  relationJoins MORE promising, since collapsing statement count is the only lever
  a single connection responds to.
  Also learned: membership.findMany was never parallelisable anyway — the JIT
  auto-join loop above it CREATES the Membership rows it then reads.

D.6  YOU CANNOT SIGN IN VIA A BROWSER ON ANY PREVIEW.  [V]
  BETTER_AUTH_TRUSTED_ORIGINS is https://familiarisenow.com in EVERY Netlify
  context, so POST /api/auth/sign-in/email returns 403 INVALID_ORIGIN on preview
  and branch-deploy hosts. Logged-in behaviour is therefore unmeasurable in a real
  browser on a preview; that is why #1116's logged-in "before" number is derived.
  Spoofing the Origin header with curl gets a SERVER-side session (covers endpoint
  latency) but never a browser cookie, since the session cookies are HttpOnly.
  Fixing it is a security-relevant loosening on hosts that SHARE THE PRODUCTION
  DATABASE — user's call, and scope it per-context with `netlify env:set --context`,
  never unscoped.
