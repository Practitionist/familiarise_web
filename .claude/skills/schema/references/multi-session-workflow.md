# Many sessions, one database: the migration workflow

This is the working procedure for changing the schema in this repository now that it
is managed by versioned Prisma migrations. Several agent sessions and several git
worktrees work at once, and all of them share **one** Postgres database that serves
development, every deploy preview and production. Everything below was observed on
2026-11-09 in a local rehearsal on Postgres 17.11 with Prisma 7.10.1, unless a line
says otherwise. Re-run the rehearsal (last section) after every Prisma or Postgres
bump before trusting any of it again.

## The rule in one paragraph

A schema change is a migration folder under `prisma/migrations/`, committed in the
same pull request as the `prisma/schema.prisma` edit and the code that uses it. No
session ever applies a migration to the shared database. When the pull request merges
to `dev`, `.github/workflows/db-migrate.yml` applies it with `prisma migrate deploy`,
and because the database is shared, that is the moment production sees it. So a
migration that merges to `dev` must be an **expand** (additive, safe for the code
already running), and a **contract** (destructive) ships in a folder ending in
`_contract`, which the workflow refuses until the owner dispatches it by name after
the release that stopped using the object is live.

## Vocabulary

| Term             | Meaning here                                                                                                                                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Expand           | A change the running code ignores: a new table, a nullable column, a new enum value, a non-unique index, a new CHECK that every existing row passes. Applied on merge.                                                               |
| Contract         | A change that can break running code or reject existing rows: a drop, a rename, a type narrowing, `SET NOT NULL`, an enum value removal. Folder suffix `_contract`, applied only by dispatch.                                        |
| Sidecar object   | Anything `prisma/schema.prisma` cannot declare: CHECK and exclusion constraints, partial and `NULLS NOT DISTINCT` unique indexes, triggers and their functions, views, row-level security. Written by hand into the migration SQL.   |
| Baseline         | `prisma/migrations/0_baseline/migration.sql`, generated by `scripts/db/generate-baseline.sh` from the schema. It is regenerated only until it has been applied anywhere; after that it is frozen like every other applied migration. |
| Scratch database | A database on a local Postgres 17 cluster, never a Supabase project. Every command that writes in this file targets one.                                                                                                             |

## Set up a local cluster once

The rehearsal cluster is Homebrew `postgresql@17` (17.11) on port 55432. CI uses the
`postgres:17.6` image, matching Supabase's minor; the local cluster is for speed, CI
is the exact-version check.

```sh
export PATH=/opt/homebrew/opt/postgresql@17/bin:$PATH
initdb -D ~/pg17 -U postgres --auth=trust
pg_ctl -D ~/pg17 -o "-p 55432" -l ~/pg17/log start
psql -h localhost -p 55432 -U postgres -c "ALTER SYSTEM SET timezone = 'UTC'" -c "SELECT pg_reload_conf()"
psql -h localhost -p 55432 -U postgres -c "
  DO \$\$ BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'anon') THEN CREATE ROLE anon NOLOGIN; END IF;
    IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'authenticated') THEN CREATE ROLE authenticated NOLOGIN; END IF;
    IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'service_role') THEN CREATE ROLE service_role NOLOGIN BYPASSRLS; END IF;
  END \$\$;"
```

**TimeZone must be UTC.** Supabase and CI run in UTC. Under the Homebrew default
(`Asia/Kolkata` on this machine) four seat tests in `jest.db` fail, because the
`timestamp` columns without a time zone make seat counts depend on the session time
zone. Under UTC all 246 pass.

**Create the three Supabase roles.** The REVOKE migration
(`20261109000001_revoke_data_api_grants`) only runs its real branch when `anon` and
`authenticated` exist; without them the guarded `DO` block skips and the rehearsal
proves nothing about grants. Roles are cluster-wide, so this is done once.

**Point every command at the cluster explicitly.** The main checkout's `.env` holds the
live `DATABASE_URL` and `DIRECT_URL`, and `prisma.config.ts` loads it. An explicit
variable on the command line wins over `.env`, so always write all three:

```sh
L=postgresql://postgres@localhost:55432
DATABASE_URL=$L/scratch DIRECT_URL=$L/scratch SHADOW_DATABASE_URL=$L/shadow npx prisma …
```

Echo the host before each command when working in the main checkout. A secondary
worktree has no `.env` at all, which is safer.

## How a session adds a migration

1. **Rebase onto the newest `dev`** and build a scratch database from the history alone:

   ```sh
   createdb -h localhost -p 55432 -U postgres scratch
   DATABASE_URL=$L/scratch DIRECT_URL=$L/scratch npx prisma migrate deploy
   ```

   Twenty migrations applied to an empty 17.11 database in 1.35 s.

2. **Edit `prisma/schema.prisma`.** Keep to the expand rules for anything that will
   merge to `dev`. Money columns stay `BigInt` paise; enums go below the models using
   them.

3. **Generate the SQL against a shadow database, never against a shared one:**

   ```sh
   createdb -h localhost -p 55432 -U postgres shadow   # once; Prisma resets it on each run
   SHADOW_DATABASE_URL=$L/shadow npx prisma migrate diff \
     --from-migrations prisma/migrations --to-schema prisma/schema.prisma --script
   ```

   `prisma migrate dev` is never used: it writes to whatever `DIRECT_URL` points at
   and can offer to reset the database.

4. **Delete the three standing drops from the output.** Every diff of this history
   against the schema proposes:

   ```sql
   DROP INDEX "appointment_feedback_level_key";
   DROP INDEX "consultant_earnings_occurrence_key";
   DROP INDEX "organization_earnings_split_key";
   ```

   These are `NULLS NOT DISTINCT` uniques the schema cannot declare. They are not
   your change; never commit them. `scripts/db/sidecar-objects.ts`
   (`sidecarOwnedUniqueIndexes`) derives this set from the migrations, and both
   `check-migrations.ts` and `check-db-live-drift.ts` filter exactly it.

5. **Create the folder with a timestamp later than the newest on `dev`:**
   `prisma/migrations/<YYYYMMDDHHMMSS>_<what_it_does>/migration.sql`. Use UTC now.
   Add `_contract` to the end of the name if the change is destructive.

6. **Wrap the file** (the reasons are under "The transaction convention" below):

   ```sql
   -- One line saying what this migration guarantees.
   BEGIN;
   SET LOCAL lock_timeout = '3s';

   ALTER TABLE "Plan" ADD COLUMN "sortOrder" INTEGER;

   COMMIT;
   ```

7. **Edit the generated SQL by hand where Prisma is wrong:**
   - A rename appears as `DROP COLUMN` plus `ADD COLUMN`. Replace the pair with
     `ALTER TABLE … RENAME COLUMN … TO …`, or the data is gone.
   - A sidecar object goes in by hand: `CHECK`, exclusion constraint, partial unique,
     trigger and `CREATE OR REPLACE FUNCTION … SET search_path = public`. Write each
     idempotently (`DROP … IF EXISTS` then create) so a rolled-back retry works.
   - A view that reads a column you are changing is dropped and recreated in the same
     migration (the `demand` view in `20261109000018_analytics_views`).

8. **Prove it locally, in this order:**

   ```sh
   DATABASE_URL=$L/scratch DIRECT_URL=$L/scratch npx prisma migrate deploy
   SHADOW_DATABASE_URL=$L/shadow npx tsx scripts/ci/check-migrations.ts origin/dev
   DATABASE_URL=$L/scratch DIRECT_URL=$L/scratch npx tsx scripts/ci/check-db-sidecars.ts
   ```

   For a change that touches booking, money or seats, rebuild the `ci` database and run
   the database tier, which refuses any database not named `ci` on localhost:

   ```sh
   dropdb -h localhost -p 55432 -U postgres --if-exists ci && createdb -h localhost -p 55432 -U postgres ci
   DATABASE_URL=$L/ci DIRECT_URL=$L/ci npx prisma migrate deploy
   CI=true DATABASE_URL=$L/ci DIRECT_URL=$L/ci npx jest -c jest.db.config.ts
   ```

9. **Run `npx prisma generate`** from the main checkout after the merge (worktrees
   share `node_modules`, so a generate in a worktree rewrites the main checkout's client).

10. **Open the pull request** with the schema, the migration and the code together.
    CI's database steps build a `postgres:17.6` container in UTC from the history,
    run `check-migrations.ts`, `check-db-sidecars.ts` and `jest.db`.

## One database serves dev and prod

| Change                                              | Lane     | When it reaches the shared database                                             |
| --------------------------------------------------- | -------- | ------------------------------------------------------------------------------- |
| New table, nullable column, new enum value          | Expand   | On merge to `dev`, before or with the code that reads it                        |
| New CHECK every existing row passes, partial unique | Expand   | On merge; a CHECK that existing rows fail is a contract                         |
| Column rename                                       | Contract | Never in one step after launch: add, dual-write, backfill, then drop            |
| Drop column, table or enum value                    | Contract | Dispatched after the release that stopped reading it is live                    |
| `SET NOT NULL`, type narrowing                      | Contract | Dispatched after every writer is fixed and every row complies                   |
| Index on a large table                              | Expand   | Its own file holding one `CREATE INDEX CONCURRENTLY` statement and nothing else |

**Expand on merge.** A push to `dev` that changes `prisma/migrations/**` starts
`db-migrate.yml`. Its gate (`scripts/ci/migrate-gate.ts`) runs `prisma migrate status`,
lets the run continue only when the sole problem is pending migrations, then
`prisma migrate deploy`, then `prisma migrate status` again (must exit 0), then
`scripts/ci/check-db-sidecars.ts`. It connects through the Supabase session pooler
(port 5432) because runners are IPv4-only. It never retries, and a failure notifies
ops through `scripts/ci/notify-ops-failure.sh "db-migrate"`.

**Contract via dispatch.** The push run refuses any pending `_contract` folder:

```text
::error title=Migration gate::pending contract migration(s) 20261109000099_rehearsal_drop_contract need a workflow_dispatch run that names exactly one of them
```

The owner then runs **Actions → DB Migrate → Run workflow** on `dev`, typing the exact
folder name. A wrong name is refused (`the dispatch input "…_drop" is not a _contract
folder`); the exact name passes (`migrate-gate: ok — will apply …_contract`). Dispatch
needs write access to the repository, which is the approval, because GitHub Free has
no environments with required reviewers on a private repository.

**A pending contract blocks every later expand.** `migrate deploy` applies all pending
migrations in order and cannot skip one, so while a `_contract` folder waits, every
later push run fails at the gate. Dispatch the contract promptly, or keep the contract
pull request unmerged until its release is ready.

**The contract outage window.** While the database is shared, a dispatched contract
breaks `prod`'s older code until `dev` is promoted. Pre-launch that is accepted; time
the dispatch right before the promotion and record the window.

## What changes after the database split

When production gets its own database (the database split in issue #1873,
"Separate the production database from dev/preview/QA"), the lanes stay and only the
targets move. `db-migrate.yml` on `dev` migrates the dev database; a second job (on
the release branch, or a dispatch at promotion) migrates production, still through
the same gate. Contracts can then run on dev as soon as dev's code stops using the
object, and on production after promotion, so the outage window disappears. The dev
database is rebuilt from the history (`migrate deploy` on an empty project) and
seeded; the history, not a dump, is the source of truth. Local, preview and CI
variables point at the dev project, and the schema-required gate reads dev instead of
the shared database.

## Deploy previews

A preview runs the branch's code against the shared database, so a pull request that
adds a column previews against a database that does not have it yet: every read of
that model returns a 500 until the migration merges. Its build still passes, because
the build only runs `prisma generate`. `scripts/ci/check-db-schema-required.ts`
(`.github/workflows/schema-required.yml`) fails such a pull request loudly and lists
the objects; its message now says to merge the migration, never to apply the objects
by hand, because a hand-applied column makes the migration fail on merge
(`ALTER TABLE … ADD COLUMN` without `IF NOT EXISTS`). Verify such a pull request on a
scratch database instead.

## Conflicts between sessions and worktrees

- **Two pull requests, two migrations.** Whichever merges second must have a folder
  that sorts after the first. `check-migrations.ts` fails it otherwise:

  ```text
  ::error title=Migration history::20261109000000_too_early sorts before feat/migration-cutover's newest migration; rename it to a later timestamp
  ```

  Rebase, regenerate the SQL against the new history (step 3), and
  `git mv` the folder to a new timestamp. Never hand-merge two `migration.sql` files.

- **Never edit an applied migration.** Prisma 7.10.1 does not notice. After appending a
  line to an applied file, `migrate status` printed `Database schema is up to date!`
  and exited 0, and `migrate deploy` printed `No pending migrations to apply.` The only
  guard is `check-migrations.ts`, which compares against the base branch:

  ```text
  ::error title=Migration history::prisma/migrations/20261109000005_payment_guards/migration.sql is applied on feat/migration-cutover and was edited; add a new migration instead
  ```

- **A worktree behind `dev` sees a clean status.** When the database holds migrations
  the local folder lacks, `migrate status` still printed `Database schema is up to date!`
  with exit 0. Rebase before trusting any status output.

- **Schema edited without a migration.** `check-migrations.ts` diffs the history
  against the schema on the shadow database and fails on anything beyond the three
  standing drops:

  ```text
  ::error title=Migration history::schema.prisma and the migrations disagree; a migration is missing for: ALTER TABLE "Payment" DROP COLUMN "x"
  ```

- **The baseline is special.** Until it has been applied to the shared database,
  regenerate it with `scripts/db/generate-baseline.sh` after every schema merge; after
  that it is frozen.

## The transaction convention

Every `migration.sql` is `BEGIN; SET LOCAL lock_timeout = '3s'; … COMMIT;`, and
`check-migrations.ts` (`lintMigrationSql`) fails any file that is not. Rehearsed facts
behind it (prisma/orm#30640 is still open at 7.10.1):

1. An unwrapped migration is not atomic: `migrate deploy` commits each statement on its
   own. A file of `CREATE a1; CREATE a2; SELECT 1/0;` left `a1` and `a2` committed and
   the migration marked failed.
2. An explicit `BEGIN; … COMMIT;` restores atomicity. A wrapped file that failed left
   nothing behind (`rehearsal_a1` did not exist afterwards).
3. `SET LOCAL lock_timeout` has no effect unwrapped (it read back `0`) and works wrapped.
4. A plain `SET` leaks into every later migration of the same `migrate deploy` run, so
   the lint refuses session-level `SET` and `RESET` inside a migration.
5. The one exception is a file whose only statement is `CREATE INDEX CONCURRENTLY` (or
   `DROP INDEX CONCURRENTLY`), which Postgres refuses inside a transaction. Check
   `pg_index.indisvalid` after it runs; a failed concurrent build leaves an invalid index.
6. `ALTER TYPE … ADD VALUE` works inside the transaction, but the new value cannot be
   used until the transaction commits, so a migration that adds a value and writes it
   must be two migrations.

## When a migration fails

The wrapped file rolls back completely, so recovery is almost always "mark it rolled
back, fix it, deploy again". Exact output from the rehearsal:

```text
Applying migration `20261109000020_rehearsal_fail`
Error: ERROR: current transaction is aborted, commands ignored until end of transaction block
```

The error Prisma prints is **not the cause**: the real error (`division by zero` here)
happened one statement earlier and Prisma reports the next statement's refusal. Find the
cause by running the file against a scratch database with
`psql -v ON_ERROR_STOP=1 --single-transaction -f <file>`.

Every later deploy then refuses with `P3009`:

```text
Error: P3009
migrate found failed migrations in the target database, new migrations will not be applied.
The `20261109000020_rehearsal_fail` migration started at 2026-11-09 19:04:48.841214 UTC failed
```

Recovery, run by the owner against the shared database (an agent runs it only against
a scratch database):

1. `npx prisma migrate status`, and read the failed name.
2. Confirm in the catalog that nothing of it committed. With the wrapper this held.
3. `npx prisma migrate resolve --rolled-back <name>` printed
   `Migration <name> marked as rolled back.`
4. Fix the file. It never applied, so editing it is allowed; do it in a pull request.
5. Re-run the workflow (dispatch with an empty input for an expand). `migrate deploy`
   then printed `All migrations have been successfully applied.`

`P3018` is the same situation reported while the run is in progress. If a migration was
somehow unwrapped and partly applied, either finish it by hand and
`migrate resolve --applied <name>`, or undo the committed part and `--rolled-back`.

## `migrate status` outputs the gate is pinned to

| Situation                         | Exit | Text the gate keys on                                                      | Gate verdict |
| --------------------------------- | ---- | -------------------------------------------------------------------------- | ------------ |
| Nothing pending                   | 0    | `Database schema is up to date!`                                           | proceed      |
| Pending only                      | 1    | `Following migrations have not yet been applied:` then one folder per line | proceed      |
| A failed migration                | 1    | `Following migration have failed:` (singular, on stderr)                   | stop         |
| Unreachable database              | 1    | `Error: P1001: Can't reach database server at …`                           | stop         |
| Database ahead of the local files | 0    | `Database schema is up to date!` (not detected)                            | proceed      |
| Applied file edited               | 0    | `Database schema is up to date!` (not detected)                            | proceed      |
| Non-empty database, no history    | —    | `migrate deploy` refuses with `P3005 The database schema is not empty`     | n/a          |

`__tests__/db/migration-gates.test.ts` pins these strings. Re-pin them after a Prisma bump.

## `@ignore` during a contract

Marking a column `@ignore` (step R2 of a contract) removes the field from the generated
client while the column stays in the database: with `ReferralCode.referrerReward @ignore`,
the client had no `referrerReward` field, and `migrate diff` (both from the history and
from the database) proposed no drop. The column only goes when the `_contract`
migration drops it explicitly.

## Rehearsing on the local cluster

Run this before any change to the migration machinery, and after every Prisma or
Postgres bump.

1. **Build from history:** `createdb`, `migrate deploy`, `check-db-sidecars.ts`, then
   the `jest.db` tier on a database named `ci` with `CI=true` (2026-11-09: 56 suites,
   246 tests, 126 s).
2. **History matches the schema:** `check-migrations.ts` with `SHADOW_DATABASE_URL`.
3. **Catalog diff:** list `pg_constraint`, `pg_indexes`, `pg_trigger`, `pg_proc`,
   `pg_views`, enums, columns, RLS flags and Data API grants on two databases and
   `diff` them:

   ```sql
   SELECT conrelid::regclass::text, conname, pg_get_constraintdef(oid) FROM pg_constraint
    WHERE connamespace = 'public'::regnamespace ORDER BY 1, 2;
   SELECT tablename, indexname, indexdef FROM pg_indexes WHERE schemaname = 'public' ORDER BY 1, 2;
   SELECT tgrelid::regclass::text, tgname, pg_get_triggerdef(oid) FROM pg_trigger WHERE NOT tgisinternal ORDER BY 1, 2;
   SELECT proname, proconfig, md5(regexp_replace(regexp_replace(prosrc, '--[^\n]*', '', 'g'), '\s+', ' ', 'g'))
     FROM pg_proc WHERE pronamespace = 'public'::regnamespace ORDER BY 1;
   ```

4. **Gate and failure drills:** a database missing the last migrations (pending-only), a
   wrapped migration that fails (rollback, `P3009`, `resolve --rolled-back`, redeploy), a
   temporary `_contract` folder with no, a wrong and the exact dispatch input, an
   unreachable URL.
5. **Reset drill:** drop the app objects in `public` of a database built the old way,
   then `migrate deploy`. On 2026-11-09 the drop took 0.22 s, the extensions migration
   moved `btree_gist` from `public` to `extensions`, and the catalog matched a fresh build
   exactly.

## Facts observed on 2026-11-09

- The baseline from `prisma/schema.prisma` is 6,962 lines: 184 tables and 162 types,
  generated with no database connection.
- `btree_gist` installed `WITH SCHEMA extensions` still serves the exclusion constraints:
  `occurrence_no_confirmed_overlap` and `program_assignment_no_active_overlap` resolved
  `extensions.gist_text_ops` with `search_path` = `"$user", public`, because a default
  operator class is found by type, not by search path.
- The history leaves 170 asserted objects: 113 constraints, 44 indexes, 11 triggers, one
  view and one row-level-security table, and no table grant to `anon` or `authenticated`.
- Against a database built the old way (`migrate diff --from-empty` plus the former
  `prisma/sql` files), constraints, indexes, triggers, views, enums and columns were
  identical. The intended differences: the 13 `assert_*` functions carry
  `search_path=public` (bodies identical), `btree_gist`'s 188 support functions live in
  `extensions` instead of `public`, `OrgDataExportArtifact` has RLS enabled, and
  `_prisma_migrations` exists.
- The former sidecar parser missed seven constraints declared inside `DO` blocks; the
  migration parser asserts them.
- A `pg_dump -Fc` of the rebuilt database (0.8 MB) restored into a fresh database with
  `check-db-sidecars` green and `migrate status` up to date.

## Deprecated & Superseded Approaches

- **`npm run db:push` and the sidecar replay** (`scripts/db/preflight-push.ts`,
  `scripts/db/apply-sidecars.ts`, `prisma/sql/*.sql`, `prisma/sql/known-drift.json`).
  Removed by the cutover. Do not re-create a replay path or a drift allowlist; a
  divergence is fixed by a migration.
- **`prisma migrate dev`** against any database a teammate uses. Use `migrate diff`
  against a local shadow database instead.
- **`resolve --applied` baselining of the live database.** The owner chose a reset and
  rebuild from history instead, so the live database's `_prisma_migrations` records real
  applications from the first day.
