# Retention windows

Single source for how long each log-like and audit table is kept. The human-readable copy is in `docs/compliance/02-dpdp-and-privacy.md` (Retention windows) and the decision record is `docs/decisions/2026-11-01-data-retention-windows.md`. Change all three together.

Rules for agents:

- A new log-like or audit table needs a row here, a named driver, and a prune folded into `prune-audit-logs` (audit class) or `prune-system-job-executions` (telemetry and secondary). Do not add a ticker target: `MAX_TARGETS_PER_TICK` is 12 and the busiest tick holds 11.
- Never prune a live booking's `BookingStatusHistory` rows; `readRescheduleOrigin` reads a live booking's `PENDING` row at any age.
- Never prune `SupportCaseEvent` alone; `purgeEligibleWhere` finds unpurged cases by the absence of an `EVIDENCE_PURGED` event.
- `prune-system-events` keeps the newest event per `(correlationId, category)` for `STATE_BEARING_EVENT_PREFIXES`. A new feature that reads "the latest event for key X" as state must add its prefix there.
- A new back-office surface must be classified in `OPS_SURFACE_WINDOW` (the `Record` type makes this a compile error).
- CERT-In requires 180 days of ICT logs. The logs may be stored outside India if they can be produced to CERT-In in reasonable time (FAQ question 35). Do not write "inside India".
- Year windows (`prune-audit-logs`, `EmailEvent`, `WebhookEvent`) are UTC calendar years through `yearsBefore` in `lib/cron/retention-cutoff.ts`, not N x 365 days.
- The 8-year money-audit horizon is the owner's choice; confirm with the CA.
