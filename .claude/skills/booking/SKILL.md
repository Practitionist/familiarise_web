# Booking

This is the index for the booking domain. The doctrine below is inline because
every rule here is non-negotiable and has been violated at least once, each
violation costing real money or real bookings — the issue numbers are the
receipts. The four references carry the detail for a specific concern.

The appointment waitlist ("Notify me") and slot backup interest share one lifecycle (`lib/booking/interest/lifecycle.ts`); their product rules, vocabulary and roadmap are in the `growth` skill (`.claude/skills/growth/SKILL.md`).

## Doctrine

Seven rules govern every change in this subsystem. Treat any diff that breaks one
as wrong until proven otherwise.

### 1. Every status write goes through a CAS transition helper

`lib/booking/transitions.ts` exports seven guarded helpers, and no booking
status column may be written any other way. As of wave 5 (#1319) the set is
complete:

| Helper                           | Guards                                   | Allowed-from map                     |
| -------------------------------- | ---------------------------------------- | ------------------------------------ |
| `transitionConsultationRequest`  | `Consultation.status`                    | `REQUEST_ALLOWED_FROM`               |
| `transitionSubscriptionRequest`  | `Subscription.status`                    | `REQUEST_ALLOWED_FROM`               |
| `transitionWebinarEvent`         | `Webinar.status`                         | `EVENT_ALLOWED_FROM`                 |
| `transitionClassEvent`           | `Class.status`                           | `CLASS_EVENT_ALLOWED_FROM`           |
| `transitionOccurrenceCompletion` | `AppointmentOccurrence.completionStatus` | `OCCURRENCE_COMPLETION_ALLOWED_FROM` |
| `transitionTrial`                | `Trial.status`                           | `TRIAL_ALLOWED_FROM`                 |
| `transitionRescheduleRequest`    | `RescheduleRequest.status`               | `RESCHEDULE_ALLOWED_FROM`            |

Every map is keyed by **target** state: `ALLOWED_FROM[to]` lists the only states
the row may currently be in, and that set is baked into the `updateMany`'s
WHERE clause. An illegal transition therefore matches zero rows rather than
corrupting state, and the helper throws `IllegalTransitionError` (409,
`ILLEGAL_TRANSITION`, defined in `lib/enterprise/transitions.ts`). The WHERE
clause is the state machine; application-level pre-checks are only friendly
error text. Never swallow the zero-row case.

Two helpers depart deliberately. `transitionOccurrenceCompletion` takes a full
`Prisma.AppointmentOccurrenceWhereInput` because callers sweep by appointment rather
than by slot id, accepts `allowZero` because a cancel or reschedule sweep
legitimately matches no live rows, and returns the matched count.
`transitionRescheduleRequest` also clears `openForAppointmentId` and stamps
`resolvedAt` on any terminal target, so callers never have to remember to
release the one-open-proposal lock.

Every helper accepts `fromIn` to narrow or widen the set for a flow-specific
edge, and narrowing is safer: automated completion from a Stream webhook passes
`fromIn: ["SCHEDULED"]` so it can never lift a slot a human pulled back to
UNVERIFIED. As of wave 5 (#1322, ADR A12) each helper also appends one
`BookingStatusHistory` row in the same transaction, reading the from-status
before the CAS, so a lost race logs a stale from-status but never a wrong
state. Wave 6 (#1333) widened that same pre-read to fetch the owning
appointment, so `appointmentId` is stamped without a caller supplying it, and
added `appendCreationHistory` — the one row that is not a transition, written
from the literal `"CREATED"` in the same transaction as the create, because a
booking that has never moved still needs a timeline. The creation call
sites are `app/api/scheduling/request-for-approval`, the consultation and
subscription checkout handlers, and, as of 2026-09-19 (#1583 A-P1-06), the
capture webhook's legacy consultation and subscription creators in
`lib/payments/webhooks/handlers.ts` — every request birth now writes it.
The one reader, `getBookingTimeline` (`lib/data/booking-history.ts`, behind the drawer timeline and the entity trace), excludes in its query a same-status row with neither reason nor actor and lists a reschedule as "proposed", its answer being the request's own status row; the writes keep their self-edges.

Participant seats follow the same shape outside `transitions.ts`. Every
`AppointmentParticipant.status` write goes through `transitionParticipant` in
`lib/booking/participants.ts`. Its map, `PARTICIPANT_ALLOWED_FROM`, is keyed by target
like the others, and the from-set is ANDed with the caller's WHERE rather than
merged into it, so a caller that narrows keeps its narrower set and a caller
that forgot cannot make an illegal move. REFUNDED is terminal, HELD is
entry-only, and the one edge out of a released seat is `recordParticipants`'
revive, which widens `fromIn` explicitly. Unlike the seven helpers it returns
the count, never throws on zero rows, and writes a SEAT history row only when an
event caller passes `history` (a learner seat on a webinar or class; 1:1 seats
write none).

Two ending shapes are shared rather than copied, and a new ending must call
them. `declineOpenReschedules` (`lib/booking/reschedule-decline.ts`) closes
every open proposal on a booking that is ending, so the cancel route, the
abandon door, moderation and the maintenance freeze all decline the same way
and free `openForAppointmentId`. `restoreRescheduledBooking`
(`lib/booking/reschedule-restore.ts`) puts a booking back exactly as it was
before a reschedule released it — the `RESCHEDULED` slots back to `SCHEDULED`
and the parent back to the status the release recorded in
`RescheduleRequest.originStatus` (written in the release transaction; a legacy
row with no `originStatus` falls back to the release's history row). The
initiator's withdrawal, the counterparty's decline and the expiry sweep all use
it, and a restore that moved sessions stamps `RescheduleRequest.restoredAt`, so
the request costs no reschedule. The restore can meet the overlap constraint
when the original time was taken: withdraw answers 409 `ORIGINAL_TIME_TAKEN` and
leaves the proposal open, a decline still commits and parks the parent
(`parkParentForUnrestoredEnding`), and the sweep expires without the restore and
counts `proposalsExpiredUnrestored`.

Every party release opens a `RescheduleRequest`, with or without proposed times.
A release with no times ("any time works") is **preference-only**: it takes the
same one-open-proposal reservation (`openForAppointmentId`), gets the same
expiry, withdraw and restore, and the allocator closes it `ACCEPTED` when it
places the replacement, with or without a stated preference; a request that
named times and got different ones closes `DECLINED`
(`lib/booking/allocation/preference.ts`). A move an organisation actor opened
may be withdrawn by anyone acting for that same side; a move the side's own
party opened is theirs alone (`rescheduleWithdrawAuthority` in
`lib/booking/reschedule-withdraw.ts`, which the detail read also asks to stamp
`viewerMayWithdraw`). There is no release without
a request (reschedule route, `app/api/appointments/[appointmentId]/reschedule/route.ts`;
409 `NO_RESCHEDULABLE_SLOTS` when there is nothing to move). The allocator never
closes the consultant's own open proposal that names times, because that waits
on the client's consent: placing over it answers 409 `PROPOSAL_AWAITING_CLIENT`;
nor does it place over the consultant's own bare release of a paid session
(409 `PROPOSE_TIMES_REQUIRED`): the expert proposes times or the expiry restores.
A move from or to a time less than 24 hours away is an agreed move: it needs
proposed times, never auto-confirms (`needsOtherSideAcceptance`), expires at the
session's join window (15 minutes before the start), and a released session is never placed under 24 hours away
without an accepted proposal (`assertReplacementNotice`, 409 `NEEDS_ACCEPTANCE`).
An allocate on a consultation that already has a confirmed session is 409
`ALREADY_ALLOCATED` whatever the client sends (`mustBeUnscheduled`): moving it is
the reschedule door's job. Decision record:
`docs/decisions/2026-11-14-allocation-reschedule-and-short-notice-moves.md`.
A booking with an open proposal or released sessions is being moved, not
requested, so no decline door ends it (`assertNotBeingMoved`, 409
`USE_RESCHEDULE_RESPOND` / `USE_CANCEL_ENDPOINT`). The release records
what it released in `RescheduleRequest.releasedSessions` (ordinal and start), and
that record, not occurrence rows or history, is what the reschedule caps and the
refund notice floor read (`countedReleases` in `lib/booking/released-sessions.ts`).
A webinar never reschedules: the host re-times it (`retimeWebinar` in
`lib/booking/event-retime.ts`), and a class session is cancelled and made up.

### 2. Nothing that a Payment points at is ever deleted

`Payment.appointment` is `onDelete: Restrict` (`prisma/schema.prisma`), so
Postgres refuses to delete an Appointment a Payment points at, and the delete
throws instead of destroying the Payment rows, the refund trail and the credit
usage. That backstop exists because a trial cancellation once deleted the
appointment (#1074). The app rule is mechanical and sits in front of it: **the
payment guard rides inside the DELETE's WHERE clause**, never in an earlier
read, so a lost race becomes a clean zero-row answer. A payment that commits
after the statement's snapshot can still hit the `Restrict` foreign key; treat
that error as the same lost race, never as a reason to cascade.

The allocator's form is `tx.appointment.deleteMany({ where: { id, payment:
{ none: {} } } })`. A count of zero means a Payment committed between the read
and the write, so the caller keeps the appointment and strips only its
sessionless slots (`deleteExistingAppointments` in
`lib/booking/allocation/commit/release-tentative.ts`). Requests are retired by status: `DELETE
/api/bookings/consultations/{id}` and its subscription twin answer **405** with
`code: "DELETE_NOT_SUPPORTED"`, and
`__tests__/payments/appointment-delete-forbidden.test.ts` keeps the six sweep
scripts free of the forbidden call shapes.

Slot rows are soft-deleted uniformly as of #1380/#1424: `cleanup-abandoned-payments`,
`expire-stale-requests.ts`, and `cleanup-tentative-occurrences.ts` all release a
tentative hold the same way, through `transitionOccurrenceCompletion` to `CANCELLED`
with `deletedAt` set in the same call, so the row's history survives the
release. If you think you need a delete on an Appointment or a confirmed slot,
you are almost certainly wrong: reconcile in place, as `replaceContiguousSlotRun`
does precisely so Stream `Meeting` and `Recording` rows survive. The one
remaining exception is the allocator, which still hard-deletes the superseded
occurrences of a re-allocation (`release-tentative.ts`), cascading their
`Meeting`, attendance and feedback rows; until it is replaced by release-by-status
when the busy-time ledger lands **(planned)**, it refuses with 409
`SESSION_HAS_REMEDY` rather than delete a session that carries an incident
remedy. The reschedule cap therefore counts the release records on
`RescheduleRequest`, never occurrence rows (see the invariants table).

Offerings obey the same rule (#1846 CT-02). The consultation-plan,
subscription-plan, webinar and class DELETE routes run one Serializable
transaction under the offering's `event-checkout:` lock through
`deleteUntouchedOffering` (`lib/booking/offering-delete.ts`), with the no-history
guard from `lib/offerings/delete-guard.ts` inside the `deleteMany` WHERE. Only
subscription-plan, webinar and class checkout take that key; consultation
checkout locks its slot atoms, so for a consultation plan the Serializable
transaction and the in-WHERE guard alone carry the race. History
is a payment of any status, any consultee seat ever held, and for a subscription
plan any trial; a zero-row delete answers 409 `OFFERING_IN_USE`, and the offering
is archived instead. The Offerings card's `canDelete` runs the same fragments as
a query, so it never offers a Delete the server refuses. The unguarded
`crud-with-plan/[id]` DELETE routes are gone.

### 3. Refunds have exactly two front doors

One booking refunds through `refundBookingPayment`
(`lib/payments/operations/booking-refund.ts`); a whole webinar or class refunds
through `refundWholeEventPayments` (`lib/payments/operations/event-refunds.ts`).
A removed attendee's single seat is the third entry point,
`refundRemovedAttendeeSeat`, in the same event-refunds module. Never call
`createRefund` directly. The front doors exist because there are three rails and
only they split them correctly, keyed off the payment intent prefix.
`isInternalFundedIntent` matches `org_` — the synthetic intents org-funded
bookings carry — and refunds as an in-ledger reversal, because a gateway call on
these dies on `UNKNOWN_GATEWAY` and historically reversed nothing (#1003,
#1020). `isFreeCreditIntent` matches `free_` and restores referral credits
rather than moving gateway money. Everything else is the two-phase gateway refund.

### 4. Org scoping is explicit on every list

`lib/api/scope/parse.ts` is the single definition of the `?orgScope=` vocabulary
and resolves it to one of four kinds: `personal`, `org`, `orgMember`, and `all`.
An active membership alone does not earn `org` scope, which carries no user
filter — below `operations.read` the resolution deliberately downgrades to
`orgMember` (the member's own rows within that org) rather than returning 403.
Compose filters with `scopeOrgId` and `scopeToWhereOrgId`, end every `buildWhere`
with `assertNeverScope` so an unhandled kind is a compile error instead of an
unfiltered cross-tenant read, and never hand-roll an org filter.

The `org` arm is **rows this org owns, and only while it is readable**:
`orgOwnedAppointmentWhere` in `lib/api/scope/list-appointments.ts`. A row is
the org's on either of two grounds, each pinned to `ORG_SCOPE_READABLE_STATUSES`:
it is tagged to this org (`Appointment.organizationId`) AND either has no payment
yet (a request or free trial awaiting payment) or a payment on it carries this
org's id on a `WALLET`, `INVOICE` or `LICENSE` rail (the `sponsoredSeatsWhere`
predicate); OR the org hosts the catalog plan being delivered
(`plan.organizationId`), whatever tag or rail the buyer used. The host org
therefore sees every booking on plans it hosts, still metadata-only. The same
predicate gates the org's pending queue, documents, recordings, the org detail
page's operator branch and the org-party support grant. SUSPENDED stays in the
readable tuple on purpose — its OWNER has to be able to open the org to find
whatever suspended it; DEACTIVATED is the one exclusion. The `all` arm is
deliberately left unfiltered, because verifying a teardown means being able to
read the dead org.

The `personal` and `orgMember` arms split on two different facts, and both are
load-bearing (`buildWhere` in `lib/api/scope/list-appointments.ts`). The buyer
side (booked or attended, including a live webinar or class seat) splits on the
row's tag, `Appointment.organizationId`. The delivery side (the plan's consultant
or an ACCEPTED co-host) splits on the **plan's host org**, `plan.organizationId`,
never the buyer's sponsor tag: a sponsor-tagged booking on a consultant's personal
plan is on that consultant's personal tabs. A trial is always personal for the
learner, and splits on the subscription plan's host org for the consultant.
`scopeToWhereOrgId` and every scope builder end in `assertNeverScope`, so an
unknown kind fails closed.

The ownership pin and the grounds are both load-bearing and they close different
holes. #1166 ORG-8 removed the funded-elsewhere arm — `payment: { some:
{ organizationId } }` OR-ed beside the row's own `organizationId`, so the list
offered rows the detail page 404s; the payment grounds now ride the tag as an
**AND**, so they cannot re-open that hole, and the detail page admits exactly
the rows this predicate does. They also close the half the tag
never established — checkout stamps `Appointment.organizationId` for ANY org in the
request body, including `fundingSource === "PERSONAL"`, so filtering on the tag
alone published the amount of a member's personal card purchase to every MANAGER+
in the "Everyone" feed. A tagged, card-paid booking on a plan the org does not own
is therefore excluded. Cross-org funding visibility remains the money views' job.
Org lists stay metadata-only by design (ADR 20): an org sees that a session
happened, never its content.

`list-documents.ts` and `list-recordings.ts` reach the same predicate through
the parent `Appointment` (a document's or recording's org is its booking's), so
the readable-status pin rides along. `resolveOrgScope`'s own `orgStatus` field is the other door:
`app/api/collaborations/route.ts` passes the matched membership's
`organization.status` and gates its org-hosted view on `ORG_SCOPE_READABLE_STATUSES`
plus `catalog.manage`. The resolver refuses a DEACTIVATED org (403 `ORG_DEACTIVATED`) only when some
status source is present (`ctx.orgStatus`, the membership's `orgStatus`, or its
`organization.status`); a caller that supplies none is not checked, so pass one or
filter on the predicate.

### 5. An approved request that was never paid has one outcome: EXPIRED

The lapsed pay-link sweep is `cleanupExpiredApprovalPendingPayments` in
`scripts/payments/cleanup-abandoned-payments.ts`, and it transitions the request
to `EXPIRED` with `fromIn: ["APPROVED_PENDING_PAYMENT"]` — narrower than the
map's default, so only the lapsed shape moves. The status guard is not enough on
its own: the sweep also **repeats the cohort read's money predicate**
(`appointment: { payment: { none: { paymentStatus: SUCCEEDED } } }`) inside the
CAS `where`, so a capture that landed between the read and the write matches zero
rows instead of expiring a paid booking. Payment rows then expire from `PENDING`
only, through a conditional `updateMany`, so a racing capture keeps its
`SUCCEEDED`. Any new sweep must carry both guards. It is deliberately not REJECTED,
which reads as "the consultant declined" on every surface, and deliberately not
CANCELLED. As of wave 5 (#1321) the unscheduled
`app/api/cleanup/approval-payments` route is deleted and its work rides inside
the abandoned-payments run, so there is one code path and one semantics. Sibling
sweeps with _different_ cohorts still end in CANCELLED, so the one-outcome rule
is about approved-but-unpaid specifically, not all abandonment. No captured
money moves in this sweep, because a paid row never reaches the expiry:
`SUCCEEDED` payments are filtered out by the cohort read and again by the CAS
`where`, and the payment rows themselves expire from `PENDING` only. What does
move is what the open order's checkout consumed: after the request CAS wins,
`lapseApprovedRequest` calls `expirePendingPaymentsInTx(tx, …)`, which claims
each `PENDING` order by its own CAS and returns its referral credit, code use and
engagement in the same transaction. A captured, already-expired or second-lapsed
order returns nothing, and no gateway cancel runs. An approval re-mint returns
the old order's credit and, for a still-PENDING order, its code use at once, and
drops the code and the welcome discount from the row (`claimRowForRemint`), because the new order charges
the full price (`docs/decisions/2026-11-20-unpaid-approval-orders-return-what-checkout-consumed.md`; no
backfill). The sweep that does refund is a
different cohort — `expireApprovedUnallocatedSubscriptions` in
`scripts/appointments/expire-stale-requests.ts` expires an `APPROVED` plan that
never had a confirmed session and has no open proposal (`approvedUnallocatedWhere`,
repeated in its CAS) and stamps a full refund for every `SUCCEEDED` payment; a
plan that ever had a session waits for plan-end settlement instead. The
sibling pass in that same file, `expirePaymentPendingRequests`, is the pattern
rather than a counter-example as of #1423: it flips `APPROVED_PENDING_PAYMENT`
to `EXPIRED` through `transitionConsultationRequest`, with `fromIn:
["APPROVED_PENDING_PAYMENT"]` and the `UNPAID_CONSULTATION` money predicate
repeated inside the CAS `where`, the same two guards this rule requires of any
new sweep.

A lapsed pay-link (#1703 D2) can be seen first by either of two sweeps —
`cleanupAbandonedPayments` and `cleanupExpiredApprovalPendingPayments`, both in
`scripts/payments/cleanup-abandoned-payments.ts` — and both now call one shared
helper, `expireLapsedPayLink`, rather than each running its own CAS. The helper
is the same `fromIn: [APPROVED_PENDING_PAYMENT]` plus repeated-money-predicate
shape this rule already requires, and the consultee's `PAY_LINK_LAPSED_REASON`
notice is tied to the CAS **win** inside the helper, not to either caller
individually, so the notice fires exactly once regardless of which sweep gets
to the row first. Before this was fixed (#1724 QA, 2026-09-19), whichever sweep
claimed the row first could leave the consultee un-notified. The rule this
generalizes to: when two sweeps can legally claim the same row, give them one
shared CAS-plus-notice function, not two copies that only one of them
remembers to notify from.

As of 2026-09-19 (#1732, #1589 P-P1-01) a subscription's lapsed pay-link rides
the exact same `expireLapsedPayLink` path a consultation's does — the
`cleanupAbandonedPayments` cohort read was widened to subscriptions, closing
the gap where a subscription's placeholder appointment has no tentative
occurrence for the abandoned-payment cohort to match before allocation. The
same date retired `cleanup-stale-pending-consultations` entirely: it CANCELled
the same `APPROVED`/`APPROVED_PENDING_PAYMENT` unpaid-after-seven-days cohort
`expire-stale-requests` EXPIREs, which was two sweeps and two terminal words
for one event — the exact violation this rule exists to prevent. There is now
one sweep pair and one outcome.

A buyer who walks away is the other half of this rule, and it has one door:
`POST /api/bookings/[bookingId]/abandon` (`lib/booking/abandon.ts`, #1527
decision 11). The buyer decided, so the outcome there is CANCELLED, and the
`paymentDueAt` sweep stays the EXPIRED backstop for when nobody acted. The door
takes the appointment lock, cancels a consultation, subscription or trial or
releases only the caller's HELD webinar or class seat, expires the caller's
PENDING payment by CAS, gives back credits and org engagement, and cancels the
gateway order after commit. The money predicate rides every CAS WHERE, so a
capture that commits first answers 409 `ALREADY_PAID` and the policy-quoted
cancel owns it.

"Book again" on a booking whose window already closed while its order is still
PENDING is a lapse, not a walk-away, and it has its own door:
`POST /api/bookings/[bookingId]/request-again` (`closeOrderForRequestAgain` in
`lib/booking/request-again.ts`), behind the shared `RequestAgainButton`, which
decides at the click, warns first and navigates only on `{ closed }`. Ownership
is read before the lock. Under the lock it asks the gateway first, as the
abandoned sweep does (a live payment answers 409 `PAYMENT_IN_PROGRESS` and stays
PENDING for reconciliation; an unanswered ask answers 503
`GATEWAY_UNCHECKED`), then in one Serializable transaction it expires the caller's PENDING orders through
`expirePendingPaymentsInTx` (payment before booking), then ends the booking
through its own sweep's writer: `lapseApprovedRequest` with reason
`REQUESTED_AGAIN` (EXPIRED), the abandoned pass's shape for a pay-first hold
(`DIRECT_CHECKOUT` only, never under an open move), CANCELLED for a paid trial
with its hold notices staged, the caller's HELD seat for an event. A CAS miss
throws so the expiries roll back; the answer is then 409 `ALREADY_PAID` when
`holdsCapture` finds a kept capture its refunds do not cover, and 409
`NOT_CLOSABLE` otherwise. After the
commit each closed order is re-read once, and a capture found goes through
`handlePaymentSuccess` and is refunded; a later capture on the EXPIRED order is
refunded
(`docs/decisions/2026-11-20-request-again-closes-the-old-order.md`).

A manual Remind on an approved-but-unpaid request is offered and accepted
under one predicate, `liveReminderPayment`
(`lib/booking/payment-reminder-eligibility.ts`): `APPROVED_PENDING_PAYMENT`, a
`pendingPaymentUrl`, an appointment, a consultee email, and a newest PENDING
payment whose `expiresAt` is still ahead. The Requests inbox read ships only that
expiry (`reminderExpiresAt`) and the row hides Remind at that instant;
`remindApprovedPayment` re-checks the same predicate and answers 409
`NOT_AWAITING_PAYMENT`. An `AWAITING_PAYMENT` presentation alone is not proof
that there is a link to resend, so never gate Remind on the booking state.

### 6. There are no backfill migrations

The schema is managed with `prisma db push`, not migrations, and everything
currently in the database is seed data awaiting the one-time pre-MVP reset
(`docs/prisma/README.md`). The doctrine is therefore to freeze
the schema shape before launch, have every code path write the new tables from
day one, and never write a data migration for pre-reset rows. This is why wave 5
added `AppointmentParticipant` and `BookingStatusHistory` with no backfill.
Several constraints are staged behind a commented banner at the end of
`prisma/sql/check-constraints.sql` because they cannot pass against pre-reset
data; do not uncomment them outside the reset window.

## Compensation and misses (decided 2026-11-03; the class exit right is built, the rest is planned)

See the decision record `docs/decisions/2026-11-03-booking-v2-direction.md`. A 1:1 plan that ends with unused sessions will offer the client up to 4 extra weeks (if the expert has open hours and agrees) or a refund, defaulting to a refund after 7 days; no-shows and late cancels are not compensated (#2561 / #2568). A missed class session keeps today's make-up-within-14-days-or-refund rule. A class with many misses keeps each learner's exit right, and at half the class missed a support case opens (support may cancel for everyone; nothing cancels automatically). Decided 2026-11-04 (#2563): a learner's class exit right is 3 host misses in any rolling 30 days or max(3, 15% of N) misses in total, kept once tripped unless an ops correction withdraws it before it is used (built: `exitRightFor`, `exitThresholdFor` in `lib/booking/class-series.ts`), with the support case at twice that or 3 misses in a row; an ADMIN executes a class-wide cancel (refund of unheld sessions, no second admin); staff can grant a no-money make-up ("add N sessions" / "add up to 4 weeks"); a half-missed class holds only that class's unpaid host earnings. Apart from the exit right, until these ship, don't write compensation copy.

## Three time pickers (built 2026-11-13)

One per job; do not add a fourth, and do not give a new surface its own picker (`docs/calendar/allocate-heatmap-ux.md` §9). **Pick one time:** `SingleTimePicker` with `MonthGrid` (`components/scheduling/`), options from `lib/scheduling/single-session-options.ts`; the caller passes its writer's `purpose`, so the lead is `leadMsFor` or `eventLeadMs`, never restated. A buyer gets free times inside published hours, and the day's taken times behind "Show N taken times", each with "Notify me" in the One-time dialog; a host gets free and "Booked" times and an "outside my hours" switch. **Place many sessions on a week:** `UnifiedCalendar`/`WeekGrid`/`SessionTray`, `MobileDayListPicker` on a phone. **A repeating class pattern:** `ClassPatternScheduler`. On an instant-booking expert a held 1:1 time is taken, never a request: `consultationCtaFor(mode)` and 409 `REQUEST_NOT_OFFERED` at the request door.

## Booking states (built 2026-11-14)

Every booking badge, for every viewer, comes from `bookingStatus` (`lib/appointments/booking-status.ts`): one of Requested, Awaiting payment, Confirmed (Registered for a seat), Being moved, Completed, Cancelled, Refunded, with one reason line. A host's own webinar or class keeps its event words. Never add a label map beside it; pass it more facts instead. "Approved" appears only as a timeline step, read from the history edge (`expertApproval`). A booking is Completed when its sessions' outcomes are recorded, not when the clock passes. The reschedule buttons come from `rescheduleAnswersFor` and send `rescheduleAnswerRequest`, pinned by `__tests__/booking-algorithm/reschedule-answer-contract.test.ts`. The record is `docs/decisions/2026-11-14-booking-states-and-demand-guidance.md`.

A pending move is filed by who answers it next: `deriveBucket` puts the proposer's row under Waiting and the other side's under Needs you with `ANSWER_MOVE`, before the generic pending branch. Only a whole-booking move (status `PENDING`) is refiled; a per-session subscription move keeps the plan in Upcoming. Whose move it is comes from `listStatusFacts(…, { side, userId })`, which compares `initiatedById` with the signed-in user, as `openReschedule` and the learner's Home strip do (`__tests__/appointments/move-bucket-by-answerer.test.ts`). See `docs/booking/07-rescheduling-flow.md`, "Where an open move is listed".

## Deprecated & Superseded

Recognise these leftovers and delete them; never reintroduce them.

- `APPOINTMENT_STATUS_BADGE`, `TRIAL_STATUS_BADGE`, `eventUnionStatusBadge`, `BOOKING_LABEL` and the organisation and operator status maps: replaced by `bookingStatus`.
- `setParticipantStatus`: replaced by `transitionParticipant` (`lib/booking/participants.ts`).
- Reschedule caps and the refund notice floor counted from `BookingStatusHistory`: both read the release records on `RescheduleRequest` now (`countedReleases`).
- A reschedule release with no request behind it, and a decline that left the sessions released: every release opens a request, and every ending that can restore does.
- An allocator that took only `auto-allocate:` (or its day-sharded keys) and no slot atoms: it takes the shared atomic slot batch.
- `schedulingPeriodEndsAt` read as the plan end: read `subscriptionPlanEnd`.
- Group-event "Unschedule": replaced by re-time and the `retimeBy` free leave.
- `leadTimeFor` and the one 15-minute "Too soon" on every grid: replaced by `leadMsFor(purpose, { settled })` and the grid's `?purpose=`.
- The delivery-gated rolling subscription cycle: replaced by fixed plan weeks in `subscriptionEntitlement`.
- A sold plan's cadence read from the live plan row: replaced by the frozen `Subscription.sessionsPerWeek` / `sessionMinutes` (`soldTermsOf`).
- A 1:1 request and a trial priced and sized from the live plan, a re-mint of a live pay link at the new amount, and the same-calendar-day rule for consultations (`validateSameDaySlots`, `validateDayBasedConsecutiveSlots`): replaced by the agreed price, the booked session's length and one consecutive block.
- `linkCompletedTrialToSubscription` at checkout start: replaced by `convertCompletedTrial` at payment.
- A trial request with no time that the consultant scheduled later, and a paid trial charged against a session-less placeholder: replaced by the learner's pick (`bookTrialInTx`); a paid trial holds its time as AWAITING_PAYMENT.
- Trials that could not be rescheduled or cancelled by the expert: each side moves a trial once (`confirmTrialProposal`) and the expert cancels through trial DELETE.
- A REJECTED PATCH that ended a booking being moved: refused by `assertNotBeingMoved`.
- `splitSlotsByDay`: deleted; grid windows sit on the UTC half-hour lattice.
- Dead-hour folding (`lib/scheduling/dead-hour-bands.ts`, "Unavailable · HH:MM–HH:MM" strips) and per-cell run labels: replaced by the open-hours window (`openHoursWindow`) and session blocks (`buildGridBlocks`); see `docs/calendar/allocate-heatmap-ux.md`.
- `exitRightFor(misses, N)` (three misses or a quarter of the series, so a 100-session class tripped at 3): replaced by `exitRightFor({ hostMissAts, misses, N })`, 3 host misses inside 30 days or max(3, 15% of N) in all.
- A whole-event cancel that committed with a seat's refund owned by another door's marker (first writer wins) and drove whatever marker it found: it refuses like every other cancel door and drives only its own keys.
- `EVENT_WAITLIST_RENOTIFY_COOLDOWN_MS` and `EVENT_WAITLIST_RETENTION_MS`: replaced by `INTEREST_RENOTIFY_COOLDOWN_MS` and `INTEREST_RETENTION_MS` in `lib/booking/interest/lifecycle.ts`, which slot backup interest now shares (it used to notify a row once ever and never purge).
