# Enterprise

This is the index for the parts of the organisation subsystem that touch money and commercial configuration. It sits beside `finance` rather than folding into it because an organisation's funding rail, 7-axis program/overage permutation engine, progressive-disclosure UI guidance, and host-org payout pipeline are product concepts specific to the B2B side, layered on top of the same checkout, ledger, and TDS machinery `finance` documents.

## Non-negotiables

1. **Same Money Spine, Unlocked 7-Axis Permutation Engine**: An organisation's booking runs through the same checkout, price derivation, GST calculation, single writer, and double-entry ledger as a personal booking; only the funding legs and entitlement metering differ. Every `(FundingSource × ProgramType × OverageBehavior × overageSurchargeBps)` permutation (`WALLET × LICENSED_SEAT`, `LICENSE × CREDIT_POOL`, `PERSONAL × (CREDIT_POOL | LICENSED_SEAT)`, `CHARGE_MEMBER` synchronous co-pay split-leg or post-hoc pay-link with earnings hold, `WALLET × CHARGE_ORG` with surcharge + GST, and `LICENSE × CHARGE_ORG` child invoice accrual) is supported end-to-end in the engine **without backend HTTP 400 refusal walls**.
2. **3-Tier UI Motivation & Progressive Disclosure (`RECOMMENDED` / `ADVANCED` / `DISCOURAGED`)**: Instead of blocking valid edge permutations in API routes, `lib/enterprise/reachable-paths.ts` classifies each permutation into `RECOMMENDED` (Golden Path, default visible), `ADVANCED` (Guided Friction behind `<AdvancedPermutationGate />` with explanatory `<MotivationBanner tier="ADVANCED" />`), or `DISCOURAGED` (High-Friction Confirmation inside `<AdvancedPermutationGate />` + `<MotivationBanner tier="DISCOURAGED" />` with a 1-click switch to the recommended alternative).
3. **Cross-Org & Multi-Collaborator Settlement Integrity**: `Payment.organizationId` identifies the buyer/sponsor org while `Payment.hostOrganizationId` identifies the supply/host org (`Buyer Org != Host Org` supported). `OrganizationEarnings` is keyed by `@@unique([paymentId, organizationId, consultantProfileId, role, cycleOrdinal])` so multiple collaborators in the same host org and recurring subscription cycles each receive their own snapshot-isolated earnings row, and `createOrgPayoutBatch` claims rows atomically before computing payouts. Full detail and sources live in the two references above.
