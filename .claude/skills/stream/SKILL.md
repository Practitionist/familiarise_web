# Stream Chat & Video Operational Skill

Two products under one API key: **Stream Chat** (`stream-chat`, `stream-chat-react`) and **Stream Video** (`@stream-io/video-react-sdk`, `@stream-io/node-sdk`). They share a user store, a JWT signing secret, and a token-revocation timestamp (`revoke_tokens_issued_before`) — while billing independently (Chat by MAU, Video by participant-minute).

## 3. Server-Action Boundary, Call Isolation & Webhook Security Rules

1. **1 Occurrence = 1 Active Stream Call (`ADR-01`) & Stale-Link Aliasing**:
   - Every `AppointmentOccurrence` maps 1:1 to a `Meeting` row (`appointmentOccurrenceId @unique`). `Meeting.streamCallId` stores bare IDs (`occurrence-<uuid>`, rotating to `occurrence-<uuid>-r<base36>` on pre-start device-test resets or host reopens), never `default:`-prefixed strings.
   - `loadMeeting` (`lib/meetings/access.ts`) looks up `where: { streamCallId }` first and falls back to `parseOccurrenceIdFromCallId(callId)` (`occurrence-<uuid>`) so bookmarks and email calendar links route directly into active rotated call segments.
2. **Never Call Stream RPCs Inside `prisma.$transaction` (`PG_POOL_MAX=1`)**:
   - `assertCanMintToken` (`actions/stream/chat/stream.action.ts`) refuses when the user row is missing, erased or banned; the Prisma delegates are called directly, never through optional chaining.
   - Execute all Stream network requests outside Prisma transactions wrapped in `withStreamCircuitBreaker`, and guard database transitions via conditional compare-and-set (`updateMany`).
   - Internal Stream modules (`user.action.ts`, `channel.action.ts`, `meeting.action.ts`) never expose unguarded `"use server"` actions; client-callable Server Actions verify `getSession()`, reject banned users, and strip emails (`stripStreamUserEmails`) from the Stream objects they return.
   - Stream user payloads come only from `toStreamUser()` (`lib/stream/user-payload.ts`: `id`, `name`, `image`, `role`); never add email or another contact field. `performStreamUserSync` (`stream-sync`) unsets `STREAM_CONTACT_FIELDS` from older Stream users and reports `totalContactFieldsScrubbed` and `totalFailedScrubs`; it skips deactivated users, because Stream fails the whole `partialUpdateUsers` call on one; a failed scrub ends the run with the checkpoint held at the start of that page, before its deletions, so the next run replays it.
3. **Deterministic IDs Without `localeCompare` & Explicit Token `iat` / `exp`**:
   - Derive channel IDs using UTF-16 code-unit ordering (`a < b ? [a, b] : [b, a]`) capped at 64 chars (`lib/stream-channel-ids.ts`).
   - Always pass both `exp` and `iat` (`Math.floor(Date.now() / 1000) - 60`) when minting tokens so `revoke_tokens_issued_before` cutoffs take effect immediately.
   - `default` call-type grants strip `join-call` from `user`/`guest`, grant `call_member` only `join-call` (never `join-ended-call`, so an ended room stays sealed at Stream), `create-call-reaction`, and creator `-owner` moderation grants, and assign accepted presenter collaborators `co_presenter` (mute, pin, backstage, publish; never `end-call`).
4. **Webhook Ingress, Decompression Guard & Subscription Parity**:
   - `/api/stream/webhooks` is exempt from `MAINTENANCE_MODE`, verifies `X-Signature` (HMAC-SHA256 with `STREAM_WEBHOOK_SECRET` + `STREAM_WEBHOOK_SECRET_PREVIOUS` fallback) and `X-Api-Key`, enforces `MAX_WEBHOOK_COMPRESSED_BYTES = 512 KiB` and `MAX_WEBHOOK_DECOMPRESSED_BYTES = 2 MiB`, ignores deliveries outside `[-10m, +2m]` skew without DB bloat, deduplicates on `stream_${X-Webhook-Id}` (`stream_${eventType}_${sha256(rawBody)}` fallback), and stores only the schema-parsed payload in `WebhookEvent.payload` (`schemas/webhooks/stream.ts` drops names, images and custom data; every field a handler reads is declared there), writes the receipt with one `create` (a unique violation is a duplicate; only a duplicate tries `reclaimAbandonedWebhookReceipt`), hands the held claim to `processStreamEvent` (which has no self-claim branch; the sweeper claims through the fenced `reclaimStaleProcessingWebhookEvent` in `lib/stream/webhook-receipt.ts`), throttles its three error-path Sentry reports (`captureThrottled`), and accepts only the `default` call type (`OWNED_CALL_TYPES`).
5. **Control-Plane Contract & Daily Drift Detector**:
   - `lib/stream/control-plane-contract.ts` is the one intended state (one webhook hook per product — `video` for the `call.*` events, `chat` for `user.unread_message_reminder` — `default` and unused call-type grants, `co_presenter`, inactivity timeout, app settings, and `TARGET_CHAT_REMINDERS`: `reminders` + `read_events` on `messaging`, `reminders_interval: 1800`); `scripts/stream/ensure*.ts` write it and the read-only ticker job `stream-control-plane-drift` (`lib/stream/control-plane-drift.ts`, daily 01:15 UTC, `/api/cleanup/stream-control-plane-drift`) reads it and sends one Sentry message of finding keys on drift. It takes a fail-open `withCronLock` lease so each run writes a `SystemJobExecution` row, which gives it a paging freshness requirement in `/api/health/jobs` (`jobNameFor` never returns `null`); a run that finds drift is still a `COMPLETED` row, so the signal stays the Sentry message. There is no GitHub workflow for it. `user` and `call_member` hold only `remove-call-member-owner` and `update-call-member-owner`; member changes run server-side as admin. The `messaging` channel type's `user` role holds no `truncate-channel-owner`, `delete-channel-owner`, `update-channel-members-owner`, `recreate-channel-owner` or `update-channel-owner` (`scripts/stream/ensure-messaging-grants.ts`), so channel membership and history change only through server actions.

## 4. 4-Part DM & Trial Policy, Booking Tag, Managed Channels & Revocation

1. **One Human Pair = One Canonical DM Channel**:
   - **B2C Personal Scope**: `dm-<a>-<b>` (or `dmh-<sha256>` if $> 64$ chars).
   - **B2B Enterprise Org Scope**: `dmo-<orgHash>-<pairHash>` with `custom.organization_id = orgId`.
   - Consultee-to-consultee peer DMs are prohibited (`canDirectMessage` in `lib/stream/dm-eligibility.ts`).
2. **Paid / Confirmed Gate (`DM_ELIGIBLE_STATUSES = ["APPROVED", "SCHEDULED", "COMPLETED"]`)**:
   - Confirmed webinar/class enrollments (`OPENABLE_EVENT_STATUSES`) provision both the group `team` channel (`webinar-<id>` / `class-<id>`) and a 1:1 personal DM with the host, preserving `ACCEPTED` collaborators in `syncUserEventChannels`.
3. **A Free Trial (`TRIAL`) Never Grants Chat**:
   - No provisioning: `ensureChannelsForAppointment` (`lib/payments/webhooks/ensure-channels.ts`, not `handlers.ts`) stamps and returns `skipped: "trial_chat_blocked"`.
   - No DM: `canDirectMessage` / `pairBookingContexts` exclude consultations and subscriptions whose appointment is a `TRIAL` or whose client seat is `REFUNDED` (`excludeNonDmDirectBooking`).
   - No in-call chat or Q&A: `isInCallChatAllowed("TRIAL") === false` (`app/meetings/[id]/components/MeetingRoom.tsx`, the Q&A route 403). Do not cite `enableChat={false}`; that is the whole meetings layout.
4. **Booking Tag, Not a Posted Card**:
   - `POST /api/stream/channels/open` posts nothing. A DM opened from an appointment shows a removable chip (`BookingTagComposer` in `components/chat/BookingTag.tsx`) that adds `booking_appointment_id` to the sender's next message only, through `MessageComposer`'s `overrideSubmitHandler`.
   - Message custom fields are client-written: a rendered tag comes only from `GET /api/stream/booking-tag` (`resolveVerifiedBookingContextTitle` for both DM humans plus `isDmChannelIdEligible`), never from message fields. Old `system-booking-context` cards are hidden.
   - On the appointment detail page and the list quick view, chat actions carry an `AppointmentChatTarget` and open `AppointmentChatSheet` (one Stream client via `ChatSurface`); the Messages deep links still work.
5. **Chat is text-only**:
   - The `messaging` and `team` channel types run with `uploads: false` and no base attachment grant (`upload-file`, `upload-attachment`, `create-attachment`) for any role. The `-owner` / `-any-team` attachment grants and the giphy command are kept on purpose: GIFs are attachments, and `uploads: false` is what blocks files, which go through appointment documents. The setting was applied to the shared Stream app on 2026-10-24; a post-apply dry run and a client attachment probe confirmed it. `scripts/stream/ensure-chat-text-only.ts` is dry-run by default, backs up the pre-image and re-reads the type to verify; run it with `--apply` after any control-plane restore. The community page that advertised uploads is deleted.
6. **Managed Channels & Derived Membership**:
   - `MANAGED_CHANNEL_PREFIXES` (`lib/stream-channel-ids.ts`) = `webinar-`, `class-`, `collab-`, `dm-`, `dmo-`, `dmh-`. Legacy `consultation-`/`subscription-` and `webinar_`/`class_` are NOT managed. `isManagedChannel` is the predicate.
   - `addMemberToChannel` refuses non-staff adds to a managed channel (`DERIVED_CHANNEL_MEMBERSHIP`), audits staff adds via `recordOpsAction`, and keeps DMs closed. The info dialog hides Add Members and Clear chat on managed channels (truncate wipes every member's thread).
   - `createCollaboratorChannel` is get-or-create only and returns `frozen`; never unfreeze it. The open route answers `423 CHANNEL_FROZEN` and `403 ORG_DEACTIVATED` (checked before host/collaborator arms; staff exempt).
7. **Revocation Is Server-Side, Not Client-Cooperative**:
   - After the mutating action commits, call `lib/stream/access-revocation.ts`: `revokeEndedSeatAccess` (cancel route, `leaveEventSeat`) or `revokeRefundedSeatAccess({ refundId, payerUserId })` (`refundBookingPayment`, only when the refund ends the seat, which a refund with no amount always does while a `keepSeatIfPartial` explicit amount reads the balance; intent keyed by the `Refund` row, written through `tx` inside the internal and credits rails' refund transaction (`persistRefundRevocationInTx`) and persisted before the gateway seat stamp, re-stamped by `restampRefundedSeats` only while the refund is SUCCEEDED/PENDING; any refunded seat an open `SEAT_ACCESS_REVOKE` row already owes is skipped whatever the booking's status, since the door that wrote it drives it (`seatsWithoutOpenSeatIntent`)). `leaveEventSeat` and the cancel route write their seat intents inside the transaction that ends the seat (`persistSeatRevocationInTx(tx, appointmentId, userIds)`, every query on `tx`), then pass the returned generation to `revokeEndedSeatAccess` after the commit so it settles only that generation; the 1:1 replay of a committed cancel runs no transaction and calls it without a generation, which persists first. Each persists an intent before any lookup or Stream call, then remove the channel, the DMs `isDmContextEligible` no longer justifies and every provisioned room inside an 8 s budget (chat gets at most half, so rooms are never starved); the sweep owns the rest. A whole-event cancel revokes exactly the client seats its transaction released (`transitionParticipantSeats` returns them), never a seat that ended earlier. Membership writers (`/join`, seat adds, provisioning) call `fenceSeatGrants` after granting (a provision whose `Meeting` row fails to save calls `releaseUnsavedRoom` instead, since no row means no drive can reach that call); it returns `verified`/`lost`, and on a read failure persists intents and `/join` answers 503 `SEAT_UNVERIFIED` to non-hosts (hosts admitted). The drive never revokes staff (plan owner, accepted collaborators, occurrence hosts). Room progress persists in `StreamRevocationRetry.resumeAfter`.
   - A Stream failure enqueues a `StreamRevocationRetry` row (`kind`: `ERASURE_REVOKE` default, `COLLAB_REVOKE`, `EVENT_CHANNEL_REMOVE`, `DM_REMOVE`, `ORG_REVOKE`, `SEAT_ACCESS_REVOKE` (appointment), `REFUND_ACCESS_REVOKE` (refund); `planId` = the kind's target). The DB enforces `stream_revocation_retry_owner` (CHECK) and `stream_revocation_retry_open_key` (one open row per target) in `prisma/sql/check-constraints.sql`. `retry-moderation-enforcement` (30 min) drains via `redriveAccessRevocation` (stops starting rows after `SWEEP_START_DEADLINE_MS`, and a seat or refund row with under 5 s left), which treats Postgres re-grants as settled. Each write stamps a fresh `nextRetryAt` generation; a writer settles only its own generation and the sweep's outcome write is conditional on `attempts` + `nextRetryAt`, so a re-armed row stays owed. Seat, refund and erasure rows never give up: past `REVOCATION_ATTEMPT_CAP` (`lib/stream/revocation-retry-policy.ts`) they retry daily and the ops digest counts them. When `isStreamConfigured()` is false nothing is attempted and every row stays owed (`STREAM_UNCONFIGURED`), never settled (`STREAM` vendor erasures are counted, not fetched, so they never block other vendors); the sweep's warning is a `reportStandingFinding` (once a day across instances). `cancelAgedParkedConsultations` only calls `persistSeatRevocation` (the sweep drives it), never a synchronous drive inside its money job.
   - `revokeMemberStreamAccess` (`lib/stream/org-access-revocation.ts`, called by `removeMember` in `lib/enterprise/member-removal.ts`) revokes tokens issued before the removal, drops the member from org calls, queues `ORG_REVOKE`. Without Stream's keys it returns `complete: false`, so the `ORG_REVOKE` row is queued and stays owed. `sdkTokenProvider` (`providers/StreamProviderImpl.tsx`) skips the token cache on every SDK re-request after the first.
   - `syncUserEventChannels` only tidies the viewer's own list. The `initialSyncCompletedUsers` set, the `stream_sync_<id>` flag and its `force` parameter are gone; do not reintroduce a suppression gate.
   - `reconcile-stream-memberships` (`lib/stream/membership-reconciler.ts`) is the daily audit: ticker only (hourly `:20` in a 00:00-03:00 UTC window, 50 channels), `created_at` keyset resumed via `withCronLock`'s persisted `checkpoint` (`readJobCheckpoint`), never offsets. It reuses the open-path predicates (`eventParticipantsAmong` / `isEventParticipant`, `collabChannelAccess`), skips DMs entirely, brakes (`channelsSkippedSuspicious`) when more than half a channel would go, and never removes the Support user, `system-` users or event-channel staff. Not in any GitHub Actions workflow.
8. **Event Join Failures**: `addUserToEventChannel` returns `success: false` with `reason: "member_not_added"` or `"account_refused"`; `member_not_added` leaves `chatChannelEnsuredAt` unstamped so the sweep retries. `isEventParticipant` host arms require the host profile's `deletedAt` to be null.
9. **Unread Digest (`ADR-09`) — the Only Chat Push**:
   - Stream's `user.unread_message_reminder` (chat hook, same route and HMAC) reaches `handleUnreadMessageReminder` (`lib/stream/chat/unread-digest.ts`), which stages one `CHAT_UNREAD_DIGEST` bell (`appointment` family) and email per user per 30-minute window, claimed by an `IdempotencyRecord` (`stream.chat-digest`, `<windowStart>`, `<userId>`). It skips `familiarise-support`, ids with no user row, banned and erased users, honours the `appointments` category, and never reads message `text` (the schema omits it). Applying the hook and reminder settings is an owner `--apply` after deploy.

## 5. Unified Lifecycle Algorithms, Reopen Asymmetry, Attendance & Stage Q&A

1. **Unified Session Window Envelope & Timezone Normalization**:
   - Enforces `[startsAt - 15m, roomEndsAt + 30m]` symmetrically across `CONSULTATION`, `TRIAL`, `SUBSCRIPTION`, `WEBINAR`, and `CLASS`, where `roomEndsAt = endsAt + Meeting.extendedSeconds` (`resolveRoomEndsAt`), with SFU duration cap `clamp(room + 45m, 45m, 12h)` (`resolveRoomCapSeconds`). The booked `endsAt` stays the reference for the outcome classifier, sweep selection, reminders, money and retention.
   - A webinar or class attendee is admitted on a fulfilled entitlement (`paidParticipant`, one query in `resolveMeetingAccess`): a `CONFIRMED` or `ATTENDED` seat with a `SUCCEEDED` payment or none, or a `HELD` seat whose `SUCCEEDED` capture owes no refund (`refundOwedKey` null), has no `PENDING` or `SUCCEEDED` refund, and carries no `notSettledElsewhereWhere` marker (`Auto-refund pending:`, `Auto-refunded:`, `Auto-refund stuck:`, `REQUIRES_MANUAL_RECOVERY:`, `Replay sale:`). Never admit on seat status or `SUCCEEDED` alone: a rejected capture is `SUCCEEDED` too (`docs/decisions/2026-11-02-group-room-fulfilled-entitlement.md`).
   - All relative labels format in `viewerZone` (`formatInViewerZone`) and subtract integer civil day numbers (`Date.UTC(year, month - 1, day) / 86_400_000`) rather than DST-unsafe `now + 86_400_000`.
2. **Synchronous Termination & Pre-Start Device-Check Rotation (`POST /api/meetings/[meetingId]/end` — `ADR-03`)**:
   - Calls `call.end()` on Stream and synchronously invokes `recordMeetingEndedSynchronously` (`lib/stream/session-handlers.ts`) via CAS (`where: { id, endedAt: meeting.endedAt }`). It returns `{ kind: "not_found" | "already_ended" | "recorded" }` and refuses to overwrite a deliberate end; the route answers `404 MEETING_NOT_FOUND` for `not_found` and returns `callId` = the id that now represents the room. `handleCallEnded` and `handleSessionEnded` apply the same refusal.
   - `endedReason` is one of `MEETING_END_REASONS` (`lib/meetings/end-reasons.ts`); never write a freeform string (the CHECK `meeting_ended_reason_known` rejects it). Read `END_REASON_POLICY` (`deliberate`, `rejoinable`, `hostReopenable`, `money`) through `isDeliberateEnd`, `endBlocksRejoin`, `endAllowsHostReopen` and `endReasonPolicy` instead of comparing reason strings. Map a `call.ended` webhook only with `mapStreamCallEndedReason`; NULL reads as deliberate and host-reopenable, an unknown value as `stream_ended`.
   - Webinar and class capacity is capped at `MAX_GROUP_SESSION_PARTICIPANTS = 200` (`lib/events/capacity.ts`, enforced by `maxParticipantsSchema` in `schemas/plans.ts`). Provisioning and reopen set Stream `limits.max_participants` through `resolveCallParticipantLimits`: capacity + 5 with `max_participants_exclude_owner` and `max_participants_exclude_roles = ["co_presenter", "admin"]` for 1:N, a fixed 6 for 1:1; extend re-sends the call's existing limits. Stream does not document the counting rules, so Postgres seats stay the authority. The join route skips the membership write for a 1:N attendee who already holds the role (`call.queryMembers`, falling back to the write on any read failure), and `addSeatHoldersToOpenCalls` pre-adds confirmed buyers to provisioned calls. SFU error 301 (`CALL_PARTICIPANT_LIMIT_REACHED`) is client-only; there is no server `ROOM_FULL`. The join route only logs the first `ROOM_NOT_PROVISIONED` refusal of a meeting (the client self-heals it) and reports a repeat within two minutes at error level through `captureThrottled`.
   - Mutating routes use `meetingControlLimiter` (10/min/user: end, extend, reopen, live; `meetingStageLimiter` 60/min for stage; `meetingQaLimiter` 30/min for qa; `meetingJoinLimiter` 10/min/user for join, with the edge `streamJoinLimiter` kept as a 1,500/min/IP backstop so a cohort on one NAT is not throttled) via the `limiter` argument of `guardMeetingRoute`.
   - "Host is live" is rung after the host's call join, never from the join route (the lobby calls `/join` on page load): `MeetingSetup` fires `pingHostLive` (`app/meetings/[id]/host-live-ping.ts`, one retry, never awaited) once the host's `call.join()` resolves, and `POST /api/meetings/[meetingId]/host-live` (`guardMeetingRoute` with `meetingJoinLimiter`; plan host only, 403 otherwise) runs `stageHostLiveBell` (`lib/meetings/host-live.ts`): one `session-host-live` bell to the paid seats, claimed once per occurrence (`IdempotencyRecord` scope `meeting.host-live`), attempted after the response. It needs no Stream webhook; never move it onto `call.session_started`, which reaches production only.
   - If `endedAt < startsAt` (**pre-start device test**), classifies as `"ended_early"` and immediately rotates `streamCallId = "occurrence-<uuid>-r<base36>"` while leaving the occurrence scheduled (`SCHEDULED`).
   - If `endedAt >= startsAt` (**live end**), stamps `endedReason = "call_ended"`, closes the segment's active `MeetingPresence` rows (through `closeSegmentPresences`, `closedByEnd = true`) and `MeetingAttendance` rows, and propagates any unexpected persistence error as **HTTP `500`**. The `ended_early` rotation closes the rotated-away segment the same way in its CAS transaction.
3. **Host Room Reopen & Asymmetric Webhook Lookup (`POST /api/meetings/[meetingId]/reopen` — `ADR-02`)**:
   - Because `call.end()` permanently seals a Stream `cid`, `/reopen` verifies host/co-presenter/DPDP/booking-status/window guards, requires `endAllowsHostReopen`, builds the payload with `buildRoomCallPlan` (shared with the provisioner), creates the Stream call FIRST (`getOrCreate` on the new id), and only then CAS-rotates `Meeting` (`where: { id, streamCallId, endedAt }`). A Stream failure rotates nothing; a lost CAS answers `reopened: false` and leaves the fresh call unused.
   - **Asymmetric Webhook Rule**: `handleRecordingStarted`, `handleRecordingReady`, `handleRecordingFailed`, and `handleSessionParticipantJoined`/`handleSessionParticipantLeft` fall back to `appointmentOccurrenceId` (`parseSlotIdFromCallId`) so pre-reopen recordings and presence are preserved. A participant event found only through that fallback is a prior segment: its `MeetingPresence.streamCallId` keeps the event's call id and it never reopens or takes the end of the current room; `handleCallEnded` and `handleSessionEnded` strictly query `where: { streamCallId }` so delayed webhooks from old segments never terminate reopened rooms. A recording event clears `Meeting.isRecording` only through `clearRecordingFlag` (current `streamCallId`, and `recordingStartedAt` no later than the event), and a started event arms it only for the current call.
4. **`+15m` Extension on `Meeting`, Stream as a Derived Mirror (`POST /api/meetings/[meetingId]/extend` — `ADR-04`)**:
   - Never write `AppointmentOccurrence.endsAt` to extend. Host-only; `409 SESSION_NOT_EXTENDABLE` if ended, deleted, not `SCHEDULED` or has an outcome. Checks conflicts within `[startsAt, max(roomEnd, now) + 15m]` (host, co-hosts, presenter collaborators, active participants), then one `prisma.meeting.updateMany` CAS (`endedAt: null`, `extensionsUsed: { equals: read, lt: MAX_MEETING_EXTENSIONS }`, occurrence still `SCHEDULED`, no outcome, not deleted) increments `extendedSeconds` and `extensionsUsed`.
   - Then, outside any transaction, `mirrorExtensionToStream` sets `max_duration_seconds = max(existing, derived cap)` and `custom` (`sessionEndsAt`, `sessionBaseEndsAt`, `extendedSeconds`, `extensionsUsed`), always derived from Postgres, never added. A Stream failure answers `503 EXTEND_SYNC_PENDING`; a retry converges.
   - The overlap EXCLUDE `occurrence_no_confirmed_overlap` sees only booked ends, so the extension is app-enforced only (the conflict check).
5. **Single Exit Control (`CallExitButton` — `ADR-05`) & Lobby Backoff (`MeetingLobbyGateCard`)**:
   - Attendees see a single local `Leave call` button; hosts open a 2-choice popover (`Leave call` vs `End session for everyone` with a `< 10m` remaining caution warning).
   - `MeetingLobbyGateCard` handles `TOO_EARLY` countdowns with clock-skew backoff (`MAX_AUTO_RETRIES = 3`, `5_000ms` backoff); the attempt counter is state in the effect's dependencies, so each retry re-arms the timer.
   - Join failures other than a typed refusal are classified by `classifyJoinFailure` (`app/meetings/[id]/join-failure.ts`) into `provider_unavailable` (auto-retry, four attempts, capped jittered backoff), `room_full` (SFU code 301 or the message) and `unknown`, each rendered by `JoinFailureCard` with a Retry. The lobby swaps Join for `LobbyEndedPanel` when the call ends under it; the join route stays the end-reason policy oracle. Hosts get `MuteAllButton` gated on `useHasPermissions(OwnCapability.MUTE_USERS)`; the plan owner holds `-owner` mute, kick and block grants through `call_member`, `co_presenter` holds only `mute-users`.
6. **Attendance Lock Ordering, Webinar Backfill & Stage Q&A (`StageQaDrawer`, `/api/meetings/[meetingId]/qa`)**:
   - Participant webhooks execute in strict `Meeting -> MeetingPresence -> MeetingAttendance` lock order (`createMany({ skipDuplicates: true })`), clamping out-of-order `firstJoinedAt` monotonically (`firstJoinedAt: { gt: joinedAt }`). A reported leave always replaces an end stamp's assumed close (`closedByEnd`), and a leave reported after the current room ended moves `MeetingAttendance.lastLeftAt` only up to `Meeting.endedAt`. Webinar/class end handlers run best-effort `reconcileWebinarAttendance` so missed presence rows are backfilled before settlement.
   - **Stream participant sessions are the attendance witness (`ADR-06`)**: never treat an end stamp's close as evidence. `decideSlotOutcome` (`lib/booking/session-outcome-sweep.ts`) reads `getCallParticipantSessionsFromStream` for every segment with an assumed or open interval (and for the current segment when there are no rows, no report count, or a larger report count) before the outcome transaction, corrects rows by `userSessionId`, and leaves an unconfirmed interval open so the classifier returns `INCONCLUSIVE`. When rows show only one side (`LEARNER_ABSENT` / `HOST_ABSENT`) and Stream gave neither a call report nor a participant-sessions answer, it defers (`stream-evidence`) until 24 hours past the booked end (`STREAM_EVIDENCE_WAIT_MS`) and then writes `UNVERIFIED` / `INCONCLUSIVE` with `hostAttributed: false`; any Stream answer, even an empty sessions list, lets the classified verdict stand. Never add a path that forfeits, voids or strikes on webhook rows alone; `classifySessionOutcome` stays pure. `null` from that helper means "no evidence", never "nobody came". A run spends at most `STREAM_WITNESS_READS_PER_RUN` (100) reads, defers the rest, and reports failed reads as one Sentry message.
   - Supports persistent questions (`qa_<uuid>`), upvoting, host answers, lower-third stage banners (`custom.activeStageBanner`), and `<ReactionsButton />`.
7. **Staff-Editable Video Quality (`PlatformVideoConfig` — `ADR-08`)**:
   - Call, screen-share and recording quality come from the `id = "singleton"` row via `getPlatformVideoConfig(db)` (defaults 720p / 1080p / 720p when absent, no cache, no env var) and are applied only by `buildCallSettingsOverride` for 1:1 and 1:N rooms at provisioning, reopen, extension and presenter-role sync. Never hard-code a `target_resolution` elsewhere; the keys, Stream mapping and cost hints live in `lib/stream/video-quality.ts` and the `platform_video_config_values` CHECK must match them.
   - Staff and admin edit it at `PATCH /api/admin/video-config` (`videoConfig.manage`, reason required, `OpsActionLog` row). A per-call `recording` override must carry `mode` ("available"); a 1:1 `video` override must be the complete block.

## 6. Recordings Architecture, DPDP Privacy & Rate-Limit Ceilings

- **Cloudflare R2 Multipart Storage**: `READY` recordings live on `STREAM_S3` (`streamUrlExpiresAt = end + 14d`) until `transfer-recordings` (every 15 minutes via ticker background admission) streams SigV4 multipart parts to R2 (`status = AVAILABLE`, `storageType = PLATFORM`) under CAS `TRANSFERRING` claims and SSRF allowlisting (`isAllowedStreamRecordingUrl`). The core admits one eligible copy per run behind a fail-closed 15-minute Postgres lease; claim-time attempt increments plus exact claim CAS protect stale retries. The 12-minute signal cancels source reads, multipart operations and verification; cleanup has independent 15-second deadlines. The unscheduled `netlify/functions/recording-transfer-background.mts` background adapter uses the same core and cleanup admission guard. HTTP 202 only acknowledges queue admission; inspect eventual execution and object/row progress. Actions no longer schedules recording transfer. Cleanup and staff recovery queue the same narrow adapter; 202 is admission only, and the 45-minute completion probe requires owned successful execution. One aggregate risk alarm covers future-expiring READY Stream sources within 72 hours or with at least three attempts, conditionally throttled per recording to six hours without changing its retry timestamp; preserve stale claim consumption. Follow the deployment and manual orphan-cleanup gates in `docs/stream/recording-background-worker.md`; classify genuine sources before invoking shared production obligations. Retention is enforced by daily `expire-recordings` (1:1/sub +90d, webinar/class +365d). A host delete also removes Stream's copy for that segment (`recording-stream-delete.ts`); if the vendor delete cannot be confirmed the row keeps `streamRecordingId` and is left retryable.
- **Organisation wind-down completion**: A truncated or failed tagged-channel scan leaves both wind-down and retention-complete markers unwritten for that organisation; retention completion uses the pre-wind-down error baseline. Successfully frozen messaging channels leave the vendor filter, but unchanged prefixes can still hide the tail. Related database scans cap at 5,000 plus one sentinel and must report truncation; organization/member cursors rotate independently. A persistent vendor prefix can still block full channel discovery. The ticker now queues daily background slices with a five-minute start budget, two-organization rotation and ten-recording purge slices; incomplete or changed recordings and active transfers withhold retention completion. Claim EXPIRED before vendor deletion and retain failed pointers for cleanup; see `docs/stream/17-channel-lifecycle.md#organisation-wind-down-completion`.
- **Wind-down error reporting**: Pass the invocation's existing failure reporter through circuit-breaker, video-end, member-removal and recording-delete helpers. Flush once per invocation with a bounded sample; do not reintroduce per-row Sentry captures through shared helpers.
- **Removed recordings stay removed**: erasure claims `FAILED` rows too and stamps `removedAt` at the claim; `absorbIntoErasedRecording` (`lib/stream/recording-handlers.ts`) absorbs a later `recording_ready` into an erased or host-deleted pre-ready row, which stays `EXPIRED`; `DELETE` on an `EXPIRED` recording answers `GONE`; the decline discard no longer needs `session_id`; asset deletion removes every R2 object under `recordings/<id>/`; vendor failures report once per run through `createRunFailureReporter`.
- **Recording start and delete guards sit inside their claims**: `POST /api/stream/recordings/start` claims `isRecording` only on an unended room whose occurrence is still `SCHEDULED`, has no outcome and is not deleted (`RECORDABLE_ROOM_WHERE`; the pre-read answers `APPOINTMENT_TERMINAL`). `DELETE /api/stream/recordings/[recordingId]` puts `purchases: { none: <PENDING or SUCCEEDED> }` in the `EXPIRED` claim itself, so a purchase landing after the earlier check refuses the delete (`RECORDING_HAS_BUYERS`); never rely on a read before the claim.
- **Recording erasure owns the current pointers before vendor I/O**: `scrubUser` repeats its unsold 1:1 eligibility predicate in `updateManyAndReturn`, writes `EXPIRED`, then deletes Stream's copy and the R2/preview assets for only the returned identities. Clear pointers (including `streamRecordingId`) only with matching identities and `EXPIRED` in the `WHERE`; retain them on any vendor failure. A zero-row clear succeeds only after a re-read confirms an `EXPIRED` row with both storage pointers and `streamRecordingId` null. Erasure retries include eligible expired rows with a known R2 path, preview path or `streamRecordingId`, preserve removal timestamps, and keep the admin request `IN_PROGRESS` while deletion fails; the existing `expire-recordings` entry provides a fallback. Preserve group unpublish behavior and purchase protection. Do not claim this recovers an unpublished transfer attempt whose cleanup failed without ever recording its key; see `docs/stream/19-recordings-lifecycle-and-access.md`.
- **Publishing is closed at launch**: recordings are included with the booking and `publish/route.ts` has only `DELETE` (unpublish). Do not re-add a per-recording `POST`; replays return as a `ReplayListing` product (#2412). When they do, publish with a conditional `AVAILABLE` / `PLATFORM` update matching the validated storage pointer, listing status and preview fields, and return `409 RECORDING_CHANGED` if it loses. The storage/listing SQL check permits `EXPIRED` + `PUBLISHED` with a path, so it does not replace this write fence or erasure cleanup ownership.
- **Native background loading**: The recording entry and shared cleanup factory use `next/server.js` for Node ESM. Generic shared telemetry APIs come from `@sentry/core`, pinned with the Next SDK; initialization keeps the shared policy. A compiled no-network check and deployed unauthenticated preview verify loading and rejection without the former flush failure. Accepted telemetry and copy completion remain activation gates in `docs/stream/recording-background-worker.md`; a symlink-containing worktree ZIP is not deployed-artifact proof.
- **Background failure and orphan cleanup**: The adapter throws on cleanup-handler server errors; Netlify discards returned background responses. Lost-publication cleanup checks both rejected deletes and `success: false`, fails the run and leaves the winning/EXPIRED row untouched. Successful/absent deletion remains skipped. This reports failure without persisting an orphan retry owner; verification-failure and prior-attempt cleanup remain best effort. Require durable orphan ownership or reviewed manual recovery before activation, separately from the erasure pointer race.
- **Erasure ordering gate**: Met by `scrubUser`'s claim-first purge (see the erasure-ownership bullet): it claims `EXPIRED` and returns the current asset identities before vendor deletion, keeps failed pointers for retry and clears only matching identities. The transfer claim fence alone does not provide this ownership.
- **Listing results, not nulls**: `getCallRecordingsFromStream` returns `listed`, `call-not-found` (404 / code 16, the copy is gone) or `unavailable` (retry later) and never reports to Sentry; loop callers (`expire-recordings`) run at most 10 lookups at once (`mapBounded`) and report once per run. A lapsed `READY` row expires only on `call-not-found` or a listing without its filename.
- **Recording notices are at-most-once**: ready and failed emails go through `stageDocumentAndRecordingEmailOnce`, an `IdempotencyRecord` claim per recipient (`recording-ready:<recordingId>:<userId>`); bells dedupe on `transactionId`. A row that is not `READY`/`TRANSFERRING`/`AVAILABLE` is never announced. The user sync route (30 days, 25 meetings a page, cursor) never notifies; only the orphan reconciler passes `notify: true`. A ready for an unknown meeting dead-letters with `permanent:`.
- **Video client timeout**: `getStreamVideoClient` uses 15 s, not the SDK's 3 s default, inside the ~26 s function ceiling.
- **Refund-aware replay access**: `loadRecordingViews` nets refunds with `isPaymentEntitled` and passes `paymentRevoked` to `recordingViewerOf`. A 1:1 learner whose only succeeded payment is fully refunded loses both the list and playback, and a credit-funded booking whose credits were restored loses it the same way; a partial refund keeps access, and a `FAILED` or `CANCELLED` restoration revokes nothing. `/api/recordings` applies the same `isFullyRefundedPurchase` predicate and withholds the thumbnail and preview clip.
- **DPDP Consent & Right to Erasure (`principal:<userId>`)**: Enforced across `upsertUsersToStream`, `assertCanMintToken`, `resolveMeetingAccess`, and `/reopen`; `scrubUser` invokes `eraseStreamPrincipalFootprint` with durable retry queue (`StreamRevocationRetry`, kind `ERASURE_REVOKE`), and `wind-down-deactivated-orgs` terminates active video calls and freezes channels on tenant deactivation. Erasing a user also deletes the R2 object, preview folder, thumbnail, transcript and Stream's copy of their 1:1 recordings; the row is claimed `EXPIRED` first and its pointers are cleared only after both deletes are confirmed, otherwise the erasure reports failure and stays retryable.
- **Rate Limits & Pinned SDKs**: Chunk user upserts / roster adds at `100` (`RATE_LIMIT_DELAY_MS = 10_000`), page channel queries at `30` (`queryChannelsPaged`), and keep `stream-chat` on `9.x` (`9.53.0`). Verify control-plane state with `npm exec -- tsx scripts/stream/ensure.ts` and `npm exec -- tsx scripts/stream/ensure-webhook-subscription.ts --apply`; `tsx scripts/stream/ensure.ts` (dry run) shows any drift the detector reports.

## 7. Chat Client Resilience (`providers/StreamProviderImpl.tsx`, `components/chat/`)

1. **A Dropped Socket Is a Grace Window**:
   - `connection.changed` offline sets `chatReconnecting` (15 s, `DISCONNECT_GRACE_MS`) while `chatConnected` stays truthful; the app-level reconnect starts at 8 s. `components/chat/ChatSurface.tsx` (the one gate for the three Messages pages) keeps `<ChatLayout />` mounted while `chatConnected || chatReconnecting` and shows a banner, so drafts, scroll and the active channel survive a blip. A longer outage unmounts it, so `ComposerDraftPersistence` keeps the unsent composer text in `sessionStorage` under `chat-draft:<userId>:<cid>` and restores it on mount; sign-out (`disconnectStreamClients`) removes every `chat-draft:` key.
   - A retryable failure on an already-connected chat client is held back until `MAX_CONNECT_ATTEMPTS`; a success (retry loop or the SDK's own `online` event) clears a retryable `failure`. Do not reorder consumers to hide a stale failure.
2. **One Connect In Flight**:
   - `joinInFlight` shares the chat and video connect per user, only the newest `connectServices` generation commits, `mergeSettledClients` never downgrades a registered client to `null`, and `retryConnection` clears the retry timer and ignores calls while a run is active.
3. **Profile Fetch Retries**: `useUserData` makes 4 attempts with `withJitter` backoff (`lib/stream/backoff.ts`), then returns a `profileLoadFailure` with Retry; a 401 is neither retried nor reported.
4. **Sidebar, Badge, Send Status**: an unlisted channel's `message.new` is watched and inserted at the top (dedupe by cid, load-more via `appendUniqueChannels`); a successful pin, unpin or hide calls `rebaseList`, which re-reads the loaded rows, resets `fetchedCountRef` and bumps `listGenerationRef` so an older load-more page is dropped; a full refresh bumps the generations when it starts, so an older refresh landing after a newer rebase is dropped per list; a dropped refresh, rebase or load-more page has already written its older `membership` into the shared stream-chat `Channel` objects, so if the newest read of that list has landed (`appliedGenerationRef`) the list is rebased once more; a rebase retries once, and if that fails `staleListRef` makes the next Load more re-read the loaded rows plus a page instead of using the old offset; a pin override is dropped once a re-read returns its row and no request for it is pending, so the server's `pinned_at` order wins; the nav badge is `total_unread_count` minus org-tagged unread (one throttled `getUnreadCount` plus cached cid classification); `CustomMessage` renders `failed` and `sending` with `handleRetry`.

## Deprecated & Superseded Approaches

- **Hard-coded 720p in the 1:N builder, or quality left to the call type**: Superseded by `PlatformVideoConfig` (`ADR-08`); delete any literal `target_resolution` in `lib/meetings/**`.
- **Browser-side call creation (`call.getOrCreate`) and direct `call.endCall()`**: Superseded by server-only `provisionAppointmentMeeting`, `POST /api/meetings/[meetingId]/join`, and `POST /api/meetings/[meetingId]/end` (`end-call` and `join-call` are stripped from default roles).
- **Webhook-only `Meeting.endedAt` writes or HTTP `200` on failed synchronous end**: Superseded by synchronous CAS dual-write (`recordMeetingEndedSynchronously`) returning HTTP `500` on failure and converging monotonically (`supersedesRecordedEnd`) with incoming webhooks.
- **Extending by writing `AppointmentOccurrence.endsAt`, or keeping the extension counter in Stream `custom`**: Superseded by `Meeting.extendedSeconds` / `extensionsUsed` (`ADR-04`); the moved end lost 15 minutes at classification and reopen reset the counter.
- **Freeform `endedReason` strings and per-site `call_ended`/`maintenance` sets; reopen that rotates before creating the call**: Superseded by `END_REASON_POLICY` and Stream-first reopen.
- **End stamps closing every open presence row as fact, and presence rows without a call id**: Superseded by `closedByEnd`, `MeetingPresence.streamCallId` and the sweep's Stream witness (`ADR-06`); a lost host leave read as presence until the end and could pay out a cut-short session.
- **Uniform `where: { streamCallId }` lookup on all webhooks**: Superseded by asymmetric webhook resolution (`ADR-02`) preserving pre-reopen recordings/presence via `parseSlotIdFromCallId` while shielding reopened rooms from late `call.ended` webhooks.
- **Group-room admission on seat status, or on any `SUCCEEDED` payment beside a held seat**: Superseded by the fulfilled-entitlement predicate `paidParticipant`.
- **Dual red hangup buttons & unbounded lobby auto-retries**: Superseded by unified `<CallExitButton />` (`ADR-05`) and clock-skew-safe `<MeetingLobbyGateCard />` retry backoff (`MAX_AUTO_RETRIES = 3`, `5_000ms`).
- **Legacy per-booking `consultation-*`/`subscription-*` channels**: Superseded by canonical human-pair DM channels (`dm-` / `dmo-`) and the verified booking tag; the prefixes are no longer managed.
- **A single "Meeting Error" screen for every join failure, and `useMeetingRecording` flipping to `recordingEnabled: false` on any non-404 error**: Superseded by classified `JoinFailureCard` faces and last-known-value retention with backoff.
- **Blanket `COPY_LAPSED` expiry and per-row listing errors to Sentry**: Superseded by confirmed-absence expiry and one report per run.
- **R2-only recording deletes**: Marked a recording `EXPIRED` while Stream's copy stayed playable for up to 14 days and the thumbnail stayed public. Superseded by `recording-stream-delete.ts` plus a purge that clears the thumbnail and transcript.
- **Chat file and image uploads**: The channel types allowed `upload-file`, but there was no storage or moderation story and the community page advertising it did not exist. Superseded by `uploads: false`, the base attachment grants stripped by the script, and the deleted page.
- **Instant skeleton on a socket blip, a badge summed over the loaded page, and a `null` client committed by an overlapping connect**: Superseded by the reconnect grace window, `total_unread_count` minus org-tagged unread, and single-flight connects with a generation token.
- **Client-cooperative revocation (sync gates), unfreeze-on-open, DM Clear chat**: Superseded by synchronous revocation plus the retry queue and daily reconciler, get-or-create collaborator channels, and hiding truncate on managed channels.
- **Booking cards posted on DM open (`booking-ctx-`, caller-authored and then `system-booking-context`)**: Read as a support message, dated the first session, written for both people even unanswered. Superseded by the verified booking tag; old cards are hidden.
