## Read this first if the question is "why is it slow sometimes"

The #1124 cold-start stall (~24–38 s on new Lambda instances, culminating in the 2026-10-03 `504 Inactivity Timeout` outage) was **root-caused and permanently resolved on 2026-10-03 in PR #1972**: `@netlify/plugin-nextjs` v5 instantiates `NextNodeServer` with `minimalMode: false`, which caused Next.js 15's default `experimental.preloadEntriesOnStart: true` and `appDocumentPreloading: true` to synchronously execute `this.unstable_preloadEntries()` across all 606 routes (`1,676,071 webpackRequire` calls) on the single-threaded event loop during cold start — stalling even the zero-import `/api/perf/probe-bare` route for 24–32 s and consuming 496–512 MB V8 heap against Node 22's 512 MB old-space limit on 1024 MB Lambda containers. Setting `preloadEntriesOnStart: false` and `appDocumentPreloading: false` in `next.config.mjs` (#1972) cut cold-start V8 heap to **33 MB** and reduced 12-request concurrent cold bursts across 8 newly spawned Lambda instances on `ap-southeast-1` to **`0.97–1.90 s`**. Consequently, the temporary `netlify/functions/keep-warm.mts` scheduled pinger (PR #1685) was retired and deleted in PR #1972. See `docs/deployment/netlify.md` (Section 14.2) and `netlify/platform-limits.md` for full benchmarks and the verified platform limits from ticket #1112198.

On 2026-11-05 a same-day A/B on `/api/perf/probe-bare` (deploy permalinks, 8-request bursts) measured cold boots (`uptimeAtEntryMs`) of 2.9–3.7 s for webpack and 2.5–2.7 s for Turbopack. There was no stall and the preload guard was intact. The two deploys differ by ten commits, so this is an observation, not a controlled bundler test. No drift since 2026-10-03 is established, because that baseline used a different network path and no boot timing. The large fixable cold cost is the authenticated route graph: `probe-full` reaches its handler about 4 s after `probe-bare`, because of the `lib/auth` import graph (Better Auth, SSO, passkey, and the email stack via the `lib/email` barrel). Treat the 2026-11-05 numbers as the current baseline (ADR 32, the 2026-11-05 section), and compare any cold-start change against a deploy permalink burst, never against a single request.

On 2026-11-06 the cold boot was measured as CPU-bound. Cold rows report `cpuAtEntry` at 0.58–0.62 CPU-seconds per second of uptime, which is the whole ~0.58 vCPU share of a 1,024 MB Lambda. Peak memory is only 124–261 MB. Loading the email stack lazily cut cold `probe-full` by about 0.4 s, from 6.3–6.6 s to 6.2–6.3 s, while `probe-bare` stayed at 2.5–2.7 s (ADR 32, the 2026-11-06 subsection). Never statically import `@/lib/email` (or `send-to-recipients`) from anything `lib/auth-helpers.ts` reaches; load senders with `import()` where they send. Check the graph with an esbuild metafile before you merge. Burst a preview only after it has been ready for 15 minutes, because the first instances are booted the moment it turns ready. Memory is set per deploy by `netlify.toml` (`m` in `getDeploy`'s `available_functions`); a 2,048 MB test belongs on a throwaway branch that is never merged, and needs the owner's approval first.

On 2026-10-02 the visible form of the cold-instance stall was documented: when the Postgres connect times out on a cold instance, the session lookup throws `SessionLookupFailedError`, which is deliberately a 503 and never a sign-out (#1716). The dashboard error boundary now shows "Reconnecting…" and retries once, and the platform cause is tracked in #1826.

## Non-negotiables

There are two ceilings on a Netlify request, not one, and Netlify has now named the second: an edge receive-timeout of roughly 37–38 s from the moment the request arrives if nothing has started streaming, not configurable on Pro (ticket #1112198); the ~26–27 s 504 measured in #1454 sits inside that same class. The Lambda execution limit is 60 seconds (documented since the 2026-06-25 functions redesign, and invocations of 32 to 39 seconds complete on this site), but an edge 504 lands on the client at roughly 26 seconds if the response has not started streaming; a Route Handler that awaits a long query before returning any bytes therefore fails at ~26 s while its database write completes underneath (#1454). Fitting under ~25 s, streaming early, or moving the work to a Background Function are the fixes; waiting for a bigger limit is not.

Memory did not fix the cold-instance stall, and that result no longer decides anything. The 2026-08-22 test (`m=2048`, verified on deploy `6a8954981e6f`) ran while the route preload was blocking the event loop, which #1972 fixed. The boot is now CPU-bound at about half a core, so a 2,048 MB test on a throwaway branch is the open measurement (ADR 32, the 2026-11-06 and 2026-11-13 subsections). Proposing that test is allowed. Proposing 2,048 MB for production without its result is not. Module loading is single-threaded, so expect one full core to be the ceiling.

A warm instance is warm only for the code it has loaded. On 2026-11-13, instances that had already served `probe-bare` took 4.8–6.1 s on their first `probe-full` request. Never treat a keep-warm ping of a light route, or the ticker's `CRON_SECRET` routes, as warming signed-in routes.

Functions run in Singapore (`sin`), the closest region Netlify offers to Supabase in Mumbai; Mumbai is not on Netlify's menu. Any issue that still says "us-east-2" or "Ohio" is describing a state that ended by 2026-08-22 at the latest.

The Netlify MCP reads projects, deploys, teams, and env vars and writes env vars; it cannot read function logs, change function limits, or touch billing. Use `netlify logs --url <deploy permalink>` and `netlify api` for those, per `netlify/mcp-and-cli.md`.

**Multi-Host Portability & Hot-Standby Failback (`#2095`, `#2096`, `#2097` / `docs/deployment/`)**:

- **Launch job runtime (owner decision, 2026-10-31, `docs/decisions/2026-10-31-job-runtime-experiments.md`):** launch on the Netlify ticker plus Background Functions for jobs over 30 s. This governs the job runtime only, not the web tier: the web-tier scale path below (a Vercel Pro `bom1` trial before about 300 concurrent users) is separate and rejects only the always-on Mumbai container plan for web plus worker, not a Mumbai VM for jobs. After launch, choose the job runtime between Vercel Pro `bom1` plus Workflows and a Mumbai VM with DBOS once the real-app `bom1` test and the Mumbai VM test report cost and latency; revisit then, or at about 300 concurrent users. Moving the real app to Vercel needs code and build changes.
- **Decided scale path (2026-10-31, `docs/decisions/2026-10-31-ticker-scale-path-and-queue.md`)**: keep the Netlify ticker through launch; before about 300 concurrent users, trial the web tier on **Vercel Pro `bom1`** with Vercel Cron as the ticker and Netlify as hot standby. The always-on Mumbai container plan for web plus worker ($100–440 a month) is rejected on cost, so the scorecard below is evaluation history, not the plan. No hosted job service fixes the ~95 ms per statement, because none runs compute in India. Supabase stays Free on the shared database until real customers, then Pro; the database split follows launch.

- **Previews share production's database, so they stand down (`lib/cron/dispatch-refusal.ts`, `lib/production-state.ts`).** Every preview and branch deploy refuses every job, money or not: `jobsMayRunHere()` is true only when `NEXT_PUBLIC_SENTRY_ENVIRONMENT` (else `SENTRY_ENVIRONMENT`) is `production`, or in a local development or test process (`NODE_ENV` is `development` or `test`, not on Netlify). The refusal is a 409 `JOB_RUN_PRODUCTION_ONLY` on both the `/api/cleanup/[job]` door and the admin Run door, written as a `CANCELLED` run row with outcome `refused` and no Sentry event. `mayWriteProductionState()` skips the maintenance window and its Redis mirror, the discount-code pause and `cron:heartbeat:last` off production, and the admin maintenance route answers 409 `MAINTENANCE_PRODUCTION_ONLY`. Local `next dev` still runs jobs but no longer toggles maintenance or touches the heartbeat; a local `next start` with a non-production Sentry environment refuses. `NEXT_PUBLIC_SENTRY_ENVIRONMENT=production` is what lets a deploy run jobs and write that state, so it must stay `preview` on deploy-preview and branch-deploy. Each non-production context has its own `CRON_SECRET`. Do not test a job on a preview; run it locally or after release.
- **Environment matrix (`docs/start-here/10-environment-split.md`).** Every Netlify context runs `NODE_ENV=production`; `NEXT_PUBLIC_SENTRY_ENVIRONMENT` is the only runtime production marker. Never put a Cloudflare Turnstile test key on production: `turnstileCaptcha()` (`lib/auth/captcha.ts`) then verifies with the always-fail test secret, so sign-up and reset refuse. The branch deploy has carried the always-pass test keys since 2026-11-06. Run `netlify env:get` only from the main checkout: in an unlinked git worktree it prints a sentence instead of the value, and piping that into a secret once sealed the QA TOTP rows under the sentence (`requireAuthSecret()` now refuses whitespace).
- **The database split is planned, not done** (`docs/deployment/db-split-plan.md`), and the staged load test waits for it (`docs/enterprise/50-operations/11-load-test-plan.md`).
- **Ranked 2026 Platform Scorecard (`docs/deployment/multi-platform-evaluation.md`)**: **#1 Google Cloud Run (`asia-south1` Mumbai — `93/100`)**, **#2 Vercel Pro (`bom1` Fluid Compute — `89/100`, requires refactoring `> 4.5 MB` uploads/downloads first)**, **#3 Fly.io (`bom` Mumbai — `88/100`)**, **#4 DigitalOcean (`blr1` Bangalore — `87/100`)**, **#5 Railway (`sin` — `87/100`)**; **Cloudflare Workers (`@opennextjs/cloudflare` — `60/100`) is hard-disqualified** (`128 MB` isolate memory wall + no native `sharp`/`bcrypt`/Chromium).
- **Dual-Boot & `< 90s` Failback (`docs/deployment/emergency-failback-runbook.md`)**: Keep `netlify.toml` and `netlify/functions/cron-tick.mts` intact on every branch so `familiarise.netlify.app` remains a pre-built hot standby. Resolve the client IP only in edge middleware (the rightmost `x-forwarded-for` hop on Netlify, where the edge function never sees `x-nf-client-connection-ip`) and let Node code read only the middleware-stamped `x-familiarise-client-ip`, include standard `Vary: Cookie` alongside `Netlify-Vary`, gate `output: "standalone"` and `sharp` exclusion by platform env var, renew standby TLS via ACME `DNS-01` (`POST /api/v1/sites/${NETLIFY_SITE_ID}/ssl`) or Cloudflare `Orange-Cloud Full (strict)`, and control active cron ownership via Upstash key `ops:active_cron_platform`.

Every number in these references carries the date it was verified and the source it came from. When a number matters for a decision, re-open the source if the date is more than a quarter old; otherwise trust the file.

## Billing facts agents need

The full figures, sources and the credit-plan status are in `.claude/skills/billing-guardrails/references/netlify.md` (sections 1.1 and 1.2); the rules here are the short form.

- The legacy Pro bill is $19 per member plus a flat $25 add-on once a site passes 125,000 function invocations in a billing period, covering up to 2,000,000, with usage above 2,000,000 billed per 500,000 (MEASURED: 282,162 for 4 September to 3 October, so the 2026-10-06 bill was $44). Invocations are the only meter that has crossed a line; bandwidth, edge functions and build minutes are far below their allowances.
- There is no hard spend cap on legacy Pro, only usage alerts at 50, 75, 90 and 100 percent (DOCS, Netlify support ticket #1112198, 2026-09-17). Keep-warm pings bill like real invocations, and a cold-start stall bills as duration (about 28 GB-seconds for a 28 second stall at 1,024 MB). Never add a pinger.
- Every dispatched target is an invocation; idle due targets are skipped. The ticker skips targets that have no work (`docs/decisions/2026-11-01-ticker-skip-idle-targets.md`); a new job needs an idle probe or an `alwaysRun` reason.
- A move to a credit-based plan is PENDING and not decided. It is permanent (Netlify: "You cannot revert to a Legacy plan from a Credit-based plan"), so do not propose or perform it without the owner. See [how credits work](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/how-credits-work/) and [pricing](https://www.netlify.com/pricing/).

- **Production builds with Turbopack so source maps fit (2026-11-05):** webpack source-map generation does not fit Netlify's 8 GB builder (nosources maps, server-only maps and the build worker all ran out of memory), while `next build --turbopack` with maps compiled in 72 s. The `build` script uses `--turbopack` on every host. Netlify previews, branch deploys and `CI_LEAN_BUILD` skip maps; every other build (Netlify production, a container or another host) generates them and uploads only where `SENTRY_AUTH_TOKEN` is set. `build:analyze` stays on webpack (plain `next build`) because the bundle analyzer needs the webpack hook. Turbopack ignores custom `webpack()` configuration, so never add one without its Turbopack equivalent. See `docs/decisions/2026-11-05-turbopack-production-build-for-source-maps.md`. Netlify build logs can be read through the websocket `wss://socketeer.services.netlify.com/build/logs` by sending `{deploy_id, site_id, access_token}`; the REST build-log endpoint answers 404.
