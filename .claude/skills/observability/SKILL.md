# Observability

The index for the error-tracking and job-telemetry domain: how an event leaves a route, how it comes to name a person and an organisation, how a missed or half-done job becomes visible, and how any of that is proven rather than assumed. The whole-subsystem design is `docs/observability/00-system-design.md`, the per-topic facts live in `docs/observability/sentry/`, and the money-adjacent consequences live under `/finance`. This skill holds the non-negotiables and the decision procedure, and the detail sits in the references below.

## Non-negotiables

The full reasoning for each rule is in `references/sentry.md` and `references/job-telemetry.md`.

- **Name the rung of evidence you reached.** Calling `reportSentryError` proves intent, the wire envelope proves serialisation, and a queryable event proves the lot. Never collapse them.
- **Worker helpers import `@sentry/core`.** Standalone Node ESM workers keep Core and the Next SDK at matching pinned versions, and `__tests__/observability/native-sentry-runtime.test.ts` runs with the real SDK; a 202 or an invocation receipt proves neither completion nor flush.
- **Never hardcode a Sentry coordinate.** Read organisation, project and URLs from the environment, by slug. A DSN literal in source is a history-rewrite failure.
- **The org id is in the DSN host and the project id is the last path segment.** Both are sixteen digits. Slugs go in config and ids come out of the DSN.
- **Unset token is off; empty token is broken on.** Gate token paths on presence, not truthiness.
- **The SDK is not on `window`.** Attach a listener from a `<script>` in the page's main world, because a DevTools evaluation runs in an isolated world and looks identical to "Sentry is not initialised".
- **A 2xx is not acceptance, and acceptance is not queryability.** Read `x-sentry-rate-limits`; a working session or transaction stream is no evidence that errors are taken.
- **The canary spends no error quota.** It reads `stats_v2` once a day with `SENTRY_STATS_TOKEN` (an Internal Integration token (Organization: Read)) and pages by email, plus an error-level Better Stack line when `ENABLE_BETTERSTACK_TELEMETRY=true` and the source token and ingest URL are set, on a `rate_limited` outcome, a `usage_exceeded` / `error_usage_exceeded` reason, or a failed read. An unset token is a config skip.
- **A check that reports its own failure through the failing system is not a check.**
- **Modelled refusals are warnings.** A `BUSINESS_ERROR_CODES` code is `expected: true`, re-levelled by `beforeSend`, and never an error event.
- **A repetition is throttled; a set is aggregated.** Never aggregate a repetition, and remember that a shared `fingerprint` groups events without saving any.
- **Never capture to Sentry per row.** Collect failures with `createRunFailureReporter` and flush once per run, with a stable fingerprint and a ten-id sample.
- **Sentry fixes the system; the console fixes the customer.** Per-item remediation reads Postgres, never Sentry samples.
- **Never attach a person to a synthetic event.** Test and probe events carry no user, org, IP or URL.
- **The identity disclosure is opt-in and off.** `SENTRY_IDENTITY_ENABLED` must be exactly `on`; `Users: 0` is the expected state.
- **`SystemEvent` is the row; Sentry is the pager.** When they disagree, believe the row.
- **Scrub everything.** Spans, metrics and Sentry Logs go through `lib/observability/sentry-scrubber.ts`, and `console.*` bypasses the scrubber, so never log raw payloads or full Prisma errors.
- **A job's row is not proof the work finished.** A run can record `COMPLETED` for partial work until #2424 Phase 1; do not build a new alert on that status without stating it.
- **Sentry is escalations only.** A one-off ticker failure is a log line; only `isRepeatedFailure` (three cadences with no `COMPLETED` run) sends a per-target error. Config skips are `skipped` run rows, business findings are `SystemEvent` rows (Sentry fixes the system, the console fixes the customer), and preview deploys report as environment `preview` with a `branch` tag, which no paging alert rule matches. Money is the standing-finding exception, once per new id set: wallet drift `fatal`, ledger drift `error`, the dispute deadline `warning` (each dispute once), and refund-reconcile money findings `warning`; thrown errors and failed runs always page. Spike Protection is on. A background target (202) is judged one tick late, from its newest finished run (`lastFailedAt`).
- **A backlog breach pages via Better Stack, not Sentry, and per-item history is never a Postgres table.** Current state sits on the entity row; until traction per-item history is the run row's `result.failures` (ids only, at most 50), and batched Better Stack events are deferred. Better Stack events use the fixed Zod schema in `emitTelemetryLog`, never a caller's context, and an ingest rejection is counted on the run row, never sent to Sentry. Existing `SystemEvent` rows stay the record for business and system events. See `references/ownership-and-telemetry.md`.
- **A job that does not run must alert, by construction.** `/api/health/jobs` derives a freshness budget for every ticker target from `lib/cron/schedule.ts` and answers 503 when a `paging` one lapses; an external Better Stack monitor polls it. Never hand-list a job or a budget; demote only housekeeping, through `WATCHED_TARGETS`. Every target must write a run row (`jobNameFor` never returns `null`), so the canary and the Stream drift check take a fail-open `withCronLock` lease. `checkJobCoverage` (`lib/cron/job-coverage.ts`) enforces target, requirement and `MANUAL_ONLY` coverage inside `npm run build`, so it still guards when Actions is refused. See `docs/decisions/2026-11-02-job-freshness-from-schedule.md`.
- **Four watchers, four jobs.** Sentry reports code faults, the `cron-tick` monitor and the free uptime monitor on `/api/health/jobs` (the second vendor, live since 2026-11-05). Better Stack reports absence: the tick heartbeat, the `/api/health/jobs` HTTP monitor, the digest heartbeat and the SQL backlog alerts. Postgres run rows and queues are the facts. The console (System Jobs, Stuck work) is where the daily digest sends you. See `docs/observability/00-system-design.md`.
- **The daily `ops-digest` is always sent.** The registry job (`lib/observability/ops-digest.ts`, 03:50 UTC) goes through `deliver()` to `OBSERVABILITY_ALERT_EMAIL`, pings `BETTERSTACK_DIGEST_HEARTBEAT_URL` only after a successful send (`/fail` otherwise), never reports to Sentry and never repairs. Its run row holds `result.summary` (`lib/observability/ops-digest-summary.ts`), from which `/api/health/jobs` answers 503 `RELEASE_LAG_OVERDUE` (`lib/observability/release-lag.ts`, `GITHUB_RELEASE_LAG_TOKEN`, `BUILD_SHA` inlined by `next.config.mjs`) or, once `collectionsAreLive()` is true, 503 `STANDING_CONFIG_SKIP`. A probe poll never calls GitHub. See `docs/decisions/2026-11-02-reliable-jobs-digest-and-release-lag.md`.
- **Monitors are verified by state and created by API.** The live inventory is in `docs/observability/00-system-design.md`; the matrix of questions, vendors and gaps is `docs/start-here/08-how-we-know-a-job-did-not-run.md`. Overlap is deliberate for the probe and the ticker (two vendors) and absent for the digest (one). The Sentry uptime monitor watches `/api/health/jobs`, never the homepage. Require `paused: false` and status `up` after any monitor change, create monitors through the vendor API or CLI with secrets on stdin, and never retrieve, paste or log `CRON_SECRET` (write-only; rotate it). To run a job by hand, `curl -X POST` with the bearer to `/api/cleanup/<registry-key>`. Gotchas: macOS has no `timeout`, `netlify env:get` prints `***`, Netlify env changes need a deploy, and the Better Stack API base is `uptime.betterstack.com/api/v2`. See `docs/decisions/2026-11-05-detector-rollout-and-redundancy.md`.
- **`cron-heartbeat.yml` watches only the Actions-scheduled workflows** (`db-live-drift`, `security-audit`). It is not a runtime watchdog; never add a runtime job, a Redis write or a Sentry init to it.
- **Cron mutual exclusion is Postgres only.** Never add a Redis lock or a Redis failure counter for a job.
- **The entity trace and the metrics card are read-only.** One bounded query per source, run in sequence, and skip a source that needs an unindexed JSON scan.

## Entity trace and job run metrics

Sentry answers "what failed", Better Stack and the ticker check-in answer "what did not run", and the read-only entity trace (`lib/backoffice/entity-trace.ts`) with the Run metrics card (`lib/backoffice/job-run-metrics.ts`) answers "what happened to this payment or booking". Read `references/entity-trace-and-console.md` before extending either one, and `docs/observability/three-layers.md`.
