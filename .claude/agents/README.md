# Subagents in this repo

`.claude/agents/` is flat — Claude Code does not support nesting agent definitions the way project skills nest under a domain folder. This page is the index: the tier table an orchestrator uses to pick a model and effort level, the role agents that carry those tiers, the Razorpay vendor pack, and the dispatch rule that ties them together.

## The tier table

The full rationale — current model prices and context windows, what each effort level does, session-budget economics, the rules for running a fleet on one machine, and the resume-from-worktree pattern — lives in `.claude/skills/workflow/references/model-orchestration.md`. The summary:

| Role                                            | Model                                          | Effort                                                                                | Why                                                                                                                                                                                                                                                                                                                                             |
| ----------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Advisor (judgment, not keystrokes)              | Fable 5.2                                      | xhigh (audit/design day) or high (orchestration day); max only for a rare ceiling run | Owns architecture and doctrine decisions, money-path review, adversarial verification of other agents' claims. Costs 2× Opus 5.5 per base input and output token ($8/$40 against $4/$20; cache reads cost the same $0.20 on both), so it should write specs an executor can run without judgment calls rather than execute breadth work itself. |
| Teacher (executes complex, well-specified work) | Opus 5.5                                       | high (build a PR) or medium (triage)                                                  | Multi-file coherence in money code, and claim-vs-code verification on review threads.                                                                                                                                                                                                                                                           |
| Student (mechanical breadth)                    | Sonnet 5.5, or Haiku 5.5 for the smallest jobs | medium (doc regen, enumeration) or low (rename, lint sweep)                           | Regenerates a reference doc, sweeps unused imports, applies an already-decided change across many files.                                                                                                                                                                                                                                        |

## Rules every role agent carries

These came out of the 2026-11-13 lifecycle and booking trains, where each one cost a review round or a QA round.

- **No nesting.** Each role agent sets `disallowedTools: Agent`, so it cannot spawn sub-agents. A subagent can otherwise nest three layers deep, the children share the worktree and commit into it, and stopping the parent leaves them running.
- **Whole suite on the final head.** A builder runs the whole jest suite before a push, and the database tier locally when CI will skip it. Named-directory runs missed real failures three times.
- **Proof before fix.** A review finding is reproduced with a failing test first. A function shared by several screens is tested through each screen's real reader output, and a control through what it sends against the route's schema. A fix proven only with mocks is listed as not verified until a preview shows it.
- **A QA run pins the head.** While a preview QA run is in progress on a branch, its builder pushes only on the orchestrator's message, and the QA agent writes its report file once, at the end. The `qa-push-hold` hook enforces it: the QA agent takes a hold under `/tmp/fw-qa-hold/` with `scripts/dev/qa-hold.sh` for the run, and the hook blocks a `git push` to that branch while the hold is fresh (model-orchestration section 6h). There are two exceptions: a hold older than 3 hours is stale and lets the push through, and any error inside the hook (input it cannot parse, an unreadable hold) allows the push. It is a guard that fails open, not a boundary: a push hidden behind an alias, `sh -c` or a variable is not seen.
- **Reports name numbers and gaps.** Every report gives suites and tests passed out of the total and a "Not verified" list. Long results go to a report file under `temp/`, so they survive the orchestrator's context being summarised.

## Built-in agents and briefs

`Explore` and `Plan` are built into Claude Code and have no file here, so their rules live in the brief:

- Pass `model: "sonnet"` to `Explore`; otherwise it inherits the orchestrator's model and its price.
- `Explore` locates code from excerpts; it does not audit it. Before one of its claims reaches the owner, a spec or an issue, read the cited lines yourself. It once reported a hard-coded platform fee where the code reads the stamped fee first.
- `Explore` and `Plan` are one-shot and cannot be resumed. A role agent can be resumed with `SendMessage` and keeps its whole history, which is cheaper than a new brief for a second round on the same PR.

A brief is the only context a fresh agent has. Give it four things: the objective, the output format (a file path and a word limit), the tools and sources to use (the files, the reference doc, the MCP), and the boundaries (what it must not touch, what is another agent's job, and when to stop and report). Hand over the evidence, not your conclusion, when you want an independent check.

Sources: [Create custom subagents](https://code.claude.com/docs/en/sub-agents) (frontmatter fields, `disallowedTools`, resuming); [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (the four parts of a delegation brief).

## The `razorpay-*` pack

Nine vendor-specific agents operate on and audit this repo's Razorpay and RazorpayX integration (`Prisma` + `BigInt` paise, Orders/Standard Checkout, saved cards, webhooks, two-phase refunds, REST disputes API, RazorpayX payouts + Penny Drop / Reverse Penny Drop, and in-house GST invoicing): `razorpay-setup`, `razorpay-one-time-payment`, `razorpay-subscription`, `razorpay-webhook`, `razorpay-test-webhook`, `razorpay-invoice`, `razorpay-db-schema`, `razorpay-diagnostics`, and `razorpay-code-audit`. They are narrower and more mechanical than the role agents above, are scoped to Razorpay integration code specifically, and are documented in full at `.claude/skills/finance/references/razorpay/README.md`.

## Dispatch rule

Money code goes to `pr-builder` at opus/high. Review triage on money code or on state code (a status, a transition, an access rule) also goes to `pr-builder`, because verifying a reviewer's claim against those paths needs the same multi-file coherence as building the code did, and `pr-triager` leaves such threads as needs-decision. All other triage goes to `pr-triager`. Docs work goes to `documentation-writer` at sonnet/high, because verifying each claim in code is where docs here have gone stale; regenerating a doc from a verdict already written goes to `mechanic`. A full preview QA round on state or money goes to `qa-preview` at sonnet/xhigh, where a false pass leads to a bad merge. A lean re-check of a few named cases goes to `sweeper` instead: one five-case re-check on `qa-preview` used about 305,000 tokens. Purely mechanical work goes to `mechanic`.

A pre-push check run or a local database-tier run goes to `check-runner`, so its log never enters the builder's or the orchestrator's context. A question about how many database statements a path issues goes to `statement-counter`. The `independent-reviewer` is never run proactively or automatically: when a PR that touches money, state or access code is otherwise ready, the orchestrator may offer it (in the ask tool or in chat) and runs it only after the owner says yes, at most once per reviewed head and never again after a fix round unless the owner asks, because re-reviewing our own work in a loop overspends tokens. Its brief hands over the code, the head and the decision record, never the builder's conclusions or the list of what was fixed. The QA push hold is not a dispatch decision: it is a hook (`.claude/hooks/qa-push-hold.sh`), and a blocked push waits for the orchestrator.
