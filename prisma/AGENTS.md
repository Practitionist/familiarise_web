# Schema & Migrations

Applies to `prisma/schema.prisma` and `prisma/migrations/`. The root `AGENTS.md` still applies.

1. **Check Postgres before writing a reconciler**: read the hand-written migrations after `0_baseline` (`*_guards`, `*_triggers`, `*_views`). If a `CHECK` constraint, the `EXCLUDE USING gist` constraint (`occurrence_no_confirmed_overlap`), or a `CONSTRAINT TRIGGER` (`ledger_txn_balanced`, `payment_legs_sum_to_amount`, `ledger_*_immutable`) already prevents an invalid state at `COMMIT`, **do not** write application-level sweeps to re-verify it. Only reconcile across external vendor boundaries (Razorpay, Stream, Resend, Supabase Storage).
2. **Every schema change is a new migration folder in the same PR.** Name it `<YYYYMMDDHHMMSS>_<what_it_does>` later than the newest on `dev`, wrap it `BEGIN; SET LOCAL lock_timeout = '3s'; … COMMIT;` (a single `CREATE INDEX CONCURRENTLY` file is the only exception), and never edit one that has been applied anywhere. `scripts/ci/check-migrations.ts` enforces all three. Step-by-step: `.claude/skills/schema/references/multi-session-workflow.md`.
3. **Expand merges, contract waits.** One database serves dev and prod and `db-migrate.yml` applies a migration on the merge to `dev`, so only additive changes merge freely. A drop, rename, type narrowing, `SET NOT NULL` or enum value removal goes in a folder ending `_contract`, which applies only when the owner dispatches it by name after the release that stopped using the object.
4. **Generate SQL against a local shadow, never a shared database**: `SHADOW_DATABASE_URL=<local> npx prisma migrate diff --from-migrations prisma/migrations --to-schema prisma/schema.prisma --script`. Delete the three standing `DROP INDEX` lines for `appointment_feedback_level_key`, `consultant_earnings_occurrence_key` and `organization_earnings_split_key`; replace any drop-and-add that is meant as a rename with `RENAME`. Never run `prisma db push`, `migrate dev`, or `migrate deploy`/`resolve`/`reset` against the shared database. Until the baseline is first applied live, regenerate it with `scripts/db/generate-baseline.sh`.
5. **`CHECK` constraints, partial unique indexes, triggers, views and RLS are written by hand into the migration.** Write each idempotently (`DROP … IF EXISTS` then create), pin `SET search_path = public` on functions, and keep them inside the transaction. A trigger that rebuilds a summary or aggregate must be `FOR EACH STATEMENT` with transition tables, or a dirty-mark plus a sweep. Guard and constraint triggers stay `FOR EACH ROW`. `scripts/ci/check-db-sidecars.ts` asserts every such object the history declares.
6. **Supabase MCP: reads run freely; every write waits for the owner.** One Supabase project serves dev and prod, so every query is a production query.
   - **Reads** need no approval. Batch several reads into one `execute_sql` call to cut round trips. The `.claude/hooks/supabase-sql-gate.ts` hook lets a call through without a prompt only when every statement is provably read-only (`SELECT`, `WITH … SELECT`, `EXPLAIN`, `SHOW`, with no data-modifying CTE, `SELECT … INTO`, row lock or known mutating function).
   - **Anything else** (DML, DDL, `SET`, `DO`, unparseable SQL) needs the owner's approval of the exact statement in this session. The hook asks with the statement type; in bypass-permissions mode it denies instead, so show the owner the statement in chat and re-run after they leave bypass mode. `apply_migration` and the branch, project and edge-function tools always ask (`permissions.ask`).
   - **Schema changes** go through a migration. MCP DDL is only for an owner-approved emergency, mirrored by a migration in the same PR (written idempotently, so it is a no-op where the emergency DDL already ran).
   - When a separate dev Supabase project exists, the hook can allow writes on that project ref without a prompt.
7. **Playbook**: `.claude/skills/schema/SKILL.md`.
