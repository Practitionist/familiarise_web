# Sentry hotfix of 2026-09-14: three issues from the last three days

**Date:** 2026-09-14 · **Branch:** `hotfix/sentry-2026-09-14` · **PR:** #TBD · **Scope:** `lib/data/needs-you.ts`, the Razorpay webhook dispatch, the pending-refund reconciler and its seed.

This entry records the three Sentry issues triaged out of the three days after the #1638 vocabulary reset shipped to `dev`, what each one turned out to be, and the shape of the fix. One optional item, FAMILIARISE_WEB-1H, was investigated and not fixed; its candidates are listed at the end.

## FAMILIARISE_WEB-3Y: the consultant dashboard route threw on a relation #1638 made singular

`pendingSubscriptionWhere` in `lib/data/needs-you.ts` still filtered on `appointments: { none | some }`, but #1638 gave `Subscription` a single optional `appointment` relation, so Prisma rejected the query at runtime with `Unknown argument 'appointments'` on every `GET /api/dashboard/consultant/[consultantId]`. The compiler could not see it because the helper returned an untyped object literal, and TypeScript performs no excess-property check on a returned value. The predicate now uses the singular relation with the same meaning as before (personal is "no wrapper, or a wrapper with no organisation stamp", an organisation scope pins the wrapper's `organizationId`, and the `all` scope keeps the old `some: {}` reading of "any wrapper at all" as `isNot: null`), and both helpers are typed as `Prisma.SubscriptionWhereInput` and `Prisma.ConsultationWhereInput` so the next relation rename fails `tsc` rather than the route. A repository-wide search found no other `appointments:` filter on a model whose relation became singular.

## FAMILIARISE_WEB-3W: a Razorpay payload that fails its schema was re-driven for a week

`TERMINAL_ERROR_PREFIXES` in `lib/webhooks/event-log.ts` documents `permanent:` as "written at dispatch" for a schema mismatch, but only the Stream dispatch ever wrote it. The Razorpay dispatch stored the raw `ZodError` message, which the stuck-webhook sweep treated as transient, so one hand-crafted `pay_S4Priya00000001` payload was re-driven on every five-minute tick for the whole seven-day give-up window and produced 122 Sentry errors. The Razorpay catch now recognises a `ZodError`, stamps `permanent: schema mismatch: <event type> — <first five issues>` (capped at 500 characters) on the row, and reports the event once through `reportSentryError` as an expected `warning` with `op: razorpay.schema_mismatch`, which is the same shape the Stream dispatch uses. The schema itself was not loosened: real Razorpay payloads carry every nullable field as `null`, and the mismatching payload was synthetic. The pin lives in `__tests__/enterprise/webhook-dispatch-gaps.test.ts`.

## FAMILIARISE_WEB-3V: the refund reconciler polled a refund id the gateway had never seen, forever

Razorpay answers `refunds.fetch` for an id it has no record of, and for a test-mode id read with live-mode keys, with HTTP 400 `BAD_REQUEST_ERROR` / `input_validation_failed`, never with a 404. `getRazorpayRefund` reported every such answer as an error-level Sentry event and the reconciler's real-id pass logged and retried it on the next tick, which is right for a timeout and wrong for an id that cannot become known; the seed mints twenty percent of gateway refunds as `PENDING` under random `rfnd_` ids, so the loop restarted after every reseed and reached 722 events. The owner decision is to classify this answer as terminal. `RefundError` now carries Razorpay's `reason`, `isRazorpayUnknownRefundIdError` names the shape in one place, and the reconciler moves the row to `FAILED` through a CAS on `status = PENDING` (an `updateMany` whose `WHERE` repeats the money predicate, the idiom every payout transition uses) with a `failureReason` that names both causes and says the customer was not refunded, so `notifyFailedRefunds` carries that sentence to the payer exactly as it does for a refund the gateway declined. It reports once per row as an expected `warning`, and the run summary and the HTTP twin gain a `failedUnknownId` counter, which is a subset of `failedCount`. Any other error keeps the log-and-retry behaviour. The seed no longer mints `PENDING` rows for Razorpay or Stripe; the twenty percent is redistributed as seventy percent `SUCCEEDED` and twenty-five percent `FAILED`, with the total count unchanged. The pin lives in `__tests__/payments/reconcile-reservation-match.test.ts`.

## FAMILIARISE_WEB-1H: "Rendered more hooks than during the previous render" on the class offering editor

Two events, on two different previews, both on `/dashboard/consultant/[consultantId]/offerings/class/[offeringId]/edit`. The stack is minified and carries no component name. Within the time box the edit page, `OfferingEditorContainer`, `OfferingEditor`, `OfferingField` and its four composite fields, `ContentItemsEditor`, `FaqEditor`, `CollaboratorsTab` and `PlanImageUploader` were read for a hook after an early return or a hook called on a condition, and none has one; the page calls `notFound()` before its `useQuery`, but a thrown render never commits and cannot be the "previous render". The item is left open with those components ruled out.
