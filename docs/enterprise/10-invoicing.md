# Invoicing

**Status**: Partially implemented (Apr 2026)
**Branch**: `feature/enterprise`
**Scope**: INVOICED_MONTHLY billing mode

**Deferred**: Inngest cron (#661), PDF rendering (#438), credit notes (#661)

## Overview

Organizations using the INVOICED_MONTHLY billing mode accumulate bookings throughout the month without upfront payment. Each booking creates a `Payment` record with `paymentMethod: ORG_INVOICED` and `paymentStatus: SUCCEEDED`. At the end of the billing cycle (or on demand), unbilled payments are aggregated into a single `OrganizationInvoice` with status SENT. The org admin then pays the invoice, typically via Razorpay, before the due date determined by `paymentTermsDays`.

## Invoice Generation

### Manual Trigger

```
POST /api/organizations/[orgId]/billing/generate-invoice
Role: ORG_OWNER
```

The manual trigger aggregates all unbilled payments for the calling org and rolls them into a single invoice. The route:

1. Validates that `billingMode === INVOICED_MONTHLY` (returns 400 otherwise)
2. Queries all `Payment` rows where:
   - `organizationProfileId` matches the org
   - `paymentStatus === SUCCEEDED`
   - `paymentMethod === ORG_INVOICED`
   - `billableToOrgInvoiceId === null` (not yet billed)
3. For each payment, nets out successful refunds: `netAmount = payment.amount - sum(refunds.amount)`
4. Filters out fully-refunded bookings (netAmount <= 0)
5. Returns 400 if no billable payments remain
6. Creates the invoice and links payments in a single Prisma transaction:
   - Creates `OrganizationInvoice` with status `SENT`
   - Sets `dueDate = now + paymentTermsDays`
   - Updates all unbilled payments to point at the new invoice via `billableToOrgInvoiceId`

Invoice number format: `INV-{SLUG_8}-{YYYYMM}-{RANDOM_4}`, e.g. `INV-INFOSYS-202604-A3KZ`.

**File**: `app/api/organizations/[orgId]/billing/generate-invoice/route.ts`

### Automated (Deferred)

An Inngest scheduled function will run on the 1st of each month at 00:00 UTC, invoking the same aggregation logic for every INVOICED_MONTHLY org. The core logic will be extracted to `lib/payments/operations/org-invoicing.ts` and shared between the manual route and the cron.

Issue #661 tracks this work.

## OrganizationInvoice Model

```
OrganizationInvoice
  id                    String (UUID)
  organizationProfileId String (FK -> OrganizationProfile)
  invoiceNumber         String (unique)
  amount                Int (paise)
  currency              String (default "INR")
  status                OrgInvoiceStatus (default DRAFT)
  items                 Json
  taxAmount             Int?
  taxRate               Float?
  hsnCode               String? (default "999293")
  gstin                 String?
  paymentId             String? (unique FK -> Payment)
  billingCycleStart     DateTime?
  billingCycleEnd        DateTime?
  autoGenerated         Boolean (default false)
  dueDate               DateTime?
  paidAt                DateTime?
  pdfUrl                String? (deferred, Issue #438)
  billedPayments        Payment[] (back-relation)
```

**Schema location**: `prisma/schema.prisma` (around line 773)

### Status Lifecycle

```
  DRAFT ------> SENT ------> PAID
                  |
                  +-------> OVERDUE
                  |
                  +-------> CANCELLED
```

| Status    | Meaning                                              |
|-----------|------------------------------------------------------|
| DRAFT     | Invoice created but not yet finalized                 |
| SENT      | Invoice finalized and visible to org admin            |
| PAID      | Payment received (paidAt timestamp set)               |
| OVERDUE   | Past dueDate and still unpaid (set by future cron)    |
| CANCELLED | Voided (e.g., all line items refunded)                |

### Items JSON Shape

Each item in the `items` array:

```
{
  "paymentId": "uuid",
  "description": "Booking (CONSULTATION)",
  "quantity": 1,
  "unitPrice": 500000   // in paise (= Rs 5,000)
}
```

### GST Fields

| Field     | Purpose                                          |
|-----------|--------------------------------------------------|
| taxAmount | GST amount in paise (calculated from taxRate)    |
| taxRate   | GST rate as decimal (e.g., 0.18 for 18%)         |
| hsnCode   | SAC code, defaults to `999293` (educational)     |
| gstin     | Org's GST identification number                  |

## Credit Limit Enforcement

INVOICED_MONTHLY orgs can have an optional `orgInvoiceCreditLimit` (in paise) on their `OrganizationProfile`. This caps how much unbilled exposure the platform allows before blocking new bookings.

### How Exposure Is Calculated

At checkout time (`lib/payments/operations/checkout.ts`):

```
exposure = netUnbilled + outstandingInvoices
```

Where:
- `netUnbilled` = sum of (payment.amount - refunded) for each ORG_INVOICED payment with `billableToOrgInvoiceId === null`
- `outstandingInvoices` = sum of amounts on invoices with status SENT or OVERDUE

If `exposure >= orgInvoiceCreditLimit`, the checkout is blocked with:
> "Organization has reached its invoice credit limit. Outstanding invoices must be paid before new bookings."

### Worked Example

TCS has `orgInvoiceCreditLimit = 10,00,000` (Rs 10L).

| Unbilled payments (net) | Outstanding invoices | Exposure   | New Rs 5,000 booking? |
|--------------------------|----------------------|------------|------------------------|
| Rs 3,00,000              | Rs 4,00,000          | Rs 7,00,000 | Allowed               |
| Rs 6,00,000              | Rs 4,00,000          | Rs 10,00,000| Blocked               |
| Rs 8,00,000              | Rs 0                 | Rs 8,00,000 | Allowed               |
| Rs 0                     | Rs 10,00,000         | Rs 10,00,000| Blocked               |

## Payment Terms

The `paymentTermsDays` field on `OrganizationProfile` controls how many days after invoice creation the payment is due:

| Value | Industry Term |
|-------|--------------|
| 7     | NET-7        |
| 15    | NET-15       |
| 30    | NET-30       |

Default: 30 days. The invoice's `dueDate` is set to `new Date() + paymentTermsDays` at creation time.

## Invoice Payment

Org admins pay invoices through the billing dashboard at `/dashboard/organization/[orgId]/billing`. The flow:

1. Admin sees outstanding invoices with SENT/OVERDUE status badges
2. Clicks "Pay" on an invoice
3. Payment processed via Razorpay
4. Invoice status transitions from SENT to PAID
5. `paidAt` timestamp is recorded
6. `paymentId` links the invoice to its settlement Payment record

## Post-Invoice Refunds (Deferred)

**Problem**: If a booking is refunded after its invoice has been PAID, the invoice total and the actual received amount diverge.

**Current behavior**: The payment's `billableToOrgInvoiceId` is cleared (unbilled), which means the payment is excluded from future invoices but the already-paid invoice total is not adjusted.

**Future solution**: A credit note system (Issue #661) will create `OrganizationCreditNote` records that offset future invoices. This maintains an immutable audit trail: the original invoice stays unchanged, and the credit note reduces the next invoice's total.

## Edge Cases

| Case | Behavior |
|------|----------|
| All payments fully refunded | `generate-invoice` returns 400: "No billable payments after refund adjustments" |
| Zero unbilled payments | Returns 400: "No unbilled payments to invoice for this period" |
| Exposure exactly at limit | Checkout blocked (uses `>=` comparison) |
| Multiple invoices in same month | Allowed -- each covers only payments not yet linked to an invoice |
| Non-INVOICED_MONTHLY org calls endpoint | Returns 400 with billing mode mismatch error |
| Concurrent invoice generation | Prisma transaction ensures each payment is billed exactly once |
