# Invoicing

`OrganizationInvoice` is the India-compliant invoice model for
sponsor-side flows. Every row is paired with zero or more `PaymentLeg`
records (one per stackable funding source) and optionally a
`PurchaseOrder` (for NET-X enterprise customers).

## Schema highlights

```prisma
model OrganizationInvoice {
  id               String @id @default(uuid())
  billingAccountId String
  organizationId   String
  purchaseOrderId  String?
  contractId       String?     // SetNull — keeps invoice audit-readable if contract dies

  invoiceNumber String @unique
  status        OrgInvoiceStatus @default(DRAFT)

  // Money
  displayCurrency    Currency
  fxRateUsed         Decimal?
  inrEquivalentPaise Int           // always captured for GST filings
  subtotalPaise      Int
  igstPaise          Int @default(0)
  cgstPaise          Int @default(0)
  sgstPaise          Int @default(0)
  totalPaise         Int
  taxRate            Decimal?

  items Json   // [{ description, quantity, unitPrice, paymentId? }, ...]

  // GST
  hsnCode       String  @default("999293")
  placeOfSupply String? @db.VarChar(2)
  reverseCharge Boolean @default(false)
  lutNumber     String?   // zero-rated exports
  gstin         String?   @db.VarChar(15)

  // E-invoice (IRN)
  irn             String? @db.VarChar(64)
  ackNumber       String?
  ackDate         DateTime?
  signedQrPayload String? @db.Text
  irpStatus       IrpStatus @default(PENDING)
  irpUploadedAt   DateTime?

  // Lifecycle
  billingCycleStart DateTime?
  billingCycleEnd   DateTime?
  autoGenerated     Boolean @default(false)
  issuedAt          DateTime?
  dueDate           DateTime
  paidAt            DateTime?
  pdfUrl            String?

  providerPaymentId String?
  paymentId         String? @unique  // for one-off invoices
  billedPayments    Payment[]  // INVOICE_MONTHLY: rolled-up payments
  ...
}
```

## `OrgInvoiceStatus`

```
DRAFT ──► ISSUED ──► PAID
              │
              ├──► OVERDUE (cron sets when dueDate passes)
              └──► VOID / CANCELLED (terminal)
```

`PATCH /api/organizations/[orgId]/billing-account/invoices/[invoiceId]`
is OWNER-only and gates transitions:

- `DRAFT → ISSUED` — sets `issuedAt = now()` and kicks off the IRN
  upload stub.
- `ISSUED → PAID` — sets `paidAt = now()` and writes a
  `SettlementLedgerEntry(kind=INVOICE_PAID)` in the same transaction.
- `ISSUED → VOID/CANCELLED` — blocked if already partially paid.

## GST breakdown (CGST / SGST / IGST)

Indian GST splits across three components depending on whether the
supply crosses a state boundary:

| Condition                                     | Tax columns populated |
|-----------------------------------------------|------------------------|
| Intra-state (buyer and seller in same state)  | `cgstPaise` + `sgstPaise` (usually 9% + 9%) |
| Inter-state (buyer and seller in different states) | `igstPaise` (usually 18%) |
| Export (zero-rated)                           | All tax columns = 0; `lutNumber` populated |
| Reverse charge                                | `reverseCharge = true`; invoice carries no tax but the buyer self-accounts |

`placeOfSupply` is the buyer's GST state code (2 chars, e.g. `"27"`
for Maharashtra). The helper that populates the tax columns is at
`lib/compliance/india/gst.ts` (stub in v1 — see
`19-harness-verdict.md`).

## HSN code

`hsnCode` is the SAC (Services Accounting Code) under which the line
items fall. The default `999293` is "commercial training and coaching
services"; custom line items can override per-item but the invoice-level
default covers 95% of our bookings.

## IRN (E-invoice)

India mandates e-invoicing for registered GST taxpayers above a
threshold. The model carries every field the IRP (Invoice Registration
Portal) returns:

```
irn             — the 64-char Invoice Reference Number
ackNumber       — portal acknowledgement number
ackDate         — portal ack timestamp
signedQrPayload — signed QR for the printed PDF
irpStatus       — PENDING | GENERATED | CANCELLED | FAILED
irpUploadedAt   — our request timestamp
```

Upload is stubbed in v1; the integration lands in a follow-up PR.
Fields are schema-final.

## Line items (`items: Json`)

Stored as a JSON array; each item is:

```json
{
  "description": "Consultation session with Expert X",
  "quantity": 1,
  "unitPriceInrPaise": 100000,
  "paymentId": "<payment.id>"   // optional, for INVOICE_MONTHLY roll-ups
}
```

Why JSON and not a dedicated table? Invoice lines are read only at
render/audit time. A dedicated table would add a join on every
invoice read and wouldn't pay for itself until we hit the rare
"rewrite one line without rewriting the invoice" case (which requires
a CANCELLED + new invoice anyway for statutory reasons).

## Purchase orders (`PurchaseOrder`)

```prisma
model PurchaseOrder {
  id             String @id @default(uuid())
  organizationId String
  poNumber       String
  poDate         DateTime
  validUntil     DateTime?
  totalAmountPaise     Int
  remainingAmountPaise Int
  currency             Currency @default(INR)
  uploadedDocUrl       String?
  status               PoStatus @default(ACTIVE)
  contracts Contract[]
  invoices  OrganizationInvoice[]
  ...
  @@unique([organizationId, poNumber])
}
```

Created via `POST /api/organizations/[orgId]/billing-account/purchase-orders`
(OWNER). `requiresPO = true` on the Organization row triggers a
dashboard warning when an OWNER tries to create a contract without
attaching a PO. The PO is decrement-tracked via `remainingAmountPaise`
as invoices bill against it.

## 3-way match

The classic enterprise AP control. When an INVOICE-funded (monthly
roll-up)
is generated:

1. **PO** declares the commit (`totalAmountPaise`).
2. **Contract** ties the billing cycle + payment terms to that PO
   via `Contract.purchaseOrderId`.
3. **Invoice** points at the same PO
   (`OrganizationInvoice.purchaseOrderId`) and decrements
   `remainingAmountPaise`.

If the running sum of invoices against a PO exceeds
`PO.totalAmountPaise`, the invoice POST refuses with a 409. When
`remainingAmountPaise` hits zero, the PO transitions to `CLOSED`.

## Auto-generated vs hand-rolled

- `autoGenerated = true` — the monthly roll-up cron emitted this row.
  `billedPayments[]` is populated with every payment it captured.
- `autoGenerated = false` — an OWNER manually created this via
  `POST /billing-account/invoices`. Used for ad-hoc charges (setup
  fees, overage bundles).
