# Enterprise org billing playbook — technical reference

> **Audience:** engineers onboarding an enterprise customer.
> **Prerequisite reading:** `01-organization-types.md`,
> `02-funding-and-programs.md`, `04-roles-and-permissions.md`.

This document walks through every supported **capability × funding
source** combination, including setup calls, relevant schema fields,
checkout behaviour, and cron dependencies.

## Taxonomy refresher

- Capability is controlled by two booleans on `Organization`:
  `canSponsor` and `canHost`. See `01-organization-types.md`.
- Funding source lives on the `BillingAccount` row (one per sponsor
  org): one of `PERSONAL | WALLET | INVOICE | LICENSE | PROJECT`
  (PROJECT is v2-reserved). See `02-funding-and-programs.md`.
- The deprecated `OrganizationKind` enum and the
  `TAG_ONLY/SEAT_PACK/INVOICED_MONTHLY/PREPAID_UNLIMITED` billing
  modes are gone; the mapping is in `02-funding-and-programs.md`.
- The `ENABLE_PROVIDER_ORGS` env flag only gates the *settlement*
  logic for host-side earnings (`lib/payments/payouts/earnings-service.ts`).
  Every API route below is live regardless of the flag.

The four sponsor combos (with `canHost = false`) plus the three
hybrid combos (with `canHost = true`) are the sell-supported matrix.
HOST-only orgs (canSponsor=false) share the hybrid's host plumbing.

## 1. Sponsor · PERSONAL

### Use case

Company wants visibility into employee bookings without prepaying. The
learner pays on their own card at checkout; the org is attribution-
only.

### Create

```
POST /api/organizations
{
  "name": "Acme Corp",
  "canSponsor": true,
  "canHost": false,
  "fundingSource": "PERSONAL",
  "billingEmail": "ap@acme.com"
}
```

Creates `Organization(status=PENDING_VERIFICATION)` + `BillingAccount
(fundingSource=PERSONAL)` + OWNER `Membership`. Admin flips status
via `POST /api/admin/organizations/[orgId]/verify`.

### Invite members

```
POST /api/organizations/[orgId]/invitations
{ "email": "alice@acme.com", "role": "LEARNER" }
```

### Checkout flow

- `Payment.organizationId = <org.id>` (attribution tag).
- `PaymentLeg(source=CARD, amountPaise=<price>)` — the learner's card.
- No `WalletEntry`, no `PaymentLeg(source=WALLET)`, no
  `ProgramAssignment` debit.

### Cron dependencies

None.

## 2. Sponsor · WALLET

### Use case

Org pre-loads a credit pool; members book freely until the pool
empties.

### Create

```
POST /api/organizations
{ ...baseOrg, "canSponsor": true, "canHost": false, "fundingSource": "WALLET" }
```

`BillingAccount.walletBalance = 0` is set at creation time.

### Top-up

```
POST /api/organizations/[orgId]/billing-account/wallet/top-ups
{ "amountPaise": 5000000, "clientIdempotencyKey": "t_acme_2026_04_001" }
```

- Returns `{ providerOrderId }`; client completes Razorpay checkout.
- Razorpay webhook (`/api/webhooks/razorpay`) calls `confirmTopUp()`
  which credits the wallet atomically and replaces the placeholder
  `WalletEntry` with the real confirmed row.

### Checkout flow

- `walletDebit()` runs inside the checkout transaction:
  `UPDATE BillingAccount SET walletBalance -= :price WHERE walletBalance >= :price`.
- On insufficient funds → `WalletInsufficientFundsError` → 402 at
  checkout.
- Writes `PaymentLeg(source=WALLET)` + `WalletEntry(reason=BOOKING)` +
  `FundingLedgerEntry(reason=BOOKING_DEBIT)`.

### Cron dependencies

None. (Top-up confirmation is webhook-driven, not cron-driven.)

## 3. Sponsor · INVOICE

### Use case

Enterprise procurement. PO is cut upfront; sessions accrue over the
month; one invoice is emitted at month-end with NET-X terms.

### Create

```
POST /api/organizations
{ ...baseOrg, "canSponsor": true, "canHost": false,
  "fundingSource": "INVOICE", "requiresPO": true, "paymentTermsDays": 60 }
```

### Optional: attach a PO

```
POST /api/organizations/[orgId]/billing-account/purchase-orders
{
  "poNumber": "PO-2026-00412",
  "poDate": "2026-04-01",
  "validUntil": "2027-03-31",
  "totalAmountPaise": 50000000,
  "uploadedDocUrl": "https://..."
}
```

### Sign a contract

```
POST /api/organizations/[orgId]/contracts
{
  "billingAccountId": "<ba.id>",
  "purchaseOrderId": "<po.id>",
  "effectiveFrom": "2026-04-01",
  "effectiveTo": "2027-03-31",
  "paymentTermsDays": 60,
  "status": "ACTIVE"
}
```

### Checkout flow

- `Payment.status = SUCCEEDED` without a gateway charge.
- `PaymentLeg(source=INVOICE_ACCRUAL, amountPaise=<price>)`.
- `BookingUtilization` row (via the attached `LICENSED_SEAT` program
  if one exists).
- End of month: `jobs/billing/generate-subscription-invoices.ts` (stub)
  rolls every `INVOICE_ACCRUAL` leg into an `OrganizationInvoice` with
  `autoGenerated=true`, computes GST (CGST/SGST or IGST), decrements
  `PurchaseOrder.remainingAmountPaise`, and emits the IRN request
  (stubbed; row is created with `irpStatus=PENDING`).
- `PATCH /api/organizations/[orgId]/billing-account/invoices/[id]`
  flips `DRAFT → ISSUED`; `.../pay` flips to `PAID` and writes
  `SettlementLedgerEntry(INVOICE_PAID)`.

### Cron dependencies

- Monthly: `jobs/billing/generate-subscription-invoices.ts` (stub —
  manual POST /invoices works today).
- Daily: OVERDUE sweep (`dueDate < today && status = ISSUED`).

## 4. Sponsor · LICENSE

### Use case

Flat-fee annual / quarterly license. Sessions are unmetered within the
contract period.

### Create

```
POST /api/organizations
{ ...baseOrg, "canSponsor": true, "canHost": false, "fundingSource": "LICENSE" }
```

### Signed contract with unlimited Program

```
POST /api/organizations/[orgId]/contracts
{ "billingAccountId": "<ba.id>", "effectiveFrom": "...", "effectiveTo": "...", "status": "ACTIVE" }

POST /api/organizations/[orgId]/programs
{
  "type": "LICENSED_SEAT",
  "contractId": "<contract.id>",
  "name": "2026 Institutional License",
  "licensedSeatConfig": {
    "ratePerSeatPaise": 0,
    "cycle": "ANNUAL",
    "coveredEngagementsPerCycle": null,
    "overageBehavior": "BLOCK"
  }
}
```

`coveredEngagementsPerCycle = null` means unlimited. `ratePerSeatPaise =
0` because the license fee was collected offline.

### Checkout flow

- `PaymentLeg(source=LICENSE, amountPaise=0)` — the program absorbs
  the booking, no money moves.
- `BookingUtilization` is written for analytics; `engagementsUsed`
  increments but there is no cap to check.
- No invoice.

### Cron dependencies

Contract-expiry cron flips `ContractStatus: ACTIVE → EXPIRED` on
`effectiveTo` (stub).

## 5. Host only

### Use case

Coaching institute / expert network. Org brings experts; org earns a
share of every booking.

### Create

```
POST /api/organizations
{ ...baseOrg, "canSponsor": false, "canHost": true }
```

No billing account is created.

### Add experts

The expert applies (or is invited directly with `role=EXPERT`) and the
MAINTAINER approves via `PATCH /members/[memberId]`. See
`06-expert-lifecycle.md`. Set `payoutRecipient = ORGANIZATION` at
approval time to collapse the split (the org captures the expert's
share).

### Configure rate card

```
POST /api/organizations/[orgId]/rate-cards
{
  "platformBps": 1000,
  "orgBps": 1500,
  "consultantBps": 7500
}
```

The default is 10/10/80. Bumping writes a new card + closes the old
one — `bumpRateCard()` in `lib/api/organizations/rate-card.ts`. Old
earnings settle against their bps snapshot; new earnings use the new
card.

### Configure payout account

```
PUT /api/organizations/[orgId]/payout-account
{
  "accountHolderName": "Coaching Co Pvt Ltd",
  "accountNumberEncrypted": "...",
  "accountNumberLast4": "4242",
  "bankName": "HDFC Bank",
  "ifscCode": "HDFC0001234"
}
```

### Booking flow

- `OrganizationEarnings` row created alongside `ConsultantEarnings`.
- `rateCardIdApplied`, `platformBpsApplied`, `orgBpsApplied`,
  `consultantBpsApplied` snapshotted.
- `EarningStatus` flows `PENDING → HELD → RELEASED → PAID`.

### Payout

```
POST /api/organizations/[orgId]/payouts
{ "periodStart": "2026-04-01", "periodEnd": "2026-04-30" }
```

Rolls all RELEASED earnings into an `OrganizationPayout(PENDING)`.
Admin flips to `PROCESSED` via PATCH after the payout provider
confirms. See `07-payout-pipeline.md` for the India statutory columns
(`tdsSectionApplied`, `mustPayByDate`, `rbiPurposeCode`, etc.).

### Cron dependencies

- Daily: `hold → RELEASED` sweep based on `holdUntil`.
- Per payout cycle: the actual wire (Razorpay Payouts / Cashfree)
  + TDS compute stubs.

## 6-9. Hybrid combos

Hybrid orgs pair one sponsor funding source with the host plumbing
above. Each side runs independently — the sponsor flow never sees
earnings rows, the host flow never sees wallet debits.

| # | Capability  | Funding | Sponsor-side setup | Host-side setup |
|---|-------------|---------|--------------------|-----------------|
| 6 | HYBRID      | PERSONAL| same as Sponsor#1 | same as Host#5 |
| 7 | HYBRID      | WALLET  | same as Sponsor#2 | same as Host#5 |
| 8 | HYBRID      | INVOICE | same as Sponsor#3 | same as Host#5 |
| 9 | HYBRID      | LICENSE | same as Sponsor#4 | same as Host#5 |

### The HYBRID self-booking case

If a HYBRID org's own learner books its own expert:

- Sponsor side: wallet debit / invoice accrual / license absorption
  fires as usual.
- Host side: an `OrganizationEarnings` row is written. If the expert
  has `payoutRecipient = ORGANIZATION`, the consultant share collapses
  into the org share and `ConsultantEarnings` is skipped for that
  booking.
- Net effect: 10% platform fee + 90% retained by the org (the org
  effectively pays itself, minus the fee).

## Common operations

### Change funding source

```
PATCH /api/organizations/[orgId]/billing-account
{ "fundingSource": "WALLET" }  // or INVOICE / LICENSE
```

Owner-only. Refuses to drop `canSponsor` while the wallet has
non-zero balance (see `01-organization-types.md`).

### Suspend / deactivate

```
POST /api/admin/organizations/[orgId]/verify
{ "action": "SUSPEND", "reason": "Invoice 60 days overdue" }
```

Allowed transitions in `05-organization-lifecycle.md`.

### Bulk add via HRIS

```
PUT /api/organizations/[orgId]/hris
{ "provider": "WORKDAY", "tenantKey": "acme" }

POST /api/organizations/[orgId]/hris/sync
```

or fallback CSV:

```
POST /api/organizations/[orgId]/hris/csv-upload
(multipart body)
```

## Failure modes and recovery

| Situation | What happens | Recovery |
|-----------|--------------|----------|
| WALLET funds exhausted at checkout | `WalletInsufficientFundsError` → 402 | Owner tops up; retry. |
| Cap hit on LICENSED_SEAT with `overageBehavior=BLOCK` | `ProgramAssignmentLimitError` → 402 | Owner increases cap via PATCH `/programs/[id]`, or member waits for next cycle. |
| PO exhausted | Invoice generation refuses with 409 | Owner uploads a new PO via POST `/purchase-orders`. |
| SSO misconfigured and enforcement on | `customSession` marks `ssoEnforcementFailed=true`; user bounced to SSO selector | Owner disables `enforceSSO` from `/api/organizations/[orgId]/sso` (doesn't itself require SSO). |
| Duplicate top-up request | `WalletEntry.providerOrderId @unique` P2002; handler returns existing row with `reused: true` | No action needed — idempotent. |
| Rate-card bump race | Winner's row takes effect; loser sees `effectiveTo` already set | Read wins via `effectiveFrom DESC`. |
