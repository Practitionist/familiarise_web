# Scenarios and examples

Four representative orgs worked end-to-end against the current schema.
Every model / column mentioned is real. Rate splits used for the bps
math are illustrative; the default 10/10/80 is baked into
`DEFAULT_RATE_CARD` in `lib/api/organizations/rate-card.ts`.

## 1. Wipro (large enterprise sponsor, INVOICE funding)

**Shape:** sponsor-only, intra-group subsidiary structure.

| Field | Value |
|-------|-------|
| `canSponsor` | `true` |
| `canHost` | `false` |
| `fundingSource` | `INVOICE` |
| `dataResidencyRegion` | `IN` |
| `requiresPO` | `true` |
| `paymentTermsDays` | `60` |
| `contractCurrency` | `INR` |

Wipro has two subsidiary orgs (`parentId = Wipro.id`), but the subtree
UI is not built in v1 — see `17-hierarchy.md`. Each subsidiary carries
its own `BillingAccount`, but consolidated reporting against `rootId`
is a follow-up cron.

### Booking flow

1. A Wipro learner books a CONSULTATION against an independent
   marketplace expert.
2. Checkout creates `Payment` with `organizationId = <Wipro.id>`,
   `PaymentLeg(source=INVOICE_ACCRUAL, amountPaise=<gross>)`. No money
   moves at booking time — the payment is accrued.
3. `BookingUtilization` is written against the active `ProgramAssignment`
   under Wipro's LICENSED_SEAT Program (session cap per cycle = 4).
4. End of month: a cron rolls every `PaymentLeg.source=INVOICE_ACCRUAL`
   for Wipro into one `OrganizationInvoice`:
   - `autoGenerated = true`
   - `items = [{...}, {...}, ...]` (one per Payment)
   - `purchaseOrderId = <active PO>`; `remainingAmountPaise` decremented
   - GST split by place of supply (Bangalore → KA; intra-state with
     Familiarise Bangalore base → CGST+SGST)
   - IRN upload queued (stubbed in v1)
5. Wipro AP has 60 days to pay. A cron flips the status to `OVERDUE`
   if `dueDate` passes.

### Why the LICENSED_SEAT Program matters here

Wipro's HR negotiated 4 sessions / learner / quarter with
`overageBehavior = CHARGE_ORG`. A 5th booking in the same quarter
still succeeds but is marked `wasOverage = true` on the
`BookingUtilization`, and the next `OrganizationInvoice` line carries
a flagged item.

## 2. LearnPro (HYBRID; curated catalog + its own experts)

**Shape:** HYBRID, WALLET funding, 30-day quarterly contract.

| Field | Value |
|-------|-------|
| `canSponsor` | `true` |
| `canHost` | `true` |
| `fundingSource` | `WALLET` |
| `enforceOrganizationPlans` | `true` |
| `autoApproveConsultants` | `false` |

### Sponsor side

- WALLET funded with ₹5,00,000 upfront via Razorpay top-up
  (`WalletEntry(reason=TOPUP, deltaPaise=+50000000)`).
- Every learner booking debits the wallet via `walletDebit()`:
  `Payment` + `PaymentLeg(source=WALLET)` + `BookingUtilization` +
  `UsageLedgerEntry` + `WalletEntry(reason=BOOKING, deltaPaise=-<price>)`
  + `FundingLedgerEntry(reason=BOOKING_DEBIT, balanceAfterPaise=<new>)`.
- `enforceOrganizationPlans = true` means learners can only book from
  the curated `OrganizationPlan` rows.

### Host side

- LearnPro's 12 experts each have a `Membership(role=EXPERT,
  status=ACTIVE, payoutRecipient=ORGANIZATION)`.
- Bookings against these experts by LearnPro learners (the HYBRID
  self-booking case) route money through the sponsor WALLET flow AND
  book an `OrganizationEarnings` row on the host flow.
- The expert share is collapsed into the org share (via
  `payoutRecipient = ORGANIZATION`) so net effect: 10% platform fee
  + 90% to LearnPro. LearnPro pays the expert offline (salary).

### Rate card

A contract-scoped `RateCard(planType=CONSULTATION, platformBps=1000,
orgBps=9000, consultantBps=0)` supersedes the org default. The card
was bumped from 10/10/80 at Month 3 via `bumpRateCard()` — old
earnings still settle at 80% to expert because their
`consultantBpsApplied = 8000` snapshot survives the bump.

## 3. IIT Madras (university; LICENSE funding)

**Shape:** sponsor-only, flat annual license.

| Field | Value |
|-------|-------|
| `canSponsor` | `true` |
| `canHost` | `false` |
| `fundingSource` | `LICENSE` |
| `dataResidencyRegion` | `IN` |
| `sizeBucket` | `ENTERPRISE_1000_PLUS` |

### Contract + Program

- `Contract(paymentTermsDays=30, effectiveFrom=Apr-2026,
  effectiveTo=Mar-2027, autoRenew=true)`.
- `Program(type=LICENSED_SEAT, coveredSessionsPerCycle=null,
  cycle=ANNUAL, ratePerSeatPaise=200000, overageBehavior=BLOCK)`.
- `coveredSessionsPerCycle = null` is the v1 "unlimited" marker — it
  replaces the old `PREPAID_UNLIMITED` enum value.

### Booking flow

1. Learner (a student) books a WEBINAR.
2. Checkout validates `program.status = ACTIVE` and claims the active
   `ProgramAssignment`. Cap check is skipped (unlimited).
3. `PaymentLeg(source=LICENSE, amountPaise=0)` — the booking is
   "absorbed" by the license. No money moves, no wallet debit, no
   invoice row.
4. `BookingUtilization` records the usage for analytics;
   `sessionsUsed` increments on the assignment.

Settlement reads: the Program absorbed the price; no
`SettlementLedgerEntry(kind=PAYMENT_RECEIVED)` is written because
there is no payment. This is one of two cases where the settlement
ledger legitimately skips a row (the other is pure PERSONAL funding
— the learner card charge lands in marketplace Payment but the
org-side settlement is a no-op).

## 4. Rahul (solo marketplace consultant; no org at all)

**Shape:** no Membership row; isolated marketplace flow.

Rahul has `ConsultantProfile.isIndependent = true` (no ACTIVE EXPERT
memberships). A booking against him by a marketplace learner:

1. `Payment.organizationId = null`. Attribution is unset.
2. `PaymentLeg(source=CARD, amountPaise=<gross>)`.
3. `ConsultantEarnings` written with the default 80/20 split (10%
   platform + 10% marketplace reserve; see the default rate card).
4. No `OrganizationEarnings` row, no BookingUtilization (no program),
   no wallet debit.
5. Rahul's own payout pipeline (via `Payout` not
   `OrganizationPayout`) processes as usual.

This scenario exists in the doc set because the enterprise layer must
not interfere with the marketplace flow. Every `lib/` primitive in
the enterprise layer checks "is there an org?" before writing. The
settlement path short-circuits at `resolveOrgShare() === null`.

## Rate-card math worked example

Default card: `platform=1000, org=1000, expert=8000` bps.
Gross: ₹10,000 paise = `1000000`.

```
platformFeePaise      = 1000000 * 1000 / 10000 = 100000
orgSharePaise         = 1000000 * 1000 / 10000 = 100000
consultantSharePaise  = 1000000 * 8000 / 10000 = 800000
```

Integer division. Remainder (always zero because 10000 | gross * bps?
Not generally — the remainder is rounded toward zero; the platform
absorbs ±₹0.01 rounding in its own line).
