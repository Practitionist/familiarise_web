# Required secrets — the scheduled-workflow manifest

## Why this file exists

A GitHub Actions expression that references a secret which does not exist does
not fail. It silently interpolates an empty string, the job runs, and the code
takes whatever "credential missing" branch it has — usually a warning log and an
early return. The job then reports success. That failure mode is invisible from
the Actions UI, invisible from the code, and invisible from the schedule, which
is exactly why it survived two rounds of remediation.

It has already bitten this repository twice. Issue #677 PM-1 found that seven
reconciliation scripts read `RAZORPAY_KEY_SECRET` while the environment defined
`RAZORPAY_SECRET`; the application code was corrected, and the workflows were
then wired to source _both_ environment names from `secrets.RAZORPAY_KEY_SECRET`,
a secret that has never existed. Payout submission, payout-status reconciliation,
payment-status reconciliation and stuck-payout handling therefore ran with empty
Razorpay credentials for months while reporting green. Separately, the money-cron
pager added in #864 has never sent a single alert, because `SLACK_OPS_WEBHOOK_URL`
was wired into all fifty-six workflows of the old fleet but never provisioned. The same secret now also feeds the
application's critical-alert mirror (`lib/observability/ops-chat.ts`, read from the Netlify environment), so it must be set in both places: the GitHub secret and the Netlify environment variable.

This manifest is the fix. Every `secrets.NAME` reference in `.github/workflows/`
must appear in the table below, and `scripts/ci/check-workflow-hygiene.ts` fails
the build when one does not. The table is therefore the single reviewed place
where "this workflow needs this credential, and here is what breaks without it"
is written down.

## How to use it

When you add a secret reference to a workflow, add a row here in the same commit.
When you provision a secret, change its status. When a row's status is `missing`,
the consequence column tells you what is currently silently broken, and that is
the queue an operator should work through before launch.

The status column records whether the secret is set at the **repository** level as
of the last review. It is maintained by hand — the CI guard checks that a
reference is _declared_, not that it is _provisioned_, because a workflow cannot
read the repository's secret list. Confirm the live state with `gh secret list`.

The application side has its own guard. `.env.sample` lists every environment variable the runtime reads, and `__tests__/maintenance/env-sample-coverage.test.ts` fails when code reads a key that is missing from it. When you add a `process.env.X` read, add the key to the matching section of `.env.sample` in the same commit; a value that is a tuning knob or a fixed identity should be a constant in code instead of a new key.

## Manifest

Since 2026-10-31 every registry job runs on the Netlify ticker, so the job credentials below are read
from the runtime host's environment, not from GitHub. Ten workflow files remain, and three of them are
scheduled (`cron-heartbeat.yml`, `db-live-drift.yml`, `security-audit.yml`). `cron-heartbeat.yml` watches only the
Actions-scheduled workflows and reads no application secret beyond the failure-notifier ones. The "Consumers" column
names the workflows that still reference each secret; "jobs (host env)" means only ticker jobs read it,
so the GitHub copy is unused and can be removed after a `gh secret list` check.

## The second surface: Netlify runtime environment

Everything above concerns GitHub Actions secrets, which is where the scheduled
fleet reads its configuration. The running application reads a different store
entirely — the Netlify site environment — and a name can be present in one and
absent from the other. `scripts/ci/check-workflow-hygiene.ts` cannot see the
Netlify side at all, because it parses workflow files rather than querying a
deploy, so this section has to be maintained by hand.

Netlify scopes each variable to a set of deploy contexts, and the default when a
variable is added through the UI is production only. A value that works in
production is therefore not evidence that branch deploys and deploy previews
have it, which is the trap described below.

The one confirmed gap was found on 2026-07-28 while exercising the refund
webhook against the deploy preview for PR #1042. Every request to
`/api/webhooks/razorpay` returned `500 {"error":"Webhook secret not
configured"}`, because `app/api/webhooks/razorpay/route.ts` reads
`process.env.RAZORPAY_WEBHOOK_SECRET` and refuses to verify a signature without
it. The consequence is narrow but worth stating plainly: gateway webhooks cannot
be exercised on a preview, so refund, dispute and payout events can only be
tested against production or locally.

Any other value, including `true`, leaves it off. Not a credential; it is listed because the two surfaces read the same money code, and a value present in only one store would settle the same booking two different ways depending on which surface accrued it. |

Confirming production is a two-minute check and it has never been done, so it is
worth doing before the first live payment rather than after: open the Netlify
site environment, confirm `RAZORPAY_WEBHOOK_SECRET` is present for the
production context, and confirm the value matches the secret configured on the
Razorpay dashboard webhook. An endpoint that 500s on every delivery would be
invisible today, because no live payment has ever produced one.

## The supplier identity on statutory documents

`getPlatformSupplier()` in `lib/pdf/supplier.ts` is the single source of the supplier block printed on every tax invoice, credit note and IRP payload. Its contract is fail-closed: with no valid `PLATFORM_GSTIN` it returns null rather than a placeholder, and callers choose their own failure shape (a 503 on a download route; on a GST job, `platformSupplierForJob()` makes an unset variable a config skip and a set but unusable one a thrown error). A fabricated fallback GSTIN would produce legal-looking invoices that a GST officer would read as impersonation, which is worse than issuing none.

- **The state comes from the GSTIN.** `supplierStateCode()` and `resolveSupplierStateCode` read the first two digits of `PLATFORM_GSTIN` (06 is Haryana). While no GSTIN is set they fall back to the registered office's state in `lib/company.ts`. A GSTIN whose state contradicts the registered office makes `getPlatformSupplier()` return null and `supplierStateCode()` throw, so every GST document refuses instead of guessing, because the documents would print one state and tax as another. There is no environment override.
- **The legal name and address come from `lib/company.ts`.** The supplier is Practitionist (OPC) Private Limited at its registered office in Gurgaon, Haryana (`COMPANY_INFO` and `REGISTERED_OFFICE`), the same entity the public pages and the footer name. The IRP uploader splits the same address into `Addr1`, `Loc` and `Pin`. Rule 46 of the CGST Rules requires the supplier's name, address and GSTIN as registered, so if the GSTIN's principal place of business differs from the registered office, change `lib/company.ts` by pull request, never by environment.
- **Where the variable must be set.** It is a per-context Netlify variable, so production needs its own value; a value set only for deploy previews leaves production returning 503. Previews share the production database, so a real GSTIN on a preview lets a preview mint real statutory invoice numbers; decide that deliberately.
- **Smoke test.** After setting it, an org admin downloading a voided org invoice should receive 200 `application/pdf` starting with `%PDF`; repeat for a consumer invoice and credit note once such rows exist, and confirm the next monthly outward-supplies register mints.

## PDF rendering needs its fonts traced into the function

The four statutory PDF routes (consumer invoice, consumer credit note, org invoice, org credit note) render with `pdfkit`, which loads its standard-font metrics through `createRequire()('#standard-fonts/*')`, a package `imports` subpath the Next file tracer cannot follow. Without help the font files are absent from the deployed function, the render step throws `MODULE_NOT_FOUND` as an unhandled rejection, and the Lambda crashes, so the client sees Netlify's bare 502 `An unknown error has occurred` instead of the route's own JSON error. Cached PDFs still work, so the failure appears only on a first render or after the 24-hour cache window.

`next.config.mjs` therefore lists `PDFKIT_FONT_FILES` (the package manifest and `js/standard-fonts/**`) in `outputFileTracingIncludes` for all four routes, next to the Devanagari font and the `react` package they already needed. A new PDF route, or a new library that loads files by a computed or `#` path, needs the same entry. The symptom to recognise is a 502 without a JSON body that only occurs on a cache miss.

## Related

The companion guard `scripts/ci/check-workflow-hygiene.ts` also enforces that no
two scheduled workflows start on the same minute of the same hour. Start-time
collisions do not cause runtime conflicts — every job in this fleet completes in
about sixty seconds — but simultaneous starts contend for the same Supavisor
connection pool, which is the failure mode behind #932.

## Deprecated & Superseded Approaches

- **A hard-coded fallback GSTIN**: the supplier used to fall back to a dummy GSTIN when the variable was unset, producing invoices that carried a fabricated number. Superseded by the fail-closed null above; never reintroduce a default.
- **Assuming the Netlify build traces every file a route reads**: a file the tracer cannot resolve is missing from the deployed function. The known cases, the Devanagari fonts read through `path.join(process.cwd(), …)`, PDFKit's `#standard-fonts/*` import-map files and `react/jsx-runtime`, are named in `outputFileTracingIncludes`, and any new runtime file read of that shape needs an entry there too.
- **Env switches for run inputs and escape hatches**: `DPDP_SWEEPER_DELETE`, `PLATFORM_INVOICE_PREFIX`, `CLEARTAX_GSTIN`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` and the `RAZORPAY_KEY_SECRET` fallback no longer exist. The consent-retention sweeper is count-only by default (`?delete=1` deletes), the invoice prefix is a constant in `lib/company.ts`, the IRP uses `PLATFORM_GSTIN`, and nothing reads the anon key. Delete any leftover copies from GitHub Actions and Netlify.
