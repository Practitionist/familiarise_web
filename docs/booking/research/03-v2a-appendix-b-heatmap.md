## 2. Scenario traces: what the cell shows vs what the writers accept

### (a) Normal week (consultant in IST, viewer in IST, consultation)

- The weekly row is projected through `weeklyRowIntervalsInRange`. Segments start on the grid because IST midnight is 18:30Z, which is on-grid. Cells are UTC `:00/:30`, and `serverCells.get` matches `dayRows`. **Consistent.** VERIFIED (`intervals.ts:226-278, 355-404`; `grid-zone.ts:151-172`).
- **Exception: the last atom of the visible window is never painted.** The client sends `end = nextDayStart − 1 ms` (`useCalendarData.ts:390-404` → `grid-zone.ts:107`). The route clips the occurrence to that end (`intervals.ts:263-265`), so the final segment is `[23:30, 23:59:59.999)`. That fails `currentStart + 30min <= end` (`intervals.ts:709`), so the Saturday 23:30 atom (or the cycle's last-day 23:30 atom) shows "Unavailable" even though checkout accepts it. Mobile pages have the same problem: `dayListBounds` → `dayRangeBounds` (`day-list.ts:120-126`). The expert page avoids it with `zonedWeekWindow` (pinned by `__tests__/scheduling/weekly-dst-projection.test.ts:192-210`). VERIFIED → **B-09**.

### (b) DST week: America/New_York consultant, Asia/Kathmandu (+05:45) viewer

- **Projection is correct.** Weekly rows resolve per local date. On fall-back, a 1:00–3:00 row spans 3 real hours; on spring-forward, the gap is skipped (`utils/schedule/weekly-projection.ts:227-249, 267-308`). Checkout's `createWeeklyCoverage` uses the same generator (`weekly-projection.ts:333-359`). VERIFIED.
- **Client rows are correct.** For Kathmandu, `dayStartInstant` is 18:15Z. Rows run from ceil 18:30Z (labelled 12:15 am) to 18:00Z (11:45 pm), 48 per day, all on UTC `:00/:30`. Nepal has no DST, so there are no missing or duplicated rows. A New York viewer on 1 Nov gets 50 rows, with "1:00 am (2nd)" (`grid-zone.ts:134-174`). VERIFIED.
- **Server cells are off-grid for a :45 viewer. This is the bug.** `splitSlotsByDay` cuts every published block at the **viewer's** local midnight, which is 18:15Z for Kathmandu (`intervals.ts:365-376`). `breakDownSlotsByDuration` then slides 30-min windows **from each segment's own start** (`intervals.ts:707-744`). `processWeeklySlots` also clips a block to the request's `startDate`, and the Kathmandu week start is 18:15Z (`intervals.ts:260-262`). Simulation of the New York row 09:00–17:00 EST (14:00–22:00Z) on Sat 7 Nov 2026, viewed in Kathmandu:
  - Segments are `[14:00Z, 18:15Z)` and `[18:15Z, 22:00Z)`.
  - Cells come out as 14:00 … 17:30, then **18:15, 18:45, 19:15, … 21:15**. The 18:00Z atom is lost, and every post-midnight cell is `:15/:45` UTC.
  - The same input in Asia/Kolkata gives clean `:00/:30` cells.
- **What each surface does with those cells:**
  - **Heat map.** `describeAtom` looks up `serverCells.get(18:30Z)`, which is undefined, so the cell paints "Unavailable" (`week-grid-model.ts:84-86`). The consultant's whole post-midnight (Kathmandu) supply is invisible. This loses bookable supply.
  - **Expert page and mobile list.** They do offer the `:15Z` windows (`booking-windows.ts:73-100`; `day-list.ts:155-194`). In Kathmandu these read as tidy local times like "12:00 am – 1:00 am". Checkout and request-for-approval then refuse them with **`SLOT_NOT_ON_GRID` "Times start on the hour or half hour"** (`slot-validation.ts:47-48`), although the user picked a time that is on the hour locally. **Unbookable, with a self-contradicting error.** VERIFIED (code plus simulation) → **B-01**.
  - The same applies to Australia/Eucla (+08:45) and Pacific/Chatham (+12:45/+13:45). There are no tests: neither `__tests__/scheduling/weekly-dst-projection.test.ts` nor `__tests__/booking-algorithm/availability-grid-snap.test.ts` runs `processAvailabilitySlots` with a `:15/:45` viewer zone. `__tests__/scheduling/grid-zone-dst.test.ts:53` only tests the client rows.
- **Footer zone label uses today's offset, not the viewed week's.** `footerZoneLine(now, …)` (`components/scheduling/UnifiedCalendar.tsx:1086`) calls `zoneDisplayLabel(now)` (`lib/time/viewer-zone.ts:124-131`). A New York viewer on 30 Oct looking at the week of 1–7 Nov reads "EDT (UTC−04:00)" over cells that are mostly EST. VERIFIED → **B-14**.
- The cell's accessible name for the repeated fall-back hour drops "(2nd)". The row header has it (`grid-zone.ts:170`), but the cell label is `stateLabel · formatDateTimeLabel(start)` (`components/scheduling/WeekGrid.tsx:146-152`), so two cells read identically. SUSPECTED (I didn't open `formatDateTimeLabel`) → **B-17**.

### (c) Lapsed tentative hold vs live hold

- **Live hold** (PENDING request, live checkout hold, APPROVED_PENDING_PAYMENT inside its pay window) paints "Booked" with a lock. There is no "held" state (HLD `docs/start-here/01-booking-system-hld.md:94`). Checkout refuses it, so this is consistent. VERIFIED (`route.ts:808-831`).
- **Lapsed hold** (every payment EXPIRED/FAILED/PENDING-past-expiry, or a DIRECT_CHECKOUT PENDING) is dropped by `isOccupiedByLiveAppointment` and becomes Free. Checkout's `buildDeadHoldFilter` agrees (pinned by `hold-expiry-predicate.test.ts`, `references/availability.md` §5). `nextHoldExpiry` is in the ETag, so a 304 can't freeze it. **Lag:** up to the 60 s poll plus `max-age=30`. That's acceptable (ADR 16).
- **Mismatch 1: the buyer's own hold.** The consultee grid adds the consultee's own occupying bookings as busy (`route.ts:733-751`), so a buyer who backed out of the payment page sees their own time as "taken" (on the expert page it's counted under "N times on this day are already taken", `slot-list-policy.ts:20-26`). Checkout, however, excludes `selfHoldAppointmentIds` (#1463, `lib/payments/checkout/revalidate.ts:332-341, 366-371`) and would accept the re-buy. SUSPECTED (I didn't trace `validateSlotAvailability` internals) → **B-08**.
- **Mismatch 2: the consultee's own PENDING request.** It shows as an anonymous "taken" time with no "You requested this" marker. That's the same root cause → **B-08**.

### (d) Subscription whose current cycle is full ("Limit reached")

- The overlay is applied when `remainingThisCycle === 0`: every cell overlapping `[windowStart, windowEnd)` gets `limitReached` (`grid-quota.ts:118-126`). `windowStart = max(periodStart, lastHeldEnd, now)` (`lib/booking/entitlement.ts:275-287`). Footer copy: "2 of 3 this week · next opens Sun 8 Mar" (`grid-quota.ts:136-150`).
- **Allocate grid.** `allowedStart/End` equal the cycle window (`lib/data/allocation-request.ts:165-166`), and that's the same window the allocator enforces (`event-data.ts:458-459`). **Consistent.** VERIFIED.
- **Consultee reschedule of a subscription (desktop and mobile).** `allowedStart = schedulingPeriodStartsAt` and `allowedEnd = planEnd` (`lib/scheduling/time-picker-subject.ts:125-130`). With `releasing`, `remainingThisCycle = rescheduling > 0` (`grid-quota.ts:95`), so **no cell is ever `limitReached`**. Cells after `windowEnd` (now or last completed session + about 7 days, `entitlement.ts:275-300`) paint **Free**. The picker hint promises "Green means your consultant is free — choosing one of those confirms straight away" (`components/scheduling/time-picker-policy.ts:192-193`). The auto-confirm, though, is a manual allocate inside the cycle window (`reschedule-auto-confirm.ts:71-78`; `ScheduleValidationService.ts:346-353`). It fails with `VALIDATION_FAILED`/`VALIDATION_ERROR`, which is **final** (`reschedule-proposals.ts:307-317`), so the proposed times are dropped (`reschedule/route.ts:881-884`). The session stays released, waiting on the consultant. VERIFIED → **B-03**.
- **Mobile, cycle full.** The quota footer isn't read at all. The list shows "No free times in these two weeks. Try the next two weeks." (`MobileDayListPicker.tsx:361-367`), which looks like a sparse expert, not a plan limit. VERIFIED → **B-11**.
- `limitReached` has one hint for three causes: "This plan's sessions for that week or day are already used." (`interval-status-tokens.ts:147-155`). It's also painted for at-or-after plan-end cells and for `allBooked` (`grid-quota.ts:116-117`). VERIFIED → **B-12**.

### (e) Plan end (`planEndsAt`) and incident extension

- The route reads the stored `planEndsAt` (`route.ts:408, 447`), which incident extensions move. `subscriptionEntitlement` uses it (`entitlement.ts:288-300`), `cellLimitReached` paints `endMs > planEndsAt` (`grid-quota.ts:116`), and the allocator refuses `PERIOD_ENDED` once `windowEnd <= windowStart` (`event-data.ts:443-451`). The reschedule picker's `allowedEnd = subscriptionPlanEnd(subscription)` (`time-picker-subject.ts:128-130`). The detail payload includes every subscription scalar (`lib/data/appointment-detail.ts:119-122`), so the extension is honoured. **Consistent.** VERIFIED.
- Painting: `outsidePeriod` outranks `limitReached` (`interval-status-tokens.ts:308-310`), so on both pickers the post-plan-end cells read "Outside period". That's acceptable, but the extension itself is never shown ("Plan now ends Fri 6 Mar — extended 2 days after the 28 Feb outage") → **B-16** (design).

### (f) Lead-time trim (`lib/booking/lead-time.ts`)

- The grid uses **one** threshold: `MINIMUM_BOOKING_LEAD_TIME_MS` (15 min) (`route.ts:1098, 1114`). The client copy hard-codes the same number: the token hint "Starts in less than 15 minutes." (`interval-status-tokens.ts:156-158`) and the toast (`UnifiedCalendar.tsx:1254-1259`).
- The writers use **three** thresholds:
  1. 15 min for checkout and settled allocation.
  2. **2 h** for an unpaid approval or allocation (`lead-time.ts:8-13`).
  3. **24 h** for reschedule proposals (`reschedule/route.ts:457-469`).
- Mismatches:
  - **Consultation in REQUEST mode, priced and unpaid.** The expert page offers a cell 15 min–2 h out (`booking-windows.ts:81, 97`), and request-for-approval accepts it (`schemas/slots.ts:55-68`). The consultant can **never approve it** (`TOO_CLOSE_TO_START`, `consultations/[consultationId]/route.ts:442`). Meanwhile the dead request **holds the expert's calendar** (PENDING occupies) and uses one of the consultee's 3 request slots (`request-for-approval/route.ts:394-406`). VERIFIED → **B-04**.
  - **Consultant allocating an unpaid request.** `allocatePolicy.minLeadHours = 0` (`time-picker-policy.ts:165-178`). Cells 15 min–2 h out paint Free, and the allocator refuses with `TOO_CLOSE_TO_START`. VERIFIED → **B-05**.
  - **Reschedule (both roles, desktop and mobile).** Cells 15 min–24 h out paint Free with "Green … confirms straight away", and the server answers 400 `PROPOSAL_TOO_SOON` (`reschedule/route.ts:457-469`). `MobileDayListPicker` supports `minLeadHours` (`MobileDayListPicker.tsx:51-52, 142`; `day-list.ts:181-185`), but `TimePicker` **doesn't pass it** (`components/scheduling/TimePicker.tsx:383-400`). `UnifiedCalendar` has no such prop (`UnifiedCalendar.tsx:432-486`). The amber note only talks about releasing, not about new times (`TimePicker.tsx:408-416`). VERIFIED → **B-02**.
- **Stale `tooSoon` on desktop.** The flag is computed once per server answer. The client never recomputes it (`week-grid-model.ts:97`, `selectionConflicts` `:236-241`), so between polls, and especially after the 5-min failure backoff, a cell that slid inside 15 min stays Free and checkout answers `SLOT_TOO_SOON`. Mobile recomputes it (`day-list.ts:181-185`). There's also a boundary difference: the grid flags `start < now+15m` (`route.ts:1114`), while the edge refuses `start <= now+15m` (`slot-validation.ts:51`). VERIFIED → **B-13**.
- **The in-progress half-hour** (start < now < end) paints "Too soon — Starts in less than 15 minutes" although it already started (`isInPast = endMs < now`, `week-grid-model.ts:90`; precedence `interval-status-tokens.ts:307-309`). VERIFIED → **B-18**.

### (g) Off-grid legacy occurrences (start not on the 30-min atom)

- Inside published hours: an occurrence at 10:15–10:45 overlaps the 10:00 and 10:30 cells at 50% each, so both are `partially-booked` (`intervals.ts:515-525`). Outside published hours: orphan cells snap to the UTC atom and are `fully-booked` (`intervals.ts:1011-1036`).
  - **Heat map.** `partiallyBooked` isn't interactive; the toast says "Part of this half-hour is taken — choose another time." (`UnifiedCalendar.tsx:1270-1276`). That's consistent with the writers.
  - **Expert page.** `isBookableWindow` only drops `fully-booked` (`booking-windows.ts:103-110`). For a **30-min plan**, a partially booked atom becomes a single-atom window with `isAllocated = true`. It's **listed as bookable with a "Request" tag** (`slot-list-policy.ts:36-41`). Request-for-approval runs `checkSlotAvailability` → `validateNoConflicts` and refuses with **"Slot no longer available"** `SLOT_TAKEN` (`request-for-approval/route.ts:476-507`; `ScheduleValidationService.ts:173-189`). Checkout refuses too. VERIFIED → **B-06**.
  - For plans of 60 min or more the partial atom can't host a window, because `mergeConsecutiveSlots` only merges available atoms (`intervals.ts:628-639`). So B-06 is limited to 30-min plans.
- **Off-grid availability rows** (legacy, before the GRID contract) produce `:15/:45` cells. On the heat map they're invisible; on the expert page they're offered and then refused `SLOT_NOT_ON_GRID` (`lib/scheduling/availability-contract.ts:136-147` documents this). New writes are refused with `GRID`. Pre-reset data only → **B-19**.

### (h) Mobile day list paging (`MobileDayListPicker.tsx`)

- Pages are 14 days from the anchor, which is the latest of now, `allowedStart` and the focused session, clamped to `allowedEnd` (`day-list.ts:132-142`). Paging is floored at today/`allowedStart` (`MobileDayListPicker.tsx:102-113`). A pick survives paging, and stale picks are dropped only inside the current read range (`day-list.ts:251-266`). VERIFIED.
- Mismatches:
  1. The **last atom of each 14-day page** is dropped (the −1 ms window, **B-09**). The next page starts at the next day, so that atom is never offered.
  2. There's no 24 h reschedule notice (**B-02**).
  3. The subscription upper bound is plan end, not the cycle (**B-03**).
  4. There's no quota footer or limit explanation (**B-11**).
  5. `dayCap` days are scheduling-zone days (`TimePicker.tsx:291-301`), but chips are display-zone days. A Kathmandu consultee picking 11:45 pm and 12:15 am on two different chips can hit "You already picked a time on this day" (`MobileDayListPicker.tsx:348-353`) for what looks like two days, or the reverse. VERIFIED (logic) → **B-15**.
  6. Empty-state copy never says _why_: booked, too soon, plan limit or outside the period (`MobileDayListPicker.tsx:361-367`) → **B-11**.
  7. Chip a11y is good (`role=radio`, `aria-label` "Thu 24 Sep, 3 times free", arrow-key roving). Disabled chips are skipped (`MobileDayListPicker.tsx:281-318`), which is fine.

### (i) Legend and icons vs what the cell means, and accessibility

- **One vocabulary.** The legend and cells share one token table (`interval-status-tokens.ts:89-203`). The legend shows only painted keys (`legendKeysFor` `:342-348`), has an sr-only "Label: hint, N half-hours this week" (`components/scheduling/SlotStatusLegend.tsx:96-98`), and icons are `aria-hidden` (`components/scheduling/SlotStatusIcon.tsx:22-28`). The cell's accessible name is "State · Requested · date-time" (`WeekGrid.tsx:146-158`), with `aria-disabled` for non-interactive cells, so they stay focusable and a click explains via toast. Good baseline. VERIFIED.
- **Colour-only meaning remains between two states.**
  - "Partly booked" uses `HATCH_AMBER` (45°, 1.5px/6px) and "Outside period" uses `HATCH_SLATE` (45°, 2px/7px), same angle (`interval-status-tokens.ts:32-39`). In greyscale or for colour-blind users they're the same diagonal stripe, which breaks the file's own promise at `:5-6`.
  - "Too soon" and "Limit reached" share fill and border colours (slate-100/slate-500) and differ only by a dotted border vs a 1px cross-hatch at 28px cell height (`:147-164`; cell `h-7` `:257-258`). That's a weak cue.
  - VERIFIED → **B-10**.
- **Hint copy contradicts behaviour.**
  - "Too soon: Starts in less than 15 minutes" is wrong for reschedule (24 h), unpaid allocation (2 h) and the in-progress cell.
  - "Limit reached" uses one hint for weekly, per-day, all-booked and plan-end causes.
  - "Partly booked: choose another time" on the heat map vs a "Request" CTA on the expert page for the same server state.

- **Counts mislead.** The legend shows "Free · 12" (visual only) counting half-hours, not sessions. The month view shows "3h free" summing free half-hours, ignoring `outsidePeriod` and session length, so a day with six scattered half-hours reads "3h free" for a 60-min plan with zero fitting sessions (`UnifiedCalendar.tsx:1338-1354, 1400-1408`; `SlotStatusLegend.tsx:91-95`). VERIFIED → **B-20**.
- **Tooltips.** On booked cells the tooltip replaces `title`, so the hint isn't in `title` (`WeekGrid.tsx:159, 185-200`). Touch users get no hint for booked cells. Minor.

## 4. Design options

### Option L: one lead-time source for every grid (fixes B-02, B-04, B-05, B-12, B-13)

- **L1 (client only).** Thread `minLeadMs` through `TimePickerPolicy` → `UnifiedCalendar` / `MobileDayListPicker` → `AtomContext`, and recompute on the client.
  - Pros: no API change.
  - Cons: the server `tooSoon` stays 15 min, so the expert page and the trial picker drift again. The 304/ETag doesn't fold the context.
- **L2 (server-authoritative, recommended).** The route accepts `purpose=book|request|allocate|reschedule` (plus the event id it already gets), resolves the lead itself with `leadTimeFor({settled})`, `RESCHEDULE_MIN_LEAD_HOURS` or the 15-min floor, and returns `leadMs` at the top level and `tooSoon` per cell.
  - The ETag folds `purpose` and `leadBucket(leadMs)`.
  - The client also recomputes against `leadMs` between polls (B-13).
  - Pros: one oracle; the expert page, mobile, desktop and trial picker all agree; copy is generated from `leadMs`.
  - Cons: one more cache-key dimension. That's cheap, since the route already folds `subscriptionId` and `releasing`.
- **Recommendation: L2.** Keep `MINIMUM_BOOKING_LEAD_TIME_MS` as the floor. Add a contract test enumerating every writer's lead threshold, so a new writer can't add a fourth number silently.

### Option C: cell generation (fixes B-01, B-09, B-19)

- **C1.** Patch `breakDownSlotsByDuration` to snap each segment start up to the UTC atom.
  - Minimal, but `splitSlotsByDay` still cuts at 18:15Z, which loses the straddling 18:00Z atom (23:45–00:15 local) on both sides of the cut.
- **C2 (recommended).** Replace split-then-slide with **atom enumeration**. For each published interval, iterate `atom = ceil(start/ATOM)…` while `atom+ATOM <= end`. Key each atom by `loc.dateKey(atomStart)`. Status, flags and orphans then work per atom. This is what the client `dayRows` already assumes ("every atom whose start falls on that calendar date", `grid-zone.ts:129-133`), and it makes the `processAvailabilitySlots` ↔ `dayRows` contract structural. It also removes the off-grid cells for legacy off-grid rows (their edges just aren't offered).
- Pair it with the exclusive window end (B-09), and with an assertion in the route that every emitted cell satisfies `startMs % ATOM === 0` (via `reportStandingFinding` once per day if violated).

### Option R: what a subscription reschedule may target (B-03)

- **R1 (recommended for now).** The grid matches today's server: clamp to the current cycle window, computed with releasing counted as released. Copy for other cells: "Next cycle".
- **R2.** Let a reschedule move a session anywhere before plan end, as long as the per-day cap holds and the target cycle has room. This needs an entitlement change, since the allocator checks only one window. It's better for users ("move my Tuesday session to next week"), but it's a policy change. Out of scope for a grid fix; flag it to product.

### Option H: should holds look different from bookings? (B-08)

- Today every hold reads "Booked" (HLD:94). That's correct for strangers: it doesn't leak that someone is mid-checkout, and "may free up" invites refresh-camping.
- **Recommend:** keep strangers' holds as "Booked". Add **only** the viewer's own hold or request as a distinct, actionable `yours` state (see B-08). No new information is leaked, and the dead end disappears.

### Option P: "Partly booked" for buyers (B-06, B-10)

- A buyer can never book part of a half-hour, so "Partly booked" is engineer vocabulary.
- **Recommend:** on buyer surfaces (expert page, mobile list, trial picker), collapse it into **Booked**, and keep "Partly booked" only on the consultant's allocate grid, where the tooltip explains the overlapping session. That shrinks `BUYER_LEGEND_KEYS` (`interval-status-tokens.ts:315-320`) to Free / Booked / Too soon (+ "Your hold").

### Option Q: plan-limit explanation on mobile (B-11)

- Reuse `quotaFooterText` as a sticky line under the day chips, and make the empty state reason-aware (copy in B-11). Don't add a new grid state on mobile: a list with "why nothing is here" text is more legible than greyed rows.
