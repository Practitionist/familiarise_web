### 1.1 Multi-week subscription allocation — how it actually works today

**Data model (prisma/schema.prisma)**

**Entitlement size.** `planTotalSessions = sessionsPerWeek × durationInMonths × 4` (`lib/booking/entitlement.ts:227-230`). So "6 months × 3/week" is **72 sessions, not 78**; but `planEndOf` gives a real calendar span (~26 weeks, `entitlement.ts:142-161`). Cycles = `ceil(72/3) = 24` (`entitlement.ts:262-265`), so there are ~2 weeks of slack between the last cycle and the plan end. VERIFIED.

**The one counter — `subscriptionEntitlement`** (`lib/booking/entitlement.ts:249-325`), VERIFIED:

- `completed` = live occurrences in `COMPLETED|UNVERIFIED` (`:71`, `:88-94`, `:254`); `scheduled` = `SCHEDULED && !isTentative` (`:96-98`, `:255`). `VOIDED` is live but counts as neither → it frees a session back into the cycle.
- `ordinal = min(floor(completed / capacity), count-1)` (`:265`). **The cycle advances only when sessions are _delivered_, not when time passes.**
- `filled = completed − ordinal×capacity + scheduled` (`:268`); `nextBatch = min(capThisCycle − filled, remaining)` if the window is non-empty (`:301-304`).
- `windowStart = max(schedulingPeriodStartsAt, last end of completed∪scheduled, now)` (`:275-287`) — during a reschedule only completed ends anchor (`:271-279`).
- `windowEnd = min(cycleEnd(windowStart) [midnight after 7th zone-day], planEndsAt)` (`:124-133`, `:295-300`).
- Consequence: the "week" is a **rolling 7-day window anchored on the last session end or on _now_**, not a calendar week and not "week N of the plan".

**What the allocator accepts.** `fetchEventData` (subscription arm) recomputes the entitlement and passes `cycleTargetSessions = nextBatch`, `schedulingPeriodStartsAt = cycle.windowStart`, `schedulingPeriodEndsAt = cycle.windowEnd` into the search config (`lib/booking/allocation/event-data.ts:432-461`). An empty window throws `PERIOD_ENDED` "This plan ended on …, so no more sessions can be booked. Any unused paid sessions are refunded automatically." (`event-data.ts:443-451`). `calculateRequiredSlots` returns `cycleTargetSessions × slotsPerCall` (`utils/scheduling-engine/ScheduleCalculationService.ts:437-438`). With held sessions a subscription allocation is automatically a _top-up_ (additive, never a replan): `isSubscriptionTopUp` (`lib/booking/allocation/counts.ts:61-71`), target `existingConfirmed + nextBatch` (`counts.ts:78-94`), `requiredSlots = (target − existingConfirmed) × slotsPerCall` (`modes/auto.ts:355-357`). VERIFIED.

**Consultant journey for a 6-month × 3/week plan (VERIFIED unless marked):**

1. Consultee pays; subscription is `PENDING` with no occurrences. Consultant must allocate **cycle 1 within 48 h** of capture or the buyer is refunded in full (`scripts/appointments/expire-stale-requests.ts:118-122` `PAID_UNALLOCATED_HOURS = 48`; cohort `unscheduledPaidPlanWhere` `:257-268`). Consultant gets a nudge bell: "…Schedule cycle 1 within 48h or the buyer is refunded in full." (`lib/novu/templates/b2c.ts:193`). Dashboard action "Schedule cycle 1" with deadline (`lib/dashboard/money-state.ts:721-726`, deadline `:263-275`).
2. Allocator places **only `nextBatch` (≤3) sessions inside the current rolling 7-day window**. Manual mode refuses more: "This cycle takes N sessions. Pick no more than that." (`lib/booking/allocation/modes/manual.ts:371-390`). Subscription moves `PENDING → APPROVED` ("1st Cycle Allocated", `docs/start-here/01-booking-system-hld.md:271-272`).
3. Until **all 3 of those sessions have been delivered and classified** (`COMPLETED/UNVERIFIED`, which happens ≥1 h after each session end via `auto-complete-appointments`, HLD §7 `:342`), `nextBatch = 0`. The allocate footer reads "This cycle is set · next opens after 8 Mar · 4 of 12 booked" (`entitlement.ts:348-349`).
4. When the last session of the cycle completes, the completion path calls `settleSubscriptionCycleWithNotice` (`lib/booking/subscription-cycle.ts:82-235`): stamps earnings holds for matured tranches (`:150-189`), and if nothing is scheduled and entitlement remains (`:191-194`) sends the **consultee only** a bell + email: "Cycle {n} of {plan} is done — {consultant} will schedule your next {N} sessions ({remaining} left)." (`subscription-cycle.ts:196-234`, template `lib/novu/templates/b2c.ts:383-394`, recipients `[consulteeUserId]` `:225`).
5. **The consultant receives no notification.** The only consultant signals are passive: Requests inbox "Next cycle" chip / "Next cycle open" badge (`components/dashboard/shared/requests/labels.ts:30-36,80-85`, source `lib/data/requests-inbox.ts:830-881`, predicate `lib/data/needs-you.ts:236-263`), and the booking card action "Schedule the next N" **with no deadline** (`money-state.ts:727-731`). VERIFIED (grep of `lib/novu/templates`, `lib/email/senders/booking.ts:812-863` finds no consultant-side next-cycle notice).
6. The consultant must therefore come back **once per cycle — ~24 times over 6 months** — and can never put more than one week on the consultee's calendar.
7. **Hourly top-up sweep** (`reconcile-occurrence-availability`, every 60 min: `lib/cron/schedule.ts:275`, registry `lib/cron/cleanup-registry.ts:1690-1715`) runs `topUpIncompleteEvents` (`scripts/appointments/reconcile-occurrence-availability.ts:875-991`): candidates are APPROVED subscriptions with ≥1 confirmed and no tentative occurrence whose derived `nextBatch > 0` (`:651-733`). **But a candidate is only attempted if the consultant's availability rows changed after the subscription's `updatedAt`** (`:898-905`). Completing sessions does not touch `Subscription.updatedAt` (the completion path only reads the subscription, `subscription-cycle.ts:93-133`), so in the steady state (consultant publishes weekly hours once) **the sweep never auto-places the next cycle**. It is a "retry after you opened more hours" mechanism, not a cycle scheduler. Limits: 25 events / 60 s / 3×200 scan pages per run (`:571-578`). VERIFIED.
8. **If the consultant never schedules the next cycle:** no deadline, no escalation, no strike (strikes are cancel/no-show only, `.claude/skills/booking/SKILL.md:337`), no expiry — the 30-day `expireApprovedUnallocatedSubscriptions` arm only matches subscriptions with **zero** confirmed occurrences ever (`expire-stale-requests.ts:146-152` `NO_LIVE_SESSION`, `:241-247`, `:1115-1200`). The plan simply runs to `planEndsAt`, then `settle-cancelled-sessions` completes it and refunds the never-placed sessions pro rata (`scripts/appointments/settle-cancelled-sessions.ts:1000-1078`, share `:1262-1285`), and both parties get the generic `APPOINTMENT_COMPLETED` bell (`:1201-1222`). A consultee who stopped getting sessions in week 3 waits until month 6 for money back.
9. **Drift:** because `windowStart` floors at `now`, every day the consultant is late shifts all later windows; the last windows get clipped by `planEndsAt` (`entitlement.ts:295-300`) while `nextBatch` stays at full capacity (`:301-304`), so the final cycle can demand 3 sessions in a 1-day window → `SLOT_SHORTAGE`/`DAILY_LIMIT`, then a pro-rata refund at plan end. Conversely, sessions bunched at a window's start let the next window open early (Mon/Tue/Wed then Wed-evening/Thu/Fri = 6 sessions in 5 days); there is no minimum spacing. VERIFIED (arithmetic on `:265-304`).

**What the consultee sees between cycles.** Booking state "Awaiting schedule" (`money-state.ts:305-310`) with the sentence **"Cycle done · schedule the next 3."** — `deriveBooking` is viewer-agnostic (`money-state.ts:390-397`, called without viewer `:952`), so the consultee is shown an imperative meant for the consultant (`money-state.ts:465-469`). Their calendar is empty beyond the current week. VERIFIED.

**Reschedule within cycle.** While a release is open, `rescheduling > 0` re-anchors the window on completed sessions only so the whole active cycle is pickable (`entitlement.ts:271-279`) and the heading targets the released count (`:342`). Grid overlay counts `releasing` ids as freed (`.claude/skills/booking/references/availability.md:175-185`; `lib/scheduling/grid-quota.ts:95`).

**Returns / voids / incidents.** Return ≥24 h ahead, ≤2 per plan, each moves `planEndsAt` +7 d (`.claude/skills/booking/references/money-boundary.md:426-438`). Declared incident on a subscription session: session returns to allowance and plan end +7 d (HLD `:370`). A `VOIDED` session drops out of `completed` so the cycle does not advance and `nextBatch` gains 1 → make-up must fit the _current_ rolling window (`entitlement.ts:254-268`). Mid-plan voids are not refunded; they settle at plan end (`money-boundary.md:506-513`).

### 1.2 Classes (multi-week series)

- Class rows keep a real `schedulingPeriodStartsAt/EndsAt` (top-up candidate filter `schedulingPeriodEndsAt: { gt: now }`, `reconcile-occurrence-availability.ts:736-822`). A class owes the plan's **whole total** at once (`counts.ts:73-94`), so a class is allocated as a full series up front (auto window "whole period (sub/class)", HLD `:101-103`); `allowPartial` + the hourly top-up fill the shortfall after availability changes (`reconcile-occurrence-availability.ts:791-818`). VERIFIED.
- Class occurrence count uses `notIn: ["CANCELLED","RESCHEDULED"]` rows (`:770-783`), i.e. VOIDED counts as confirmed (the void remedy is a 14-day make-up or refund, HLD `:325`).

### 1.3 Allocation algorithms (auto / manual / requested)

**Entry & authz** — one handler `lib/scheduling/allocate-route.ts`: auth → participant check → `resolveEventHostActor` (403 `ALLOCATE_FORBIDDEN`, "Only the expert or their organisation can set times for this booking.", `:78-93`) → `canOverride = hostActor !== "host-org"` (`:95`) → limiter → Zod → `allocate()` with `override/allowPartial/topUp` **silently dropped** for host-org operators (`:144-149`). Unknown 500 copy: "Couldn't save these times — check whether they appear, then retry." (`:289-301`). VERIFIED.

**Auto** (`lib/booking/allocation/modes/auto.ts:95-520`), VERIFIED:

- Lock order consultant (`lockAutoAllocate`, `:141`) → read/search/validate outside txn (`:170-176`) → consultee lock + `tryLockSlotBatch` that **never waits** (`:461-476`) → on held atoms, exclude them and re-search, max `MAX_ALLOCATION_RESEARCHES = 2` (`lib/booking/allocation/slot-batch.ts:26`) under one 10 s budget (`search/constants.ts:35`, `auto.ts:390-395`) → `AllocationRaceError` "These times are being booked right now. Please try again in a moment." (`slot-batch.ts:39-45`, `auto.ts:431-434,481-482`).
- Search for subs/classes (`search/find-available-slots.ts:357-698`): **greedy earliest-fit day walk** from the window start in **UTC days** (`:620-645`), placing up to `maxPerDay` per day (`:638-643`); per-day cap = 1 for subscriptions, 2 for classes (`utils/scheduling-engine/sessionCaps.ts:11-15`); the calendar-week cap applies **to classes only** — "A subscription's weekly limit is its rolling cycle" (`find-available-slots.ts:477-495`); the validator's weekly check is likewise `validateClassWeeklyLimits` (`utils/scheduling-engine/ScheduleValidationService.ts:1553-1627`).
- Preference (#1065) reorders, never filters: two sweeps, preferred-only then all (`find-available-slots.ts:647-653`); ties break chronologically.
- Row order: weekly rows sorted by next occurrence after `now` (`search/recurrence.ts:10-23`); rows are loaded **without `orderBy`** (`lib/booking/allocation/event-data.ts:284`), so equal-key ties fall back to Postgres heap order. Custom rows sorted by `startsAt` (`find-available-slots.ts:316-322`).
- Shortage copy: "Only {n} of {m} sessions fit in the free times. Open up more availability, or schedule the ones that fit now." (`:690-694`); period-ended copy: "This plan's scheduling period has ended. Extend the period on the plan to place more sessions." (`:664-674`).
- `allowPartial` returns the placeable prefix (`:684-688`); top-up + partial with zero placeable → silent `noChange` (`auto.ts:428-430`, `:264-279`).

**Manual** (`modes/manual.ts`): recurring top-up must pick ≤ this cycle's batch: "This cycle takes N sessions. Pick no more than that." / fewer → `SlotShortageError` "This cycle takes N; you picked M." unless `allowPartial` (`:370-400`). Reschedule must pick exactly the released count (`:353-369`). VERIFIED.

**Requested** (`modes/use-requested.ts`): webinars/classes refused "Only consultations and plans have times requested by the client. Pick the times instead." (`:98-105`); "No requested slots found" (`:177-179`, raw, untyped); refuses released rows (`:211-221`); atom-coverage check "The requested times changed since this page loaded. Reload and try again." (`:235-250`). For subscriptions `requestedSlots` is built from **all** non-void occurrences incl. completed ones (`event-data.ts:464-466`). VERIFIED.

**Refusal copy** (`lib/booking/allocation/refusal-copy.ts:11-28`): first tagged finding wins; times are stripped from user copy (`:1-3`). Toast titles keyed by `errorCode` (`lib/scheduling/allocationMessages.ts:310-395`); success copy "Sessions scheduled / All sessions were placed automatically." (`:265-269`); partial "Some sessions scheduled — {placed} of {required} … stay unscheduled until more availability opens." (`:282-295`); partial dialog (`components/scheduling/UnifiedCalendar.tsx:1843-1887`) is shown to every host, including host-org operators.

**Mobile:** the consultant allocate grid is wrapped in `DesktopOnlyNotice` — "Please access this on desktop for now. Choosing times needs a wider screen than this one." (`components/scheduling/TimePicker.tsx:369-379`, `components/scheduling/DesktopOnlyNotice.tsx:52-58`). Auto-allocate lives inside that grid, so **no allocation of any kind is possible on a phone**. VERIFIED.

## 3. Design options

### 3.1 How should a 6-month × 3/week plan be scheduled?

| Option                                                                     | What the consultant does                                                                                                                                                                                                                                      | What the consultee sees                            | Pros                                                                                                                                                                             | Cons                                                                                                                                                                                                                 |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Status quo + reminders** (rolling cycle, notify host)                 | Returns every week (24×), desktop only                                                                                                                                                                                                                        | One week ahead at most                             | Smallest change; tranche escrow untouched                                                                                                                                        | Still daily-pace bug (C-01), still 24 visits, still no SLA                                                                                                                                                           |
| **B. Whole series up front** (place all 72 at purchase)                    | One sitting; reschedules for exceptions                                                                                                                                                                                                                       | Full calendar                                      | Best visibility; one decision                                                                                                                                                    | Allocator hard-deletes on re-plan (`release-tentative.ts`, HLD `:133`) so later edits are risky until Wave 3; availability 6 months out is rarely real; blocks the consultant's calendar far ahead; many reschedules |
| **C. Fixed plan weeks + rolling horizon + weekly pattern** _(recommended)_ | Sets a **weekly pattern** once ("Mon/Wed/Fri 6 pm"); the system places the next **H weeks** (default 2, max 4) from the pattern, each plan week capped at `sessionsPerWeek`; consultant can tweak any week; gets notified only when a week couldn't be filled | 2–4 weeks visible, a stable rhythm, "Week 5 of 26" | Fixes pacing (C-01) structurally; turns 24 visits into ~0–3; mobile-friendly (confirm a preview); reuses `topUp`/`allowPartial`/preference machinery and the hourly sweep (C-03) | Needs a pattern field and a horizon rule; need to define make-up allowance per week                                                                                                                                  |

**Recommendation: C**, delivered in three steps:

1. **Correctness first (no schema):** fixed plan weeks derived from `planStartsAt` (today `schedulingPeriodStartsAt`) + `schedulingTimezone`; per-plan-week cap in search and validator (extend `validateClassWeeklyLimits` to subscriptions with week keys = plan-week index, not ISO week); `nextBatch` = cap − placed-in-current-plan-week (+ make-up credit for voided/returned sessions, placeable in any plan week with room ≤ cap+1 or until plan end). Allow placing the current **and next H−1** plan weeks (`windowEnd = min(start of week k+H, planEndsAt)`).
2. **Notifications + deadlines (C-02, C-04, C-05):** host bell when a plan week inside the horizon is empty; consultee-facing copy keyed by viewer; missed-week refund offer.
3. **Pattern auto-fill (C-03, C-12):** `schedulePattern` (§4) captured from the first allocation ("Use Mon/Wed/Fri 6 pm every week?" toggle in the success toast); the hourly sweep keeps the horizon full from the pattern (falls back to preference-ordered search when a pattern slot is busy) and notifies both parties: **"We booked week 6 for you: Mon 23, Wed 25, Fri 27 Mar, 6 pm. [Change]"**.

Money impact: none to tranches (still mature on delivered count, `subscription-cycle.ts:150-189`); plan-end settlement unchanged; missed-week refund is a new owed-marker key through the existing front door.
