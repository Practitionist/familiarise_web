# Schema reference: the booking tables

This page lists every column and index of the tables the #1554 vocabulary reset touches directly — `AppointmentOccurrence`, `AvailabilityWindowWeekly`, `AvailabilityWindowCustom`, `AppointmentParticipant`, `Meeting`, `MeetingAttendance`, `RecordingConsent`, `Trial` and `RescheduleProposedTime` — with the reasoning that is too long for a schema comment, in the same shape as [`docs/reviews/06-schema-reference.md`](../reviews/06-schema-reference.md). It also covers the three `ConsultantProfile` booking-mode columns added by #1703, the 1:1 plan terms and the `RegularTime` and `PlanEndChoice` tables added by train B, and `AppointmentFeedback`'s two-level rating rule, which spans `AppointmentOccurrence` and its own sidecar unique.

## `AppointmentOccurrence`

One row per held call. The table below lists its columns.

| Column                                                                 | Why it exists                                                                                                                                                                                                                                                      |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ordinal`                                                              | The call's 1-based position in its purchase. A replacement row written after a reschedule inherits its predecessor's `ordinal`, which is why the live-row uniqueness on this column is a partial index rather than a plain `@@unique` — see the index table below. |
| `startsAt`, `endsAt` (`Timestamptz`)                                   | The call's time range. The sidecar CHECK `occurrence_time_order` requires `endsAt > startsAt`.                                                                                                                                                                     |
| `isTentative` (default `false`)                                        | Marks a hold made before payment or reschedule confirmation completes. The DB-level overlap guard (see the index table) exempts tentative rows on purpose, because two tentative holds for the same consultant may legitimately coexist until one wins.            |
| `completionStatus` (`OccurrenceCompletionStatus`, default `SCHEDULED`) | The call's own lifecycle state, distinct from the parent `Appointment`'s purchase-level status.                                                                                                                                                                    |
| `completedAt?`                                                         | When the call was marked complete.                                                                                                                                                                                                                                 |
| `appointmentId` (`Cascade`)                                            | The purchase this call belongs to.                                                                                                                                                                                                                                 |
| `consultantProfileId?`                                                 | Denormalized from the appointment for the DB-level overlap guard (#440). Nullable for attendee (webinar/class) rows, which the partial-index guard excludes; many same-window rows per event are legitimate there.                                                 |
| `meeting`                                                              | The `Meeting` row for this call, if one has been created.                                                                                                                                                                                                          |
| `attendances`                                                          | Retired `MeetingAttendance` rows; nothing writes or reads them, and the relation goes when the table is dropped at the next schema step. Who attended is read from `presences`, Stream's settled record.                                                           |
| `deletedAt?`                                                           | Soft-delete tombstone (#676), mirroring `Appointment.deletedAt`.                                                                                                                                                                                                   |

The table below lists the occurrence row's indexes and sidecar constraints.

| Index or constraint                                                                                  | Why it exists                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `appointment_occurrence_live_ordinal_key` (sidecar unique, `prisma/sql/check-constraints.sql`)       | `("appointmentId", "ordinal") WHERE "completionStatus" NOT IN ('RESCHEDULED', 'CANCELLED', 'VOIDED') AND "deletedAt" IS NULL`. Live rows only, because a replacement written after a reschedule inherits the predecessor's `ordinal` and the superseded row keeps its number for history; since #1569 a voided session's make-up takes its ordinal the same way.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `occurrence_no_confirmed_overlap` (sidecar `EXCLUDE` constraint, `prisma/sql/check-constraints.sql`) | `EXCLUDE USING gist ("consultantProfileId" WITH =, tstzrange("startsAt", "endsAt") WITH &&) WHERE ("consultantProfileId" IS NOT NULL AND NOT "isTentative" AND "deletedAt" IS NULL)`. The DB-level last line against double-booking a consultant; the application guards (the consultant allocation lock, and the confirm-time conflict recheck inside the payment webhook's Serializable transaction, #827) are the first line. `tstzrange` is `'[)'`, so back-to-back occurrences do not conflict, and a violation surfaces to the application as Postgres error `23P01`. The `deletedAt` arm (#1694) exempts tombstones: a cancel or a hold release keeps the row as CANCELLED with `deletedAt` set and leaves `isTentative` untouched, so without the arm the time a cancelled booking used to hold could never be booked again. On a live database the predicate is changed through `scripts/db/swap-occurrence-overlap-constraint.ts`, never by replaying the sidecar chunk. |
| `@@index([appointmentId])`                                                                           | The parent-purchase lookup.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `@@index([consultantProfileId, startsAt, endsAt])`                                                   | Serves the overlap recheck and the exclusion constraint's own scan.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `@@index([isTentative, appointmentId])`, `@@index([isTentative, startsAt, endsAt])`                  | The tentative-hold sweep (expiry cron) and its time-range variant.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `@@index([startsAt, endsAt])`                                                                        | Time-range scans that are not consultant-scoped.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `@@index([createdAt])`                                                                               | Chronological listing.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `@@index([completionStatus, endsAt])`                                                                | The no-show and completion detectors, which scan by state and past `endsAt`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `@@index([deletedAt])`                                                                               | The soft-delete filter.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

## `MeetingAttendance`

Retired. It was a per-person join and leave summary written by the participant webhooks; nothing writes or reads it now except the three-year retention prune, and the owner drops the table at the next schema step. ## `ConsultantProfile` booking-mode columns (#1703)

Four columns on `ConsultantProfile` decide how a consultee reaches a consultant's calendar, how many requests the consultant is willing to hold open at once and how many plan clients they take. The first three were added in one PR with the code that reads them, per the schema-freeze rule, and existing rows take the defaults, so no backfill was written. The table below lists the columns.

| Column                                           | Why it exists                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bookingMode` (`BookingMode`, default `INSTANT`) | Decision D1 of the 2026-09-18 requests train. `INSTANT` keeps the behaviour the platform had before the column existed: a free slot goes straight to checkout, and only a contended slot (one the grid marks `isAllocated`) becomes a request for approval. `REQUEST` routes every slot through `POST /api/scheduling/request-for-approval`, so the consultant reviews before any money moves. The column lives on the profile rather than on a plan because the choice is about how the consultant works, not about one product, and because the expert page reads a single profile payload to decide the CTA. Subscriptions ignore the mode: they are always paid first and scheduled later.                                                                                                                                                       |
| `acceptingRequests` (`Boolean`, default `true`)  | Decision D4. The pause toggle, the analogue of Airbnb's snooze. While `false`, the request route refuses with `409 CONSULTANT_PAUSED` before it takes any lock, the Requests tab shows a banner, and the expert page tells the consultee to pick another expert or try later. It is a switch on the consultant, not a change to any request already open, so pausing never touches a `PENDING` row.                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `maxOpenRequests` (`Int?`, null = no cap)        | Decision D4. An optional per-consultant ceiling on open `PENDING` requests (consultations and subscriptions together, live rows only). Null means the cap is off, which is the default: research found no marketplace that documents a numeric queue cap, so this is an opt-in tool for a flooded consultant rather than a platform behaviour. The count runs inside the request route's slot lock, which is keyed by consultant and 30-minute interval rather than by consultant alone, so a burst on one slot cannot overshoot the cap by more than that lock already allows (requests for different slots are not serialised against each other, a bound the decision accepted), and the refusal is `409 CONSULTANT_AT_CAPACITY`. The per-consultee cap of three open requests and the ten-per-hour limiter are unchanged and sit in front of it. |
| `maxActivePlanClients` (`Int?`, null = no limit) | Added 2026-11-13 ([subscription demand bounds ADR](../decisions/2026-11-13-subscription-demand-bounds.md), decision 2). The most distinct buyers holding one of the expert's 1:1 plans at once. Checkout refuses a new client at the limit with `409 PLAN_CLIENTS_FULL` (`assertPlanClientRoom` in `lib/booking/plan-demand.ts`), counted under the expert's `request-cap:` key; a buyer who already holds a plan with the expert is never refused by it, and lowering it leaves sold plans alone. It is private: public pages get only the server-computed "Fully booked" flag (`planClientsFull`). The sidecar CHECK `consultant_profile_max_active_plan_clients_min` keeps a set value at 1 or more. No backfill: every expert starts with no limit.                                                                                              |

The `BookingMode` enum is declared immediately after `ConsultantProfile`, the one model that uses it, following the repository's enum-after-model convention. No index was added: the request route and checkout read these columns by primary key, and no list filters on them yet.

## 1:1 plan terms, `RegularTime` and `PlanEndChoice` (train B)

Train B touched the schema once, additively: every new column is nullable or defaulted, nothing was backfilled, and nothing was dropped or renamed. The columns ship with their readers in the same pull request; the two new tables ship empty and are filled by the Regular-time and plan-end-choice pull requests ([ADR](../decisions/2026-11-04-booking-v2-train-b.md), decisions 1, 6, 7, 8 and 9). The table below lists the columns.

| Column                                                       | Why it exists                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SubscriptionPlan.durationInWeeks` (`Int?`)                  | A plan sold in weeks (1–52; the editor offers 4, 8, 12, 26 and 52). Sessions are `weeks × sessionsPerWeek`, so 26 weeks at 3 a week sells 78, not the 72 that `months × 4` gives. `durationInMonths` stays as a derived label (`monthsForWeeks`). Null keeps a months plan, which is every row sold before this column. CHECK `subscription_plan_weeks_range`.                                                                                                                                                                                                                                                                                                                                                                               |
| `Subscription.sessionsPerWeek`, `sessionMinutes` (`Int?`)    | The weekly cap and the session length, frozen at purchase by `purchaseTermsOf` (`lib/booking/entitlement.ts`) alongside `sessionsTotal`. Every reader of a sold plan's cadence goes through `soldTermsOf`, `soldSessionsPerWeek` and `soldSessionMinutes`, which read these first and the plan only for a row sold before the freeze. A plan edit stamps those legacy rows (cadence, length, total and, where it was derived, `planEndsAt` from the pre-edit length) in the same transaction before it changes the plan (`freezeSoldTerms`, `lib/booking/sold-terms.ts`), so no edit ever moves a sold plan; a sold plan cannot switch between months and weeks (409 `PLAN_LENGTH_UNIT_LOCKED`). CHECK `subscription_frozen_terms_positive`. |
| `Subscription.sessionsRefunded` (`Int`, default 0)           | Sessions a support partial refund removed from the plan. The schedulable total is `sessionsTotal − sessionsRefunded` (`subscriptionEntitlement().total`), while the plan-end settlement keeps `T = sessionsTotal` and subtracts what was already returned, so a session is never paid twice. Written only by CAS on the count read (`removePlanSessions` / `restorePlanSessions` in `lib/booking/plan-refund.ts`). CHECK `subscription_sessions_refunded_range` (0 ≤ refunded ≤ `sessionsTotal`).                                                                                                                                                                                                                                            |
| `Subscription.lastRolledAt`, `rollPausedAt` (`Timestamptz?`) | Roll-forward fair rotation and the pause after three plan weeks with nothing placed. Unread until the Regular-time pull request.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `Subscription.@@index([status, planEndsAt])`                 | The plan-end settlement keyset filters on status and walks `planEndsAt`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `SupportFinancialRecommendation.sessionsRemoved` (`Int?`)    | The k of a support remedy priced in sessions: the recommendation's amount must be `min(floor(paid × k / sold), refundable)`, and the approval removes k sessions in the same commit. Null for a money-only remedy. CHECK `support_recommendation_sessions_removed_min`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

`RegularTime` holds one weekly slot of a plan's Regular time: `weekday` (ISO 1–7) and `localStartMinutes` (0–1439) in `timezone`, versioned by `validFrom` / `validUntil` and attributed by `createdByUserId`. CHECK `regular_time_ranges` bounds the two numbers, and the partial unique `regular_time_one_live_slot` on `(subscriptionId, weekday, localStartMinutes) WHERE validUntil IS NULL` allows one live row per slot while superseded rows stay as history.

`PlanEndChoice` is one row per subscription (`subscriptionId @unique`) with status `PlanEndChoiceStatus` (`OFFERED`, `EXTENDED`, `REFUNDED`, `EXPIRED`, `EXPERT_DECLINED`). CHECK `plan_end_choice_shape` requires `decidedAt` exactly when the status is not `OFFERED`, and `plan_end_choice_extended` requires `extraWeeksOffered` in 1–4 and `previousPlanEndsAt` on an `EXTENDED` or `EXPERT_DECLINED` row, so a declined extension can always restore the plan end. `@@index([status, deadline])` serves the timeout sweep.

## Agreed price on `Consultation` and `Trial`

A 1:1 request and a trial keep the price they were requested at, and a plan edit never moves it. Each model gained one nullable column, and nothing was backfilled: a null means a row created before the column, which reads the plan. The owner applies the two `ADD COLUMN` statements through the ordered procedure in [docs/prisma/README.md](../prisma/README.md): preflight, push, sidecars, assert.

Only the price is stored. The length is not, because a request and a trial hold a time from creation, so the session they hold already records it. `bookedSessionMinutes` (`lib/appointments/occurrences.ts`) returns the live session's length, else the latest session row's, and the plan's length only when the booking has no session row at all. A subscription differs and keeps its stored `sessionMinutes`, because its sessions are placed later. The price differs too: a request made at the request door has no payment row, so nothing else records what the buyer saw. Webinar and class seats need neither, because they are paid at checkout, where the payment row carries the amount, and the time belongs to the event.

| Column                                             | Why it exists                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Consultation.agreedPricePaise` (`BigInt?`)        | The plan price in paise at request, before tax. Written where the row is created: the request door (`app/api/scheduling/request-for-approval/route.ts`), the checkout consultation handler (`lib/payments/checkout/handlers/consultation.ts`) and the legacy webhook creator (`createConsultation` in `lib/payments/webhooks/legacy-appointment-creation.ts`). Read through `agreedConsultationPricePaise` (`lib/booking/sold-terms.ts`). The Prisma client maps it to a `number` in `lib/prisma-extensions.ts`. |
| `Consultation.requestFingerprint` (`varchar(64)?`) | The sha-256 of what the learner submitted to the request door with an `Idempotency-Key` (plan, start, end, organisation), written in the transaction that creates the request. A same-key retry replays the original only when it matches, whatever times the booking holds since. Null means a row created before the column, whose retry compares the held times instead.                                                                                                                                      |
| `Trial.agreedPricePaise` (`BigInt?`)               | The plan's trial price at request, written by `bookTrialInTx`. Read through `agreedTrialPricePaise`.                                                                                                                                                                                                                                                                                                                                                                                                             |

The database refuses a negative price in the sidecar `prisma/sql/check-constraints.sql`: `consultation_agreed_price_valid` and `trial_agreed_price_valid` each require the price to be null or at least 0. A row whose price is still null is stamped by `freezeConsultationPrice` or `freezeTrialPrice` (`lib/booking/sold-terms.ts`), which the plan edit routes call inside the plan edit's own transaction before the plan row changes. `PUT /api/plans/consultations/[consultationPlanId]` freezes only when the price changes, and `PUT /api/plans/subscriptions/[subscriptionPlanId]` freezes trials only when `trialPriceInPaise` changes.

## The `AppointmentFeedback` two-level rating rule

`AppointmentFeedback.appointmentOccurrenceId?` is nullable by design: `NULL` means the rating is about the whole appointment (a subscription or class as a purchase), and a set value means the rating is about one specific held call. Both levels can be rated independently, and the row that keeps them from colliding is the sidecar unique `appointment_feedback_level_key` in `prisma/sql/check-constraints.sql`:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS "appointment_feedback_level_key"
  ON "AppointmentFeedback" ("appointmentId", "appointmentOccurrenceId", "userId") NULLS NOT DISTINCT;
```

`NULLS NOT DISTINCT` (Postgres 15) is what makes this a two-level rule rather than an accidental free-for-all: without it, Postgres treats every `NULL` in `appointmentOccurrenceId` as distinct from every other, so a person could write unlimited whole-appointment ratings for the same appointment. With it, one person gets exactly one whole-appointment rating (`appointmentOccurrenceId IS NULL`) and exactly one rating per occurrence they were rated against, and Prisma cannot express the clause itself, which is why the constraint lives in the sidecar rather than as a schema `@@unique` (#1268).

## Deprecated & Superseded Approaches

- **A sold subscription read its weekly cap and session length from the live plan row.** A plan edit therefore changed what existing clients had bought; only `sessionsTotal` was frozen. Superseded by the frozen `sessionsPerWeek` / `sessionMinutes` columns and `freezeSoldTerms`.
- **Plan length only in months, with sessions = `months × 4 × perWeek`.** Kept for plans sold in months; new plans use `durationInWeeks`.
- **A 1:1 request and a trial read their price and length from the live plan row.** A pending request was priced from the plan at approval, a live pay link was re-minted at the new amount, and a booking sold at 60 minutes could not be moved once the plan became 30. Superseded by `agreedPricePaise` (with `freezeConsultationPrice` / `freezeTrialPrice`) and the booked session's length (`bookedSessionMinutes`). A first version stored `pricePaise` and `sessionMinutes` on both models; the length columns were dropped because the held session already records it.
