# Engineering log — 2026-09-20 — the booking money train

**Date:** 2026-09-20 · **Issue:** #1775 · **Scope:** the Requests inbox (PR-A) and the consultant's actions on an awaiting-payment request (PR-B), built in parallel worktrees against the same `dev`.

## PR-B — Remind + Withdraw approval, self-approval guard, cycle-aware allocate page, QA seed timezone (2026-09-20)

An `APPROVED_PENDING_PAYMENT` row had no consultant action: the pay order either got paid or lapsed after 7 days. The owner locked two actions on 2026-09-20 and this PR ships them with the shape below.

- **B-1, the lapse core.** The per-row body of the 7-day sweep (`expirePaymentPendingRequests`) moved into `lib/booking/lapse-approved-request.ts` as `lapseApprovedRequest(tx, { kind, id, reason, actorUserId })`. It runs the request CAS to `EXPIRED` from exactly `APPROVED_PENDING_PAYMENT` with the money predicate (no succeeded payment on the wrapper) in the WHERE, then tombstones the open PENDING order to `EXPIRED` by status and releases the tentative holds by status; a lost CAS returns `{ moved: 0 }` without throwing and without any further write. The sweep calls it per row. The spec described this body as already living in the 7-day arm; in fact that arm only did the request CAS, and the fuller body (holds plus order) lived in the 24 h arm in `scripts/payments/cleanup-abandoned-payments.ts`. The core now carries the fuller body for both callers, which for the 7-day arm is a no-op in the normal case because the 24 h arm has already released and tombstoned by then.
- **B-2, Withdraw.** `POST /api/bookings/{consultations,subscriptions}/[id]/withdraw-approval` for the request's consultant or a privileged user: the lapse core under `withAppointmentLock` in a Serializable transaction, then the consultee's lapsed-link notice (`notifyConsulteeRequestExpired`, reason `WITHDRAWN_BY_CONSULTANT_REASON`) after the commit. A lost CAS answers `409 REQUEST_CHANGED_ELSEWHERE`. The Redis lock is injected into the service rather than imported by the module, because the sweeps import the same module and the Upstash client does not load under jsdom. Both race orders are pinned in `__tests__/booking-algorithm/withdraw-approval.test.ts`; the late capture's refund itself is the `captured_after_release` pin in `__tests__/payments/capture-amount-parity.test.ts`, not duplicated.
- **B-3, Remind.** `POST …/[id]/remind` re-sends the approval's own template with the existing `pendingPaymentUrl` and the open order's amount and expiry, once per 24 hours per appointment through `remindLimiter` (`lib/rate-limit.ts`), answering `200 { nextAllowedAt }` or `429 { code: "REMIND_RATE_LIMITED", nextAllowedAt }`, and `409 NOT_AWAITING_PAYMENT` without a live order. The outbox row carries `PAYMENT_LINK_MANUAL_REMINDER`, a distinct email type from the sweep's `PAYMENT_LINK_REMINDER`, so neither reminder dedupes the other. `sendPaymentLinkEmail` hard-wires its email type from its `reminder` flag and `lib/email/index.ts` was outside this PR's files, so the manual reminder renders the same `PaymentLinkEmail` element and hands it to `deliver()` under the manual type. No bell is staged: the approval flow itself stages none, and adding a Novu event was out of scope.
- **B-4, self-approval.** Both detail PATCH routes refuse an approval status (`APPROVED`, `APPROVED_PENDING_PAYMENT`, `SCHEDULED`) when the consultant profile's user is the requester's user, with `403 SELF_APPROVAL`, unless privileged. Pinned as a source contract in `__tests__/payments/approval-path-correctness.test.ts` (the guard sits before the transaction), since the route's existing suites are source-level too.
- **B-5, the CTA.** `NextActionKind` gains `REMIND_OR_WITHDRAW`; a consultant viewing an `AWAITING_PAYMENT` booking gets Remind (cooling down on the limiter's `nextAllowedAt`, from the 200 or the 429) and Withdraw approval behind a confirm; a 409 reads as "changed elsewhere" and refetches. The consultee keeps `PAY`. Pinned in `__tests__/dashboards/money-state.test.ts`.
- **B-6, the allocate page.** The window banner reads "This cycle" for a subscription and "Requested window" for a consultation (label only). A subscription's week grid starts on its cycle's start day through `weekStartFor` in `components/scheduling/UnifiedCalendar.tsx`. Changing the grid's start alone would have blanked cells, because `hooks/scheduling/useCalendarData.ts` anchors both the fetch window and the precomputed status map on Sunday; the hook now takes the same `weekStartsOn` (default 0), so the columns drawn are the columns fetched, and the quota bucketing stays on Sundays as before. The legend was already one wrapping flex row in `SlotStatusLegend.tsx` and was left alone.
- **B-9, allocation lands by money (P0, found by the preview QA).** Every UI approval of a REQUEST-mode request went through the allocate handler and `SchedulingService.updateEventStatus`, which CASed the request to `APPROVED` from `ALLOCATION_APPROVABLE_FROM` with no payment predicate and no mint; the minting branch lived only in the detail PATCH, which no UI calls with `status: APPROVED`. On the preview a ₹2,361.97 request became "Confirmed · Nothing was charged for this booking" three times, and a re-allocation of an awaiting-payment row flipped it to `APPROVED` under a live pay order. `lib/booking/approve-request.ts` now holds the two arms of the decision (`SETTLED_*`: a SUCCEEDED, non-deleted payment or a free plan; `UNPAID_*`: no succeeded payment, the lapse core's arm) and the detail PATCH's post-commit mint block, moved there verbatim as `mintApprovalPaymentAfterCommit` (mint under the mint lock with the live-intent reuse, the `pendingPaymentUrl` CAS, the orphan tombstone, the email); both PATCH routes call it. `updateEventStatus` makes two CAS attempts with the money predicate in each WHERE and returns `approved` or `awaiting_payment` through the three allocation paths to `handleAllocate`, which mints before the response on `awaiting_payment` (a failed mint is a PAYMENT system error) and answers `awaitingPayment: true`; the callout's Approve toast reads it. Pinned in `schedulingService.test.ts` (unpaid → `APPROVED_PENDING_PAYMENT` with the no-payment predicate; paid → `APPROVED` on the first CAS; an awaiting-payment re-allocation stays on the self-edge; both misses → 409) and `allocate-mints-on-awaiting-payment.test.ts` (one mint on `awaiting_payment`, none on `approved`, a live link is reused). Two consequences worth naming: the `APPOINTMENT_BOOKED` bell the allocation stages still fires for an awaiting-payment approval (it names the times; the pay-link email follows), and the Requests page's own toast (PR-A's `request-decision.ts`) does not yet read `awaitingPayment`.
- **B-7, the seed.** The first `QA_ACCOUNTS_PER_ROLE` users of each role, the `SeedPass123!` logins, get `timezone: "Asia/Kolkata"`; the random population keeps faker's spread.
