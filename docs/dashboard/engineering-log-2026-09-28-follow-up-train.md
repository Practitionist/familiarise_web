## Bucket B, money and concurrency (#1853)

The latent P0 was a double payment. A RazorpayX payout whose submit timed out was marked FAILED and its earnings were released, so the next Monday batch paid the consultant again under a new idempotency key even though the first transfer might already have left. The fix is that once the gateway request has left, only a definitive rejection (a 4xx other than 408, 409 or 429) may fail a payout. Anything else keeps the payout PROCESSING with its earnings BATCHED, and the payout webhook or the four-hourly `handle-stuck-payouts` sweep settles it by asking RazorpayX for the payout by its reference id, which is our row id, before anything is resubmitted or failed. A Stripe payout stuck without a provider id goes to manual review, because Stripe idempotency keys expire after 24 hours, which is exactly the sweep's stuck threshold.

The same PR gave the capture webhook's five auto-refund branches a durable marker. Phase 1 stamps `Auto-refund pending:` on the payment in the transaction that decides the refund, and the `retry-auto-refunds` sweep drives each one to `Auto-refunded:`, or to `Auto-refund stuck:` with one operator page after three failed gateway refunds. It also put the overage side-charge writes under compare-and-set, moved the org payout PATCH onto the shared transition map, declared `EARNING_ALLOWED_FROM`, and bounded request-path payout runs to 20 seconds with a two-minute lock, so a run the function limit kills no longer holds the payout lock for 35 minutes.

The owner made three decisions on this PR. FAILED stays final for an org payout, a stuck Stripe payout with no provider id goes to manual review, and an org payout became payable from PENDING or APPROVED. #1860 later tightened the last one, as described below. The docs are in [payout processing](../payments/payouts/03-payout-processing.md), [payment webhooks](../enterprise/10-money-and-ledger/12-payment-webhooks.md), [earnings lifecycle](../enterprise/10-money-and-ledger/06-earnings-lifecycle.md), the cron reference and ADR 27.

## Bucket C, the membership lifecycle, and #1852 mixed-affiliation seats (#1854)

Before #1854, role and status changes were checked in several places that disagreed: the dashboard PATCH, SCIM and bulk import each had their own rules, and SCIM could revive a REMOVED or ERASED membership. One guard, `lib/enterprise/membership-guards.ts`, now serves all three. Joining is invite and accept only, so the members POST answers 405 and bulk import sends invitations, and accepting an invitation is the one door back into ACTIVE for a REMOVED or legacy PENDING row. A LEARNER or EXPERT with history at the organization cannot change role in place, removal checks upcoming sessions, live seats and money still moving, and only an OWNER can force past those obligations. A MAINTAINER now manages only the operational roles, and a payout recipient changes only for OWNER or BILLING_ADMIN, through the member PATCH or the new "Experts' payout routing" section on Org › Payouts.

The #1852 half moved group-session attribution onto the seat. A webinar or class seat records its payer organization only when that organization's money paid for it, and feedback, support and the new sponsor view read that seat org instead of the host's. Every webinar and class registration now shows the owner's locked group-session disclosure line.

The owner decided four items on this PR: ownership transfer belongs to #1844, BILLING_ADMIN routes expert payouts from Org › Payouts, removal stays strict unless an OWNER forces it, and SCIM keeps OWNER authority while being fully guarded. The docs are in [roles and permissions](../enterprise/00-foundations/04-roles-and-permissions.md), [organization lifecycle](../enterprise/00-foundations/05-organization-lifecycle.md), the enterprise API reference, the audit catalogue in `05-system-events.md`, the SCIM and SSO docs, and ADR 20.

## Bucket A, the booking lifecycle (#1858)

A buyer who walks away from an approval-pending booking now has one door, `POST /api/bookings/[bookingId]/abandon`, which ends the booking by kind, expires the caller's pending payment by compare-and-set, returns credits and org engagement, and answers `ALREADY_PAID` if a capture committed first. An expired reschedule proposal now restores the original booking in the same transaction under the appointment lock, instead of leaving both parties with nothing, and notifies both of them through the EXPIRED outcome of the existing `appointment-rescheduled` family. Offering deletes run as one Serializable transaction under the offering's checkout lock with the no-history guard inside the delete's WHERE, and the Offerings card reads the same guard from `lib/offerings/delete-guard.ts`, so it never offers a Delete the server refuses. `transitionParticipant` replaced `setParticipantStatus` so that REFUNDED is terminal for a seat.

The owner decided four items on this PR: expiry notifies both parties, a paid trial's cancel shows its refund quote first and refunds only the confirmed amount, the Offerings card follows the server rule, and the maintenance freeze tombstones the slots it cancels. After merge, `npm run novu:sync` must run for the EXPIRED template branch; Development was synced on 2026-09-28, and Production is owed at release with a `--dry-run` first. The docs are in the booking lifecycle, state machines, API reference, trials, rescheduling and cron docs, the maintenance and notifications docs, and the booking skill.

## The org RBAC action-level matrix (#1860)

#1860 moved every org route onto the permission matrix in `lib/auth/org-permissions.ts`. The matrix now keys actions as well as surfaces, every handler under `app/api/organizations/**` names a key, the rank helpers that routes used to call are deleted, and a jest pin fails on a rank check or on a handler without a key. Each retired rank gate became a key holding exactly the roles it resolved to, so nothing widened, and the only role changes came from owner decisions that narrowed access. The role × action table in [roles and permissions](../enterprise/00-foundations/04-roles-and-permissions.md) is now the literal output of `npx tsx scripts/utils/print-org-role-matrix.ts`.

The owner decisions that shipped here are the following. Act-for-org cancel and reschedule reach only 1:1 and subscription bookings and write MEMBER audit rows. Plan materials are managed by org roles only on org-owned plans, and learner uploads and recordings are never deletable by an org role. Only the OWNER subscribes a webhook to member events. Billing-account edits are audited under INVOICE rather than SETTINGS. An expert's Compensation page shows only their own split.

The decision with the widest effect is payout approval. #1853 had made an org batch payable without sign-off, and the owner then decided that an org batch is paid only after approval, under a two-person rule with a typed self-approval in a one-person organization. Batches already PENDING when #1860 deployed need an approval before the weekly run pays them. [How payouts work](../payments/payouts/00-how-payouts-work.md) now explains both payout rails and the go-live steps in plain language, because the owner asked for that explanation on 2026-09-28.
