# The GitHub Actions failure sink

Every money job that runs on GitHub Actions (the daily, weekly and monthly workflows under `.github/workflows/`) ends with a `Notify on failure` step that runs `scripts/ci/notify-ops-failure.sh <job>` when the job step failed. This page records what that script does, why it delivered nothing for three weeks, and how to tell whether it is working.

## What the script does

If `SLACK_OPS_WEBHOOK_URL` is set it posts to Slack first. Otherwise, or as the fallback, it builds a Sentry event (`message: "cron failed: <job>"`, `level` fatal for the money jobs and error for the rest, `logger: github-actions`, tags `subsystem: cron` and `job: <name>`, `extra.run_url` pointing at the Actions run) and submits it to the project's envelope endpoint, `POST https://<ingest host>/api/<project id>/envelope/`, as a three-line envelope: a header line carrying the full DSN and an `event_id`, an item header of type `event`, and the event JSON. The DSN is parsed from `SENTRY_DSN`. A non-2xx answer prints a `::warning::` line and fails the step, so a dead sink is red in the Actions UI instead of silent. Slack is not provisioned today by the owner's choice; Sentry is the working sink.

## Why it delivered nothing until 2026-09-20

The 2026-09-19 sanity scan noticed that `process-payouts` had failed on every weekly run since 1 September, `reconcile-ledgers` had failed daily, and the two payout reconcilers failed every run, while Sentry held zero `cron failed:` events in thirty days. The run logs showed `curl: (22) The requested URL returned error: 403` followed by `Sentry notification failed for <job>` on every failure. The first hypothesis was the endpoint: the script posted to the legacy `/api/<id>/store/` path, which Sentry has been retiring in favour of envelopes. The ops-hygiene PR (#1761) rewrote the call to the envelope endpoint on that basis, and the rewrite is correct and stays. But the probe that verified it found the real cause: the `SENTRY_DSN` secret in GitHub (set 2025-12-09) and the `SENTRY_DSN` line in `.env` both carried project id `4509348818124800`, which exists in no organisation we own. Sentry answers `403 event submission rejected with_reason: ProjectId` to that id on either endpoint. The secret and the `.env` line were rotated to the live DSN (project `4511593990914048`, the same value as `NEXT_PUBLIC_SENTRY_DSN`) on 2026-09-20.

The first real deliveries arrived within the hour and are themselves a useful record: `FAMILIARISE_WEB-57` (`alert-dispute-deadlines`), `-58` (`cleanup-invalid-appointments`), `-59` (`reconcile-occurrence-availability`), `-5A` (`reconcile-payout-status`) and `-5B` (`handle-stuck-payouts`). A sweep that reads those as "five new production errors caused by today's merges" is misreading the sink coming alive; three of them are the seed-shaped failures #1761 retires, one is a booking script's five-second transaction timeout (#1746), and one is the known overlapping-seed-occurrence defect.

## How to tell it is working

Search Sentry for `logger:github-actions` in the last seven days. A healthy week shows one event per genuinely failed run and nothing else; a quiet week with red runs in the Actions list means the sink is dead again, and the first thing to check is the project id inside the `SENTRY_DSN` secret (`gh secret list` shows the date it was last set; the value has to be read from a run's masked log or re-set from `NEXT_PUBLIC_SENTRY_DSN`). The script can be exercised by hand from the repository root with `SENTRY_DSN=<live dsn> bash scripts/ci/notify-ops-failure.sh manual-check`; it creates one event tagged `job: manual-check`, which should be resolved with a comment afterwards.

## What still lands nowhere

A scheduled Netlify function (`cron-tick`, `keep-warm`) does not run this script; the ticker answers 200 unconditionally since #1710 because a 5xx makes Netlify re-invoke it three times, and its per-target failures are read from its logged body, not from Sentry. A bare-Node job that fails before `initJobSentry()` runs sends nothing from inside the job; only this script's `cron failed:` event marks it. And a job that succeeds while doing nothing — the historic `process-payouts` pattern of reporting "lock unavailable" when the live-payouts flag was simply off — sends nothing either, which is why #1761 made that job distinguish the two cases.
