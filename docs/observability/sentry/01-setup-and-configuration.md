# Sentry setup and configuration

This page records how Sentry is wired into the application and the operational facts that were learned the hard way, so that nobody has to rediscover them from the git history. Everything here was true on 2026-09-20, with the API configuration, the ingest canary and the identity work added on 2026-09-28; when a fact changes, change it here first. The page set is 01 this page, [02 conventions](02-conventions.md), [03 the Actions failure sink](03-actions-failure-sink.md), [04 the triage runbook](04-triage-runbook.md), [05 identity and triage](05-identity-and-triage.md), [06 the ingest canary](06-ingest-canary.md), [07 proving an event arrives](07-verifying-end-to-end.md) and [08 error telemetry and privacy](08-error-telemetry-privacy-reference.md) — a company-agnostic reference on what error telemetry discloses, where it lands, and the DPDP questions it raises, written to be reusable outside this repository.

## The project and its DSNs

There is exactly one Sentry project for this application: organisation `practitionist`, project `familiarise_web`, hosted in the US region. Production, deploy previews and branch deploys all report into that one project and are told apart by tags, not by project (see the conventions page). A second, dead project id appears in old configuration and in old `.env` files; it belongs to no organisation we own, and Sentry answers `403 event submission rejected with_reason: ProjectId` to anything that uses it. Every occurrence of that dead id is a dead value, not an alternative sink. The live organisation and project ids _are_ written down, in the next subsection, because neither is a credential and the CI guard already carries the live project id in a non-secret repository variable. The dead id is not written down here or anywhere else in this repository, on purpose: it was scrubbed, and an id that reproduces a broken configuration is a liability rather than a fact.

Two environment variables carry the DSN. `NEXT_PUBLIC_SENTRY_DSN` is what the application reads in every runtime (browser, server, edge) and what the bare-Node jobs read through `lib/observability/job-sentry.ts`; it is set on Netlify for every context and in the local `.env`, and it points at the live project. `SENTRY_DSN` is read by exactly one thing, `scripts/ci/notify-ops-failure.sh`, which runs in GitHub Actions when a scheduled job fails; it lives in the GitHub repository secrets and in the local `.env`. Until 2026-09-20 both copies of `SENTRY_DSN` carried the dead project id, which is why no GitHub Actions failure ever reached Sentry (see the failure-sink page). Both were rotated to the live DSN that day. A DSN's public key is not a secret in the usual sense — it ships in the client bundle — but the repository rule is still that no DSN literal appears in code: the init is gated on `Boolean(process.env.NEXT_PUBLIC_SENTRY_DSN)` and the one time a literal was pushed the branch was history-rewritten to remove it.

### Four identifiers, and which is which

The confusion here is real and it has already happened: someone read the number `4509348815372289` out of a DSN and reasonably concluded it was a project id. There are four distinct things in play and they are all different.

| Thing        | Value                                                                | Where it appears                                                            |
| ------------ | -------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Region       | US                                                                   | the DSN host's suffix, and the `SENTRY_API_URL` default                     |
| Organisation | slug `practitionist`, id `4509348815372289`                          | as `o<orgId>` in the DSN **host**                                           |
| Project      | slug `familiarise_web`, id `4511593990914048`                        | as the DSN's last **path** segment, and as `?project=` in Sentry's own URLs |
| DSN          | `https://<publicKey>@o<orgId>.ingest.<region>.sentry.io/<projectId>` | one string carrying all three of the above plus the public key              |

The org and the project are both called "id", both sixteen digits, and both appear inside that one string. The DSN's own shape is the only disambiguator, and it is worth being able to apply without thinking: **the id in the host is the organisation's, the id in the path is the project's.** That is the whole rule.

**The hazard is a project id shaped like an org id.** The dead project id from the 2026-09-20 mis-rotation shared its first ten digits with the organisation id, so the two read as siblings and swapping one for the other produces a DSN that is perfectly well-formed and aimed at nothing — the failure recorded on the failure-sink page, where a well-formed dead DSN looked delivered while every cron failure went unpaged. The live project id diverges from the organisation id at its third digit, so nothing about its shape gives any warning at all. The distinction has to be known rather than spotted. The dead id is not written down here, for the reason given above: "a dead project id sharing its first ten digits with the organisation id" is a complete description of the hazard without reproducing the value.

That confusion is also why the CI guard's variable is now `EXPECTED_SENTRY_PROJECT_ID`, renamed from `LIVE_SENTRY_PROJECT`. The old name was ambiguous between "the live project" and "the project id of the live thing", and a guard whose variable can be read both ways cannot fail loudly on the exact confusion it exists to catch — its error messages have to spell out that the value is the project id and not the organisation id, because that is the mistake the guard is for. It is a non-secret repository **variable**, not a secret, and `scripts/ci/notify-ops-failure.sh` refuses to skip the check when it is unset, for the same reason the alert cooldown fails open: a check that can silently skip is a check nobody sees.

## Where the code lives

The SDK is `@sentry/nextjs` (pinned on major version 10.75.x; see #1879 for why 11.x is deferred until its permissive `dataCollection` defaults and span-streaming hook contract are reconciled), installed through the official wizard in PR #901. The single initialiser is `sentry.shared.config.ts`, exporting `initSentry()`, which `sentry.server.config.ts`, `sentry.edge.config.ts` and `instrumentation-client.ts` each call for their runtime; `instrumentation.ts` registers the server hooks and `onRequestError`; `app/global-error.tsx` catches render errors; `next.config.mjs` is wrapped with `withSentryConfig`. The shared config sets `environment` from `NEXT_PUBLIC_SENTRY_ENVIRONMENT`, route-aware `tracesSampler` (0% for `/api/health` and static assets, 2% for `/api/cleanup/`, 50% for `/api/webhooks/`, `/api/payments/`, and `/api/checkout`, 10% production baseline, and 100% outside production), `enableLogs: true`, an explicit `dataCollection` allowlist (the SDK 10.54 replacement for the deprecated `sendDefaultPii`), an `ignoreErrors` list and a `denyUrls` list for third-party noise (browser wallet extensions, the React Server Components flight-stream abort), and four scrubbing hooks (`#1916`, `#1926`): `beforeSend`, `beforeBreadcrumb`, `beforeSendTransaction`, `beforeSendSpan`, and `beforeSendLog`. Together those hooks strip ungated `culture.timezone` from events, transactions, and spans, drop verbose `debug`/`trace` logs in production, and redact emails, Bearer tokens, secret query parameters, and echoed SDK error bodies (`NovuError.body`, `rawValue`). Session Replay and the ad-blocker tunnel are deliberately not enabled: replay is a DPDP and bundle-size cost, and the tunnel would bill a Netlify function invocation per event.

Reporting goes through `lib/observability/report.ts`: `reportSentryError(error, { subsystem, op, expected, extra })` and `reportSentryMessage(message, { subsystem, expected, level, extra })`. Nothing in application code should call `Sentry.captureException` directly except the few places that predate the helper; the helper is what applies the `subsystem`, `expected`, `pool_exhaustion`, and Postgres SQLSTATE (`pg_code`, `pg_constraint`) tags consistently. `lib/observability/expected.ts` provides `markExpected(error)` and `isExpectedError(error)` for the modelled-refusal path, and `lib/observability/betterstack-telemetry.ts` mirrors uptime signals to BetterStack, which is a separate sink with its own truth.

Bare-Node jobs (everything under `jobs/**` that GitHub Actions runs with `tsx`) do not get the Next.js instrumentation. They call `initJobSentry()` from `lib/observability/job-sentry.ts` and `flushJobSentry()` before exit with a five-second budget, because a job that exits before the transport flushes loses its events silently. A job that is missing the init is invisible to Sentry no matter how loudly it fails.

## Source maps and the auth token

Source-map upload runs inside `next build` through the Sentry bundler plugin and needs `SENTRY_AUTH_TOKEN`, `SENTRY_ORG=practitionist` and `SENTRY_PROJECT=familiarise_web`. On 2026-06-26 every Netlify deploy went red because the token on Netlify was scoped to a differently spelled organisation (`practionist`, an old token) while the config named `practitionist`; the upload failed, the plugin propagated the exit code, and `next build` exited 2. Two fixes followed and both still stand: the bad token was unset on Netlify so the upload is skipped, and PR #918 added an `errorHandler` to `withSentryConfig` so that a bad or expired token can never fail a build again.

This page used to say that GitHub CI has no `SENTRY_AUTH_TOKEN`, "which is why CI stayed green through that outage". The first half is false and I checked: against the GitHub API on **2026-09-29**, this repository **does** have a `SENTRY_AUTH_TOKEN` secret, created **2025-05-22** and last updated **2025-12-09** — both comfortably before the 2026-06-26 outage. (`gh secret list` prints the _update_ date, which is where the 2025-12-09 figure comes from; the create date is only in the API response. Worth knowing before quoting that column as a provenance date.)

What is true today is narrower, and it is a mapping fact rather than an existence fact. GitHub Actions _does_ build: the `test-and-build` job in `.github/workflows/ci.yaml` runs `npm run build`, and the step's own comment names "next build (+ Sentry source-map generation)" as the thing it has to raise the heap for. But `SENTRY_AUTH_TOKEN` is not in that step's environment — its only `env:` key is `NODE_OPTIONS` — and the one workflow in the repository that _does_ map the secret, `.github/workflows/gstr8-draft-export.yml`, runs a bare-Node `tsx` job that contains no Sentry bundler plugin and therefore cannot fail at upload either way. So CI has a token it does not pass to the only step that could use it, and the plugin skips the upload for want of one. That is the mechanism as the tree stands; whether it was also the mechanism on 2026-06-26 is not established, because the `errorHandler` and the workflow have both changed since, and this page will not invent a causal story it cannot evidence. Three facts, one of them corrected, is the honest total.

The `sntrys_` organisation token in the local `.env` is also dead (`401 Invalid org token`); the Sentry CLI's OAuth login is what has access. Restoring automated source-map uploads (`#900`) requires minting an org auth token under `practitionist` (`Settings → Auth Tokens`, scopes `project:releases` and `org:read`) and setting `SENTRY_AUTH_TOKEN` in Netlify's environment variables; `next.config.mjs` already gates upload via `errorHandler` so an expired or missing token degrades gracefully without failing the build.

## Where Sentry's own coordinates live

Until 2026-09-28 the Sentry organisation, project and both URLs were hardcoded in TypeScript — four literals in `sentry.shared.config.ts` and two more in `lib/observability/sentry-issues.ts`. Every one of them is now read from the environment with a `||` default to the live project, so the same code runs against a real project and a fixture in a test:

| Variable                    | Read by                               | Default                           | Purpose                                                    |
| --------------------------- | ------------------------------------- | --------------------------------- | ---------------------------------------------------------- |
| `SENTRY_API_URL`            | `sentry-issues.ts`                    | `https://us.sentry.io`            | **Bare host** — the code appends `/api/0/…` itself         |
| `SENTRY_WEB_URL`            | `sentry-issues.ts`                    | `https://practitionist.sentry.io` | Base for the issue links shown to support                  |
| `SENTRY_ORG`                | `next.config.mjs`, `sentry-issues.ts` | `practitionist`                   | Slug, not id — what the CLI and the UI paths want          |
| `SENTRY_PROJECT`            | `next.config.mjs`, `sentry-issues.ts` | `familiarise_web`                 | Slug, not id                                               |
| `SENTRY_API_TOKEN`          | `sentry-issues.ts`                    | _unset_                           | REST read token, needs `event:read`                        |
| `SENTRY_AUTH_TOKEN`         | the build plugin                      | _unset_                           | Source-map upload, needs `project:releases` and `org:read` |
| `OBSERVABILITY_ALERT_EMAIL` | `ingest-alert.ts`                     | the support mailbox               | Who the canary emails                                      |

`SENTRY_API_URL` is the **bare host**, not a base that includes the version prefix: `findUserIssues` appends `/api/0/organizations/<org>/issues/` itself, so a value already ending in `/api/0` produces `/api/0/api/0/…` and every lookup 404s. This page previously documented the default _with_ `/api/0`, which is the one way to set it wrong; the code and `.env.sample` were always right.

The org and project are **slugs, not ids**, which is the thing that goes wrong: the two numeric project ids in circulation both appear in `next build` output and neither is usable as a slug. Read the slug from the Sentry UI; never infer it from a DSN — the two ids in a DSN are the org and the project in a fixed order, and the subsection at the top of this page is the whole of what a DSN can tell you. The two tokens are separate credentials for separate jobs and neither is set today. `SENTRY_API_TOKEN` is deliberately left unset rather than set to an empty string, because an empty string enables the token path and then fails every call with an unauthenticated request; unset is the off switch.

### A malformed `SENTRY_API_URL` used to reject, and the test that hid it

`new URL` throws on a base with no scheme, and `findUserIssues` was building its URL _before_ the `try`, so a misconfigured `SENTRY_API_URL` rejected the promise outright rather than resolving to the `{ configured: false }` every other failure path in `lib/observability/sentry-issues.ts` returns. The function sits inside `readUser360` — a page an on-call support agent opens _during_ an incident — so a bad observability coordinate could take the support page down with it. A misconfigured base is a failure path, not a programming error, and the construction now sits inside the `try`.

The way that recurred is the part worth keeping. The regression test for it was a **false green**: `SENTRY_API_BASE` is a module-level `const`, read once at import, so a test that set `process.env.SENTRY_API_URL` inside its own body was still running against the valid default left by a previous `import`. It asserted the right thing and proved nothing. It passes only with `jest.resetModules()` and the env var set _before_ the first import, and the comment in `__tests__/observability/sentry-issues.test.ts` says so at the assertion rather than leaving it to be re-broken. A test that configures a module-level constant after the module has loaded is not testing the configuration; it is testing the default, and the default is the one value you already knew worked.

## What reaches Sentry today

Errors, performance traces (sampled) and Sentry Logs from all three Next.js runtimes on production and on every deploy preview; errors and messages from the bare-Node jobs on GitHub Actions; and, since the 2026-09-20 rotation, a `cron failed: <job>` event for every scheduled-job failure on Actions. Since #1868, a failed `SystemEvent` write is also reported — as an `expected: true` info event keyed on `[system-events] write failed`, which `INFRA_TRANSIENT_PATTERNS` throttles to one per class per ten minutes so a database outage trickles instead of flooding. Notably absent by design: replay, PII, anything from a job that forgot `initJobSentry()`, and any `console.error` (1,030 call sites; piping them in would recreate the 2026-09-21 flood and double-count every already-reported error).
