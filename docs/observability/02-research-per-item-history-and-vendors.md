# Research: per-item run history, needs-attention inbox, oldest-pending-age alerts

Date 2026-11-01. Research only; no repo changes. Labels: **VERIFIED** (official page fetched, URL given), **UNVERIFIED** (not confirmed from an official page), **ESTIMATE** (my arithmetic or judgement).

## 0. Verdict in six lines

> **Amended 2026-11-01.** The owner kept this verdict as the target but deferred item 2 until traction: while Better Stack stays on its free three-day plan, per-item history is the run row's `SystemJobExecution.result.failures` (at most 50 ids per run, 180-day prune). Items 4 and 5 are built. See [observability gaps and launch posture](../decisions/2026-11-01-observability-gaps-and-launch-posture.md).

1. No product gives "every attempt on payment X" without us emitting one event per item. Every candidate needs us to emit it; the question is only where it lands. Only the engine vendors (Inngest, Trigger.dev, Vercel Workflows) give per-run history for free, and only by adopting the engine, which the owner has ruled out for now.
2. Put per-item history in **Better Stack Telemetry as structured log events** (the pipe already exists in `lib/observability/betterstack-telemetry.ts`). It is SQL-queryable, alertable, OTLP-capable, and TTL is the vendor's problem, not ours. No Postgres table, no warehouse.
3. Keep **Sentry** for what it is good at: grouped errors (escalation-only), the `cron-tick` check-in monitor, and sampled traces. Do not send per-item events to Sentry (5k error quota; span sampling makes counts extrapolated, so a rare entity id may be missing).
4. "Current state" stays on the entity row (attempts, lastError, owed markers) and feeds the Needs-attention inbox directly from domain tables (what #2424 and #2453 already specify). Logs are the history, the row is the truth.
5. Oldest-pending-age: compute it in Postgres once per tick (one cheap aggregate per capability), emit it as a gauge log line, and alert in Better Stack on a SQL/threshold alert. No new table.
6. No warehouse now. Postgres with retention is enough pre-launch. First step when a trigger fires is a Supabase read replica or Parquet exports plus DuckDB, not BigQuery or ClickHouse.

Cost: about $0 added today, about $1 to $64 a month at launch. The low end is pay-per-GB logs at 1-5 GB with no responder (about $1 to $3; the vendor minimum charge is unknown); the high end, which is the selected launch plan, is the 30-day Nano bundle (about $30) plus one $34 responder licence for phone paging. Section 7 uses the same range.

**Verdict: two tools, split by question, as the owner already decided.**

- Sentry owns "what failed, grouped" (errors, the `job_run_id` tag, the `cron-tick` check-in).
- Better Stack owns "what happened, per item" (structured log events), "did it run" (heartbeat, uptime), "is work aging" (SQL alert on a gauge) and paging.

## 3. Per-item history design

Event shape for all options: the six required fields `run_id`, `job`, `entity_id`, `outcome` (ok / skipped / failed / held), `reason` and `attempt`, plus the optional extras `tick_id` and `duration_ms`. IDs only, never names or emails. That minimises disclosure but does not anonymise: `Payment.userId` references `User` and `readRootPayments()` in `lib/backoffice/entity-trace.ts` reads the customer's name from a payment id, so the events are pseudonymous personal data under [DPDP §2(t)](https://www.meity.gov.in/static/uploads/2024/06/2bf1f0e9f04e6fb4f8fef35e82c42aa5.pdf), as [Sentry identity and triage](./sentry/05-identity-and-triage.md) already holds for the Sentry cuid. EU placement does not change that; the processor, disclosure, access/erasure and retention assessment belongs in the processor inventory of [DPDP and privacy](../compliance/02-dpdp-and-privacy.md).

Enforcement: nothing in code enforces ids-only today. `emitTelemetryLog` spreads `log.context` into the payload last, so any key reaches Better Stack and a key named `dt`, `level` or `message` overrides the reserved field; `recordSystemEvent` (`lib/enterprise/system-events.ts`) mirrors every `SystemEvent` context through it. The per-item emitter must therefore build each event from the fixed field list above, with reserved fields set after any extras, and the existing `SystemEvent` mirror needs an audit of its callers' `context` keys (or an allowlist at the same boundary) before the rollout assessment can say "ids only" for all Better Stack events.

Lookup scope: entity ids are random `cuid()` or `uuid()` primary keys, so an `entity_id` is unique across tables in practice, and `job` names the entity type. Events carry no organisation scope because the reader is platform staff: the Entity trace is behind `requireBackofficePage("payments.read")`, and a Query API fallback must sit behind the same guard. Better Stack UI access is limited to platform staff accounts. If a tenant-facing view of these events is ever built, add `organization_id` to the event and enforce the tenant check before rendering.

## 4. Oldest-pending-age and the inbox

- Inbox: query the domain tables (refund owed, payouts failed/processing, unpaid invoice captures, dead-lettered outbox, recording copies) as #2424 and #2453 B specify. No new table.
- Age alert: once per tick, one `min(createdAt)`-style aggregate per money/compliance capability; emit `{metric:"oldest_pending_age_s", capability, value}` as a log line (or a metrics point); Better Stack SQL chart alert with a threshold per SLO. VERIFIED that Better Stack alerts support threshold conditions on SQL charts and can open an incident on missing data. Alternative with no Better Stack query dependency: add the ages to `/api/health/jobs` (bearer-protected), which `docs/maintenance/00-betterstack-setup.md` asks to be watched by an external HTTP monitor. ## 8. Build order (smallest first)

1. Make ingest observable before anything depends on it: record and surface 402, 403 and 5xx answers from Better Stack (today `emitTelemetryLog` awaits `fetch` and never reads the status), add a freshness check that fires through a channel independent of ingest when no gauge event has arrived for N minutes, and write a per-capability missing-data policy. Business work stays best-effort with respect to telemetry.
2. Add a **per-run batched** emit of the six fields. `emitTelemetryLog` sends one POST per call and `recordSystemEvent` calls it per event, so batching needs an owner: the run (inside `withCronLock`) buffers the items in memory and makes one array POST in its own finally step after the work commits, the same shape as `emitTickSummary()` in `netlify/functions/cron-tick.mts` but in the job's runtime. A failed or timed-out flush is counted and logged (step 1), never retried in-line and never fails the run. The payload is built from those fields only, never by spreading a `context` object. No per-row network calls.
3. Upgrade the Better Stack source to a plan with 30-day logs retention when real money traffic starts.
4. Emit `oldest_pending_age_s` per capability once per tick; one SQL alert per money/compliance SLO (#2492).
5. Entity trace: add a "Better Stack events" link built from `entity_id`; verify the Live tail URL format in the UI first.
6. Retention-audit issue from section 6 (OpsActionLog, ActivityLog, LedgerReconciliationReport decisions; `SystemJobExecution` checkpoint test).
