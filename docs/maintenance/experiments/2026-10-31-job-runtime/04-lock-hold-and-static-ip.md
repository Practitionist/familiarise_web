# Lock-hold measurement and static-egress verification (2026-10-31)

This report holds the last two experiments of the 2026-10-31 job-runtime series. Part A measures how long a row lock is held when the transaction runs from Frankfurt or from a laptop, and how long a competing user update waits. Part B checks which hosts can give a fixed outbound IP address, with the vendor page for each claim. The explanation and the decision context are in [Background-job runtime options](../../14-background-job-runtime-options.md). Statuses use the labels CONFIRMED (read on an official page) and UNVERIFIED (no primary source was read).

## Part A: lock-hold and interference

Setup: schema `lab_lock` with `account(id int pk, balance bigint, version int)`, 4 rows, on the shared Supabase DB via the Mumbai transaction pooler (port 6543). Trigger.dev task `lock-probe` (Free plan, prod environment, deployed versions 20261031.2 and .3, `region: "eu-central-1"`), pg 8.23.1 over plain `pg.Client`. Laptop baseline is node 26.9.0. The scripts are in [source-code.md](./source-code.md) under `lab-lock/`; the raw JSON stayed in the scratch directory.

### W1 (money-style, READ COMMITTED, FOR UPDATE)

The first table is run 1, the clean 10-round-trip transaction: `FOR UPDATE` + 8 statements + `COMMIT`. The hold is measured from just before the FOR UPDATE to the COMMIT ack, n=10 each. The table gives the hold per location.

| Location                 | median ms | p95 ms | per round trip (median/10) | raw (ms)                                          |
| ------------------------ | --------- | ------ | -------------------------- | ------------------------------------------------- |
| Trigger.dev eu-central-1 | 1258      | 1259   | 125.8                      | 1259,1258,1259,1258,1258,1258,1257,1257,1257,1258 |
| Laptop (39 ms RTT)       | 395       | 406    | 39.5                       | 406,393,395,395,395,395,394,397,393,395           |

Run 2 added one `clock_timestamp()` statement (11 round trips) so the user updates could be placed on the DB clock: Trigger.dev median 1379 / p95 1381 (125.4 per round trip), laptop median 435 / p95 464 (39.5 per round trip). The hold scales as round trips x RTT; DB execution time is negligible.

### Interference (run 2, DB-clock classification)

The laptop "user" issues `UPDATE ... SET balance=balance+1 WHERE id=1` roughly every 200 ms (autocommit, closed loop, about 5/s). In a closed loop one update blocks per hold, so only one update per hold is delayed; an open-loop 5/s arrival would queue about 5/s x hold seconds. The table gives the latency of that update in each scenario.

| Scenario                                          | n   | median ms | p95 ms | max ms |
| ------------------------------------------------- | --- | --------- | ------ | ------ |
| No-job baseline (20 s)                            | 99  | 37.6      | 44.1   | 68.5   |
| W1 from laptop: updates issued during a hold      | 10  | 274.9     | 367.9  | 367.9  |
| W1 from laptop: updates outside holds             | 12  | 39.6      | 45.4   | 45.4   |
| W1 from Trigger.dev: updates issued during a hold | 6   | 1110.1    | 1272.2 | 1272.2 |
| W1 from Trigger.dev: updates outside holds        | 72  | 47.5      | 53.6   | 61.6   |
| W1 from Trigger.dev: all updates (n=106)          | 106 | 47.4      | 1260.6 | 1303.9 |

Updates over 150 ms: 10 of 10 holds blocked exactly one update, for both laptop and Trigger.dev. The in-window row counts differ from 10 because the issue time is estimated from the DB timestamp minus latency; "blocked over 150 ms" is the unambiguous count. A blocked update waits for the rest of the hold: up to about 1.3 s from Trigger.dev versus about 0.37 s from the laptop. A single arrival lands uniformly in the hold, so expected wait is about half of it: about 0.6 s (Trigger.dev) vs about 0.2 s (laptop).

Caveat: run 1's interference classification used the laptop wall clock against the Trigger.dev container clock and was skewed (it showed only 44 ms medians for "during hold"), so it is discarded. Run 2 uses `clock_timestamp()` from the DB.

### W2 (SERIALIZABLE, same statements, 2 concurrent copies x 20 iterations = 40 txns per location)

The table counts commits and serialization failures (SQLSTATE 40001) per location.

| Location                 | committed | SQLSTATE 40001 | other errors |
| ------------------------ | --------- | -------------- | ------------ |
| Trigger.dev eu-central-1 | 20        | 20             | 0            |
| Laptop                   | 20        | 20             | 0            |

In both locations exactly one of each concurrent pair failed (50 percent), because both read and update the same row. Run 1's Trigger.dev W2 (0 committed, 40 failures) was contaminated by the user update loop running at the same time, and was redone without it (run 2, above). The laptop run-1 W2 also gave 20/20.
