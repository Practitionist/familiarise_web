# Cron Jobs Reference

The platform runs **5 scheduled GitHub Actions workflows** (`cron-intra-day.yml`, `cron-daily.yml`, `cron-weekly.yml`, `cron-heartbeat.yml`, and `stream-webhook-drift.yml`) executing 43 background maintenance, compliance, and reconciliation scripts alongside the Netlify sub-hour scheduled function (`netlify/functions/cron-tick.mts`). Each CLI job boots a bare Node process with `tsx`, connects straight to PostgreSQL through Prisma, acquires a distributed lock via `withCronLock`, checks `abortIfMaintenance()`, and exits.

Every HTTP cleanup twin is served by the unified dynamic route `app/api/cleanup/[job]/route.ts` backed by `lib/cron/cleanup-registry.ts`.

## Universal Cron Locking & Heartbeat

Cron locking is now universal. Before PR 6 of that train, one scheduled job ran with no mutual exclusion of any kind, and nothing in the repository could tell you that. Today every scheduled workflow either takes a `withCronLock` lock or holds a documented bespoke lock, and `__tests__/maintenance/cron-lock-registry.test.ts` re-derives that claim from source on every CI run, so the next unlocked job fails the build instead of quietly double-running for a year.

The same PR gave the fleet a way to notice its own death. Every locked run refreshes a single Redis key, `cron:heartbeat:last`, and `GET /api/health` reports its age under `cron`. If that key goes stale for more than 45 minutes the scheduled fleet has stopped — the one failure the Actions-API heartbeat below cannot report, because it would have stopped too.

## What changed in #1270

Running is not the same as being importable, and until #1270 nothing checked the difference. Five of these workflows had never completed a single run: their entrypoints reached `lib/supabase.ts`, which opens with `import "server-only"` — a marker package whose main entry does nothing but throw. Next resolves it to an empty module under the `react-server` export condition, and every other resolver, including the bare Node process a workflow runs, gets the throw. Each of those jobs therefore died during module evaluation, before a line of its own code ran, on every run it had ever had.

Nothing surfaced it. The workflows went red, but they are low-traffic housekeeping jobs that nobody watches, and the consequences accumulate silently rather than breaking a user-facing path: recordings past their organization's retention window were never tombstoned and their Supabase objects were never deleted, which is a DPDP erasure gap; permanent-storage transfers never ran, so `STREAM_ONLY` recordings simply lapsed when Stream's fourteen-day URL expired; soft-deleted documents were never purged from storage; and the sweep that re-drives stuck webhook events was itself stuck.

Building that guard immediately turned up a second, larger instance of the same class. Eight further workflows — `process-payouts`, `handle-stuck-payouts`, `reconcile-payout-status`, `reconcile-payment-status`, `sync-payment-earnings`, `handle-lost-disputes`, `reconcile-orphaned-confirmations` and `sweep-stuck-webhook-events` — reached `lib/auth-server.ts`, which called React's `cache()` at module scope. The version of React this repository actually pins, 18.3.1, has no `cache` export at all; the call resolved inside the application only because Next aliases `react` to its own vendored React 19 in the RSC layer, which `lib/auth-server.ts` already documents. A bare Node process got the declared React and a `TypeError`, so every one of those eight jobs died during module evaluation exactly as the five above did. Seven arrived there through `lib/payments/payouts/earnings-service` → `lib/collaborators/service` → `actions/stream/chat/event-channel.action`, and the eighth through the Razorpay webhook dispatcher. PR #1281 closed it by building the session memo on first call rather than at import, so the `cache()` call happens on first use inside a request rather than at module load — the correct behaviour for a one-shot cron process, not a degraded one. `KNOWN_UNRUNNABLE` in `__tests__/maintenance/workflow-import-env.test.ts` has been empty since #1281, and the test fails if a job quietly starts reaching an unloadable module again, so the register cannot silently regress.

Two things now prevent a repeat. The Supabase clients and storage primitives a job needs live in `lib/supabase-storage-core.ts`, which carries no marker, and `lib/supabase.ts` re-exports them so application code is unchanged and still gets its client-import guard. And `__tests__/maintenance/workflow-import-env.test.ts` re-derives every scheduled workflow's import graph on each CI run, failing when one reaches a `server-only` module or when a job that reaches the Supabase client module is not given the two environment variables that module throws without.

## What changed in #1356

The 2026-09-03 financial audit re-measured GitHub Actions' sub-hourly schedules and confirmed the finding ADR 22 first recorded: an every-minute schedule delivers roughly once every hundred minutes rather than once a minute, because GitHub throttles scheduled workflows rather than dropping them outright. `netlify/functions/cron-tick.mts` closes that gap for the ten sweeps where the delay matters most. It is a Netlify scheduled function that fires every five minutes and POSTs each of the following, relative to `/api/cleanup/`, with a `CRON_SECRET` bearer token and a six-second per-target timeout: `sweep-stuck-webhook-events`, `cascade-refund-earnings`, `reconcile-refunds`, `abandoned-payments`, `reconcile-payment-status`, `reconcile-orphaned-confirmations`, `sweep-orphaned-topup-captures`, `dispatch-outbound-webhooks`, `sync-payment-earnings`, and `release-earnings`. ADR 27 records why this is a scheduler fix rather than a new outbox table: the durable state an outbox exists to provide already lives on the domain rows — `Payment`, `Appointment`, `Refund`, `WalletTopUp`, `WebhookEvent`, `OutboundWebhookDelivery`, `FailedEmail` — that these sweeps already walk.

Every tick request carries a `?limit=`, and every route above reads it as an optional cap on the batch a single run may touch, defaulting to today's behaviour when the parameter is absent, so a nightly GitHub Actions run still processes the whole backlog while a five-minute tick stays inside its own budget. The default the ticker sends is fifty, but a target may override it: `abandoned-payments` is sent ten, because its per-row cost includes a gateway cancel round trip rather than a database write alone, and at fifty it could not finish inside the six-second per-target timeout (#1459). Whatever a smaller bite leaves behind is picked up by the unbounded GitHub Actions run.

That paragraph was true of the ticker and false of five of its targets until #1846. `expire-stale-requests`, `reschedule-proposals`, `appointment-reminders`, `tentative-occurrences` and `expire-unpaid-trials` all wrote `run: () => core()` — a callback that never receives the request — so the limit was appended to the URL and thrown away, and each tick ran the Actions-sized cohort inside a 6 s or 20 s abort. `appointment-reminders` was the worst of them: its cohort read had no `take` and no `orderBy` at all, in either the ticker path or the Actions one. All five now read the parameter, and each route supplies its own floor through `parseLimitParamOrDefault` so that a caller with no `?limit=` — a hand-rolled `curl`, an operator probe, a future scheduler — is bounded too. A limit enforced by one caller is a limit that disappears with that caller.

The bites are per-target in `TARGET_LIMITS` and small relative to each core's own Actions figure: 25 / 20 / 25 / 200 / 25 respectively. `expire-stale-requests`' figure is per cohort arm across seven arms, because a gateway refund may follow each expiry. They are budgets rather than drops, and the property that makes them so is worth stating because it is not universal: every one of the five is ordered (soonest-first for reminders, oldest-first for the rest), capped, holds no persisted cursor, and writes rows that LEAVE its cohort — `EXPIRED`, `CANCELLED`, a soft-cancel tombstone, or a staged `FailedEmail` for a reminder. A cap on a read with no such exit would silently truncate the backlog on every run.

`appointment-reminders` is the one that is only conditionally resumable, and it says so in the log. The `FailedEmail` row its email twin stages is now read back to skip an appointment already reminded for that window, so a re-read of a capped batch is a no-op rather than a repeat — but the cohort has no persisted position, so a window holding more sessions than the cap loses the tail of that window's reminders. The two-hour 24 h window drains over successive ticks; the 1 h window is thirty minutes wide against a fifteen-minute tick, so a burst wider than the cap in half an hour does lose 1 h reminders, and the run logs `appointment_reminders_window_capped` when it happens. The alternative — no cap — loses every reminder in a window that overflows a 20-second abort, which is strictly worse and much harder to notice.

A tick and a GitHub Actions run of the same job cannot both proceed: both go through the same `withCronLock` every entrypoint already shares, so the loser answers 409. The ticker records a 409 as `lockHeld`, not a failure, because the run that lost the lock is a run that did not need to happen — the winner is already doing the same work. A target that refuses with a 503 whose body carries the maintenance `phase` — a healthy hold, not a broken target — sorts into the same `held` bucket as a 409 rather than into `failed`, because a twin refusing inside DEGRADED or OFFLINE is expected behaviour; a bare 503 with no `phase` marker stays `failed` (#1598 P1-W03). Only a response outside `200`, `207`, `409` and a maintenance-marked `503` counts as `failed`. `docs/guides/cron-setup.md` covers running the ticker locally.

Three of the ten ticker sweeps — `sweep-stuck-webhook-events`, `reconcile-orphaned-confirmations` and `sweep-orphaned-topup-captures` — do move money, but they do it by re-driving a webhook that DEGRADED already exempts rather than by opening a new financial object, so they are deliberately absent from `FINANCIAL_JOB_NAMES` (`lib/maintenance-cron.ts`) and keep running in DEGRADED. A webhook DEGRADED lets through unconditionally must be safe to re-drive from these sweeps too, or the exemption and the sweep parity break in opposite directions.

GitHub Actions still owns every daily and weekly business cron, but it is not a backstop for ticker targets: a job listed in `TARGETS` in `netlify/functions/cron-tick.mts` runs only on the ticker unless a workflow also names it, and `__tests__/maintenance/cleanup-job-scheduler-drift.test.ts` fails for any registry job with no scheduler.

## Set-Based Ledger Reconciliation

`scripts/reconcile/reconcile-ledgers.ts` executes all fourteen ledger and cache invariants using single-pass set-based SQL aggregations (`$queryRaw` / `groupBy`) in ~1–2 seconds. Both `POST /api/admin/reconcile-ledgers` and `POST /api/cleanup/reconcile-ledgers` invoke `runReconcileLedgers` synchronously in-process under `withCronLock("reconcile-ledgers")`.

## Outbox-First Email & Notification Relays

Email and Novu triggers became outbox-first: every transactional email is a `PENDING` `FailedEmail` row before Resend is called, and every Novu trigger is a `NotificationOutbox` row before Novu is called, with one inline attempt under a time budget and a relay for whatever that attempt could not settle. The relays are two ticker targets. `retry-failed-emails` gained the CRON_SECRET twin `POST /api/cleanup/retry-failed-emails` (built with `cleanupRoute`, accepting `?limit=`), and `cron-tick.mts` posts it with `?limit=20` and a 20-second per-target timeout on every tick whose UTC minute is a multiple of fifteen, which is the ticker's first target with a cadence other than every tick; `dueTargets(now)` in the ticker decides, and a tick that fires a few seconds late still counts as its slot because the check is `minute % 15 < 5`. The worker itself now paces one send every 125 milliseconds, because Resend's team limit is ten requests a second and the inline fast path sends alongside it, and each send carries the job budget as an abort signal so one hung call cannot hold the tick past the function ceiling. The GitHub Actions workflow `retry-failed-emails.yml` is unchanged and remains the unbounded backstop (#1648). The new `drain-notification-outbox` job (`scripts/notifications/drain-notification-outbox.ts`, twin `POST /api/cleanup/drain-notification-outbox`) has no Actions workflow: the ticker posts it with `?limit=20` on every five-minute tick, it takes the fail-closed lock `drain-notification-outbox`, and it walks the same backoff ladder as the email relay with five attempts before a row is dead-lettered. Both twins answer 500 when the run reported an error (an unconfigured provider), so the tick's JSON shows them under `failed` rather than `ok`. The design and the budgets are in [docs/notifications/01-architecture.md](../notifications/01-architecture.md) and issue #1654.

## How to read the tables

Every scheduled workflow appears exactly once, grouped by the part of the product it serves. The columns mean the following.

**Schedule** is the raw cron expression in UTC, exactly as GitHub receives it. Treat it as an upper bound rather than a promise, not the delivered cadence (ADR 22): GitHub throttles scheduled workflows under load, and a job asking for every minute has been measured delivering roughly once every hundred minutes. For the ten money sweeps the Netlify ticker drives — see [What changed in #1356](#what-changed-in-1356) below — the schedule column is no longer the cadence that actually holds; the ticker's five-minute interval is (ADR 27). Minutes are deliberately staggered across the fleet so that simultaneous starts do not stampede the Supavisor connection pool, which `scripts/ci/check-workflow-hygiene.ts` enforces.

**Entrypoint** is the file the workflow or `lib/cron/cleanup-registry.ts` executes (`scripts/**` or `jobs/**`). Every HTTP cleanup twin is served by the dynamic route `app/api/cleanup/[job]/route.ts`, which looks up the job handler in `lib/cron/cleanup-registry.ts` and enforces `CRON_SECRET` authentication and `assertNotInMaintenance()`. The lock lives on the core so that every entry point inherits it.

**Lock** records how the job behaves when Redis cannot be reached. A **closed** job refuses to run and pages, on the reasoning that a missed money run is recoverable and a silent unlocked double-run is not. An **open** job runs unlocked with a warning, which is correct for work whose side effects are harmless to repeat. **bespoke** means a hand-rolled `acquireLock` predating the wrapper, and **none** means deliberately unlocked; both are enumerated and justified under [Locking](#locking) below.

**Financial** reflects membership of `FINANCIAL_JOB_NAMES` in `lib/maintenance-cron.ts`. These jobs create or cancel financial objects through an external API, or mutate earnings, payouts and refunds, so a partial deployment can leave them inconsistent.

**During maintenance** is derived, not asserted. A job that calls `abortIfMaintenance()` exits cleanly when the maintenance phase is OFFLINE, and a financial job additionally exits when the phase is DEGRADED. A job that never calls it runs regardless of the phase, and is marked **Runs anyway** — see [Jobs that ignore maintenance mode](#jobs-that-ignore-maintenance-mode).

`cleanup-abandoned-payments` cancels each abandoned payment's gateway intent before it expires the row, and the expiry no longer waits on that cancel succeeding. A cancel that fails is recorded in `errors` and counted in `errorCount`, so the run reports `success: false` and the HTTP twin at `/api/cleanup/abandoned-payments` answers 500 rather than the 200 it used to force; the payment still moves PENDING→EXPIRED through its CAS in the same transaction that hands back the referral credits and releases the hold. Skipping that write was how a Payment came to sit PENDING for ever beside a slot that had already been released — a row no later sweep could see, because nothing about it still looked abandoned (#1464). The Stripe arm also respects the #1386 fence: with `STRIPE_ENABLED` set to anything other than `true` the sweep makes no gateway call at all and logs one line per run saying so, and when the fence is open an intent Stripe cannot find, or one that is already terminal, counts as nothing to cancel rather than as a failure.

`reconcile-disputes` only reaches a gateway for Stripe disputes, and Stripe is fenced off in production, so when `STRIPE_ENABLED` is anything other than `true` the sweep leaves those disputes alone and counts them as `skippedFenced` rather than failing the run on a gateway we deliberately turned off (#1459); Razorpay disputes were already routed to manual dashboard review and are counted separately. Its HTTP twin no longer forces a 200 either, so a run that genuinely failed now answers 500 like every other sweep.

Two changes originally followed Netlify's answers to ticket #1112198 (2026-09-16/17). First, instances were temporarily kept warm by a separate scheduled function, `netlify/functions/keep-warm.mts` (PR #1685), which ran every four minutes and fired `KEEP_WARM_CONCURRENCY` (default 3) parallel unique-key requests at `/api/perf/probe-bare`. **Retired and deleted in PR #1972 (2026-10-03):** profiling `NextNodeServer` proved the ~28 s cold-start stall was caused by Next.js 15's default `preloadEntriesOnStart: true` and `appDocumentPreloading: true` under `@netlify/plugin-nextjs` v5's `minimalMode: false` (executing 1.67M `webpackRequire` calls across all 606 routes and exhausting Node 22's 512 MB V8 heap cap). Setting both flags to `false` in `next.config.mjs` brought 12-way cold-start bursts down to `0.97–1.90 s`, allowing `keep-warm.mts` (and its 32,400 monthly probe invocations) to be deleted. Second, six sweeps now run on the fifteen-minute slots instead of every tick — `reconcile-ledgers`, `sync-payment-earnings`, `release-earnings`, `cascade-refund-earnings`, `reconcile-refunds`, `abandoned-payments` — because each one's GitHub Actions twin already runs at fifteen minutes or slower, a five-minute tick on twelve parallel targets was a twelve-way cold burst that Netlify bills as duration, and none of the six delays anything a customer watches; the customer-visible sweeps `sweep-orphaned-topup-captures`, `dispatch-outbound-webhooks` and `sweep-stuck-webhook-events` also run on the fifteen-minute slot (#1792), while `drain-notification-outbox` runs every ten minutes because it has no Actions twin at all. `reconcile-payment-status` and `reconcile-orphaned-confirmations` were every-tick too, as the two latency-sensitive money confirms with no Actions twin at equal cadence, until the Upstash 500k Redis-command cap was hit a second time on 2026-09-25 with those two as the largest remaining every-tick cost (#1822 Q-3): both now ride the fifteen-minute slot alongside their siblings, each already having a thirty-minute Actions twin as the backstop. The map is `TARGET_EVERY_MINUTES` in `netlify/functions/cron-tick.mts`; the reasoning and the invocation arithmetic are in issues #1686 and #1822, with phase-stagger offsets (`TARGET_OFFSET_MINUTES`: 0, 5, 10) added in #1926.

The ticker answers 200 on every invocation since 2026-09-18, including a tick in which a target failed, and the `{"event":"cron-tick",…}` line it logs is where the outcome lives. It used to answer 500 whenever `failed` was non-empty, on the #1390 review's reasoning that a tick should not self-report healthy; what that actually bought was observed in the production function logs on 2026-09-17: Netlify re-invokes a scheduled function that answers 5xx, up to three attempts 4 to 11 seconds apart, and each attempt re-fires every due target, while the `keep-warm` function, which answers 200, fires exactly once per slot. Because `reconcile-payment-status` had been answering 500 on every tick for weeks, the ticker had been running at three times its declared cadence, and the invocation arithmetic in #1686 and in the keep-warm log (which assumed one invocation per tick) was about three times too low for the ticker. A 5xx from a scheduled function therefore buys three invocations and nothing else: the target's own route has already logged its failure message, the GitHub Actions twin is the backstop for a sweep that keeps failing, and a warm-tick failure is read by looking for a non-empty `failed` list in the tick's JSON line (a status of `0` there is a timeout or network failure on the ticker's side; any other status is the route's own answer). `statusFor` in `netlify/functions/cron-tick.mts` returns 200 unconditionally and `__tests__/maintenance/cron-tick-targets.test.ts` pins it.

`reconcile-pending-refunds` polls a real-id `PENDING` refund until the gateway itself reports it settled or failed and never ages it out locally, with one exception: a Razorpay lookup answered with HTTP 400 `BAD_REQUEST_ERROR` / `input_validation_failed` means the gateway has no record of that id (an unknown id, or a test-mode id read with live keys), which no later poll can change, so the row is moved to `FAILED` through a CAS on `PENDING` with a `failureReason` saying the customer was not refunded, reported once as an expected warning, and counted as `failedUnknownId` in the summary (FAMILIARISE_WEB-3V). Every other lookup error is logged and retried on the next tick.

`reconcile-payment-status` asks the gateway about every `PENDING` payment older than five minutes and younger than seven days that carries a non-empty `paymentIntent`, and it now tells two answers apart that used to share one `null` (#1708). A gateway that has no record of the id — Stripe's `resource_missing` (or an HTTP 404), Razorpay's 400 `BAD_REQUEST_ERROR` or 404 on the order — is a terminal outcome for that row: no later tick can change it, so the row is counted in `unresolvableCount`, its id listed in `unresolvable`, and the run stays `success: true`; the HTTP twin answers 207 while any such row exists so the ticker shows attention rather than `ok`, and one Sentry warning per run (fingerprinted on `reconcile-payment-status` / `unresolvable`) counts up instead of opening an event per row per tick — and since #1822 Q-4 that per-run warning is itself deduped to at most once per 24h per distinct stuck-id set, via a `SystemEvent` correlation id, so the same unresolved rows do not re-mint a fresh Sentry event on every tick until they resolve or age into the #1757 retire path. The reconcile does not expire, fail or otherwise write those payments — a reconcile never mutates `Payment` on its own judgement (ADR 21), and `cleanup-abandoned-payments` owns expiry. A gateway that could not be reached at all — a thrown fetch, a 5xx, or a 401/403 on our key — is still a run failure: the row is counted as skipped, the message lands in `errors`, and the twin answers 500, which is what that status is for. Before this split thirteen seeded rows with UUID-shaped intents made the route answer 500 on every five-minute tick for a week, so the ticker's `failed` list was permanently occupied and a real outage would have been invisible. #1822 Q-3 moved this target off every tick onto the same fifteen-minute slot as its siblings — see the cadence paragraph above.

`reconcile-orphaned-confirmations` runs two passes per invocation, because a capture can fail in two independent places. The first is the original #830 sweep: it finds `SUCCEEDED` payments whose slots are still tentative and re-runs the confirmation under the webhook's own Serializable discipline; "tentative" here means a live hold, matched with the shared `liveOccurrenceWhere` fragment, because a reschedule releases a row in place by flipping it to `RESCHEDULED` while leaving `isTentative` set, and without that filter the sweep re-selected every rescheduled booking on every tick and the confirm flipped the released row back into the consultant's calendar (FAMILIARISE_WEB-46). The second, added by #1356, repairs the post-capture chat leg — appointments that are paid and confirmed but whose `chatChannelEnsuredAt` is still `NULL`, limited to the last seven days and processed oldest first. It calls the same `ensureChannelsForAppointment` the live pipeline calls, so the two cannot drift, and it reports `channelsEnsured`, `channelsFailed` and `channelsSkipped` alongside the existing counters. A run in which any channel failed answers 207 rather than 200: the next run will retry it, but an operator should see that a buyer is currently without a conversation.

Two outcomes of that pass are terminal rather than retryable, and since #1708 the sweep marks them itself. When Stream's DM rule throws `DmNotPermittedError` (the two users share no booking, so no retry can ever mint the channel), or when `ensureChannelsForAppointment` reports `no_channel_branch_for_appointment` (nothing short of a code change adds one), the sweep stamps `Appointment.chatChannelEnsuredAt` through the same `updateMany` scoped to `NULL` that a successful ensure uses, counts the row in `channelsSkipped`, logs one warning line naming the reason, and raises one Sentry warning per run (fingerprinted on `reconcile-orphaned-confirmations` / `dm_not_permitted`) with the appointment ids. The stamp therefore now means "ensured or decided", not only "ensured"; a dedicated `chatChannelSkippedReason` column would have said which, but the schema is frozen ahead of the pre-MVP reset and the reason is in the log and the Sentry event, so the existing column carries both meanings until the reset window reopens the schema. `appointment_not_found`, `consultant_not_resolved` and any other throw keep the `channelsFailed` retry behaviour, because a data repair can still make those succeed. The Netlify ticker gives this target a 20 s budget and a `?limit=10` (one Stream round trip per unchanneled row, so ten fits comfortably; fifty under the 6 s default was aborted on every tick, which left the cron lock held for the next tick and the pass never converged); the target ran on every five-minute tick because a paid booking without its confirmation or its conversation is customer-visible (#1686), until #1822 Q-3 moved it to the fifteen-minute slot with its thirty-minute Actions twin as the backstop, trading a wider worst-case gap for staying under the shared Redis-command cap.

Known seed rows (2026-09-14): the reset's seed created thirteen `PENDING` payments with UUID-shaped `paymentIntent` values (three `RAZORPAY`, one `STRIPE`, five `CARD`, four `DODO_PAYMENTS`) and twenty-four appointments with a `SUCCEEDED` payment and no channel stamp, several of whose parties share no booking under the DM rule. The seed now stamps every appointment it creates with `chatChannelEnsuredAt` so the chat pass never selects seeded rows again (`prisma/seedFiles/6a-create-appointments.ts`, #1708). The payment half is documented rather than changed: `Payment.paymentIntent` is `@unique`, so seeding `PENDING` rows with an empty intent (the value the reconcile skips) would collide on the second row, and narrowing the seeded status pool is a wider change than this fix; the thirteen rows are reported as `unresolvable` (207) until they age out of the seven-day window on 2026-09-21, and any future seed run produces the same class of row until the seed suite is revisited.

That job also has an HTTP twin at `/api/cleanup/reconcile-orphaned-confirmations`, which accepts an optional `?limit=` (a positive integer up to 500) and applies it to both passes. The GitHub Actions entrypoint has minutes to spend and uses the defaults; a Netlify ticker calling the route on a short schedule does not, and passing a small limit lets it take a bounded bite of each backlog per invocation instead of exhausting the function budget on one of them. An unparseable value is refused with a `400 INVALID_LIMIT` and a value above the cap is clamped to it, which is the shared `parseLimitParam` behaviour every other ticker target already had; the route used to swallow a malformed bound and sweep the defaults instead, which hid a broken caller behind a run that looked healthy (#1459).

## Jobs that ignore maintenance mode

Three of the 67 scheduled jobs never call `abortIfMaintenance()`. It used to be twelve, and the twelve included six jobs that move money or rewrite the org entitlement state the checkout resolver reads — `dunning`, `advance-program-cycles`, `auto-renew-contracts`, `expire-contracts`, `timeout-member-overages` and `release-pending-trust-earnings` — as well as `wallet-low-balance`, which only flags a low wallet and sends the alert. All of them now carry the guard. The six that move money joined `FINANCIAL_JOB_NAMES` at the same time, so they exit on DEGRADED as well as OFFLINE; `wallet-low-balance` did not, so it exits on OFFLINE only. `auto-renew-contracts` and `expire-contracts` were additionally flipped from fail-open to fail-closed locks, because a financial job that keeps running while Redis is unreachable is exactly the window in which two runners both believe they hold the lock.

The three that remain are deliberate.

- `cleanup-empty-folders` — scripts/utils/cleanup-empty-folders.ts. Touches Supabase storage objects only and never opens a database connection, so a migration cannot catch it mid-write.
- `cron-heartbeat` — scripts/ci/check-cron-heartbeat.ts. The dead-man switch itself. Silencing the watchdog during maintenance would mean the one window in which the fleet is most likely to stop is also the window in which nobody would notice.
- `stream-webhook-drift` — scripts/stream/ensure-webhook-subscription.ts. A read-only drift check against Stream's app settings; the whole run is one API read.

The same sweep closed the other half of the hole. The forty-odd HTTP twins under `app/api/cleanup/` import these job cores directly and had no guard at all, so an ops trigger ran the job straight through an OFFLINE window. They cannot call `abortIfMaintenance()`, whose `process.exit(0)` would take the Next instance down with the request, so they call `assertNotInMaintenance()` instead: the same phase rule, surfaced as a `MaintenanceActiveError` the handler answers with 503.

The GST outward-supplies register export joined that cohort in #1370. Its twin lives at `app/api/cleanup/gst-outward-register-export` and imports `runGstOutwardRegisterExport` from the job module, which is where the fail-closed `gst-outward-register-export` lock is taken, so an HTTP call that overlaps the scheduled run answers 409 instead of racing the gapless invoice series. The one thing the twin does differently is that it does not write the CSV: a serverless filesystem is read-only and nothing would collect the file, so the HTTP path heals the missing invoices, stamps `gstr1ExportedAt` and reports the counts, while the Actions run remains the way a CA actually obtains the file.

Two more joined it in #1407, closing the last gaps in the "every job has an HTTP twin" rule. `app/api/cleanup/settle-invoice-accruals` imports `runSettleInvoiceAccruals` from `scripts/billing/settle-invoice-accruals.ts`, and `app/api/cleanup/tds-return-draft` imports `runTdsReturnDraftExport` from `scripts/compliance/tds-26q-draft-export.ts`. In both cases the exported function is where the cron lock is taken — fail-closed on the accrual rollup, because two overlapping runs would each roll the same accrual set into an invoice, and fail-open on the return draft, because that export only reads. Neither exported core calls `abortIfMaintenance()`; the maintenance guard stays on the entry points, so the Actions run exits the process and the route answers 503.

The TDS job needed one structural change to make this possible. Its `main()` used to run at import, which meant that merely importing the module from a route would have fired the quarterly export; it is now behind the usual `require.main === module` guard, the shape the other ten job modules already use. The twin runs with the same defaults as the schedule — the quarter that closed, not the quarter containing today — writes the same full-PAN CSV to the private finance bucket, and returns the storage path instead of a GitHub artifact, since there is no artifact store on the HTTP path.

#1407's claim that the last gap had closed was itself wrong: `detect-consultant-no-shows` had no HTTP twin at all, unlike every one of its 46 siblings, so neither the Netlify ticker nor a hand-rolled `CRON_SECRET` probe could drive it (#1517). `app/api/cleanup/detect-consultant-no-shows` now imports `detectConsultantNoShows` from `scripts/appointments/detect-consultant-no-shows.ts`, the same core the GitHub Actions job runs, and inherits that core's fail-closed lock and `FINANCIAL_JOB_NAMES` membership.

Both this job and `auto-complete-appointments` joined the ticker in #1846 on a 30-minute slot: each issues a refund or releases earnings, and Actions delivers an hourly schedule roughly once per hundred minutes (ADR 22). `__tests__/maintenance/cron-tick-targets.test.ts` pins both.

Both jobs also had unbounded cohorts, which is the other half of why they were absent: `auto-complete-appointments`' five parent passes read with no `take` and no `orderBy` at all, and `detect-consultant-no-shows`' candidate read was the same. Each is now oldest-first with a per-run cap (`MAX_PARENTS_PER_RUN`, `MAX_CANDIDATES_PER_RUN`), each cap is overridable per invocation, and each route reads `?limit=` — which neither did. The removals were not safe to skip: a 20-second abort landing mid-loop left some parents completed and others abandoned with no record that it had happened.

## Locking

`withCronLock` (`lib/cron/with-cron-lock.ts`) provides distributed mutual exclusion keyed `cron:lock:<jobName>`, with a fifteen-minute TTL by default and thirty-five minutes for the payout and reconcile family. It exists because the same job can be entered three ways — the schedule, a manual `workflow_dispatch`, and an authenticated HTTP call — and jobs whose side effects are only partially idempotent must not run twice concurrently.

It is a mutual-exclusion tool and nothing more. Data correctness comes from compare-and-set transitions and unique constraints, never from this lock, because Redis and PostgreSQL are separate failure domains and the lock can be lost without the database noticing. ADR 13 records that reasoning in full.

Every scheduled workflow also declares a workflow-level `concurrency: { group: ${{ github.workflow }}, cancel-in-progress: false }`, a second and redundant guard at the Actions layer that queues an overlapping run rather than killing one mid-flight; `withCronLock` remains the correctness guard, and `__tests__/maintenance/cron-lock-registry.test.ts` asserts the concurrency block is present on every scheduled entry so the two guards cannot drift apart. GitHub Actions allows one running and one pending run per concurrency group by default, and a newer run replaces the pending one rather than queuing behind it; the twelve workflows that also accept `workflow_dispatch` add `queue: max` so a second manual trigger cannot silently displace one already waiting, up to a hundred pending runs.

Four scheduled workflows do not use it, each for a stated reason.

| Workflow               | Mechanism                    | Why not `withCronLock`                                                                                                                                                                                                                 |
| ---------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `process-payouts`      | `lock:payout_processing`     | Predates the wrapper and additionally guards the HTTP approval path, which the `cron:lock:` key shape does not reach.                                                                                                                  |
| `create-payout-batch`  | `lock:payout_batch_creation` | Same lock family as above, held across a batch that outlives the default TTL.                                                                                                                                                          |
| `cron-heartbeat`       | None, deliberately           | Locking the dead-man switch through Redis would make the watchdog depend on the infrastructure it exists to report on. The check is read-only, so a double-run costs nothing.                                                          |
| `stream-webhook-drift` | None, deliberately           | A read-only drift check rather than a job. The whole run is one `getAppSettings` call, so a concurrent second run costs one extra API request, and a lock would give a guard a hard dependency on the infrastructure it does not need. |

Each entry is mirrored in `LOCK_EXEMPT` in `__tests__/maintenance/cron-lock-registry.test.ts`. That test fails both when a new workflow appears without a lock and when an exempt workflow grows a real one, so the table above cannot rot without CI saying so.

## Watchdogs

Two independent mechanisms answer "is the fleet still alive", and they are independent on purpose.

The first is `cron-heartbeat`, which runs daily and queries the GitHub Actions API for the last run of every scheduled workflow, failing when any of them has gone quiet for longer than its cadence allows. It catches the common case, including GitHub automatically disabling schedules after sixty days of repository inactivity. It cannot, however, report the case where schedules stop fleet-wide, because it is itself a scheduled workflow and would stop with them.

The same daily run also carries a third watchdog since #1822 Q-8: an Upstash usage alarm that reads the database's monthly command count from Upstash's management API and warns at 70% and 90% of the plan cap through the shared throttled-capture path. It is entirely optional — it needs the `UPSTASH_MANAGEMENT_API_KEY`, `UPSTASH_EMAIL` and `UPSTASH_DATABASE_ID` secrets, a different credential from the per-database REST token every other Redis call in this repo uses, and skips silently when any of the three is unset. The threshold comes from the `UPSTASH_MONTHLY_COMMAND_CAP` repository variable, which holds a monthly command count, never a dollar amount: the plan cap of 500,000 commands on the free tier, or a chosen command budget such as 2,000,000 on pay-as-you-go; when it is unset the run logs the month's usage and raises no alarm, because a free-tier default would mis-alarm a pay-as-you-go database. The stats request is abandoned after 15 seconds, and a failed request is reported as a warning without failing the heartbeat job.

The second closes that gap from the other side. Every locked run refreshes `cron:heartbeat:last` in Redis, the daily heartbeat check refreshes it too, and `GET /api/health` exposes its age:

```json
{
  "cron": {
    "configured": true,
    "lastRunAt": "2026-08-14T04:40:12.000Z",
    "stale": false
  }
}
```

`stale` turns true once the key is older than 45 minutes, and is `null` before the fleet has ever written one, when Redis is not configured, or when the stored timestamp will not parse — the last of those is a heartbeat we cannot date, which the probe treats exactly like one that was never written rather than guessing at an age. When the probe itself fails, `stale` is the string `"unknown"` and a `probeError: true` field appears alongside it. Those two cases used to be indistinguishable: an unreadable Redis returned exactly the same body as a fleet that had never run, so a monitor watching the field could not tell an outage from a cold start. Because this is an ordinary HTTP field, an external uptime monitor can watch it with no dependency on GitHub at all. Both the heartbeat write and this probe are fail-open: neither may ever be the reason a job fails or a health check errors.

## Keeping this page true

This page is generated from the repository, so it is only as current as its last regeneration. The mechanical claims — how many workflows exist, which are locked, which are fail-closed, which are financial — are additionally asserted by `__tests__/maintenance/cron-lock-registry.test.ts`, so those cannot drift silently even between regenerations. The prose, the **Mutates** column and the group headings are hand-written and need a human to revisit them when a job's purpose changes.

When adding a scheduled job, the checklist is: give it a `scripts/**` or `jobs/**` core, register its HTTP handler in `lib/cron/cleanup-registry.ts` (served by `app/api/cleanup/[job]/route.ts`), wrap the core in `withCronLock` with a deliberate `failMode` stated as a string literal rather than computed, call `abortIfMaintenance()` in the CLI entrypoint, add the job name to `FINANCIAL_JOB_NAMES` if it touches money, pick a cron minute within the pool budget if adding a GitHub Actions schedule, keep every module in the entrypoint's import graph free of `server-only`, give any workflow every environment variable those modules read at import time, add the failure-notification step, and add a row here.

## Deprecated & Superseded Approaches

> [!WARNING]
> **Do NOT re-introduce these patterns.**

1. **67 Individual Single-Job Cron YAML Files**: Previously, every cron job had its own standalone `.github/workflows/<job>.yml` file, burning ~340 GitHub Actions runner starts/day. These were consolidated into 3 tiered workflow files (`cron-intra-day.yml`, `cron-daily.yml`, `cron-weekly.yml`) plus 2 independent watchdogs (`cron-heartbeat.yml`, `stream-webhook-drift.yml`).
2. **Duplicate `jobs/<domain>/<name>.ts` CLI Wrappers & 50 `app/api/cleanup/<job>/route.ts` Files**: Previously, `jobs/` contained 45 thin wrapper scripts that forwarded to `scripts/`, and `app/api/cleanup/` contained 50 individual route files. All CLI entrypoints now live directly in `scripts/`, and all HTTP cleanup endpoints are served by the single dynamic route `app/api/cleanup/[job]/route.ts` via `lib/cron/cleanup-registry.ts`.
3. **Chunked Ledger Reconciler & `netlify/functions/reconcile-ledgers-background`**: Superseded when `scripts/reconcile/reconcile-ledgers.ts` was rewritten from 139 row-by-row queries to fast set-based PostgreSQL aggregations.
4. **CI Live-DB Drift Polling (`db-live-drift.yml` / `check-db-drift.ts`)**: Removed because CI is forbidden from running `db:push` against the shared live database, so polling live DB drift on every `dev` push paged Sentry whenever a newly merged PR added a sidecar constraint or enum value before a manual operator push.
