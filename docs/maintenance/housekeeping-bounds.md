# Bounded housekeeping

These workers preserve existing retention and expiry policy while limiting each invocation. Their single implementations are registered in `lib/cron/cleanup-registry.ts` and served through the cleanup/admin doors. The ticker is the only scheduler of these workers, and no Actions workflow schedules a registry job; actual successful progression must be verified independently.

The limits apply in the core, including callers that omit `?limit=`. HTTP dispatch passes its request start time through the core. Every invocation shares a 16-second start budget across reads, mutation phases and invitation/organisation attempts. Once it expires the worker admits no new database work. An already running statement or transaction may still finish or reach its own timeout; the budget is not cancellation. Audit transactions have a separate 8-second timeout.

## Concurrent refresh and replay

Selection alone grants no deletion authority. Final writes repeat expiry, age, status/category and the selected IDs. A session or idempotency row refreshed after selection survives; a draft saved after selection survives; a webhook delivery requeued from a terminal status survives. These predicates protect cross-job changes independently of the worker’s lease. PostgreSQL rechecks the search condition after a concurrent row update at Read Committed. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html).

Invitation expiry retains its PENDING/expiry conditional update and atomic INVITE_EXPIRED audit. Audit pruning commits each organisation’s selected eligible deletes with its AUDIT_PRUNED summary in one transaction, through `tx`. Counters change only after commit; a failed commit cannot claim a written summary or deleted rows. The windows themselves are in [the retention table](../compliance/02-dpdp-and-privacy.md#retention-windows).

## Continuation and evidence

After a phase, a bounded existence read checks remaining eligible work only while the shared admission budget remains. Deadline checks short-circuit that read and retain `hasMore`; they never launch a probe after the deadline. Organisation transactions run sequentially so each admission check observes the time spent by earlier commits. `hasMore` is also true when an error or deadline prevents checking or processing later work. It is continuation evidence, not an exact backlog count or a snapshot guarantee against later arrivals. Results preserve already committed counters when a later read fails. Auth phases, archive phases and audit organisations isolate failures and continue while the shared budget remains.

`prune-audit-logs` runs daily at 03:10 UTC on the ticker, sends `limit=500` and does exactly one slice of at most 500 rows per phase per day, inside the 16-second start budget. The result retains `hasMore`; it never announces an unbounded drain. The former Actions wrapper that looped up to 40 slices a run is deleted, so a backlog of expired audit rows is drained at 500 a day until it clears; measure oldest eligible age before relying on it. No wrapper or second scheduling owner exists.

A persistent failure in the oldest page can hold later work beyond that page. The worker reports failure/continuation rather than inventing a durable cursor, changing eligibility or skipping evidence. Operators must repair that fault and measure oldest eligible age and throughput before claiming coverage or handing scheduling ownership to another platform. Daily/weekly cadence plus bounded capacity must match actual arrival rate; this PR does not establish that SLO from configuration alone.

Tests cover selected-page bounds, refreshed-row preservation, replay eligibility, shared deadlines, isolated failures and committed summary counters with mocked database boundaries. They do not establish deployed throughput, live deletion, or provider effects. No shared-data retention run is part of validation.

The auth-token Verification and IdempotencyRecord phases and the audit phases share the bounded delete-page executor in `lib/cron/run-deadline.ts`. The auth-token Session and SessionAccessLog phases instead drain 100-row pages (each Session page is deleted and its removed rows stamped in one transaction) until a page comes back short, a page fails or the start budget is spent; they run no continuation probe and report `hasMore` only on a budget stop or a failure. `archive-webhook-events` instead repeats single `DELETE ... WHERE id IN (SELECT ... ORDER BY ... LIMIT 2000)` statements, each re-evaluating its predicate, until a batch comes back short or the start budget is spent; its capacity arithmetic is in [the retention decision](../decisions/2026-11-01-data-retention-windows.md). Callers retain their eligibility predicates and error labels. A continuation-probe failure preserves committed deletion counts and visible remaining work.

Worktrees use the canonical shared dependencies, including the generated Prisma
client. Regenerate from the checked branch’s schema before typechecking when
model sets differ, with one compiler at a time. This updates local types only;
the shared database still requires its separate owner-reviewed rollout.

## Deprecated & Superseded Approaches

These workers formerly used unbounded deleteMany/groupBy scans, and onboarding expiry lived inline in the registry. The canonical onboarding core now owns both its bound and lease. Omitting a limit no longer requests an unlimited backlog. An execution lease alone was never a substitute for the final eligibility predicate or atomic audit evidence.
