# The first Stream token arrives with the page (2026-09-15)

**Date:** 2026-09-15 · **Branch:** `fix/stream-initial-token-ssr` · **Scope:** `lib/stream/initial-tokens.ts`, `lib/stream/seed-token-cache.ts`, `lib/stream/token-ttl.ts`, `components/stream/StreamInitialTokens.tsx`, `providers/StreamProviderImpl.tsx`, `app/dashboard/layout.tsx`, `app/meetings/layout.tsx`.

Sentry issues FAMILIARISE_WEB-4A and FAMILIARISE_WEB-3N recorded `Call to tokenProvider failed with message: TypeError: Failed to fetch` on the consultant appointments page and on `/meetings`. The page had already rendered, so the session and the instance were fine at render time; what died was the browser's first server-action call for the Stream token, which is a fresh function invocation that can land on a stalled instance. The cold-start isolation run in `docs/perf/2026-09-15-cold-start-isolation-results.md` established that the stall is platform-side (#1124), so the fix removes the hop rather than retrying it harder. The server layouts that already own the session now mint the first chat and video tokens during their render, a few milliseconds of HMAC and no extra invocation, and pass them to the client through a context in the shape of `ServerUserIdProvider`. The connector seeds its identity-scoped token cache from that context once per user id, before any effect runs, so the first `connectUser` finds a valid token in the cache and makes no network request; the seed helper is pure and refuses tokens minted for a different user or past their cache horizon, and refresh after the fifty-minute window still goes through the token action with its session bind and refusal path intact. The pin is `__tests__/stream/seed-token-cache.test.ts`.

The same change reclassifies the end of the retry ladder. When five retryable connect attempts are exhausted the connector now captures a Sentry warning with tags `expected: true`, `stream.failure: retryable-exhausted` and `platform: cold-instance` under the fingerprint `["stream-connect", "retryable-exhausted"]`, where it previously went through `streamLogger.error`, which captures at error level with no fingerprint and so produced one issue per message shape. Non-retryable outcomes keep their existing error-level report, and a person on a stalled instance still sees the Retry action from #1625. The token lifetime and the cache window moved into `lib/stream/token-ttl.ts` because the `"use server"` action module cannot export a constant for the connector to share. The full description of the flow lives in `docs/stream/08-token-management.md` under "The first token arrives with the page".
