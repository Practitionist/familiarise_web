# Engineering log — 2026-09-18 — the ticker answers 200, and two sweeps dead-letter their permanent states

Reading the production function logs on 2026-09-17, on both the pre-release deploy (`6aa9858c`) and the post-release deploy (`6aac6c00`), surfaced three defects that predate the release and compound each other. None was a regression; all three had been running for as long as the ticker had been authenticating on production.

The first is that the ticker was being re-invoked. `netlify/functions/cron-tick.mts` answered 500 whenever its `failed` list was non-empty, on the #1390 review's reasoning that a tick should not self-report healthy. Every tick with a non-empty `failed` was invoked three times, 4 to 11 seconds apart (22:50:18, 22:50:25 and 22:50:35 UTC; 22:55:13, 22:55:21 and 22:55:29 UTC; and every five-minute slot from 20:10 to 21:25 on the previous deploy), and each attempt re-fired every due target, while the `keep-warm` scheduled function, which answers 200, fired exactly once per slot. Netlify's documentation says scheduled functions "don't return a response body" and says nothing about retries, so this is recorded as an observed fact in `.claude/skills/deployment/netlify/platform-limits.md`. Because the second defect had made one target fail on every tick, the ticker had been running at three times its declared cadence: the arithmetic in #1686 and in the 2026-09-17 keep-warm log assumed one invocation per tick and was about three times too low for the ticker (roughly 3 × 13 × 288 ≈ 337,000 invocations a month, not 106,000). The fix is that `cronTick` always answers 200; `ok`, `lockHeld` and `failed` stay in the JSON line it logs, which is where the outcome has always been read, and the GitHub Actions twin is the backstop for a sweep that keeps failing. A 5xx bought three invocations and reported nothing the log line did not.

The second is that `reconcile-payment-status` answered 500 on every tick. Its gateway helpers returned `null` on any failure, and the loop pushed every `null` onto `errors`, so a Stripe reference the gateway does not know (`No such payment_intent: '103e6474-…'`, a UUID stored as the Stripe reference by a seed row) and three Razorpay order ids answered with HTTP 400 failed the run on every tick forever. The helpers now distinguish a reference the gateway will never know (Stripe `resource_missing`; Razorpay HTTP 400 or 404 on the order lookup with `error.code` of `BAD_REQUEST_ERROR`, the shape `reconcile-pending-refunds` already treats as terminal) from a lookup that could not complete (a 5xx, a network failure, a timeout). A permanently unknown reference on a PENDING row that is already older than five minutes can never capture, because the reference is minted by the gateway and stored only after the gateway returned it, so the row moves PENDING to EXPIRED through the same `updateMany` guarded on PENDING that `cleanup-abandoned-payments` uses, the run logs `permanent: gateway_reference_unknown <gateway> <reference>`, and the row is counted as `deadLetteredCount`. A transient failure stays in `errors` and still makes the twin answer 500.

The third is that `reconcile-orphaned-confirmations` re-drove the same two dozen appointments' chat channels on every tick. Its channel pass selects appointments with a SUCCEEDED payment and a NULL `chatChannelEnsuredAt`, and `ensureChannelsForAppointment` stamps the column only on success, so a pair the #1188 DM gate refuses (`DmNotPermittedError: Direct messages are only available between people who share a booking.`) failed at about 1.2 seconds of Stream latency each, every tick, until the route ran for 30 to 60 seconds (one invocation logged `Duration: 60334 ms`, the Lambda kill), long after the ticker had abandoned it at six seconds, with Netlify billing the whole run: roughly 70 to 145 GB-hours a month of the 1,000 included. The gate refusing a pair is policy, not an outage, and no retry can change it. The sweep now stamps `chatChannelEnsuredAt` itself for such a row, logs `permanent: dm_not_permitted <appointmentId>`, and counts it as `channelsDeadLettered`. Stamping is safe because the DM channel is derived from the pair (and the funding context), not from the appointment: `ensureChannelsForAppointment` is called from exactly two places, the capture pipeline and this sweep, and every later event that makes the pair eligible mints the same pair-derived channel through a different path — the consultation and subscription approval routes call `createDirectMessageChannel` on APPROVED, a later capture for the pair calls `ensureChannelsForAppointment` on its own appointment, and `POST /api/stream/channels/open` creates the channel on demand when either party opens the conversation. The channel pass also carries a fifteen-second soft deadline measured from the sweep's entry, so a bad batch defers its remainder to the next run rather than running to the Lambda ceiling.

After PR #1685's cadence change and this one, the zero-user baseline is roughly 71,000 sweep invocations, 8,600 ticker invocations and 43,000 keep-warm invocations a month, about 123,000 against the 125,000 included, and the D3 duration waste is gone. The pins are `__tests__/maintenance/cron-tick-targets.test.ts` (a non-empty `failed` still answers 200) and `__tests__/maintenance/sweeps-dead-letter-permanent-states.test.ts` (an unknown reference is EXPIRED through the CAS with no error while a 5xx stays an error with the row untouched; a `DmNotPermittedError` stamps the row while a transient throw leaves it).
