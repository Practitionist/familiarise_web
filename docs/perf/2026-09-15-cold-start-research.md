# Cold-start research: making familiarise_web fast, and whether the Netlify ticket is still worth sending

Prepared 2026-09-15, time-boxed to sixty minutes, in response to the owner's question: before escalating to Netlify or considering a migration, what does our own configuration and the vendors' documented best practices say would make the user experience fast, how does Netlify compare to Vercel Fluid Compute for this app specifically, and is the drafted support ticket still worth sending. This file was written incrementally so partial work would survive the time box; anything still marked "not found," "not verified," or "pending" below is an honest gap rather than a placeholder that was simply forgotten.

Every claim about this repository below carries a `file:line` reference so it can be checked directly. Every claim about a vendor carries a URL that was actually opened while writing this document, listed in §6. Where something could not be verified in the time box it says so rather than guessing.

## 0. The one-paragraph answer

The measured 28–32 second cold-start tail on this site is very likely **not** explained by this app's code: issue #1124's own diagnostics show the stall happening *after* every application module has already been evaluated and *before* any application code runs, on brand-new instances under concurrent creation, and doubling memory/vCPU made it worse rather than better. That evidence points at a Netlify platform-side contention problem during burst instance creation. This document nonetheless checked every on-Netlify lever this app's own code controls: Prisma's low-cold-start WASM query compiler is already in use, the root layout is already static with no session read, and the dashboard is already implicitly dynamic-and-streamed via `loading.tsx` on 119 of 124 route segments (five are missing one, a cheap independent fix); nothing found rises to the scale of the platform stall itself, and a few config-level questions (Netlify's classic bundler settings under runtime v5) could not be verified in the time available. It then compares Netlify Functions with Vercel Fluid Compute on the specific properties this app depends on, and concludes — see §5 — that the ticket is still worth sending, with three additions.

### 1.2 What a normal Netlify Next.js cold start looks like, for comparison

Not found as a single Netlify-specific, vendor-published figure, and not fabricated here: Netlify's own functions documentation does not state a typical cold-start duration for the Next.js runtime handler, and this handler emits no `Init Duration:` log line the way AWS Lambda's own console does, which is itself a documented gap this repo hit (`docs/perf/netlify-stall-ticket-draft.md:46`, question 3, and independently confirmed as a live community pain point in §2's hypothesis 6). Two proxies fill the gap, both opened directly. First, since Netlify Functions run on AWS Lambda underneath, a general Lambda Node.js baseline applies: Mikhail Shilkov's measured cold-start benchmarks (https://mikhail.io/serverless/coldstarts/aws/) put a lean Node.js function's cold start within roughly 400 ms most of the time and almost always within roughly 700 ms, and a 2025 cross-runtime benchmark from Deno (https://deno.com/blog/aws-lambda-coldstart-benchmarks) corroborates the same order of magnitude; dependency-heavy functions run slower but the literature's pessimistic case is still low single-digit seconds, not tens of seconds. Second, and more directly comparable, the one closely-matching public report of a Netlify Next.js server-handler cold start specifically (https://answers.netlify.com/t/frequent-slow-cold-start-for-function-next-js-server-handler/148600) measured 1.6–2.2 seconds, and Netlify staff treated even that as possibly not a genuine cold start. Both proxies agree on the same order of magnitude — hundreds of milliseconds to a few seconds — which makes this app's 28–32 second concurrent-burst tail roughly five to eighty times larger than either baseline, not merely "slow."

## 2. Where the 28–32 seconds most plausibly goes

This section is the heart of the document: a ranked list of hypotheses, each with the evidence for and against it drawn from this repository's own configuration, and the cheap experiment that would confirm or kill it. Hypotheses are ordered by how well they currently explain the evidence, strongest first.

### Repo inventory used as evidence below

Before the ranking, the facts this section reasons from. `netlify.toml` sets `NODE_VERSION=22` and a build-only `NODE_OPTIONS=--max-old-space-size=6144`, and carries a large comment block recording the memory A/B as measured-dead (`netlify.toml:1-44`); it has no `[functions]` block for the server handler beyond that history. `next.config.mjs` sets `serverExternalPackages` to `pg`, `@prisma/adapter-pg`, `pg-pool`, `pg-connection-string`, `@react-pdf/renderer`, `razorpay`, `stripe`, `resend`, `bcrypt`, `@stream-io/node-sdk`, `libsodium-wrappers` (`next.config.mjs:255-267`), `outputFileTracingExcludes` drops the build toolchain (typescript, esbuild, webpack, terser) from the deployed function to save "~40MB with zero runtime surface" (`next.config.mjs:199-220`), `outputFileTracingIncludes` force-includes fonts and the React JSX runtime for four PDF routes whose imports the tracer cannot see (`next.config.mjs:221-247`), `experimental.optimizePackageImports` covers `framer-motion`, the Stream SDKs, Radix icons, and the two Novu packages (`next.config.mjs:170-189`), and `compiler.removeConsole` strips `console.log` (not `error`/`warn`) in production (`next.config.mjs:296-315`). `instrumentation.ts` imports `sentry.server.config.ts` (Node runtime) or `sentry.edge.config.ts` (edge runtime) on every cold start (`instrumentation.ts:1-11`), both of which call the shared `initSentry()` in `sentry.shared.config.ts`, which runs `Sentry.init()` with `tracesSampleRate` 0.1 in production, `enableLogs: true`, and several `ignoreErrors`/`denyUrls`/`beforeSend` rules (`sentry.shared.config.ts:22-102`). `lib/prisma.ts` constructs `PrismaClient` with the `PrismaPg` driver adapter **at module scope** — i.e., on first import, which happens on every cold instance the first time any code path touches the database (`lib/prisma.ts:48-146`) — with a 3 s runtime connect timeout (30 s at build), a 6 s query timeout, and `PG_POOL_MAX` read from the environment (`lib/prisma.ts:21-68`). `lib/observability/job-sentry.ts` documents, for the separate cron-job Sentry bootstrap, that "OpenTelemetry auto-instrumentation patches http/pg/Prisma at require time" (`lib/observability/job-sentry.ts:19-23`) — the same auto-instrumentation runs for the main app's `Sentry.init()` in `sentry.shared.config.ts`, so importing `pg`/Prisma anywhere in the request path triggers OpenTelemetry's patching of those modules in addition to Prisma's own client construction. `app/layout.tsx` is confirmed clean: no server-side session read, no heavy SDK import, just component/provider imports and a `sora` font (`app/layout.tsx:1-17,62-69`). `middleware.ts`, the one edge function, imports `better-auth/cookies` (cookie-presence check only, explicitly not a DB-hitting session validation, `middleware.ts:36-43`) and `@upstash/ratelimit`/`@upstash/redis` for a table of route-scoped rate limits (`middleware.ts:1-27,240-365`); this is a separate, smaller Lambda-or-edge runtime from the Next.js server handler and is not implicated in the server-handler stall.

On disk, `du -sh` against `node_modules` (measured 2026-09-15, not the deployed bundle, which file-tracing shrinks to 68.8 MB zipped) shows `@prisma` at 164 MB, `@sentry` at 78 MB, `@stream-io` at 57 MB, the generated `.prisma` client at 28 MB, `stream-chat-react` at 22 MB, `@novu` at 18 MB, `stream-chat` at 8.6 MB, `stripe` at 8.0 MB, `@react-pdf` at 2.8 MB, `bcrypt` at 1.1 MB, `sharp` at 596 KB, `razorpay` at 460 KB, and `pg` at 144 KB, against 1.5 GB of `node_modules` in total. Critically, `node_modules/.prisma/client` contains `query_compiler_fast_bg.wasm` and its JS loaders, and **no** `libquery_engine-*.node` binary — this app already runs Prisma's WASM query compiler with the `pg` driver adapter, not the classic Rust query-engine binary that historically dominated Prisma's Lambda cold-start cost (confirmed by direct directory listing, 2026-09-15; vendor confirmation in §6). Grepping `lib/` and `app/` for module-scope imports of the five heaviest packages found 327 files importing something from `@prisma`, 302 from `@sentry`, 16 from `@stream-io`, 3 from `@react-pdf`, and 2 from `@novu` (measured 2026-09-15). Almost all of these are Route Handlers, Server Components, or Server Actions that only execute when their specific route is hit, not at every cold boot; the files that run for **every** cold instance regardless of which route triggered it are the `instrumentation.ts` → `sentry.*.config.ts` chain (always) and `lib/prisma.ts` (whenever the hit route touches the database, which is most of them).

### Hypothesis ranking

1. **A Netlify platform-side contention or provisioning stall during concurrent instance creation, unrelated to this app's code.** Evidence for: issue #1124's own instrumented diagnostic shows the ~24 s block occurring after all of this app's modules are already evaluated and while the handler is doing nothing but awaiting an idle timer loop (comment dated 2026-08-22, quoted in §1.1); it happens only when instances are created **under concurrent load** (sequential cold starts are 1.8–2.7 s end-to-end, including a real DB-backed render, per the same issue's batch A); doubling memory/vCPU made it worse, which argues against CPU starvation during JS evaluation or GC; a build with lazy SDK init still stalled at full strength. Evidence against: this is the one hypothesis this repository cannot directly falsify or fix, because it has no visibility into Netlify's control plane. Cheap experiment that would confirm it further: deploy the exact two-route comparison already proposed in #1124 — one Route Handler importing nothing from `@/lib` or `@/app`, one importing the full graph public routes pull in — to the same preview and diff their idle-phase stall under an identical concurrent burst; if the zero-import handler stalls just as long, this hypothesis is fully confirmed and every remaining hypothesis below is ruled out as a meaningful contributor to the *tail*, though they remain worth fixing for the smaller, always-present costs they do carry.

2. **Prisma client/engine cold-start cost.** Evidence against, and now vendor-confirmed. Prisma's own v7 upgrade guide (https://www.prisma.io/docs/guides/upgrade-prisma-orm/v7) states v7 "requires a driver adapter for all databases" and ships a Rust-free client generator; this repo's `.prisma/client` shipping `query_compiler_fast_bg.wasm` with no `.node` binary (confirmed above) is consistent with that path, and Prisma's own Netlify deployment guide for v7 (https://www.prisma.io/docs/orm/v7/prisma-client/deployment/serverless/deploy-to-netlify) does not mention `binaryTargets` at all — consistent with there being no native engine binary left to select a target for. One nuance the research could not fully resolve: `prisma/schema.prisma:7` still declares `provider = "prisma-client-js"`, the older generator Prisma is deprecating in favour of a new `prisma-client` provider; the WASM compiler is evidently active regardless once a driver adapter is passed to `PrismaClient`, but no primary source spells out whether `prisma-client-js`-plus-adapter and the new `prisma-client` provider are fully equivalent for cold-start purposes, so this is flagged **not fully confirmed** rather than asserted either way. On the numbers: Prisma's own cold-start blog posts ("How We Sped Up Serverless Cold Starts with Prisma by 9x", https://www.prisma.io/blog/prisma-and-serverless-73hbgKnZ6t, and "Rust to TypeScript Update", https://www.prisma.io/blog/rust-to-typescript-update-boosting-prisma-orm-performance) report a 14 MB→1.6 MB bundle-size drop and a "9x" figure for eliminating DMMF-over-GraphQL parsing, but neither publishes an absolute cold-start-seconds number, and GitHub issue prisma/prisma#11266 (still unconfirmed/unresolved) measured a large DMMF string adding **about one second** to a Lambda cold start under the *old* architecture. Every Prisma-attributable cold-start cost found in vendor sources is sub-second to low-single-digit-seconds — two orders of magnitude below this app's 24 s stall — matching issue #1124's own measurement of 0.5–1 s for first-query initialisation. The module-scope singleton pattern this repo uses in `lib/prisma.ts:88-146` (construct once, cache on `globalThis` in development only) is confirmed as Prisma's own and the wider community's recommended serverless pattern, and starting the connection pool at 1 for serverless is confirmed standard guidance — both match this repo's existing handling exactly (`lib/prisma.ts:61-68`), so neither is a change to make. Separately, Sentry's own OpenTelemetry documentation and third-party sources agree that Node auto-instrumentation (via `import-in-the-middle`) wraps `pg`/database modules at `require` time and that the instrumentation cost is paid "on every cold start," recommending disabling unneeded instrumentations for latency-sensitive serverless functions — directional support for hypothesis 3 below, but no source gives a millisecond figure, so treat it as a real but small contributor, not a 24-second one. Cheap experiment: a throwaway Route Handler that imports only `lib/prisma.ts` and does nothing else, timed under the same concurrent-burst protocol as #1124, isolates Prisma's true contribution from the rest of the module graph; not yet run as of this writing.

3. **Sentry SDK initialisation cost at boot.** Evidence against: `Sentry.init()` runs inside `instrumentation.ts`'s synchronous import chain (`instrumentation.ts:3-6`), which is part of the same "already evaluated by the time the stall starts" module graph #1124's diagnostic exonerated; Sentry's OpenTelemetry auto-instrumentation patching of `http`/`pg`/Prisma (documented for the job-runner bootstrap in `lib/observability/job-sentry.ts:19-23`) is real work but, like Prisma construction, falls inside the ~3.3 s pre-stall window rather than explaining the 24 s gap. Not yet isolated by a dedicated experiment; the zero-import-handler test in hypothesis 1 would also answer this by omission (it imports no Sentry either).

4. **Bundle size / `.next/server` trace size.** Evidence against: the handler is 68.8 MB zipped today (`.claude/skills/deployment/netlify/platform-limits.md:16`), and #1124's sequential batch shows a full cold module-load-plus-SSR-render completing in 1.8–2.7 s with no concurrency — if bundle size caused multi-second parse/eval cost, that would show up even without concurrent creation, and it does not. `outputFileTracingExcludes` already removes non-runtime build tooling (`next.config.mjs:199-220`), which was a real, previously-hit 250 MB Lambda-cap problem (issue #1158, `.claude/skills/deployment/netlify/issue-ledger.md:50-53`) but is a packaging-limit fix, not a cold-start-latency fix, and the evidence above says it is not the latency problem either. Not fully closed: the diagnostic in #1124 explicitly flags as "not measured" whether Next's own framework bootstrap or the Netlify adapter lazily evaluates further modules on the *first* request specifically (as opposed to at process start), which would still show up inside the stall window and has not been ruled out.

5. **Supavisor / database pooler handshake cost.** Evidence against, as the mechanism for the 24 s stall itself: `lib/prisma.ts`'s own comment records the direct measurement that "the database was never the slow part" — the `pg` connect-timeout `setTimeout` cannot even fire while the event loop is blocked, so on a stalled cold instance the 3 s connect budget fires at ~26 s and the subsequent retry connects in 327–340 ms (`lib/prisma.ts:14-20`). Vendor research clarifies and partly corrects the surrounding claims, though. "EAUTHTIMEOUT" is not a documented Postgres, node-postgres, or Supabase error code — node-postgres's real timeout codes are `ETIMEDOUT`/`ECONNREFUSED` — so it should be treated as this repo's own label for a slow auth-phase connect hang, not repeated to a vendor as a known term. Supabase's own connecting-to-Vercel-serverless troubleshooting guide (https://supabase.com/docs/guides/troubleshooting/troubleshooting-connect_timeout-or-hanging-queries-in-vercel-serverless-functions-775f92) attributes hanging-query symptoms to a *different*, better-documented mechanism than pooler saturation: a serverless function freezing between invocations lets its TCP socket go stale while its keepalive timers are paused, so the next invocation hangs on a dead connection; the fix it recommends is a `SELECT 1` preflight with its own short timeout to recycle a dead client, or moving to a host with proper pre-suspension cleanup hooks, or shifting read-heavy paths to the Data API/PostgREST. What IS vendor-confirmed, directly corroborating this repo's own comment: Supabase's Timeouts doc (https://supabase.com/docs/guides/database/postgres/timeouts) states plainly that a session-level `statement_timeout` "cannot be used ... with Supavisor in Transaction mode (port 6543)" — only session mode (5432) or a direct connection honour it — so the repo's client-side `statement_timeout`-as-defense-in-depth reasoning (`lib/prisma.ts:39-46`) is correct, documented pooler behaviour, not a Supavisor bug. Supabase's own Supavisor FAQ (https://supabase.com/docs/guides/troubleshooting/supavisor-faq-YyP5tI) also confirms `PG_POOL_MAX=1` is not folklore: for edge/serverless functions it states plainly that "often 1 is optimal" per function instance, to be raised only with evidence of intra-instance queuing — exactly this repo's configuration (`lib/prisma.ts:61-68`). And `?pgbouncer=true` on the connection string is confirmed to exist specifically because Supavisor transaction mode "does not support prepared statements, which Prisma will try to create in the background" (Supabase's Prisma troubleshooting page, https://supabase.com/docs/guides/database/prisma/prisma-troubleshooting). None of this changes the conclusion that the pooler is not the 24 s stall's cause, but it does mean the EAUTHTIMEOUT-under-saturation causal story in `lib/prisma.ts`'s comment is this repo's own inference, not a vendor-documented relationship, and the more likely real-world trigger for that specific symptom (when it does occur) is the frozen-function/stale-socket mechanism above.

6. **Netlify's own Next.js runtime plugin doing avoidable work per cold instance** (e.g., re-resolving routes, re-reading a large routes manifest, re-initialising the ISR/durable-cache layer). Netlify's changelog (https://www.netlify.com/changelog/ and the functions-tagged view) shows nothing published between 2026-09-12 and today, 2026-09-15, relevant to the Next.js runtime, cold starts, or function memory/concurrency — the most recent functions-relevant entries are still the already-known Node 24 default (2026-07-07) and the functions redesign (2026-06-25). A targeted search of the current runtime adapter repo (`opennextjs/opennextjs-netlify`) and the legacy `netlify/next-runtime` found no open issue describing a concurrency-triggered multi-second stall; the one tangential hit (`opennextjs-netlify#3546`) is an unrelated worker crash from a `disk-lru-cache` `mkdir` failure on Next 15.5.x, not a boot-time stall. The single closest community report (https://answers.netlify.com/t/frequent-slow-cold-start-for-function-next-js-server-handler/148600) is fifteen times smaller in magnitude (1.6–2.2 s, 6 of 121 requests) than this app's stall, has no concurrency framing, and drew a Netlify staff reply doubting it was even a true cold start because the function emits no `Init Duration` line — the same observability gap this repo's own ticket draft names as question 3. That is a meaningful, if negative, finding in its own right: nobody outside this repository appears to have reported this specific concurrent-burst-triggered pattern, so it should not be pitched to support as a known class of issue (see §5). What fast Netlify sites do instead, per Netlify's own framework docs (https://docs.netlify.com/build/frameworks/framework-setup-guides/nextjs/overview/) and corroborating write-ups, is largely to avoid invoking the SSR function at all: static or ISR pages serve straight from the CDN edge at roughly 20–50 ms TTFB with no function cold start possible, and personalisation or auth-adjacent logic runs in Edge Functions — a Deno-based runtime with a different warm-instance model from the Lambda-shaped Next.js server handler — rather than inside the consolidated SSR handler. This app's contrast is direct: every dashboard route and most explore-detail routes are dynamic by necessity (session-gated, per §3) and are therefore all served by the one 68.8 MB `___netlify-server-handler`, which also carries the Sentry-plus-Prisma boot chain described above, so the stall's blast radius is "most logged-in and many logged-out page loads," not a thin personalisation sliver. Only `middleware.ts` runs on the separate, smaller edge runtime today (`middleware.ts:1-27`), and it deliberately does no more than a cookie-presence check for exactly this reason (`middleware.ts:36-43`).

## 3. The on-Netlify plan

Read this section against §2 first: because the strongest hypothesis there is a platform-side stall this app's code cannot reach, several plausible-sounding "shrink the bundle" or "speed up Prisma" changes are demoted below to low-expected-value even where they are technically correct. Each item is marked **measure first** (run the cheap experiment in §2 before spending effort), **safe to apply** (low-risk regardless of root cause, worth doing for reasons beyond the stall), **do not repeat** (already measured and rejected), or **not verified** (the time box ran out before a vendor source could confirm it).

- **Measure first — isolate module-load from platform stall.** Ship the two-route zero-import-vs-full-graph comparison from hypothesis 1 to a deploy preview and run #1124's twelve-request burst protocol against both. This is the single highest-value next step because it either closes off hypotheses 2–4 entirely (freeing effort for hosting-level work only) or reopens them with real evidence. Effort: a few hours. Risk: none (preview-only, additive routes).
- **Low expected value given hypothesis 1, but cheap to state precisely — the ceiling on "stop paying Prisma cost on routes that never touch the database."** Measured 2026-09-15: of 401 `route.ts` files under `app/api`, 292 mention `prisma` (case-insensitive, any import path) somewhere in the file; the other 109 are the upper bound on routes that could plausibly avoid importing anything that transitively touches `lib/prisma.ts` today (an upper bound, not a confirmed count, since a route can reach Prisma indirectly through a service/action helper without the string "prisma" appearing in the route file itself — not traced further in this time box). Since §2's hypothesis 2 found Prisma's own module-scope construction cost to be sub-second and vendor-confirmed as already using the low-cost WASM path, auditing and fixing those 109 routes would shave, at best, a fraction of a second off a small minority of cold invocations — worth doing as ordinary hygiene, not worth prioritising as a latency fix ahead of the hypothesis-1 experiment.
- **Already as good as it gets without a rework — dashboard routes are implicitly dynamic and mostly already streamed.** Measured 2026-09-15: all 124 `page.tsx` files under `app/dashboard/` have neither `export const dynamic = "force-dynamic"` nor `export const revalidate`, unlike the explore/programs routes #938 converted explicitly. This is expected rather than an oversight — every dashboard route sits behind `middleware.ts`'s `PROTECTED_PREFIXES` (`middleware.ts:54-61`) and reads the authenticated session, which is itself a dynamic API that opts a route out of static rendering automatically, so an explicit `force-dynamic` would be redundant. 119 of the 124 route segments already have a sibling `loading.tsx`, which is what creates the automatic Suspense boundary that streams a skeleton immediately while the dynamic (and, on a cold instance, possibly stalled) render happens behind it — this is the "only streaming settles it" mitigation already in place for the dashboard, and it is the same mechanism #938 added deliberately for the public explore pages. Five route segments have no `loading.tsx` and would show a blank tab instead of a skeleton on a slow render: `app/dashboard/admin/leads`, `app/dashboard/admin/threads`, `app/dashboard/staff/[staffId]/(features)/threads`, `app/dashboard/organization/[orgId]/materials`, `app/dashboard/organization/[orgId]/support` (measured 2026-09-15). Adding a `loading.tsx` to these five is a safe-to-apply, low-effort fix, independent of the cold-start root cause: it improves perceived load time on every slow render, cold or warm, not just the platform stall.
- **Not verified in this time box — Netlify-specific bundling levers** (`node_bundler = "esbuild"`, `included_files`/`external_node_modules` in `netlify.toml`). This repo's `netlify.toml` does not set `node_bundler` explicitly today (`netlify.toml:1-63`, no such key present). None of this session's research passes opened Netlify's classic Functions bundling-configuration docs against the current Next.js runtime v5 specifically, so whether these keys still apply under `@netlify/plugin-nextjs@5.15.13` (which controls its own bundling, per `.claude/skills/deployment/netlify/hosting-alternatives.md:85`) or are silently ignored the way a v1 function name is (`netlify.toml:34-38`) is genuinely unknown — say "not found" rather than propose a snippet that might no-op. This is a good candidate question to fold into the support ticket itself (§5, ticket question 4 already asks about "bundle shape, esbuild vs default bundling").
- **Do not repeat — memory/vCPU increase.** Measured dead and worse than baseline (§1.1); `netlify.toml:17-44` already documents this in-place specifically so it is not re-attempted.
- **Do not repeat — lazy SDK client initialisation as a cold-start fix.** Measured to make no difference under burst load (§1.1, #1221 build). Still worth doing for unrelated reasons (avoiding unnecessary client construction on routes that never use a given SDK) but not to be sold as a latency fix.
- **See the dedicated subsection below — Next.js-specific streaming/TTFB levers (PPR, `"use cache"`, `after()`, a streaming Route Handler).** The vendor research on how far these can reduce perceived load time, and whether any can get bytes out before a boot-time platform stall like hypothesis 1 even finishes, landed after this bullet was first drafted; see "Next.js framework levers that were checked and do not apply yet," immediately below. Short version: none of them are a substitute for fixing hypothesis 1 — §1.1's own diagnostic evidence (the idle-loop probe stalling for the full ~24 s before any application code, including presumably the code that would start a stream, ever runs) suggests streaming likely cannot mask the platform stall itself, though that specific inference remains this document's own reasoning from the #1124 data rather than a vendor confirmation.

Concrete `netlify.toml`/`next.config.mjs` snippets for the bundling levers are deliberately not included above: this research could not confirm which of them are live under Netlify's Next.js runtime v5 as opposed to legacy-runtime-only settings that would silently no-op, the way a v1 function-name override did in the memory A/B (`netlify.toml:34-38`), and shipping an unverified snippet that reads as a fix but does nothing is worse than shipping none.

### Next.js framework levers that were checked and do not apply yet

Two more levers belong in this plan, both checked against Next.js's own docs rather than assumed, and both effectively **measure first** in the sense that they need a version upgrade before there is anything to measure:

- **Partial Prerendering and `"use cache"` are not usable in production at this app's Next.js version.** Opened directly (https://nextjs.org/docs/15/app/getting-started/partial-prerendering, `lastUpdated: 2025-08-05`, version `15.5.25`): "This feature is currently experimental and subject to change, it's not recommended for production" — true for this app's pinned `"next": "^15.5.0"` (`package.json:116`). PPR would help exactly this app's shape of problem, a static shell around a session-dependent dynamic island, which this app currently approximates by hand via `loading.tsx` Suspense boundaries and the `force-dynamic` + `unstable_cache` pattern from #938 (previous bullets). PPR only stabilises in Next.js 16 via the `cacheComponents` config, replacing `experimental.ppr`, and `"use cache"` is gated the same way behind Next's canary channel at 15.5. Adopting either means a framework upgrade, not a config change, so it belongs in a separate upgrade decision, not this cold-start plan.
- **`after()` is stable since v15.1.0, but its serverless guarantee is the platform adapter's job, not Next's, and this research could not confirm Netlify provides it.** Opened directly (https://nextjs.org/docs/app/api-reference/functions/after, `lastUpdated: 2026-03-13`): a serverless host must implement a `waitUntil` bridge (`globalThis[Symbol.for('@next/request-context')]`) for an `after()` callback to be guaranteed to finish after the response is sent, and Next's own reference implementation of that bridge is written against Vercel's `waitUntil`. No Netlify-specific documentation confirming or denying that `@netlify/plugin-nextjs` wires this up was found in this time box — genuinely not found, not merely unlinked. That is consistent with, though it does not prove, this repository's existing practice of treating `after()` as best-effort on Netlify rather than guaranteed; new must-happen work should keep going through the existing `CRON_SECRET`-gated outbox pattern rather than `after()` until this is confirmed one way or the other.
- **Measure first — a Route Handler streaming an early byte is a plausible, unconfirmed fix for the ~26 s edge-timeout class of route.** A Route Handler returns a standard Web `Response`, and a `Response` can wrap a `ReadableStream` written to progressively — a platform-level Web API capability, not a Next.js-specific feature, so a route can in principle flush a byte before its slow work finishes. Whether doing so actually defeats Netlify's undocumented edge inactivity timer specifically (`.claude/skills/deployment/netlify/platform-limits.md:45-47`) was not confirmed against a primary source in this time box — the mechanism itself is undocumented, so its exact trigger (no bytes sent at all, vs. no response object started) is inference either way. Cheap experiment: take a route already known to risk the timeout (`/api/cleanup/reconcile-ledgers`, issue #1454), have a throwaway branch flush one byte immediately before doing its slow work, and see whether a deliberately slow run still gets cut at ~26 s. If it does not, this is a low-effort fix applicable to every route in the "awaits everything, then returns JSON" class; if it still cuts, the Background Function already in place for that route (`netlify/functions/reconcile-ledgers-background/index.mts`) remains the right answer for that class of work.

## 4. Netlify Functions vs Vercel Fluid Compute for this app

The existing comparison in `.claude/skills/deployment/netlify/hosting-alternatives.md:9-25` (dated 2026-09-12) covers concurrent-request sharing on one warm process, `PG_POOL_MAX=1`'s implication, the Mumbai (`bom1`) region, function-duration ceilings, and price at this app's scale. Re-opened on 2026-09-15 to check for drift: every headline claim is unchanged and every source page's own `last_updated` date is identical to the 2026-09-12 record (fluid-compute 2026-08-24, memory 2026-07-15, regions 2026-08-11), so nothing has moved in the three days between the two research passes. Confirmed verbatim from https://vercel.com/docs/fluid-compute: Fluid Compute handles "multiple invocations within a single function instance" with per-request error isolation, so an unhandled error in one concurrent request cannot crash another request sharing the same warm instance — this is the property that removes ledger group 1 (the `PG_POOL_MAX=1` single-connection-per-instance constraint) outright, because a normal-sized pool can then serve genuinely concurrent requests instead of one request per instance. Confirmed from https://vercel.com/docs/functions/configuring-functions/memory: memory is 2 GB/1 vCPU ("Standard") by default on Pro/Enterprise, 4 GB/2 vCPU ("Performance") is opt-in, and — a nuance worth recording for any migration plan — memory "cannot be set using vercel.json," only in the dashboard, and only project-wide, not per function. Confirmed from https://vercel.com/docs/regions: `bom1` (Mumbai, `ap-south-1`) is one of Vercel's listed function regions, but it is **not** the default (`iad1`, Washington D.C., is), so it would have to be explicitly selected for this app's functions in a migration — an easy step, but one that has to be remembered rather than assumed. The duration ladder (300 s default, 800 s max on Pro, 1800 s in beta) and the bytecode-caching-plus-pre-warming-plus-instance-reuse cold-start mitigations are both reconfirmed unchanged. The experiment that would settle this for real traffic, decided 2026-09-13, is already fully specified at `docs/perf/vercel-experiment-runbook.md:1-33` and is referenced rather than rewritten here: it deploys the `dev` branch to a throwaway Vercel Hobby project in `bom1` with Fluid Compute on and `PG_POOL_MAX=5`, then runs the same `scripts/perf/burst-ttfb.sh` twelve-request burst against `/explore/experts` that produced Netlify's 11-of-12-slow-at-27–39s baseline, re-runs the #1435 global-client-inside-a-transaction deadlock shape through the checkout page to see whether a shared warm process with a five-connection pool avoids it, and records both results side by side in `hosting-alternatives.md` under a dated "Measured" subsection. As of 2026-09-15 there is no evidence in the repository that this runbook has been executed yet.

## 5. Is the Netlify ticket still worth sending

**Yes**, with a framing change. The strongest hypothesis in §2 (platform-side concurrent-instance-creation contention) is, by definition, not something this repository can fix from its own configuration: every code-side candidate this document and issue #1124 could test — bundle size, Prisma's engine, Sentry's boot cost, lazy SDK init, function memory/vCPU — has been tested and has failed to explain the 24 s idle-phase block, which leaves Netlify's control plane as the only remaining suspect.

The framing change matters because a dedicated search (answers.netlify.com, the current runtime adapter repo `opennextjs/opennextjs-netlify`, the legacy `netlify/next-runtime`, Hacker News, and Reddit) found **no external report matching this app's specific concurrent-burst-triggered pattern** — everything found is either this repository's own issue resurfacing in search results, or generic single-request cold-start complaints an order of magnitude smaller (1.6–2.2 s) and with no concurrency trigger. In the one closely-related community thread that does exist (https://answers.netlify.com/t/frequent-slow-cold-start-for-function-next-js-server-handler/148600), Netlify staff's own response to a much smaller anomaly was to doubt it was a true cold start at all — reasoning from the same missing `Init Duration` log line this app's handler also lacks — and to redirect the reporter to generic application-performance documentation rather than acknowledge a platform-side mechanism. That is very likely the default first response this ticket will get too, so the ticket should be framed as *reporting a pattern that does not appear to be documented or previously reported, backed by isolation evidence*, rather than as *asking for a fix to a known issue* — and it should lead with the evidence that pre-empts the "maybe this isn't really a cold start" reflex: the sequential-vs-concurrent contrast itself (1.8–2.7 s for a brand-new instance created alone, versus 27–39 s for a brand-new instance created under concurrent load) is what proves these are real new-instance events and not measurement noise, independent of whether the log line is present.

Three facts this research adds to the existing draft at `docs/perf/netlify-stall-ticket-draft.md`, beyond what it already documents: (1) the pattern reproduced again on 2026-09-13 with only three concurrent requests against the *published production* deployment, not just a deploy preview, so it is not a preview-infrastructure artifact; (2) the memory/vCPU A/B is now worth stating plainly as having made the burst *worse*, not merely shown "no improvement" — 11/12 slow at 35.9–37.6 s plus a platform 500 at 2048 MB versus 11/12 at 27.8–31.0 s at 1024 MB — which pre-empts a "have you tried more memory" first response; (3) `node_modules/.prisma/client` confirms this app already runs Prisma's WASM query compiler (`query_compiler_fast_bg.wasm`, no native engine binary) rather than the classic Rust query-engine binary, pre-empting a plausible but wrong first response about disabling a native engine that is not present.
