# Notification journey audit

Tracking: [issue 2589](https://github.com/Practitionist/familiarise_web/issues/2589). [Architecture, state and sequence diagrams](https://github.com/Practitionist/familiarise_web/issues/2589#architecture-and-journey-diagrams). Baseline `500308fed`, inspected 2026-11-05. Worktree `fw-notification-mega`, branch `fix/notification-mega-audit`.

This is a code and read-only integration audit. “Inspected” means the named producer, shared delivery path and available tests were reviewed; it does not mean every branch was executed, a live email arrived, or every vendor configuration was accessible. No real sends, broadcasts, provider changes, DB mutations or deploys were performed.

## Current delivery contract

A journey comprises a committed business change, authorized recipients, policy, durable staging, provider attempt, retry, delivery evidence, destination and operator recovery. Template existence alone does not establish coverage.

Email uses `FailedEmail`; newsletters use `FailedEmailBatch`; bells use `NotificationOutbox`. Transactional producers must use the same `tx` for recipient reads and row writes. Rendering belongs outside long transactions where possible. Post-commit network attempts and cron relays share event identity. Email provider acceptance is separate from callback delivery state. Novu workflow families are in-app only.

Optional email obeys master/channel/category/workspace routing. Required email bypasses optional settings. Bell settings remain independently enforced. Suppression and pre-launch guards apply at the wire boundary. Single-use credential bodies are redacted and never replayed.

## Announcement publication and management

The POST/PATCH/DELETE routes commit source changes and outbox staging/cancellation together. `lib/announcements/notifications.ts` uses stable source/revision/content/date identity; it does not introduce a scheduler, broker or database state. Future rows wait behind `notBefore`. The existing relay now selects that field and the attempt function honors it even when called directly as a relay.

Before the provider call, `lib/announcements/delivery-policy.ts` reads the current source and compares its revision, content, links and window with the staged snapshot. Source-read failures retain pending work; expected cancellation reasons remain durable terminal audit rows without Sentry/ops-chat failure alerts or actionable recovery badges. Malformed/missing context still surfaces for review. A provider call already in flight at the time of an edit cannot be recalled atomically.

The public list projects banner fields and caches only active records. `GET /api/announcements?view=manage` requires announcement-management permission, returns up to 100 recent records and sets private/no-store plus Vary: Cookie. Transient management failures return 503, while anonymous banner failures keep their existing graceful fallback. The admin UI edits local start/end times and links, distinguishes scheduled/expired states, and validates API success before closing a form. Common bounds now live in `lib/validation/input-limits.ts`, with the server-only body-size response helper remaining in `limits.ts`.
