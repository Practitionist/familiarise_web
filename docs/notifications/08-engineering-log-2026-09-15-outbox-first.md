# Outbox-first delivery for email and Novu triggers

**Date:** 2026-09-15 · **Branch:** `feat/email-outbox-first` · **Issue:** #1654 (design), #691 NTF-1, #1648 · **Schema:** #1659 · **Scope:** `lib/email/deliver.ts` and every sender, the payment webhook handlers, `lib/novu/service.ts` and every `notify*` call site, two relays on the Netlify ticker.

This entry records why the send-first shape that #1646 left behind was still two defects away from correct, what the outbox-first shape changed, and the budgets and cadences that were chosen.

## What was wrong after #1646

The email path after #1646 was already durable on failure: a send that threw or that Resend rejected was written to `FailedEmail` and replayed with backoff. Two gaps remained, and issue #1654 walks the failure matrix that exposed them. First, the Resend SDK calls `fetch` with no timeout, so a slow provider held the caller's request until Netlify's ~26-second ceiling; a signup that had succeeded answered 504, the user retried and was told the email already existed. Second, the row was written only after the failure, so a function that froze between the business commit and the `FailedEmail` insert lost the message with no trace. Novu triggers were worse: fired without awaiting and forgotten on failure, which is how the void-trigger losses of #1616 happened and what #691 NTF-1 had recorded.

## What changed

The order of the two writes was reversed. `deliver()` is now `stage()` followed by `attempt()`: the rendered message becomes a `PENDING` `FailedEmail` row (with `entityRef`) before any network call, and the inline send runs under a per-caller `AbortSignal.timeout` budget. Success marks the row `SENT` with `resendId`; a terminal error dead-letters it; a transient error leaves it `PENDING` with `lastError`; a timeout leaves it `PENDING` and untouched, logs once and never pages, because the relay finishes the send and the content-hash Idempotency-Key makes a late duplicate harmless. The Resend SDK swallows a fetch abort into a generic "could not be resolved" error, so `attempt()` creates the signal itself and checks `signal.aborted` to tell a timeout from a network failure.

The payment webhook handlers are the one caller with a transaction of their own. `handlePaymentSuccess` reads the receipt's inputs through its Phase 1 transaction, renders with the new render-only `renderPaymentSuccessEmail()`, stages the row inside that transaction, and attempts after the commit under the `WEBHOOK` budget; the two blocked outcomes that Phase 2 refunds stage nothing. `handlePaymentFailure` stages both its email and its Novu bell inside its transaction and attempts both after the commit. Nothing else inside the money transaction changed (ADR 21).

Novu triggers got the same shape in `lib/novu/outbox.ts`. `stageTrigger()` upserts a `NotificationOutbox` row on a `transactionId` derived at stage time by `deriveTransactionId()`, whose sort became a code-point comparator instead of `localeCompare`, because a collation-dependent sort had produced different ids for the same mixed-case recipients on different runtimes. `attemptTrigger()` makes the wire call under the client's existing five-second timeout and settles the row the same way the email side does; a 2xx the SDK could not parse counts as sent, a terminal 4xx (an unknown workflow, a rejected body, a bad key) dead-letters and pages once per reason on the fingerprint `["novu-trigger-terminal", reason]`, and a timeout, 5xx or connection failure leaves the row `PENDING`. Every `notify*` call site that was `void` is now awaited, thirty-seven of them, and the four sites inside transactions (`notifyPaymentFailed`, `notifyRefundProcessed`, `notifyDisputeCreated`, `notifyDisputeResolved`) pass `{ tx, entityRef }` and run `attemptTrigger()` after the commit. The zoned trigger variants only shape the rendered payload per recipient timezone and do not defer the send, so `notBefore` stays null until the quiet-hours work uses it.

## Budgets and cadences

The table below records the inline budgets, all named in `EMAIL_BUDGET_MS` in `lib/email/config.ts`, and the relay cadences.

| Where                     | Value                                                                        | Why                                                                                                   |
| ------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Auth senders              | 8 000 ms                                                                     | A verification link should be instant when it can be; the request has nothing else to do.             |
| Contact form and waitlist | 5 000 ms                                                                     | The visitor is waiting on a form; the row is durable either way.                                      |
| Payment webhook senders   | 3 000 ms                                                                     | The webhook has a gateway on the other end and Phase 2 work behind it.                                |
| Jobs and both relays      | 10 000 ms per send                                                           | A job can wait longer, but one hung call must not hold a tick past the ceiling.                       |
| Novu inline attempt       | 5 000 ms (the client's existing `timeoutMs`)                                 | Already bounded since #1446; the outbox only changes what happens when it expires.                    |
| Email relay on the ticker | every 15 minutes, `?limit=20`, 20-second target timeout, one send per 125 ms | Resend's team limit is 10 requests/s and the inline path sends alongside; Actions stays the backstop. |
| Novu relay on the ticker  | every 5 minutes, `?limit=20`, 20-second target timeout                       | One round trip per row under a 5-second timeout fits the target timeout even when Novu is slow.       |

## What was deliberately not done

`deliver()` does not accept a `tx` option even though the spec sketched one, because an attempt inside an open transaction would send before the business write is durable; a transaction owner calls `stage()` and `attempt()` itself. `lib/novu/org-workflows.ts` keeps its own wire helpers and does not stage rows yet; its call sites are awaited, and moving it onto the outbox is a follow-up under #691. The relays run on the existing five-minute ticker rather than a queue, which is the posture of ADR 14 and ADR 27 and the recommendation of #1654; a workflow engine is revisited only if #1653's reminder sequences and digests need orchestration the ticker cannot express.

## 2026-09-15 — email core: preference gate, one-click unsubscribe, shared layout (#1653; closes #691 NTF-2 and NTF-3 for email)

**Branch:** `feat/1653-email-core` · **Scope:** `lib/email/preferences.ts`, `lib/email/unsubscribe.ts`, `lib/email/send-to-recipients.ts`, `app/api/notifications/unsubscribe/route.ts`, `app/(pages)/email/unsubscribe/page.tsx`, `emails/components/EmailLayout.tsx`, `emails/components/styles.ts`, small extensions to `EmailFooter`, `lib/waitlist/tokens.ts`, `lib/novu/subscriber.ts`, `deliver.ts` and `config.ts`.

This is the mechanism the booking, money and people lifecycle emails of #1653 build on; it adds no email of its own and changes no existing template or sender. #691 NTF-2 recorded that no email honoured `NotificationPreference`, and NTF-3 that no email could be unsubscribed from; both are now closed for the email channel by construction, because a lifecycle sender goes through `loadEmailRecipients()` and `sendToRecipients()` and cannot reach Resend without the gate and the headers.

The gate reads the database row at send time and not Novu's copy of the flags, since Novu is in-app only and its copy is a mirror written after the PUT. To keep the two from drifting, the category → column map moved into `EMAIL_CATEGORY_COLUMN` in `lib/email/preferences.ts` and `updateSubscriberPreferences()` now derives its `category*` flags from it in a loop, with `categoryMarketing` kept explicit because marketing is not a category. A `null` category is a required notice: always allowed, no unsubscribe link, and a footer line saying so.

One-click unsubscribe reuses `WAITLIST_HMAC_SECRET` through a new `signToken()` export on `lib/waitlist/tokens.ts` rather than a second env var, under its own purpose string so the newsletter and account tokens cannot be swapped. The route flips `emailEnabled` only and leaves the category columns and the bell untouched, because the columns are shared across channels and the complaint was the inbox. `GET` writes nothing, since link scanners prefetch; the confirmation page's form POSTs back to the API, which answers a browser (`Accept: text/html`) with a 303 to `?done=1` and a mail client with JSON. An id with no user answers 200 the same as a real one (the FK violation, `P2003`, is swallowed), so the route is not an oracle.

`RenderedEmail` gained `headers`, which `attempt()` passes to Resend and `stage()` deliberately does not persist: the relay's resend of a staged row carries no `List-Unsubscribe` headers, which was judged acceptable because the footer link in the body still works and a relayed row is the exception. `sendToRecipients()` is sequential rather than `Promise.all`, because `PG_POOL_MAX=1` serialises the outbox writes on Netlify anyway; its `sent` count includes a message that timed out inline but is staged for the relay, and `failed` counts only a render failure or a message that reached neither Resend nor the outbox. `stageToRecipients()` and `attemptStaged()` are the transaction owner's twins that the money PR needs. `EMAIL_BUDGET_MS.REQUEST` (5 000 ms) is the budget API-route senders will use. `npm run email:dev` starts react-email's preview server over `emails/`.

Tests: `__tests__/email/preferences.test.ts` (no row, channel off, category off, required notice, zone fallback), `__tests__/email/unsubscribe.test.ts` (token round-trip and tamper, POST flips and mirrors, bad token writes nothing, GET writes nothing), `__tests__/email/send-to-recipients.test.ts` (gate honoured, headers attached, counts).

## 2026-09-15 — #1647 webhook receiver, suppression list and batch outbox

**Branch:** `feat/1647-resend-webhook` · **Issue:** #1647 · **Schema:** #1659 (`EmailEvent`, `EmailSuppression`, `FailedEmailBatch`, already live).

What changed. `POST /api/webhooks/resend` receives Resend's delivery events, verifies the svix signature with the SDK's `webhooks.verify()` against `RESEND_WEBHOOK_SECRET`, and stores every event as an `EmailEvent` row before doing anything else; the svix id is unique, so a redelivery answers 200 with `duplicate: true` and runs no side effect twice. A `Permanent` bounce writes the address to `EmailSuppression` as `HARD_BOUNCE` and moves its `Waitlist` row to `BOUNCED`; a complaint writes `COMPLAINT` and unsubscribes the row. A `Transient` bounce only stores the event, because a full mailbox is not a dead address. `lib/email/suppression.ts` holds the list's helpers, and the list is enforced at both ends of the outbox: `stage()` writes a suppressed recipient's row as `DEAD_LETTER` with `suppressed:<REASON>` and `attempt()` returns without calling Resend, the relay dead-letters a suppressed row the same way, and the newsletter broadcast drops suppressed addresses and reports `skippedSuppressed`.

Why the receiver answers 200 after a failed side effect. The event row is the durable fact; a suppression or `Waitlist` write that fails after it is reported to Sentry on the fingerprint `["resend-webhook", "side-effect"]` and the response is still 200, because a retry from Resend would carry the same svix id and stop at the duplicate path, so a non-2xx would only make Resend retry an event we can never re-process. A failure to write the event row itself answers 500 so that Resend does retry.

Why the per-message `FailedEmail` rows left the broadcast route. The route now upserts a `FailedEmailBatch` row under the batch's content-derived idempotency key before calling `resend.batch.send`, marks it `SENT` on success and leaves it `PENDING` with `lastError` on failure, and the relay replays up to five such rows per tick through `resend.batch.send` under the stored key. The old failure path also wrote one `FailedEmail` row per message in the batch, each replayed under its own single-send key; keeping both would have sent every message twice on a replay, once through the batch key and once through the message key, because Resend deduplicates per key and the two keys differ. The batch row is the only replay path now, and its payload is exactly the array `resend.batch.send` accepts, headers included, so the relay passes it through unchanged.

What was deliberately not done. Opens and clicks are not subscribed and no tracking is enabled; the receiver stores any event type it is sent, so widening the subscription later needs no code change. No `svix` package was added, because the Resend SDK verifies signatures itself. Registering the webhook and setting the secret in the Netlify production context are owner steps after the release, listed in [05-pre-production-checklist.md](05-pre-production-checklist.md).

`deliver()` does not accept a `tx` option even though the spec sketched one, because an attempt inside an open transaction would send before the business write is durable; a transaction owner calls `stage()` and `attempt()` itself. `lib/novu/org-workflows.ts` kept its own wire helpers in this PR and did not stage rows; that follow-up landed the same day and is recorded below. The relays run on the existing five-minute ticker rather than a queue, which is the posture of ADR 14 and ADR 27 and the recommendation of #1654; a workflow engine is revisited only if #1653's reminder sequences and digests need orchestration the ticker cannot express.

## 2026-09-15 — the `ORG_*` family onto the outbox (#691 NTF-1, #1665 §5)

**Branch:** `fix/691-org-workflows-outbox` · **Scope:** `lib/novu/org-workflows.ts`, `lib/novu/service.ts`, both org-payout failure sites, `.env.sample`.

The seventeen `notifyOrg*` helpers called `getNovuClient().trigger()` directly, so an org bell had no row, no retry and no dead-letter: a Netlify freeze or a Novu 5xx lost it silently, the same NTF-1 class the entry above fixed for the B2C helpers. The three private wire helpers in `org-workflows.ts` are now thin wrappers over the exported service cores (`triggerWorkflow`, `triggerForMultiple`, `triggerForMultipleZoned`), so every `ORG_*` event is staged as a `NotificationOutbox` row under the event id, attempted inline under the five-second client timeout, and drained if that attempt did not settle it; the "not configured" branch stages and reports instead of returning early. Every helper takes the same trailing `{ tx, entityRef }` option as the B2C helpers and returns the list of staged rows (empty when it attempted inline), because a roster helper may split one event across timezone batches and the transaction owner needs each row for `attemptTrigger()` after its commit. `TriggerOptions.tx` widened from `Pick<Tx, "notificationOutbox">` to `Pick<Tx, "notificationOutbox" | "membership">` so `rosterForOrg()` reads the `Membership` roster through the caller's transaction: on Netlify the pool holds one connection, and a global-client read while a transaction is open deadlocks the function.

The two org-payout bells moved inside their claim transactions. `markOrgPayoutFailed` and the completed-then-reversed branch of `markOrgPayoutReversed` now stage `notifyOrgPayoutFailed` with `{ tx, entityRef: "orgPayout:<id>" }` right before the callback returns, and attempt the returned rows after the commit; the lazy `await import("@/lib/novu/org-workflows")` was replaced by the top-level import that already existed in the file for `notifyOrgPayoutCompleted`, because it had never been guarding a cycle. The #813 fire-and-forget comment that described a lost notification is gone with the behaviour it described. The withholding-identity guard and every ledger write in the reversal transaction are unchanged (ADR 21). `.env.sample` stopped naming `NOVU_SECRET_KEY`, which the runtime has not read since #1650, and names `NOVU_DEVELOPMENT_KEY` and `NOVU_PRODUCTION_KEY` with the selection rule from `lib/novu/secret-key.ts`.

A grep while writing the docs showed that the "40 run in `after()`" figure was already stale, and also that four sites still hand a `notify*` call to `after()` (the three document routes and `notifyRecordingAvailable`); those are the remaining NTF-1 residue and are recorded in `01-architecture.md`, not changed here.
