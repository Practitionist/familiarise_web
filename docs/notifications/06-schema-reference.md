# Schema reference: the email and notification outbox tables

This page lists every column the email and notification work added, model by model, with the reasoning that is too long for a schema comment. Every change is additive and either nullable, defaulted or a new table, so each is compatible with the pre-MVP freeze and none needs a backfill. The transactional-email dead-letter table `FailedEmail` is the model every new table here mirrors, and its retry worker is described in [01-architecture.md](01-architecture.md).

These tables serve the outbox-first design. A side effect such as an email or an in-app bell must never be able to fail, roll back or slow down the essential step that caused it (the user row, the payment, the inquiry), and the only way to close the crash window between the business commit and the provider call is to turn the provider call into a database write. Each outbox-shaped table below is therefore written where the business change commits, ideally inside the same transaction, and an inline fast path then attempts the send immediately under a timeout budget; when the fast path succeeds the row is marked `SENT`, and when it times out or the function dies the relay finishes the job on the next tick. The relay is the existing retry worker on the five-minute scheduled ticker, which is the outbox-plus-ticker pattern [ADR 27](../enterprise/70-design-decisions/27-state-as-outbox-and-scheduled-ticker.md) chose over a broker. The Resend webhook events, the suppression list and the batch outbox come from the Resend webhook receiver, which makes bounces and complaints visible to the application so a dead or hostile address stops receiving mail.

## `FailedEmail`

The table below lists the two columns and the index added to the dead-letter row; the rest of the model is unchanged.

| Column or index        | Why it exists                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `resendId?`            | The provider's message id, written when the row reaches `SENT`. It lets support open the message in Resend's log and lets an `EmailEvent` (below) be joined back to the row that produced it. Null until the send succeeds, and null forever on a `DEAD_LETTER` row.                                                                                                                                                                   |
| `entityRef?`           | The business anchor the message belongs to, written as `payment:<id>`, `user:<id>`, `newsletter:<email>` or `contact:<email>` by the sender that knows it. A plain string rather than a set of foreign keys, because one column has to point at several unrelated tables and a support question arrives as "the receipt for payment X", not as a row id. Null on the rows written before the column and on a job alert with no entity. |
| `firstAttemptAt?`      | Stamped with a conditional update just before the first Resend request (`stampFirstAttempt`, `lib/retry/provider-window.ts`). An automatic replay 23 h or more later would outlive Resend's 24 h idempotency cache, so the relay dead-letters the row as `review:provider_acceptance_unknown`; a row never attempted (null) is always sendable.                                                                                        |
| `@@index([entityRef])` | "Every email we tried to send for this payment" becomes an index lookup rather than a scan of the whole dead-letter table.                                                                                                                                                                                                                                                                                                             |

## `FailedEmailBatch`

One row per Resend batch request, so that a batch of up to one hundred messages is replayed as the same batch it was staged as. The table below lists its columns.

| Column or index                                               | Why it exists                                                                                                                                                                                                                               |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `idempotencyKey` (`@unique`)                                  | The key the batch request carries to Resend. It is unique here so the same batch cannot be staged twice, and it is replayed verbatim so a retry after a crash is dropped by the provider as a duplicate instead of sending the batch again. |
| `emailType`                                                   | A plain tag for metrics and for the worker's terminal-classification rules, the same role it plays on `FailedEmail`.                                                                                                                        |
| `payload` (`Json`)                                            | The serialized batch request exactly as it will be sent. `FailedEmail` stores rendered fields because it holds one message; a batch is an array of messages and a `Json` column is the honest shape for that.                               |
| `status`, `attempts`, `nextRetryAt?`, `lastError?`, `sentAt?` | The retry state machine shared with `FailedEmail`, so the same worker can drain both tables with the same backoff ladder and the same terminal classification.                                                                              |
| `firstAttemptAt?`                                             | The same 23 h provider-window anchor as on `FailedEmail`, stamped before the batch request.                                                                                                                                                 |
| `@@index([status, nextRetryAt])`                              | The relay's poll, "pending or retryable rows whose retry time has passed", is an index scan.                                                                                                                                                |

## `EmailEvent`

One row per webhook event Resend delivers about a message, whatever its type. The table below lists its columns.

| Column or index                                  | Why it exists                                                                                                                                                                                                                                                                 |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `svixId` (`@unique`)                             | The svix message id from the webhook headers. Resend retries a failed delivery and lets an operator replay events from its dashboard, so the receiver has to be idempotent; a unique constraint on the delivery id makes a redelivery a no-op insert instead of a second row. |
| `resendId` + `@@index([resendId])`               | The message the event is about. It joins back to `FailedEmail.resendId` so a bounce can be traced to the row, and to the business anchor, that produced it.                                                                                                                   |
| `type`                                           | The Resend event type as a string (`email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.complained`, `email.failed`). A string rather than an enum, because a new event type on the provider's side must not need a migration to be recorded.   |
| `recipient` + `@@index([recipient, receivedAt])` | The address the event concerns, indexed with the receipt time so "what happened to mail sent to this address recently" is the query support actually runs.                                                                                                                    |
| `payload` (`Json`)                               | The full event body, kept because the bounce sub-type and the provider's diagnostic text live inside it and the suppression decision needs them.                                                                                                                              |
| `receivedAt`                                     | When the receiver stored the event, which is the only clock the application controls.                                                                                                                                                                                         |

## `EmailSuppression` and `EmailSuppressionReason`

The addresses the senders must not write to. Resend keeps its own suppression list, but the application mirrors it so that `deliver()` can refuse a send before it is attempted and so support can explain a non-delivery. The table below lists its columns.

| Column or index  | Why it exists                                                                                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `email` (`@id`)  | The address is the key: there is at most one suppression per address, and the sender's check is a primary-key lookup.                                                                                   |
| `reason`         | `HARD_BOUNCE` (a permanent bounce), `COMPLAINT` (the recipient marked the mail as spam) or `MANUAL` (an operator added the address). The reason decides whether the address may ever be released again. |
| `sourceEventId?` | The `EmailEvent` that created the row, so the suppression can be explained from the provider's own evidence. Null on a `MANUAL` row, which has no event.                                                |
| `createdAt`      | When the address was suppressed.                                                                                                                                                                        |

## `NotificationOutbox` and `NotificationOutboxKind`

The Novu trigger outbox. A Novu trigger is one HTTPS call, and a function that freezes before the call completes loses the in-app bell with no trace; this table gives the trigger the same durable shape as an email, including every `ORG_*` event. The table below lists its columns.

| Column or index                                               | Why it exists                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workflowId`                                                  | The event id from `lib/novu/workflows.ts`, not the Novu workflow family. The family is a delivery detail: `toWire()` in `lib/novu/templates/` maps an event onto its family at send time, and the mapping can move an event between families without touching any row. Storing the family would freeze that mapping into data.                                                                                                                                                                                                                                                                                                                                                                                                        |
| `kind`                                                        | `SINGLE` (one subscriber) or `MULTI` (a list of subscribers, including each ≤100-recipient page of an announcement inbox post). The Prisma enum still has `BROADCAST`, which nothing writes since announcements moved to per-page fan-out and the maintenance bells were deleted, and the relay has no special case for it; the value is due for removal in a schema change.                                                                                                                                                                                                                                                                                                                                                          |
| `recipients` (`String[]`)                                     | The Novu subscriber ids, which are Prisma `User.id` values. The first attempt of each generation replaces them with the recipients current policy still allows; a definitive Novu response narrows them to the recipients not yet accepted and starts a new generation.                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `payload` (`Json`)                                            | The typed event payload, serialized as it will be sent.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `transactionId` (`@unique`)                                   | The row's dedupe key, derived when the row is staged rather than when it is sent; staging the same notification twice returns the existing row. A row goes to Novu as one event per recipient, each under `<transactionId>:<16 hex of sha256(recipient)>`, through the normal trigger for one recipient and the bulk endpoint for more. The `Idempotency-Key` hashes `firstAttemptAt`, the recipients and the wire payload, so a resend after an unknown outcome reuses the key and a changed body never does. Terminally refused recipients split off into a `DEAD_LETTER` row keyed `<transactionId>:terminal:<digest>`.                                                                                                            |
| `entityRef?` + `@@index([entityRef])`                         | The business anchor, in the same `payment:<id>` shape as `FailedEmail.entityRef` (the dispute handlers write `dispute:<id>`), so a support question can find every notification a change produced. Null when the call site has no transaction and passes none.                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `notBefore?`                                                  | The earliest instant the relay may send the row, for a producer that schedules a notification (for example a survey after a receipt window). Null means "as soon as possible", which is the common case.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `status`, `attempts`, `nextRetryAt?`, `lastError?`, `sentAt?` | The retry state machine shared with `FailedEmail`, so the drain is the same shape as the email relay.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `firstAttemptAt?`                                             | The anchor of the row's current generation and Idempotency-Key: stamped with a conditional update just before the generation's first Novu call, and reset to null (with `lastError`) when a definitive response ends the generation, so the next attempt rechecks policy under a new key. A row with a `lastError` but no anchor was never sent, because the anchor is claimed before any Novu request, so it sends normally. An automatic retry 23 h or more after it would outlive Novu's idempotency cache, so the row dead-letters as `review:provider_acceptance_unknown`; a row never attempted is always sendable. Dead letters prefixed `policy:` (for example `policy:audience_revoked`) are expected skips and never alert. |
| `@@index([status, nextRetryAt])`                              | The relay's poll is an index scan, as on every other outbox table.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

`NotificationPreference.quietHoursEnabled`, `quietHoursStart`, `quietHoursEnd` and `quietHoursTimezone` ("HH:MM" wall clock; an overnight window wraps midnight) are read only by the plan-week reminders (`nudgeUnplacedPlanWeeks`, `lib/booking/week-nudge.ts`): inside the window the consultant's email and bell, and a host organisation operator's bell on the third day, wait for a later run. The settings page labels them "Email quiet hours"; no other notification reads them.

## Settling a row

Every settle of a row in all three tables is a conditional `updateMany` filtered on `status` being `PENDING` or `RETRY` (`UNSETTLED` in `lib/retry/provider-window.ts` for the email tables, `ACTIVE_STATUSES` in `lib/novu/outbox.ts` for bells). A writer that lost a race to another attempt matches no row, is skipped and is not counted, so nothing can overwrite `SENT`. The email paths are `settleRow` in `lib/email/deliver.ts`, the relay in `jobs/email/retry-failed-emails.ts` and `settleBatch` in `app/api/admin/newsletter/broadcast/route.ts`; the bell path is `settleRow` in `lib/novu/outbox.ts`.

## Why `EmailDeliveryStatus` is shared

`FailedEmail`, `FailedEmailBatch` and `NotificationOutbox` all use the one `EmailDeliveryStatus` enum (`PENDING`, `RETRY`, `SENT`, `DEAD_LETTER`) rather than one enum each. The tables are the same machine: a row is staged, attempted, retried on a backoff ladder, and either sent or dead-lettered for an operator to replay. One enum means one worker shape, one set of terminal-classification rules and one operator vocabulary across the three, and a fourth outbox-shaped table can reuse it without a migration. The name keeps its `Email` prefix because the two new tables arrived after it was named, and renaming an enum that live rows already use is a migration for no behavioural gain.

## Applying the schema

Every table and index above requires `npm run db:push` on each environment, because a schema-only merge does not create it; `db:push` chains the SQL sidecars and then asserts them. The push is an owner-approved operation performed by the orchestrator after review, never by the pull request that adds the schema, so CI's "Database sidecar + drift guard" check stays red on that pull request until the push has happened. `npm run db:preflight` runs first and refuses any destructive statement, which is described with the rest of the deployment order in [`docs/reviews/07-deployment-and-deferred-work.md`](../reviews/07-deployment-and-deferred-work.md).
