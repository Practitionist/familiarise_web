# ADR: The back office gets one permission matrix, one operator time zone and one totals page

- **Status**: Accepted (owner decisions, 2026-11-16 and 2026-11-17). Shipped in four back-office pull requests: access and foundations, the decision queue, the money pages, and people, support and comms (D11 to D17).
- **Date**: 2026-11-16
- **Author**: Platform engineering
- **Related**: [Authorization matrices](../authorization/01-authorization-matrices.md), [Maintenance architecture](../maintenance/01-architecture.md), [Trial sessions](../booking/09-trials.md), [Access rules after the bug hunt](2026-11-13-access-rules-after-the-bug-hunt.md)

## Context

The staff and admin consoles were audited before launch. Four things were wrong or inconsistent.

- **Access lived in two places.** Most back-office pages ask the permission matrix (`BACKOFFICE_PERMISSIONS` in `lib/auth/backoffice-permissions.ts`) through `requireBackofficePage` and `requireBackofficeSurface`. About fifty API routes still asked a raw role question instead (one helper for ADMIN or STAFF, one for ADMIN only, both in `lib/auth-helpers.ts`). A grant made that way is invisible to the file that is supposed to list every grant.
- **Totals lived on two pages.** The admin-only Analytics page held every money and role total. The staff-only Metrics page held support-queue figures and documented itself as excluding revenue. Both pages already used the `analytics.read` key, so the "admin-only" and "staff-only" labels were nav choices, not access rules.
- **Times were shown in whatever zone a screen happened to use.** About 57 back-office files used the browser zone, the server zone or a hard-coded zone, so the same instant read differently on two screens and a server-rendered label could differ from its hydrated version.
- **Some admin writes were unaudited or leaked.** The maintenance history returned every column of the last 20 windows, including each window's bypass secret. A leads status change wrote no `OpsActionLog` row and asked for no reason. The OFFLINE setup step wrote no audit row.

## Decisions

1. **D1: there is no staff "void session" door before launch.** Staff end or repair a session through the doors that already exist and are audited: the refund doors (Money, Refunds, and the support remedy path) and the incident door (Money, Incidents). Each of them runs through `withOpsAction` (`lib/backoffice/ops-action-log.ts`), so each leaves an `OpsActionLog` row with a reason.
   - Options not chosen: a new staff void door now. It would be a second way to end a session beside doors that already carry the refund caps, the step-up and the audit.

2. **D2: Analytics is folded into Metrics.** Metrics now carries the platform totals next to the support-queue figures, read through `lib/backoffice/platform-totals.ts` with the same `where` clauses the old endpoint used.
   - Kept: users and new users this month, experts, learners, staff, sessions (all, completed, upcoming, cancelled), the revenue total and this month, and refunds.
   - The cancelled count reads `Consultation` rows with status `CANCELLED`, while the sessions total counts every `Appointment`, so the two are different populations. The read stays as Analytics had it, and the card is labelled "Cancelled consultation requests".
   - Dropped: average session value and top domains, which were not on the owner's list of totals to keep.
   - Deleted: the Analytics page, its client component, its loading file, its nav entry and `GET /api/admin/analytics`.
   - Kept on purpose: `GET /api/admin/analytics/cancellations`, because the mobile API document ([Cancellation API for mobile](../api/cancellation-api-mobile.md)) names it. It moves onto the matrix as `analytics.read` and is otherwise unchanged.
   - The totals are served by `GET /api/staff/metrics` (`getPlatformTotals`, gated on `analytics.read`), next to the support-queue figures.
   - Metrics shows in both trees (`/dashboard/admin/metrics` and `/dashboard/staff/metrics`).
   - Options not chosen: keeping Analytics as its own page. Two pages with the same permission key and overlapping numbers would drift.

3. **D3: the operator display zone is IST (`Asia/Kolkata`) on every back-office screen.** The exact UTC instant shows in a tooltip. One helper pair gives the same text on the server and the client:
   - `lib/time/operator-zone.ts` holds `OPERATOR_ZONE`, `formatOperatorInstant` (for example "1 Apr 2026, 5:30 am IST"), `formatUtcInstant` (the tooltip text) and `operatorMonthStart` (00:00 IST on the first of the India month);
   - `lib/time/operator-time.tsx` holds `OperatorTime`, a `<time>` element that prints the IST text and carries the UTC reading in its `title`.

   Both go through `lib/time/display.ts` with the zone and the `en-IN` locale pinned, so a server render and the hydrating browser print identical text. The back-office layout (`app/dashboard/(backoffice)/[tree]/layout.tsx`) mounts one `DisplayZoneProvider` with that zone, so every screen that already reads the provided zone moves with no edit. A person is shown the same way everywhere through `formatPerson` (`lib/backoffice/person.ts`) and `PersonCell` (`components/dashboard/backoffice/PersonCell.tsx`): the name, the email under it, a muted id, and "Removed user" when nothing is known.
   - Rollout was split across the four pull requests: the helper, the layout provider and the first screens in the first, the money screens in the third, and the people and support screens in the fourth (D16).
   - Options not chosen: the viewer's profile zone (two operators would read the same incident at different clock times); the browser zone (the hydration mismatch the display helpers were written to prevent).

4. **D4: there is no staff door to end a paid trial now.** The trial routes refuse an operator who is not a party to the trial with 403 `PLATFORM_CANCEL_DOOR_REQUIRED` (`platformCancelDoorRefusal` in `lib/booking/platform-cancel.ts`), and no back-office door exists for a trial ([Trial sessions](../booking/09-trials.md)). Whether to build one is tracked as the issue "[backoffice][trials][P3] Decide a staff door to end a paid trial (deferred at Train 6; revisit with F8)" (#2836).
   - Options not chosen: building the door in this train.

5. **D5: only ADMIN can change the trial price floor.** `PATCH /api/admin/trial-pricing` now requires the matrix key `trialPricing.manage`, which is `ADMIN_ONLY`. The floor (`PlatformPricingConfig.minTrialPriceInPaise`) sits under every plan's trial price, so changing it changes what every expert may charge.
   - `PATCH` is an audited door (`withOpsAction`, action `trialPricing.update`): it needs a reason of at least 5 characters, reads the floor inside the transaction and changes it only if it is still that value (a lost race answers 409 `FLOOR_CHANGED`), and writes an `OpsActionLog` row with the old and new floor.
   - The key gates both `GET` and `PATCH` on that route, so STAFF can neither read nor change the floor through the API. Plan create and update routes still reject a price below it for every expert, because they read the floor on the server.
   - Options not chosen: ADMIN and STAFF, which was the access before.

6. **D6: both ADMIN and STAFF see the revenue and refund cards on Metrics.** Staff can already read every payment row on Payments (`payments.read`), so hiding the totals protected nothing. The comment on `GET /api/staff/metrics` that said it excludes revenue is removed.
   - Options not chosen: an admin-only revenue key (a new key that withholds a sum of figures staff can already open row by row).

7. **D7: "this month" on Metrics starts at 00:00 IST.** The card says "this month (IST)". The old endpoint cut the month with the server's clock, which on Netlify is UTC. Every period on the Metrics page is cut in IST by `operatorPeriodStarts` and `operatorMonthStart` (`lib/time/operator-zone.ts`): the "this month" platform cards (new users, revenue) and the support-queue figures' today, this week (a week opens on Sunday, as before) and this month. Every other read is unchanged.
   - Worked example: Priya Anderson (seed learner) pays ₹1,000 (100,000 paise) at 03:00 IST on 1 December. That instant is 21:30 UTC on 30 November. It now counts in December's "this month (IST)" total. Under the old UTC-month cut it counted in November. The all-time totals are the same either way.
   - Options not chosen: keeping the UTC month. It would put the first 5 hours 30 minutes of every IST month in the previous month's card.

8. **D8: the raw-role API routes move onto the permission matrix with their own screen's pull request.** The first pull request moves only the routes it names:
   - leads (`app/api/admin/leads/route.ts` and `leads/[leadId]/route.ts`) to `leads.manage`;
   - the trial price floor to `trialPricing.manage`;
   - stats (`app/api/admin/stats/route.ts`), `analytics/cancellations` and the Metrics endpoint (`app/api/staff/metrics/route.ts`) to `analytics.read`;
   - maintenance (`maintenance`, `maintenance/preflight`, `maintenance/booking-remediation`) to `maintenance.manage`.

   The remaining routes moved with the pull request that owns their screen, and the last of them deleted both raw helpers (D11).
   - Options not chosen: moving every route at once. It would put about fifty routes under one review with no screen to test each against.

## The second pull request: the decision queue and the appointments area

The second pull request changes only reads, paging and display on the Appointments page of both trees. It changes no money rule, no status transition and no schema.

1. **"Sessions that need a decision" is a paged, sortable table.** `readSessionsNeedingHuman` (`lib/backoffice/session-outcomes.ts`) reads one page of 20 rows over the unchanged `NEEDS_HUMAN` predicate (`lib/booking/misses.ts`), which the nav counts and the needs-attention inbox also read.
   - It costs three statements: one joined list, one count and one batched user read. The old read was two lists capped at 100 rows, with no booking or person on a row.
   - `GET /api/admin/sessions/needs-human` parses `?page` (a positive whole number) and `?sort` through `needsHumanQuerySchema` (`lib/backoffice/needs-human-queue.ts`). The sort keys are `endsAt`, `startsAt`, `outcomeAt` (shown as "Waiting since") and `lostMinutes`, with a leading `-` for descending; anything else answers 400.
   - The default order is the session's end, oldest first, so a session parked longest leads the first page. Each row still says whether it is over 7 days old (`isAgedNeedsHuman`, the same test the escalation uses), because its booking's settlement waits on it.
   - A row names the booking, the expert and the learner (`PersonCell`), or the live roster of an event ("12 attendees" for a webinar, "12 students" for a class), through the same `appointmentHeadline` helper the appointments list uses (`lib/data/appointment-headline.ts`).
   - The columns are stacked (expert over learner, the session's date over its times, the outcome over the minutes lost and the "Set outcome" button), so the table fits the card at 1440 px. "Waiting since" shows the verdict's time, or "—" when no verdict was written yet; such a row sorts last, so the column and its sort agree.
   - A sort picker above the table offers every sort, including the default "Ended, oldest first". It is the sort control on a phone, where the table becomes cards.
   - Clicking a row opens that booking's drawer, and the appointments list underneath keeps its search, tab and type: the booking is read by its id beside the list.
   - The card parses the route's body with `needsHumanPageSchema`, and the appointments list parses its own with `staffAppointmentsPayloadSchema` (`lib/data/staff-appointments-schema.ts`), so a malformed 200 shows the error state rather than an empty or broken table. Their enum fields (booking source, payment status and gateway, reschedule status, session outcome, end reason) are checked against the Prisma enums. If reading the booking a row opens fails, an error with a retry shows above the list, and clicking the row again also retries.
   - The queue keeps its page and sort in the card's own state, because the URL's `q`, `page` and `sort` belong to the appointments list below it.
   - Worked example: 45 sessions are parked. The first page shows the 20 that ended earliest. An operator who sorts by "Most minutes lost" and moves to page 2 sends `?page=2&sort=-lostMinutes` and reads rows 21 to 40 in that order.
2. **Trials are on every tab and in the search.** The Scheduled, Completed and Issues tabs and their counts each have a trial arm (`buildStatusWhere` in `lib/data/staff-appointments.ts`), the search matches a trial's plan title, expert and learner, and the Type filter has "Trial". A trial's expert is the trial's own consultant (`Trial.consultantProfileId`), not the author of the plan it was taken on, both on the row and in the search.
   - A trial is priced from what the buyer agreed to (`Trial.agreedPricePaise`), and from the plan's trial price only on rows from before that column, so a trial whose plan later went free does not read as free.
   - A removed booking (`Appointment.deletedAt` set) stays listed, carries a "Removed" badge and counts under Issues. A trial booking whose trial row is gone is titled "Trial (record removed)" and reads Cancelled.
3. **The booking drawer reads one clock.** The list row, "Scheduled At", the Ops panel's sessions, the class series doors and the documents panel print India time through `OperatorTime` or `formatOperatorInstant`, with the UTC instant on hover. A session's end prints its time alone when it falls on the start's India-time day. The relative times in the timeline and the pay-link deadline keep their words and carry the India-time instant in their tooltip. The payment line and the drawer's payment card name the status and the gateway in words (`paymentStatusBadge`, `gatewayLabel`).
4. **The booking timeline and the entity trace show only real changes.** `getBookingTimeline` (`lib/data/booking-history.ts`) feeds both. Its query leaves out a status row whose before and after are the same and that carries neither a reason nor an actor, before the 200-row limit, so such rows can never push a real change out of the window. A same-status row with a reason or an actor stays, because it records who did something. The entity trace reads a booking's sessions from the booking itself, not from the shown entries, so a session whose only history row is hidden still brings its console audit rows. Steps read as words ("Scheduled → Unverified"), and an outcome token reads as its label ("Outcome sweep: Nobody joined"). A reschedule proposal is listed as "Reschedule proposed", with where it stands now beside it ("now accepted"); the answer is the status row of that reschedule request, so the outcome appears once. The history writes are unchanged.
5. **Two more routes ask the matrix.** `GET /api/staff/appointments` and `GET /api/staff/appointments/[appointmentId]/timeline` moved from the ADMIN-or-STAFF raw guard to `appointments.manage`, which is the same ADMIN and STAFF set. The queue route keeps `classSeries.support`, the same set.
   - `GET /api/staff/appointments` reads `?page` and `?limit` through zod: a value that is not a positive whole number falls back to page 1 and 20 rows, and the limit is clamped to 100.
   - A role the matrix refuses gets a 403 whose body carries `code: "FORBIDDEN"` beside the message (`requireBackofficeSurface` in `lib/auth-helpers.ts`).
   - Options not chosen: keeping the queue's two-list read with a higher cap. A cap hides rows past it, and the rows it did show could not be told apart.

## The third pull request: the money pages

The third pull request changes reads, paging and display on the Money area, Invoices, Subscriptions, TDS, Compliance and the entity trace. It changes no money rule, amount, status transition or schema. Display logic that reads like a rule is unchanged: the refundable remainder in the refund door, the TDS CSV's division by 100, the MSME `daysLeft < 5` flag and the dispute overdue flags.

1. **Every money row names the person and the booking.** The payments, refunds, disputes and earnings lists name the buyer (`PersonCell`) and the booking (`BookingCell`, the plan's title and its kind, linked to the booking). The title comes from `bookingRefOf` (`lib/data/booking-title.ts`), whose select fragment rides the row's own read with `relationLoadStrategy: "join"`, so a page adds no statement. Payouts name the expert, Org payouts name who created and approved each payout (one batched user read), and the Invoices B2C tab names the booking an invoice bills.
2. **A console target is named, not printed as "kind id".** Approvals, the Audit log, Support spend and the refunds waiting for a human resolve a `User`, `Payment`, `Appointment`, `AppointmentOccurrence`, `Organization` or `Lead` target to its person and booking through `resolveTargets` (`lib/backoffice/target-refs.ts`). It makes at most four batched reads a page: one user read that also brings the page's payments by their buyer, one booking read that also brings its sessions, one organisation read and one lead read. Any other kind still shows its kind and id.
3. **Every list pages on the server, with a true total.** The lists use the shared `TablePagination`. `readPageParams` and `readOffsetParams` (`lib/backoffice/list-paging.ts`) read `?page` and `?limit`: a value that is not a positive whole number falls back to the default, and a page holds at most 100 rows. Paged reads break ties by `id`, so a page never repeats or skips a row. An unknown status filter answers 400 on every money list (payments, refunds, disputes, payouts, org payouts, earnings, subscriptions, invoices, proposals). Pending payouts (once capped at 100 rows), Org payouts and Earnings (once fixed at 50), Approvals (once 100), Incidents (once 50), Support spend, the compliance lists (once 200, 100 and 100) and the TDS consultants view now page. Support spend pages its operators by name, ten to a page, and reads the 30-day window for that page's operators only.
4. **One status badge and one clock.** Statuses render through `StatusBadge` and the `lib/labels` maps; the subscription plan state, the org and consumer invoice, the approval proposal, the incident phase and the reconcile job gained tone maps in `lib/labels/backoffice-labels.ts`. Times print through `OperatorTime` in IST with UTC on hover. The incident window an admin types is read as IST (`fromOperatorWallTime`), and the payouts trend and the payouts CSV filename use IST days.
5. **The payments and refunds lists answer an allowlist.** Each selects named columns and maps them field by field, so no `payerVpaHash`, `payerPhoneHash`, refund-owed note, `metadata` or `failureReason` reaches the browser; the payment detail is an allowlist too. The disputes list sends the buyer's email only to a viewer holding `disputes.manage`, as the dispute detail does. Each screen parses its body with the Zod schema the route builds it against (`lib/backoffice/money-list-schemas.ts`), so a malformed 200 shows the error state.
6. **D9: the TDS filing date is the IST day (owner decision, 2026-11-17).** `POST /api/admin/tds` reads the filing date `YYYY-MM-DD` as 00:00 IST that day (`istFilingDate` in `lib/compliance/ist-period.ts`) and accepts it when that day is today or earlier in IST; anything else answers 400 `INVALID_FILING_DATE`. Rows already filed keep their stored instant. The page's default financial year and filing date are read in IST too.
   - Worked example: Olivia Brown (ADMIN) records the Q4 return of FY 2025-26 at 00:30 IST on 1 April 2026, which is 19:00 UTC on 31 March. The page opens on FY 2026-27, the year now open in India, and she picks 2025-26. The filing date defaults to 2026-04-01 and is stored as 18:30 UTC on 31 March, which is 00:00 IST on 1 April. Before, the server read the same text as 00:00 UTC on 1 April (05:30 IST), which was still in the future, so it refused the filing until 05:30 IST; and a browser in UTC defaulted the date to 31 March and the year to 2025-26.
   - Options not chosen: reading the date at 00:00 UTC (it moves the IST day by 5 hours 30 minutes and refuses a same-day filing for that long).
7. **Links land on pages that exist.** `/dashboard/<tree>/payments` and `/disputes`, the parent crumbs of the payment and dispute detail pages, redirect to their Money tabs, and Subscriptions opens a booking on Appointments (`bookingHref`).
8. **The entity trace speaks words.** The lookup form shows the kind and id being traced, with the shared Select; the summary lists the booking once and names the customer with `PersonCell`, linked to User 360; the timeline stacks its columns and wraps long ids so it fits its card. The payment row names the gateway (`gatewayLabel`), a ledger row its accounts (`ledgerAccountLabel`, for example "Debit Cash · Credit Platform fee, Owed to expert") and a stored reason its words (`traceReason`, so `HOST_CANCELLED_SESSION` reads "Host cancelled the session"), an earnings row its role ("Expert share") and a system event its category and level ("Payment event (info)"). A payment trace lists the traced payment once and its side charges under their own label.
9. **D10: STAFF see the emails the money rows name (owner decision, 2026-11-17).** A STAFF operator reads the email of the creator and both approvers on Org payouts, of the buyer on Earnings and on the refunds waiting for a human, and of the person behind an Audit or Support spend target. This matches the payment detail, which has always shown STAFF the buyer's email. The existing gates stay: the disputes list and detail send the buyer's email only with `disputes.manage`, and Invoices and TDS withhold emails from STAFF (`showPii`). `__tests__/backoffice/money-readers-contract.test.ts` pins it.
   - Options not chosen: sending these emails to ADMIN only, as Invoices does. STAFF answer the same billing tickets from the payment detail, where the email already shows.
10. **Eleven more routes ask the matrix, with the same people.** The payments list and detail (`payments.read`), the refunds `GET` (`refunds.read`), the disputes list and detail (`disputes.read`), the subscriptions `GET` (`subscriptions.read`), the TDS return (`tds.read`), the GST register and erasure process and reject (`compliance.manage`) and the settlement lines (`payouts.read`). ## The fourth pull request: people, support and comms

The fourth pull request moves the people screens (Users, User 360, Verification, Moderation, Feedback, Leads, Organizations, Team, Announcements and Newsletter), splits the referral page from the platform fees, fixes support times (#2828 "[support][ux][P3] Support pages show times in the browser's zone instead of the viewer's profile zone"), and finishes D8. It changes no money rule, amount or schema.

11. **D11: every back-office route asks the permission matrix, and the raw role guards are deleted (owner decision, 2026-11-17).** The last 26 call sites in 23 route files moved onto a key with the same people, and the ADMIN-only and ADMIN-or-STAFF helpers were removed from `lib/auth-helpers.ts`. `requireRoleGate` stays as the body of `requireBackofficeSurface`, and `isPrivileged` stays for branches inside a handler. `__tests__/backoffice/raw-role-guards-removed.test.ts` fails if a role-named guard comes back.
    - Same people on each move: Users (`users.read`), Verification and its Documents tab (`users.verify`), Organizations (`organizations.manage`), Feedback (`feedback.manage`), the moderation queue, report detail, action and stats (`moderation.manage`), the newsletter list (`newsletter.manage`) and send (`newsletter.send`). Unban and review removal were ADMIN-or-STAFF guards with an inline ADMIN check, so they ask `users.moderate`, which is ADMIN only.
    - Routes with no screen key of their own: the support compliance report asks `compliance.manage`; support health, system events and the exchange-rate cache ask `systemJobs.manage`. All four keys are ADMIN only, as the routes were.
    - `POST /api/user/consent` is an operator recording their own consent, not a back-office surface, so it asks `requireApiAuth()` and then `isPrivileged()`, the pattern the trial routes use, and answers 403 `FORBIDDEN` to anyone else.
    - Deleted, each with no caller found by a search of `app/`, `components/`, `lib/` and `hooks/`: `GET /api/admin/users/[userId]` (it returned phone, bio and city), `GET /api/staff/stats` with `lib/data/staff-stats.ts` and `getStaffDashboardStats`, and `AppointmentContextCard`.
    - Options not chosen: a new matrix key for operator consent (a self-service action has no surface to grant); new keys for the four screenless routes (the existing ADMIN-only keys already name the same people).

12. **D12: people and comms writes are audited doors (owner decision, 2026-11-17).** A verification decision, a report status or assignee change, a moderation action (warn, dismiss, remove content, exclude from the rating, suspend, ban), an unban, a review removal and a newsletter send each run through `withOpsAction`. Each requires a reason of at least 5 characters (`opsReasonSchema`) and writes one `OpsActionLog` row with the actor, the role, the target, the before and the after. Each status change keeps its compare-and-set in the `WHERE`, and a lost one answers 409 with a code (`ALREADY_DECIDED`, `REPORT_CHANGED`, `REPORT_RESOLVED`, `REVIEW_ALREADY_REMOVED`).
    - A verification decision and a review removal are transactional doors: the decision and the audit row commit together on a Serializable transaction with retry, through the new `serializable` option of `withOpsAction`. The public-surface purge and the notice attempts run after commit.
    - A moderation action, an unban and a newsletter send end in vendor calls (Stream, Resend), so they are gateway doors: the row is written once the action has run, with `after.status` `SUCCEEDED`, or `FAILED` and the refusal code.
    - An unban of an account that is no longer banned still re-applies Stream access (the repair the route exists for) and answers 200; its row says `lifted: false`. This is the one door where a missed compare-and-set is not a 409 (owner decision, 2026-11-17).
    - A review removal of a review moderation already removed now answers 409 instead of 200 with `alreadyRemoved`, and writes no row (owner decision, 2026-11-17).
    - The newsletter `preview` only counts the audience and writes no row.
    - The dialogs gained a reason field: the verification review modal, every moderation decision (each now goes through a confirm with a reason), the review removal, the unban on Moderation and on User 360, and the three newsletter sends (the test send now has a dialog too). The request bodies come from `lib/backoffice/people-door-bodies.ts`, and `__tests__/backoffice/people-doors.test.ts` posts exactly those bodies to the routes.
    - Worked example: Maria Brown (STAFF) dismisses a spam report against Aarav Anderson (seed expert) at 14:05 IST with the reason "Duplicate of an earlier report". The door reads the report, the compare-and-set moves it from `PENDING` to `DISMISSED`, and one row records Maria, `STAFF`, `moderation.manage`, `moderation.action.NO_ACTION`, the report, the reason, before `{ reportStatus: "PENDING" }` and after `{ status: "SUCCEEDED", reportStatus: "DISMISSED" }`. If Olivia Brown (ADMIN) dismissed it a second earlier, Maria gets 409 `REPORT_RESOLVED` and the row says `FAILED`.
    - Options not chosen: keeping these writes role-gated with no reason (the state they change is the account's or the public's); one transaction around the vendor calls (a Stream call cannot roll back).

13. **D13: staff see the author of an anonymous review (owner decision, 2026-11-17).** The moderation reviews list keeps sending the reviewer's name for an anonymous review, and the card shows the name with the label "Anonymous to the public" (`PersonCell`'s `anonymousLabel`). Only the public profile hides the author. The record is in the [authorization matrices](../authorization/01-authorization-matrices.md).
    - Options not chosen: hiding the author from staff too (moderation of an abusive review needs to know who wrote it).

14. **D14: fee waivers stay on Referral credits; Platform fees holds only the fee schedules (owner decision, 2026-11-17).** Referral credits keeps credits, fee waivers, referrals held for review and the program economics on `referrals.read` (writes on `referrals.manage`). The new Platform fees page (`/dashboard/<tree>/platform-fees`, `components/dashboard/backoffice/fees/PlatformFeesPageClient.tsx`) holds the take-rate schedules on `payments.read`, with propose and approve on `payments.manage`, the keys the fee API already used, so nobody gains or loses access. The schedule list names who proposed and who approved each row, and the effective-from time an admin types is IST wall time (`fromOperatorWallTime`, owner-confirmed 2026-11-17); the field is labelled "Effective from (IST)".
    - Options not chosen: moving fee waivers to Platform fees (a waiver is a referral reward, granted with the referral program).

15. **D15: every people list pages on the server.** `?page` and `?limit` go through `readPageParams` or `pageNumberSchema` (`lib/backoffice/list-paging.ts`): a value that is not a positive whole number reads as the default, and a page holds at most 100 rows. Every paged order ends on `id`. The moderation reports and reviews (the client never sent `page`, so only the first 20 and 10 were reachable), the expert verification queue (once "Load more" over offset pages), the organization verification queue (once 100 rows), the SSO approvals (once 50, now `?ssoPage`), announcements (once 100) and fee schedules (once 50) have real pagers. Each screen parses its body with the schema the route builds it against (`lib/backoffice/people-list-schemas.ts`, `lib/backoffice/moderation-schemas.ts`), and a failed load shows an error, never an empty list. An unknown verification or organization status answers 400 `INVALID_STATUS`. The verification list sends no stored `fileUrl`; a document opens through its ACL'd download route. User 360 reads each section on its own, so one failed section shows its own error and the rest of the page still loads; the failures are reported once per page.

16. **D16: support times are IST for staff and the viewer's profile zone for customers.** Both use `lib/time/zone-clock.ts`, which prints India time through `formatOperatorInstant` (labelled IST) and any other zone through `lib/time/display.ts` (Intl only, never date-fns-tz, so no daylight-saving error), labelling UTC. `useZoneClock` reads the nearest `DisplayZoneProvider`: the back-office layout pins IST, and each customer dashboard layout (consultee, consultant, organization and org workspace) mounts `ViewerZone` (`app/support/_components/ViewerZone.tsx`), which reads `getViewerZone()` on the server, so every customer surface, a chat-opened support sheet and the create-ticket dialog included, prints the profile zone and hydration prints the same text. A viewer with no saved zone follows `resolveViewerZone` (UTC, labelled). With no provider at all the hook reads the browser zone through Intl once hydrated. The public Help Center pages show no support times, so they mount nothing. A shared component such as the chat bubble therefore prints IST to staff and the customer's zone to the customer (owner decision on the fallback, 2026-11-17). `describeWait` takes the zone. The inbox date filter cuts each day at 00:00 IST (`lib/support/inbox-query.ts`), and the Moderation "Resolved Today" card counts from 00:00 IST.
    - Worked example: a reply at 12:45 UTC on 16 Nov 2026 reads "6:15 pm IST" to Maria Brown in the inbox and "4:45 am" to a learner whose profile zone is America/Los_Angeles. A reply-by of 03:00 UTC on 17 Nov reads "by 7:00 pm today" to that learner and "8:30 am IST on 17 Nov" in the back office.
    - Options not chosen: the viewer's zone for staff (the issue's suggestion; two operators would read one deadline at different clock times, D3).

17. **D17: Organizations dates are IST.** The organization list, its verification queue and the SSO approvals print dates through `OperatorTime` (they used the US format, `9/14/2026`).

## Limits that remain

- Leads still page by cursor with "Load more"; its order (newest first, by id) cannot repeat a row.
- The compliance report, support health, system events and exchange-rate routes reuse ADMIN-only keys of other screens; a key of their own would only matter if staff were ever granted one of them.
- Support spend still reads every ops row of the 30-day window for the operators on its page. Bounding that read would cut the sums it shows, so it waits for an owner decision on how to summarise the window.
- Platform totals are counts and sums read on request, with no cache. The scaling roadmap ([Production scaling roadmap](../infrastructure/00-production-scaling-roadmap.md)) records the plan if they slow down.

## Deprecated & Superseded Approaches

- **A separate admin-only Analytics page and `GET /api/admin/analytics`**: superseded by Metrics. Delete any leftover reference to `AnalyticsPageClient` or the endpoint.
- **A "Revenue trends, User growth, Booking conversion" Analytics page**: the testing playbook once described these charts, but the page only ever showed stat cards.
- **Raw role guards on admin routes** (an ADMIN-only helper and an ADMIN-or-STAFF helper in `lib/auth-helpers.ts`): every caller moved onto a matrix key with the same role set, and both helpers were deleted (D11). Do not add a role-named helper back.
- **Reading `new Date(year, month, 1)` for a back-office "this month"**: it uses the server's zone. Use the IST month cut in `lib/backoffice/platform-totals.ts`.
- **Hand-written list interfaces for the payments, refunds, disputes and payouts lists** (once in `types/payments.ts`, `types/disputes.ts` and a deleted payouts types file): replaced by the Zod list schemas in `lib/backoffice/money-list-schemas.ts`. Do not add a hand-written interface for a list body.
- **`new Date("YYYY-MM-DD")` for a filing or report date**: it reads 00:00 UTC. Use `istFilingDate` or `fromOperatorWallTime`.
- **Support times through `toLocaleString`, `toLocaleDateString` or `display.ts` with no zone**: they printed the browser's or the server's zone. Use `useZoneClock` or `zoneClock(zone)`.
- **Hand-written moderation, verification, feedback and user list types** (`types/moderation.ts`, `types/feedback.ts`, `types/admin-users.ts`): replaced by the Zod schemas in `lib/backoffice/moderation-schemas.ts` and `lib/backoffice/people-list-schemas.ts`.
- **`reviewVerification` with its own transaction**: replaced by `reviewVerificationTx`, which runs on the audited door's transaction.
