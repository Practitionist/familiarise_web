# ADR: A refund key replays a refund only for the request it was spent on

- **Status**: Accepted by the owner on 2026-11-21. Ships in the pull request that adds this record.
- **Date**: 2026-11-21
- **Author**: Platform engineering
- **Related**: [Refunds](../finance/30-refunds-disputes/01-refunds.md), [Money remedies](../support/05-money-remedies.md), [Request again closes the old order first](2026-11-20-request-again-closes-the-old-order.md)

## Context

Every refund can carry a dedupe key, stored in `Refund.dedupeKey`, which the database keeps unique across all refunds. The key exists so that a retried click, a retried job or a lost network response never refunds twice. The writers honour it before any balance check: `refundPayment` (`lib/payments/operations/refund.ts`) and the in-ledger rails behind `refundBookingPayment` (`withDedupe` in `lib/payments/operations/booking-refund.ts`) both start by asking `findDedupedRefund`, which looks the key up and, when it finds a refund that moved money or is still in flight, hands that refund back as the answer. A `FAILED` or `CANCELLED` refund moved no money, so its key is released for a retry.

The lookup used the key alone. It never asked whether the new request was about the same payment. An external review found the consequence. A caller who reused the key of payment A's completed refund on a full-refund request for a different card payment B got A's refund back as the answer. The booking wrapper then took that answer as proof that B's refund had happened and stamped B's seat `REFUNDED` and revoked its chat and call access, although no money had moved for B.

## Worked example

Charlotte Brown paid ₹2,000.00 (200,000 paise) for payment A, a consultation with Hannah Anderson. On Saturday 21 Nov 2026 at 11:00 IST an operator refunds A in full with the key `K`. The refund for ₹2,000.00 is recorded under `K`. Charlotte also holds payment B, ₹1,500.00 (150,000 paise) for a different booking with Hannah.

| Request                                                   | Answer                                                                                                  |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Payment A, no amount (a full refund), key `K`, again      | A's refund of ₹2,000.00 is returned. No second refund exists, and nothing is sent to the gateway.       |
| Payment B, no amount, key `K`                             | Refused with HTTP 422 and code `IDEMPOTENCY_KEY_REUSED`. B's seat is untouched and B's money is intact. |
| Payment A, an explicit ₹1,000.00 (100,000 paise), key `K` | Refused the same way, because the stored refund is ₹2,000.00 and the request names another amount.      |
| Payment A, an explicit ₹2,000.00 (200,000 paise), key `K` | A's refund is returned, because payment and amount both match.                                          |
| Payment B, no amount, a fresh key `K2`                    | A new refund of up to B's refundable ₹1,500.00, as before.                                              |

Before this decision, the second row returned A's refund and the booking wrapper stamped B's seat refunded.

A replay also keeps the seat decision of the first call. Charlotte also holds a ₹500.00 (50,000 paise) webinar seat, payment W. An operator refunds ₹100.00 (10,000 paise) of W from the issue door under the key `K2`; that is a partial refund, so the seat stays live. The operator then resends `K2` with no amount. The full-refund request matches the stored refund, so the door returns the ₹100.00 refund, moves no money and leaves the seat live. Before this decision the replay judged the seat from the new request, and a request with no amount ended it, which revoked Charlotte's seat and her chat and call access although only ₹100.00 had come back.

## Decisions

1. **A key replays only a matching refund.** `findDedupedRefund` (`lib/payments/operations/refund.ts`) still finds the refund by key alone, because the key is the unique column, and now takes the request as a second argument. `assertRefundReplayMatches` compares them: the request matches when it names the same `paymentId` as the stored refund and, if it names an explicit amount, the same `amountPaise`. A full-refund request has no amount, because it asks for whatever is left to refund, and that resolves to the stored refund's own amount, so it matches on the payment alone. Any other reuse of a spent key throws `RefundKeyReusedError` (a kind of `RefundValidationError`), and the refund is never replayed. `RefundResult` also carries the `paymentId` of the persisted refund.
2. **The refusal is HTTP 422 with code `IDEMPOTENCY_KEY_REUSED`.** It is the code and status this repository already uses for a reused key with different details: `withIdempotency` (`lib/api/idempotency.ts`) and the approval-request route (`app/api/scheduling/request-for-approval/route.ts`) answer 422 with it. The operator doors answer it through `refusalResponse` (`lib/backoffice/ops-refusal.ts`), which sends `{ error, code: "IDEMPOTENCY_KEY_REUSED", paymentId }` with status 422: the issue door (`app/api/admin/refunds/issue`), the credits door (`app/api/admin/refunds/credits`) and the legacy door (`app/api/admin/refunds`). The Support refund door (`reviewSupportRefundDoor` in `lib/support/refund-door.ts`) is wrapped the same way, so a mismatch there would also be 422. In practice it cannot fire, because Support's key is `case-recommendation:<recommendationId>` and the recommendation fixes its own payment and amount. Support has a second, different `IDEMPOTENCY_KEY_REUSED`: `replayCaseActionTx` (`lib/support/case-actions.ts`) refuses a `clientActionId` reused with other details, and that one is a `CaseActionError` with its default status 409. The two share a code, not a cause or a status.
3. **Every writer and door applies the same rule.** The check lives in one place, `assertRefundReplayMatches`, and its callers pass the request through. `findDedupedRefund` takes it from `refundPayment` (the gateway rail), from `withDedupe` in `lib/payments/operations/booking-refund.ts` (the credits and in-ledger rails), and from the incident, class make-up and refund-owed callers (the last three with the payment only). `assertRefundDoorOpen` (`lib/backoffice/refund-eligibility.ts`) checks a spent key before the door's eligibility check, and `refundInFlightOr` (`lib/backoffice/refund-doors.ts`) answers the in-flight refund after a gateway error with the same request. Some callers deliberately match on the payment alone, because their amount is not the request's to fix: the refund-owed drive (`driveRefundOwed`), whose marker amount is a cap the drive may lower, and the incident and class make-up refunds. A session-link refund also matches on the payment in `assertSessionRefundable`, which judges the amount itself: a retry that resolves to the first refund's amount replays it, and any other amount is refused with `SESSION_ALREADY_REFUNDED`, which keeps its meaning.
4. **A refund decides its seat once, as it settles, counting only settled money.** Every row a booking door reserves stores the request's seat inputs as `Refund.metadata.seatIntent`: `keepSeat`, `keepSeatIfPartial`, and whether an amount was named. One hook, `settleRefundSeatTx` (`lib/payments/operations/refund-seat.ts`), makes the decision inside the transaction that moves the row to `SUCCEEDED`, on every path that does so: the live settle in `refundPayment`, the refund webhook (`handleRefundCreated` in `app/api/webhooks/utils.ts`, which also records refunds read back from Razorpay), the `reconcile-refunds` job's gateway poll and placeholder bind (`scripts/refunds/reconcile-pending-refunds.ts`), and the in-ledger rail's own settlement transaction (`refundInternalFundedPayment`). The hook counts only `SUCCEEDED` refunds and lost chargebacks as returned, never a `PENDING` one. It reads the stored intent, never a replaying request's flags, and stores its answer as `Refund.metadata.endsSeat`. When the refund ends the seat, the same transaction stamps the seat of the row's own payment `REFUNDED` and writes that payment's payer a `REFUND_ACCESS_REVOKE` intent (`persistRefundRevocationInTx` in `lib/stream/revocation-intents.ts`). So the decision, the stamp and the intent commit with the settle or not at all: a failure rolls the whole settle back, and the row stays `PENDING` for its next settle. After the commit, a live call drives the Stream revocation itself; for a webhook or job settle, the revocation sweep drives it. Because the hook stamps the persisted refund's payment, a seat effect follows the persisted refund, never the request. A refund that no booking door asked for, such as a dashboard refund or a capture auto-refund, stores no intent and leaves the seat alone. The credits rail always returns everything and stamps the seat in its own transaction, so its replay ends the seat too.

   A replay applies nothing new. A replay of a `PENDING` row answers the refund in flight, and its settle decides later. A replay of a `SUCCEEDED` row returns the refund with its stored decision. Only a `SUCCEEDED` row from before the intent was stored, with no decision, is decided at its replay, through the same hook in a Serializable transaction of its own: it ends the seat only when the replaying request does not keep it and nothing is left to refund (`legacySeatIntent`).

   For example, take Charlotte's ₹500.00 (50,000 paise) webinar seat, payment W. A ₹400.00 refund of W is at the gateway, `PENDING`, while a ₹100.00 partial settles. Only the ₹100.00 counts as returned, so ₹400.00 is still refundable and the ₹100.00 refund keeps the seat. If the ₹400.00 refund then settles, its own settle finds ₹500.00 returned and ends the seat. If it fails instead, the seat was never ended and nothing needs undoing. Likewise, a full refund whose gateway call timed out stays `PENDING` with its intent, and the webhook that later settles it ends the seat.

5. **A replayed ladder override keeps the stored amount, and a replay is never held.** The issue door's ladder override prices a tier on today's balance. When its key was already spent, `assertRefundDoorOpen` hands back the stored refund's amount and the door uses it instead of pricing again, so a retry after the balance changed neither refuses nor sends a different amount. The door's second-approver pricing prices a validated matching replay at zero, because it moves no money, so the door answers the stored refund at once instead of opening a second proposal. For example, a ₹30,000.00 (3,000,000 paise) override is above the ₹25,000.00 threshold and waits for a second admin; once approved and sent, resending the same request and key returns that refund with HTTP 200, not a new HTTP 202 proposal. The wrapper carries that pricing into the run as `priced` on the door context (`withOpsAction` in `lib/backoffice/ops-action-log.ts`), and the door sends the writer `replayOnly`. So if the stored refund fails and frees its key after the pricing, whether before the door's own check or before the writer's lookup, the request is refused with HTTP 409 and code `REFUND_REPLAY_EXPIRED` ("The earlier refund under this key failed. Open the refund again to send a new one, which may need a second approval.") and never becomes a fresh refund that skipped the second approver.
6. **A session-link retry replays before the seat check, and a racing owed-refund drive adopts the winner.** `assertSessionRefundable` looks up the stored refund under the session key before it asks for a live seat, so an identical retry after the session refund ended the seat replays the stored refund instead of failing with `SESSION_NOT_ON_PAYMENT`. The session key names both the session and the payment, so a stored refund under it already proves the session was on the payment. When two `driveRefundOwed` runs race one marker whose amount was more than the balance, one clamps to the balance and settles under the key; the other sends the marker's original amount, gets `IDEMPOTENCY_KEY_REUSED`, then reads the stored refund by key and payment and, when it is `SUCCEEDED` or `PENDING`, returns it as a replay and clears the marker once it is `SUCCEEDED`.
7. **Support opens no recommendation the refund door would refuse.** `recommendRefundTx` (`lib/support/case-actions.ts`) applies the whole `refundDoorRefusal` before it creates a recommendation, not only its free-seat rule, so a 100% discount booking that Ops already ended at ₹0 is refused with `ALREADY_FULLY_REFUNDED` at the recommendation instead of later, at preview or approval.
8. **No schema change.** `Refund.dedupeKey` and `Refund.paymentId` and `Refund.amountPaise` already hold everything the comparison needs, and the seat decision lives in the existing `Refund.metadata` JSON column. The schema is close to its pre-launch freeze, and this decision adds no column and no index.

## Why this shape

The comparison is limited to the fields that move money: the payment and the amount. The reason, free text, initiator and rail are not compared. A retry from another tab or another job run may word the reason differently, and refusing it would turn a harmless retry into an error. This is the same behaviour the payment industry settled on. Stripe compares the incoming parameters with those of the original request and returns an error when they differ, a rule it introduced as a breaking change in its 2015-09-03 API version ([idempotent requests](https://docs.stripe.com/api/idempotent_requests), [the changelog entry](https://docs.stripe.com/changelog/2015-09-03/reuse-idempotency-tokens-alter-error), [retrying idempotent requests](https://docs.stripe.com/error-low-level)). Razorpay's refund API, which is the gateway behind our refunds, accepts an `X-Refund-Idempotency` header and documents a 409 when a different request with the same key was already processed, and a 409 while the first is still in progress ([idempotent refunds](https://razorpay.com/docs/api/refunds/normal-refunds-idempotent); the same page's tips section also mentions a 400 for a changed payload, so the two statuses are not consistent there). The IETF `Idempotency-Key` header draft lets a server pair the key with a fingerprint of the whole payload, of selected fields or of each field in turn ([the draft](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header)). Its first revision says a reused key with a different payload should get 422, and a request that arrives while the first is still running should get 409 ([draft 01](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-01)). Later revisions of the draft are less explicit about the 422.

Our choice is therefore the Stripe and Razorpay semantics, applied to the money-moving fields, with the 422 of the IETF draft and of our own `withIdempotency` and approval-request routes.

One door does not follow the 422 precedent, and the difference is deliberate. The checkout door compares a request fingerprint of the priced inputs (`replayByIdempotencyKey` in `lib/payments/operations/checkout-replay.ts`) but, on a mismatch, mints a fresh attempt instead of refusing, because a changed price input is legitimately a new checkout under the page's generated key. A refund has no such reading: the same key with another payment or another amount is always a caller mistake, and refusing it is the only safe answer.

## Consequences

- A caller that reuses a key across payments now gets an explicit refusal, not a silent replay. Keys that embed the payment id, such as `admin-refund:<adminId>:<paymentId>:<key>` and `case-recommendation:<id>`, cannot collide across payments and are unaffected. Keys the caller chooses freely, such as `ops:<uuid>` on the issue door and `ops:credits:<uuid>` on the credits door, are where the refusal can fire.
- A retry that sends the same payment and the same amount (or no amount) keeps working as before, including after a gateway error, through `refundInFlightOr`.
- A `PENDING` refund never ends a seat, so a refund that later fails leaves nothing to undo. A seat that a settled refund ended is never reopened by a later settle.
- No data repair is needed. New refund rows carry two more metadata keys, `seatIntent` and `endsSeat`, and rows written before them are handled by the replay rule in decision 4. A refund that was wrongly replayed before this decision was never recorded as one for payment B.
- The refund domain doc ([Refunds](../finance/30-refunds-disputes/01-refunds.md)) says a repeat call with a spent key returns the first refund. That page now states the rule as decided here.

## Deprecated & Superseded Approaches

- **Key-only lookup.** `findDedupedRefund` used to return whatever refund held the key, whichever payment or amount the request named. It is replaced by decision 1, and no caller should compare the key alone.
- **A request-fingerprint column on `Refund`** (a SHA-256 of every input, as `Payment.requestFingerprint` does at checkout). It is the strictest option, since it catches any changed input. It was not chosen because it needs a new column while the schema is nearly frozen, and because the reason, initiator and rail are not worth refusing a retry over. The payment and the amount, read from columns that already exist, close the finding.
- **Deciding the seat from the replaying request.** The gateway rail used to decide the seat after its refund committed, from the current request's flags and amount, and the in-ledger rail did the same on a replay. A replay with no amount then ended a seat that the original partial refund had kept. It is replaced by the stored decision in decision 4.
- **Deciding the seat before its money settled.** The gateway seat was first decided when the `PENDING` row was reserved, and then once the gateway answered, with a `seatDecision: "pending"` marker on the row until then, a `reconcile-refunds` seat pass to finalise a row whose reserving call died, and a post-commit `REFUNDED` stamp that the revocation sweep re-applied (`restampRefundedSeats`). Both versions counted a `PENDING` refund as returned, and a refund whose gateway call timed out was settled by its webhook with its seat still live. The settle hook in decision 4 replaced all of it.
- **Matching on the payment alone.** It is the simplest rule, but a different amount on the same payment would silently replay the first refund, and the caller would believe the new amount was sent. The explicit amount is therefore compared whenever the request names one.
