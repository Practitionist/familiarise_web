# ADR: Left seats refuse honestly, faults reach Sentry, refusals stay quiet

- **Status**: Accepted (owner decisions, 2026-11-17). Train 7 ships in three pull requests: API answers and Sentry (7a, D1 to D3), the interface fixes (7b) and the copy (7c). The later pull requests append their decisions here.
- **Date**: 2026-11-17
- **Author**: Platform engineering
- **Related**: [Checkout and payment integration](../booking/10-checkout-payment-integration.md), [Sentry conventions](../observability/sentry/02-conventions.md), [Auth helpers for API routes](../api/auth-helpers.md), [Train 6 decisions](2026-11-16-train-6-back-office.md)

## Context

A pre-launch sweep of the API answers and the Sentry stream found four kinds of fault.

- **A buyer who left a free seat was told they were still registered.** `seatRebuyRefusal` (`lib/payments/checkout/seats.ts`) read a seat as left only when every participant row was `CANCELLED`. A free seat has no refund rows, and a seat released through a refund path ends `REFUNDED`, so the buyer fell through to `ALREADY_REGISTERED` ("You are already registered for this webinar") for a seat they no longer held.
- **Real faults never reached Sentry.** About twenty route catches answered 500 with only `console.error`, which lands in the function log and pages nobody.
- **Expected refusals did reach Sentry.** The consultation PATCH captured every error inside its transaction before the outer catch turned the typed ones into 409s. The webinar and class editors threw a plain `Error` on a 4xx, so the editor's refusal check could not see the status and captured it.
- **Some answers were the wrong shape.** Junk JSON answered 500, a webinar checkout that sent its own start time answered 500, an unknown `/api` path answered a 40 KB HTML page, and several 4xx bodies had no `code` or printed a route path or a bare "Required".

## Decisions

1. **D1: a seat whose participants are all `CANCELLED` or `REFUNDED` counts as left.** This holds for a free seat and a paid one. The buyer then gets the existing `SEAT_REBUY_UNSUPPORTED` refusal ("You left this event earlier, and a seat you've left can't be bought again yet. Contact support if you'd like to rejoin."), never `ALREADY_REGISTERED`. The same rule serves pricing, the payment write and the waitlist, because all three call `seatRebuyRefusal` or `assertSeatRemintable`.
   - Re-buying a left seat stays unsupported. Nothing is re-minted for it. Letting a learner rejoin a free seat is a separate, later piece of work (#2849).
   - Worked example: Priya Anderson (seed learner) takes a free seat on a webinar and later leaves it. Her `Payment` stays `SUCCEEDED` at 0 paise with no refund row, and her participant row is `REFUNDED`. Before this change she was told she was already registered; now she is told she left and to contact support.
   - Options not chosen: re-minting the left seat's payment so she can join again (a money and status change that needs its own design); answering `ALREADY_REGISTERED` (untrue).

2. **D2: a Sentry fix on a money path changes only what is captured and its `expected` tag.** It never changes a status code or the buyer's sentence. `ILLEGAL_TRANSITION` is not registered in `BUSINESS_ERROR_CODES`: each route that expects an illegal transition maps it to its own 409, and registering it globally would also re-label transitions that are real faults elsewhere.
   - Re-tagging the checkout lock and serialization races that `handleCheckout` wraps in "Failed to record payment information" is dropped from Train 7, because tagging them expected would drop the event reference from the buyer's sentence, which D2 forbids. It is filed as [#2853](https://github.com/Practitionist/familiarise_web/issues/2853), and Sentry keeps filing those races as errors until then.
   - Options not chosen: unwrapping the error, or answering it as a 409 with new copy.

3. **D3: every route catch that answers 500 reports to Sentry, with its response byte-for-byte the same.** Each catch calls `reportSentryError(error, { subsystem, op, expected: false })` in place of its `console.error`, and keeps its own status and body; none of them moves to `apiError`, whose body differs. The routes that gained a capture are the replay and digital-product purchase and claim routes, class plans (list and create), scheduling appointments, content topics (list, create, delete), domains and subdomains, the trial read, feedback (list and create), staff appointments and their timeline, moderation stats and reviews, and the admin invoices, leads and data-breach routes. The unsubscribe and resubscribe routes already report through `setEmailEnabled` and gain nothing, since a second capture would double-count one fault.
   - Options not chosen: switching each route to `apiError` (it changes the body a client reads); capturing per row in a loop (forbidden by the root rules).

## What 7a changes beside the decisions

- A webinar or class checkout that sends `startsAt` or `endsAt` answers 400 naming the field from the checkout schema, and a direct caller of `acquireCheckoutLock` gets the typed 400 refusal `EVENT_SEAT_TIMES_SENT`.
- `GET /api/user/consultants` takes a price bound only as a safe non-negative integer of paise; `Infinity`, `1.5` and `-1` are ignored instead of answering 500.
- Malformed JSON answers 400 `MALFORMED_JSON` across `app/api` through `readJsonBody`.
- An unknown `/api` path answers a JSON 404 from `app/api/[...notFound]/route.ts`.
- 4xx bodies that had no `code` gained one, and the sentences that printed a route path or a bare "Required" are plain sentences.

## 7b decisions

These come from #2851 "fix(ui): phone layouts reach every control, dialogs return focus, a labelled availability editor, readable pills, one zone for every time".

1. **`isValidTimeRange` still returns a boolean.** The settings loader and `formatSlotsForApi` need a yes or no. The new `timeRangeProblem` returns the one sentence per rule, and `isValidTimeRange` is `timeRangeProblem(...) === null`. The unreachable `validateDuration` (its two "Session must…" messages) is deleted.
2. **Save on the Availability page is disabled for an empty week, as the brief says.** An expert can no longer clear every row and save. Pausing requests stays on the booking-requests setting. The profile settings form, which uses the same hook, is unchanged. A week whose rows are each valid but whose overnight tail overlaps the next day still saves into the existing "Validation Error" toast, because that check spans two days.
3. **The grid-snap line is display state.** It is stored as the `snapNotice` field on `SlotType`, written only by the settings editor's update handler, and never sent to the API. The error text also moves from `red-500` to `red-600`, because red-500 fails 4.5:1 on white.
4. **Dialog focus is restored one microtask after Radix's own close handling.** This happens only when focus has fallen to `<body>` and the opener is still in the document. So a Trigger, a caller's own focus move and a dialog opened from inside another dialog are all left alone.
5. **The "Schedule N sessions" bar (CL-F4 remainder): no CSS change.**
   - The QA numbers (bottom 8 to 10 px under the nav) were taken on `ddaac8ba8`. On that head the scheduler had no scroll area of its own.
   - Since then, `ManageTimingsClient` wraps the scheduler in `min-h-0 flex-1 overflow-y-auto` inside the viewport fill, and `.h-dashboard-fill` already subtracts the 4rem nav below `md`.
   - So the sticky bar sits at the scroll area's bottom edge, 1rem (the fill's padding) above the nav. A later QA pass measured exactly that with two rows: y 728 to 764 against a nav top of 780.
   - I could not make it fail without a browser, so I changed nothing. The sweeper should measure the 3-row and 4-row cases.
6. **The feasibility route now returns `zone`.** The brief said it already did; it did not. `GET /api/plans/subscriptions/[id]/feasibility` adds the expert's scheduling zone (`resolveSchedulingTimezone`, the same value it passes to `assessExpertFeasibility`), and `planFeasibilitySchema` requires it.
   - "Starts" falls back to the viewer's zone until that read answers. "First cycle" shows only once the zone is known.
   - The client preflight's "first cycle has passed" check waits for the same read. The server still enforces it.
7. **The verify route reads the zone from the session it already holds.** It calls `describeViewerZone({ userTimezone: session.user.timezone })`, which is the rule `getViewerZone` applies, without a second session read.
8. **The requests-inbox reader derives with UTC.** `finish()` in `lib/data/requests-inbox.ts` keeps only the state, the deadline and the bucket. `InboxRow` re-derives the words in the viewer's zone.
9. **Client surfaces without a viewer prop read `useZoneClock().zone`.** That is the customer layout's provided profile zone, or the browser zone once hydrated. These are `PendingPaymentsWidget`, `PaymentsHistoryList` and the booking detail page. `RequestsInboxPreview` already had `useViewerZone()`, and its other lines use it.
10. **The back-office not-found is `[tree]/not-found.tsx`, not a catch-all page.** It follows the sibling role roots (consultant, consultee, organization), which each carry their own not-found. It renders a `<div>`, because the shell owns `<main>`.
11. **Three `lib/` files on the guard's allowlist print text a person reads.** They are `lib/booking/batch-cards.ts` (batch weekday and day labels), `lib/dashboard/earnings-state.ts` (payout days in IST) and `lib/appointments/session-schedule.ts` (UTC date-range labels). Client components import all three. The brief scoped the guard to `app/` and `components/`, so they are a follow-up.

## 7c decisions

These come from #2858 "fix(copy): refusals say what happened and what to do next, moves are filed by who must answer, back-office copy names people and zones".

1. **R1: whose move it is.** `listStatusFacts` takes the list's side and the signed-in user and sets `reschedule.mine` by `initiatedById`, the same rule as `openReschedule` and the learner's Home strip. Until the session loads it falls back to the side. `deriveBucket` reads it before the generic pending branch: mine is `waiting` (`PENDING_APPROVAL`), theirs is `needsAction` with the new reason `ANSWER_MOVE`. Home's event cards pass no `moveMine` and are unchanged; Home's "Needs you" counts were already split by proposer (`proposalsAwaiting` for the learner, `readRescheduleReplies` and `countRequestsToAnswer` for the expert).
2. **The expert list gains a "Waiting on client" tab.** The expert's own proposal needs somewhere to be listed under "waiting on them"; without a tab it would show only under All, as the Requests-owned rows do today. This is a new tab, not a new status.
3. **Item 1, how the dialog knows the amount changed.** It remembers the first figure it showed this opening and prints the line when the quote differs. `applyRefundRequote` returns the quote's currency for the toast. The organisation detail page uses the same reader and now names the amount in its error too.
4. **Item 2, the one table.** Booking refusal titles live in `TYPED_CODE_TOAST_MAP` (`EXPERT_RESCHEDULE_CAP`, `MAX_RESCHEDULES_EXCEEDED`, `MAKEUP_WINDOW_LAPSED`, `USE_RETIME`, `SUBSCRIPTION_ALREADY_ACTIVE`), read through `codedRefusalToast`. The body stays the server's sentence where the server knows the facts. A few checkout titles changed words as well as case where the old title named the wrong thing (for example `CONSENT_WITHDRAWN` "Booking Not Available" is now "This expert has paused bookings", as its body says).
5. **"Not done".** A money door's toast is titled from the door's own confirm label ("Couldn't cancel booking"); a door with no label reads "That action didn't go through". The class session controls name each action.
6. **"Couldn't publish" on a live plan: could not reproduce.** The editor already titles an edit of a live plan "Couldn't save" (`wasPublishedBeforeSave`). I extracted the title into `saveFailedTitle`, pinned it, and gave a feasibility refusal its own title ("Your open hours can't fit this plan").
7. **"Couldn't save timings" with a wrong cause.** The request callout's approve used the Timings title; it now reads "Couldn't approve this request". The unused `invalidEventId` helper is deleted.
8. **Item 3 zones.** The host's make-up route passes the viewer's profile zone; the operator door passes IST, labelled. The deadline was already counted from `missedAt` (the cancellation or void); only the sentence was wrong.
9. **Item 5.** The freeze line is on the 1:1 note only; an event seat follows its refund window, which the note already states.
10. **Item 7.** "Money taken" is the money states PAID, PARTIALLY_REFUNDED, REFUND_PENDING, REFUNDED and DISPUTED, or a co-pay of the viewer's own. The one reader shape where the old rule was wrong: an organisation-paid overage child written for the member (`charged(c)` did not exclude sponsored children).

A lapsed pay-first hold now reads "Cancelled" in the drawer, as it does in the lists.

The two field-specific 400 sentences are unchanged. The day keys come from `DAYS_OF_WEEK` rather than the Prisma runtime enum, because a client hook imports the contract module.

## Deprecated & Superseded Approaches

- **Reading a seat as left only when every participant row is `CANCELLED`**: a free seat or a refunded release ends `REFUNDED`, so that reading told a buyer who had left that they were still registered.
- **`console.error` as the only record of a 500**: replaced by `reportSentryError`, which writes the same console line and pages.
- **A plain `Error` for a non-ok response in a browser service**: replaced by `requireJsonResponse`, which throws `ApiResponseError` with the status and code.
- **`parseNumberParam` in `lib/explore/filter-codec.ts`**: it had no caller and accepted `Infinity`; it is deleted.
- **Filing every pending move by its status**: an open move read as a request on both sides, so the proposer's own move sat under "Waiting on expert" or in Requests. A whole-booking move is now filed by who answers it next.
- **The support drawer reading the stored status alone**: it showed a lapsed move as "Requested" and a refunded booking as "Cancelled"; it now reads the same facts as the lists.
