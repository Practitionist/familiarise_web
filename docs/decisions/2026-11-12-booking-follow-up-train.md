# ADR: The booking follow-up train — what was decided after the review of the scheduling surfaces pull request, and what is still to build

- **Status**: Accepted (owner decisions, 2026-11-12). Every decision below is **decided, planned** unless it says otherwise: none of it is built, and the "today" sentences say what the code does now. Decisions 10 to 17 of [the scheduling surfaces record](2026-11-09-scheduling-surfaces-and-feasibility.md) were built in that pull request and are not repeated here.
- **Date**: 2026-11-12
- **Author**: Platform engineering
- **Related**: [Scheduling surfaces, feasibility before money, and booking correctness](2026-11-09-scheduling-surfaces-and-feasibility.md), [Booking v2 direction](2026-11-03-booking-v2-direction.md), [Availability contract](../onboarding/03-availability-contract.md), [Scheduling grid UX rules](../calendar/allocate-heatmap-ux.md), [The appointment detail page](../dashboard/appointment-detail-page.md), [Trial sessions](../booking/09-trials.md), [Cancellation flow](../booking/08-cancellation-flow.md), the follow-up tracking issue [#2720](https://github.com/Practitionist/familiarise_web/issues/2720)

## Context

The review and QA of the scheduling surfaces pull request showed that most of the serious findings pre-date it: they are old behaviour that the new surfaces made visible. The owner chose to fix everything that was found, in a train of pull requests of at most 150 files each (the limit of the CodeRabbit app's review), and to keep the scheduling surfaces pull request to what it introduced or regressed. The decisions that were built in that pull request are recorded in the scheduling surfaces record. This record holds the ones that are decided but not built, each with the alternatives the owner turned down, so the reasoning is never left only in a chat.

## Decisions

1. **Delivery: fix everything, phased, at most 150 files per pull request** (decided, planned).
   - The train fixes everything that was found, not only the blockers and not only this pull request's defects. The scheduling surfaces pull request carries only what it introduced or regressed, and it merges before the operations audit pull request (the infra pull request for the job machinery). At the end of each train the owner chooses the next one.
   - A pull request over the 150-file limit is reviewed with the CodeRabbit CLI in batches (`.claude/skills/workflow/SKILL.md`), and the findings are posted as inline review threads on the pull request.
   - **Options considered.** Fixing only this pull request's own defects was rejected because the older defects would ship anyway. Fixing only blockers was rejected for the same reason. Putting everything into the scheduling surfaces pull request was rejected because it is already very large. Path filters that hide tests and docs from review were rejected because they hide exactly the files where drift shows.

2. **Three time pickers, one per job** (decided; built 2026-11-13, see [the trial and public booking surfaces record](2026-11-13-trial-and-public-booking-surfaces.md), decisions 10 and 11).
   - **Today there are eight** (see [the picker inventory](../calendar/allocate-heatmap-ux.md#9-the-time-pickers)): the week heat-map grid with its session tray (`UnifiedCalendar`, `WeekGrid`, `SessionTray`), the phone day list (`MobileDayListPicker`), the single-session "pill wall" (`SingleSessionPicker`, used by the webinar editor, the move dialog and the class make-up), the weekly pattern form (`ClassPatternScheduler`), the light two-pane month calendar (`TrialScheduleCalendar`), the dark day strip (`TrialSlotPicker`), the One-time booking dialog's date picker and slot list (`ConsultationPricingToggle` with `SlotList`), and native date inputs.
   - **Decided.** One two-pane month calendar with a times list, in a light and a dark theme, serves every "pick one time" case. The heat-map grid places many sessions on a week, with the phone day list as its small-screen form. The pattern form stays the picker for a repeating class pattern.
   - For a host, the single-time picker lists the free times inside published hours first, greys the booked ones, and shows the rest behind a "Show times outside my hours" switch, so a host can still run an event outside usual hours without editing availability. Trial time-picking becomes step two inside the mentorship dialog.
   - **Enforced by** the components named above; the lattice and lead rules stay in `lib/booking/event-time-rules.ts` and `isOnEventLattice` in `schemas/plans.ts`, which the new picker must keep calling.
   - **Supersedes** the owner's choice earlier on 2026-11-12 to give each host surface its own matching picker.
   - **Options considered.** Replacing only the pill wall was rejected because the seven others would still disagree. Keeping all eight and polishing each was rejected for the same reason. Doing it inside the scheduling surfaces pull request was rejected because it is a public booking change inside an already very large merge. Listing every half hour with a label, which is what the pill wall does, was rejected as noisy. Listing only free times was rejected because a host could not run an event outside usual hours without editing availability.

3. **Removing availability under live bookings stays allowed, with a confirm first** (decided, planned).
   - **Today.** Narrowing or deleting hours always succeeds, and existing sessions keep their times. The save response reports `uncoveredUpcoming`, which counts the upcoming sessions now outside the new hours, including how many are still awaiting payment or approval (`awaitingConfirmation`), computed by `lib/scheduling/uncovered-upcoming.ts` and returned by the availability PUT in `app/api/user/consultants/[id]/route.ts`. Only switching between Weekly and Custom is locked while anything is active (`checkActiveAppointments` in `app/api/user/consultants/utils/consultant-appointments.ts`).
   - **Decided.** Keep that rule. Add a confirm dialog before the save that lists the affected sessions, says they keep their times, and links to reschedule or cancel each. Add tests for the uncovered-sessions notice, and trace what happens when a held booking outside the new hours is later approved or paid. Confirm before a Weekly save deletes Custom rows.
   - **Enforced by** the settings availability save (the route above) for the data, with the confirm dialog on the settings page; the refusal on a type switch stays `SCHEDULE_SWITCH_BLOCKED`.
   - **Options considered.** Locking was rejected, and is documented here as the alternative: refuse to remove a window that has a confirmed or held session inside it until that session is moved or cancelled. It has no surprises, but one stuck booking would freeze the expert's calendar, and blocking out next month would mean handling every booking first. Keeping today's silent save with a count afterwards was rejected because the expert learns of the damage only after it is done.

4. **One status vocabulary everywhere** (decided; built 2026-11-14, see [the booking states record](2026-11-14-booking-states-and-demand-guidance.md)).
   - The words are Requested, Awaiting payment, Confirmed (Registered for a group seat), Being moved, Completed, Cancelled and Refunded, from one function used by the buyer, expert, organisation and back-office surfaces. "Approved" appears only in a timeline when an expert actually approved. While a reschedule is open, both sides see "Being moved" with the original time, the proposal and only the buttons the server accepts.
   - **Today** label maps live in several places: `BOOKING_LABEL` in `lib/dashboard/money-state.ts` (which also has Payment lapsed, Awaiting schedule and Declined that the new function must map onto the seven words), `APPOINTMENT_STATUS_BADGE` in `lib/labels/session-labels.ts` (which labels a status "Approved"), `eventUnionStatusBadge` in `lib/appointments/status.ts`, and the requests labels in `components/dashboard/shared/requests/labels.ts` ("Approved", "Approved — waiting for the learner to pay"). Back-office case pages read `appointmentStatusBadge` directly (`components/dashboard/backoffice/support/CaseDetails.tsx`).
   - **Options considered.** A shared set for customers only was rejected because staff would then read different words for the same booking. Patching only the three wrong states was rejected because the maps would keep drifting.

5. **The appointment detail page: one banner, and the Payment card in the right rail** (decided; built 2026-11-14, see [the booking states record](2026-11-14-booking-states-and-demand-guidance.md)).
   - The Payment card always sits in the right rail under Resources and Help. One amber banner at the top shows whenever the viewer must act (pay, accept or decline new times, approve a request), with the deadline and the primary button. A session inside a subscription or class is never paid individually, because the plan or the seat is paid once, so the page shows the plan-level payment.
   - **Today** the rail order is Payment, details, resources, timeline and help ([the page doc](../dashboard/appointment-detail-page.md)), and `NeedsYouCallout` (`components/appointments/detail/NeedsYouCallout.tsx`) carries the hold countdown for payment; the decision widens it to every must-act case.
   - **Options considered.** A banner for payment only was rejected, and so was adding a Pay button to the Payment card with no banner. The owner recorded the choices, not a reason for each; the banner covers every must-act case, which is the point of the first rejection.

6. **Trial to subscription** (decided; built 2026-11-14, see [the booking states record](2026-11-14-booking-states-and-demand-guidance.md); the completion bell and email built 2026-11-15, see [the required notices record](2026-11-15-required-notices-and-deadline-alerts.md), decision 4).
   - The buyer's trial detail page gets a "Continue with {expert}" card, quiet before the session and prominent after it completes (built), plus one bell and one email when the trial completes (planned, a notifications pull request).
   - **Today** the consultee detail page shows a "Continue with {expert}" button only for a completed one-on-one (`DetailPageClient.tsx` under the consultee dashboard), and `trial-session-completed` goes to both parties ([the trials doc](../booking/09-trials.md)).
   - **Options considered.** Showing it only after the trial was rejected, and so was a card with no notice. The owner recorded the choices without a reason for each.

7. **The buyer Appointments list** (decided; built 2026-11-14, see [the booking states record](2026-11-14-booking-states-and-demand-guidance.md)). "My alerts" (`components/appointments/consultee/MyAlerts.tsx`, mounted by `AppointmentsPageClient.tsx`) becomes a compact strip below the next appointment. **Options considered.** Giving it its own tab was rejected, and so was keeping it on top (where it pushes the next appointment down).

8. **Free bookings notify like paid ones, minus the receipt** (decided, planned). A free approval and every decline notify the buyer. The paid path stages its bells and emails from `lib/payments/webhooks/staged-emails.ts` and `lib/payments/webhooks/handlers.ts`; the free path through `lib/payments/checkout/orchestrate.ts` (the `free_` payment id) is where the gap is to be closed, and the follow-up pull request must trace what a free booking sends today. **Options considered.** A bell only was rejected, and so was a buyer email only.

9. **A genuinely free cancel writes no zero-rupee refund record** (decided; built 2026-11-13, see [the trial and public booking surfaces record](2026-11-13-trial-and-public-booking-surfaces.md), decision 7, which records the trace and supersedes the "today" sentence below).
   - A cancel with price zero and no referral credits used writes no zero-rupee refund record and sends no refund email. A credit-funded booking keeps today's record, because its refund is the restoration of the credits. The expert-cancel strike for a free booking stays.
   - **Today** `cancelRefundOwed` in `app/api/appointments/[appointmentId]/cancel/route.ts` stamps no marker when the quote refunds zero paise and a credit-funded booking restores its credit in full (`creditRestoresInFull`). Whether a free booking also writes a refund row or sends a refund email today was not traced for this record; the follow-up pull request must trace it first.
   - **Options considered.** Also dropping the strike for free bookings was rejected (see decision 17 of the scheduling surfaces record). Keeping the records and fixing only the wording was rejected.

10. **Back office: four pull requests, access and foundations first** (decided, planned).
    - The staff and admin pages were audited and will be productionized in four pull requests, with access and foundations first.
    - **Open access work, verified in code on this branch.** The maintenance GET returns the recent windows with every column, and `MaintenanceWindow.bypassSecret` is one of them, so past windows' bypass secrets reach the admin client (`GET` in `app/api/admin/maintenance/route.ts`; the model is in `prisma/schema.prisma`). Several admin routes accepted ADMIN or STAFF through a raw role guard rather than ADMIN only, for example `app/api/admin/payments/route.ts` and `app/api/admin/users/route.ts`; which of them were meant to be admin-only is the audit's call and is not decided here.
    - **Not repeated as a finding.** The claim that taking the platform offline writes no audit row was not confirmed: `setMaintenanceState` in `lib/maintenance.ts` calls `recordOpsAction` with `action: "maintenance.transition"` inside its transaction whenever a started-by or ended-by actor is passed. The audit pull request must check the paths that call it without an actor.
    - **Options considered.** None were recorded beyond the order: access first, because it carries risk, then the rest.
    - **Update (2026-11-16).** The first of the four pull requests closed the maintenance history leak, put the maintenance actor on every transition and audited the OFFLINE step. See [the back-office record](2026-11-16-train-6-back-office.md).

11. **Review findings tracked for the money and sweeps follow-up** (decided, planned). Two findings from the batched review of the scheduling surfaces pull request were accepted as real and deliberately not fixed there, because neither can overpay or lose money today.
    - The parked-consultation sweep reads its 25 oldest rows each run (`cancelAgedParkedConsultations` in `lib/booking/parked-consultation-sweep.ts`), so 25 rows that fail on every run would hold back later ones. Failures are reported once per run.
    - The series-cancel basis of `seatOwedPaise` in `lib/payments/operations/event-refunds.ts` does not subtract an earlier class-end refund. The refundable-balance cap already prevents paying more than was paid; the follow-up first checks whether the case is reachable.

    **Options considered.** Fixing both in the scheduling surfaces pull request was rejected because each is a money-path change that needs its own tests and review. Dismissing them was rejected so they stay tracked.

12. **The series-move notice names every moved session** (decided; built 2026-11-15, see [the required notices record](2026-11-15-required-notices-and-deadline-alerts.md), decision 5). Today the notice from `retimeClassSeries` in `lib/booking/class-retime.ts` carries the first old and new time and a link. Listing each pair needs a change to the shared rescheduled notification and email template, so it is part of the notifications follow-up.

## Deprecated & Superseded Approaches

- **One matching picker per host surface** (the owner's choice earlier on 2026-11-12). Superseded by decision 2: three pickers, one per job.
- **Moving the public reliability line into the Reviews section** (the owner's first choice on 2026-11-12). Reversed the same day; see decision 17 of the scheduling surfaces record. Strikes stay private.
- **A silent availability save with a count afterwards.** Replaced by the confirm dialog in decision 3.
- **Per-surface status words** ("Approved" as a buyer-facing state, "Payment lapsed", per-surface labels). Replaced by the one vocabulary in decision 4 once built.
