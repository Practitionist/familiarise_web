# Recording transfer background worker

`netlify/functions/recording-transfer-background.mts` provides an authenticated, unscheduled Netlify background adapter for the existing `transfer-recordings` core. POST `/.netlify/functions/recording-transfer-background` with the `CRON_SECRET` bearer. The adapter uses `cleanupRoute`, so authentication, maintenance admission and failure handling share the HTTP cleanup boundary. It calls the core in-process rather than waiting on a Next.js HTTP request, and uses the existing job Sentry bootstrap/flush for the standalone function runtime.

Each core invocation examines one retry-eligible READY recording, ordered by source expiry and ID. The query excludes rows in backoff, missing expiry metadata and expired sources. A copy still streams up to 20 GiB with the existing 12-minute abort signal. One stale claim and 100 newly exhausted alerts are the maximum ancillary rows selected per run. The same abort signal stops stalled source reads and all multipart operations. Canceling a source cannot hold cleanup open indefinitely. R2 cleanup requests have independent 15-second deadlines, and prior-attempt cleanup is awaited before the worker exits.

The Postgres cron lease is fail-closed and lasts 15 minutes. The 15-minute stale-claim threshold exceeds the copy deadline. An atomic claim increments `transferAttempts` and returns the source plus an ownership stamp. Completion and failure updates require the same attempt and `updatedAt`, so a late worker cannot publish over, release, or delete the object belonging to a later attempt. Retention skips active TRANSFERRING rows and can expire a completed copy on a later pass. Removal or erasure that changes the row's status prevents publication; a losing copy attempts deletion of only its own attempt object. A rejected delete or `success: false` fails the transfer result without releasing or modifying the row now owned by another operation. Confirmed deletion, including an absent key, returns `skipped`.

A successful background invocation receives HTTP 202 before work runs. That proves admission to Netlify's queue only, including requests whose bearer is subsequently rejected. `SystemJobExecution` records the core's eventual result; a failed copy returns `success: false`. The adapter throws when the shared cleanup handler returns a server error: Netlify discards background return values, so returning an HTTP 500 response alone would not fail execution. Netlify documents invocation-error retries after one minute and, on a second failure, a further two minutes. Claims, attempt-specific keys and durable backoff protect copy retries. [Background return contract](https://docs.netlify.com/build/functions/api/#background-mode), [Netlify retry clarification](https://answers.netlify.com/t/background-function-retries/39459).

Failed unpublished-attempt deletion is visible, but has no durable cleanup owner. Once another operation changes the recording, a repeated worker invocation may not select that recording or its abandoned attempt key. Verification-failure cleanup and removal of prior attempts after AVAILABLE commits also remain best effort; prior-attempt removal is awaited, but its deletion result does not change a successful publication. Resolve durable orphan cleanup or establish reviewed manual recovery before activation. Netlify retries do not provide that ownership, and a completed one-row slice does not establish backlog or source-expiry health.

## Activation and schedule handoff

This change leaves both the ticker and Actions schedules unchanged. The adapter has no `schedule` property. Code readiness does not authorize copying unclassified production rows. The existing cleanup HTTP route and admin run map still invoke the core synchronously and retain the short HTTP runtime ceiling; production recovery uses the explicit background POST door after verification.

1. Confirm the linked Netlify account grants background functions, then deploy the adapter and inspect the deployed function metadata/manifest for background invocation mode with the expected environment, database pool limit and R2 credentials. Verify the deployed shared cron lease rejects unavailable ownership/delegates without executing work. A separate static-config check with standalone `zip-it-and-ship-it` 14.7.1 recognized `config.background: true`; the native bundle check below used CLI 26.0.2's installed 14.7.0. The adapter also retains the supported `-background` suffix for CLI portability. An open upstream report describes config-only functions returning 202 but stopping at 60 seconds on later CLI deploys. That report is not a reproduction on this account. Verify a deployed isolated probe actually completes beyond 60 seconds; parsing, function metadata and 202 alone do not establish its execution budget. [Upstream report](https://github.com/netlify/cli/issues/8354). A deploy preview is suitable for packaging checks; do not invoke a shared-database copy there.
2. Read-only, classify the candidate cohort as real source obligations versus fixtures. For genuine rows, verify the Stream source and expiry using provider metadata. Missing `streamUrlExpiresAt` remains excluded; do not infer expiry from fixture timestamps or bulk-fill it.
3. Once the source cohort is verified and production recovery is explicitly authorized, invoke one adapter POST. Check the eventual `SystemJobExecution` result and verify the specific row became AVAILABLE with PLATFORM storage, matching R2 bytes and its original retention/erasure behavior. HTTP 202 alone fails this gate.
4. Prepare one reviewed cutover that makes the active platform ticker invoke this adapter and removes automatic transfer dispatch from `cron-intra-day.yml`. Route the existing cleanup/admin recovery triggers to async dispatch in that cutover, preserving admission separately from eventual completion. Retain a manual recovery door. Never enable both automatic clocks. The dispatcher must record 202 as accepted rather than completed.
5. Verify successive bounded invocations drain distinct eligible rows, transient failures preserve backoff, and missing/expired source obligations page an operator. Keep standby fleet gating and an independent absence/backlog monitor.
6. Resolve the separate erasure ordering gap in `purgeSingleUserRecordingOnErasure`: it deletes the previously read object before unconditionally clearing the row. A copy that publishes between that read and the final update can lose its new pointer without its object being deleted. The transfer claim fence prevents publication after an EXPIRED update; it does not close this earlier publication window. Require an interleaving regression and durable cleanup ownership before enabling recovery.
7. Account for unpublished and superseded attempt objects whose deletion fails. Failed lost-publication cleanup makes the run fail, but does not persist an orphan retry obligation. Verify durable cleanup ownership or a reviewed manual recovery procedure independently of the erasure pointer race.

Netlify documents a 30-second scheduled execution ceiling and a 15-minute background ceiling. One 12-minute copy leaves room for database, cleanup and telemetry; a copy that consistently cannot finish must use a different execution host rather than increasing the short HTTP timeout.

## Native Node packaging

The standalone entry and shared cleanup factory import Next's request/response classes from `next/server.js`. Their native ESM output runs outside Next's module resolver; the extensionless package subpath fails under the tested Node 22 runtime. Keep that explicit extension in both places. [Node package specifiers](https://nodejs.org/api/esm.html#import-specifiers).

Shared worker logging, capture and transport draining use `@sentry/core`; initialization still uses `sentry.shared.config.ts` and its existing environment, privacy, sampling and quota policy. Core and the Next SDK are pinned together at 10.76.0 and grouped for dependency updates. The Next SDK's native Node entry is CommonJS: its dynamically re-exported generic APIs are absent from the ESM namespace. Changing only the flush call would leave capture and logger calls broken. The native regression compiles the real shared modules to ESM, initializes one SDK client with an in-memory transport, and verifies a scrubbed tagged event and successful flush. It contacts no Sentry service. [Node CommonJS interoperation](https://nodejs.org/api/esm.html#interoperability-with-commonjs), [SDK package exports](https://github.com/getsentry/sentry-javascript/blob/10.76.0/packages/nextjs/package.json).

CLI 26.0.2's installed `zip-it-and-ship-it` 14.7.0 produced an API-v2/background artifact. In a local process with networking denied and a disposable invalid database target, the original compiled application failed with `ERR_MODULE_NOT_FOUND` for `next/server`. A fresh bundle from the corrected source loaded and rejected an unauthenticated POST with zero fetch attempts; an earlier diagnostic changed only the two compiled specifiers and reproduced the same result. This verifies the compiled application/authentication path with canonical local dependencies.

The worktree's default NFT artifact retained its external `node_modules` symlink without its dependencies. It is not a self-contained deployment artifact and must not be uploaded as proof of packaging. Preserve the canonical dependency symlink in worktrees; verify the actual CI/CLI artifact's dependency contents and deployed loading separately. No application build, database operation or recording copy was part of this check.

## Deployed runtime evidence

On 23 October 2026, a dependency-free function using both `config.background: true` and the `-background` suffix completed a 75-second wait on this account through CLI 26.0.2. The unpublished branch deployment returned 202; its logs contained START, END after 75,002 ms, and a 75,366 ms runtime report. Both temporary deployments were deleted afterwards, and the published deployment remained unchanged. The probe had no application, database, storage or scheduled work.

This verifies the isolated packaging path beyond 60 seconds. It does not verify this adapter's dependency bundle, the full 15-minute allowance, a recording copy or schedule handoff. Config-only behavior was not tested on this account; the upstream timeout report remains an external finding.

For unpublished aliases, CLI 26.0.2 can select an empty log stream when the function metadata omits its branch. Use the deployment's branch and ID to query the matching function log stream before concluding that work did not execute. An invocation entry without START/END is inconclusive.

The corrected application preview at `a505a2fbe` ran the worker in background mode on Node 22. An unauthenticated POST logged rejection and a matching 3,107 ms / 230 MB runtime report, with no SDK flush failure or timeout. Prisma initialization reported `poolMax=1`; authentication rejected before maintenance, lease acquisition or copy work. This establishes deployed dependency loading and the corrected rejection/flush path, not accepted Sentry event delivery or copy completion. The earlier `aaef1cfcb` preview exposed the missing flush export; its warning is absent on this corrected execution. Historical log ingestion lagged invocation receipts by several minutes.

## Deprecated & Superseded Approaches

The core previously admitted multiple concurrent copies over a 25-minute run budget and counted attempts only on handled failure. An interrupted run could therefore reuse an attempt object key. The one-copy envelope and atomic attempt ownership replace those assumptions. The existing Actions clock remains the scheduler until the verified handoff above; no production activation is implied by adding this adapter.
